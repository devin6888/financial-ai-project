我们这次不急着看 PostgreSQL 的 SQL，也先不背 `m`、`ef_search` 这些参数。我们从一个更根本的问题开始：

为什么 HNSW 能在几百万个向量里，很快找到与用户问题最相似的几十个向量，而不必挨个检查？

我会结合你正在设计的金融研报智能分析 Agent 来讲。你理解了背后的思路，再看 pgvector 的配置、索引结构和性能优化，就会容易很多。

# 一、先理解 HNSW 要解决的问题

## 1. RAG 为什么会有向量检索？

假设你有 100 万个研报 Chunk，每个 Chunk 都经过 Embedding 模型转换成一个向量。

<img src="C:\Users\67564\AppData\Roaming\Typora\typora-user-images\image-20261020230130633.png" alt="image-20261020230130633" style="zoom: 80%;" />

用户问：

> 为什么公司收入增长了，但现金流反而下降？

系统同样将问题转换成查询向量 \(q\)，然后寻找距离它最近的 Chunk 向量。

问题在于：假如有 100 万个向量，怎么知道该比较哪些向量？

## 2. 最笨、但最可靠的方法：全部比较

你可以把每个向量想象成地图上的一个地点。

最直接的方法就是：

1. 从第 1 个 Chunk 开始。
2. 计算它与查询向量的距离。
3. 继续计算第 2、3、4 个……
4. 检查完 100 万个后，按距离排序，取前 10 个。

这叫 暴力搜索（Brute-force Search），也可以理解为精确最近邻搜索。

它的优点是：只要距离计算和排序正确，就能找到真正的最近邻。

缺点是：每次查询都要检查大量向量。随着数据量增长，计算工作越来越多。

注意一个细节：暴力搜索的代价并不一定完全不可接受。小规模数据、较低并发、性能充足的硬件下，它可能非常合适。HNSW 的价值在于大规模场景中减少搜索工作量，而不是所有场景下都必然更快。

# 二、HNSW 的核心思想：不要挨个找，先找到路

想象你要在一座陌生城市里找一家餐厅。

你有两种方法。

方法 A：挨家挨户询问

​	你从第一个路口开始，问完附近的人，再走到下一个路口。即使城市有 100 万个地点，你也可能要检查非常多的地方。

方法 B：先看地图，再逐步靠近

​	先找到城市的大致区域，再到街区，最后在附近几家店里仔细比较。整个过程不必经过每一家餐厅。

HNSW 的思路更接近方法 B。

不过，它并不是使用真实的地理地图，而是提前为向量建立一张图。图中的每个节点代表一个向量，节点之间的边代表搜索时可以直接访问的邻居。

关键就在这里：HNSW 不只是保存向量，还保存了一条可以帮助搜索的“路网”。

## 1. 什么叫图？

在计算机科学中，图（Graph）由两种东西组成：

- 节点（Node）：这里就是一个 Chunk 向量。
- 边（Edge）：表示两个节点之间存在一条可以访问的连接。

例如，有 8 个向量：

<img src="C:\Users\67564\AppData\Roaming\Typora\typora-user-images\image-20261021000230322.png" alt="image-20261021000230322" style="zoom:80%;" />

假设当前搜索停在节点 A，它可以沿着边访问 B 和 E。

如果发现 B 更接近查询向量，就继续访问 B 的邻居；如果 E 更接近，就可以转向 E。

这样，搜索就有机会沿着图中的连接不断接近目标，而不是扫描所有节点。

但这还不是 HNSW 最精彩的部分。

普通的图可能绕很久才能走到目标附近。HNSW 又加入了一种非常巧妙的结构：**分层**。

# 三、为什么 HNSW 要分层？

HNSW 名字里的 `Hierarchical`，就是“分层”的意思。

你可以把它想成城市交通系统：

- 高层：高速公路，连接少量关键地点，可以快速跨越很远的区域。
- 中层：主干道，连接各个城区。
- 底层：普通街道，连接大量具体地点。

对应到 HNSW：

- 高层的节点很少，连接相对稀疏。
- 中间层的节点更多。
- 最底层包含全部向量节点，连接也相对密集。
- <img src="C:\Users\67564\AppData\Roaming\Typora\typora-user-images\image-20261021000320612.png" alt="image-20261021000320612" style="zoom:80%;" />

这里有一个重要的细节：

**并不是每个向量都会出现在每一层。**

一个向量可能只存在于第 0 层，也可能同时出现在第 0、1、2 层。越高层，节点通常越少。

这种分层结构让搜索既能快速移动，也能在接近目标后进行更细致的探索。

## 1. 实际查询时是怎么走的？

假设用户的问题已经转换成查询向量 \(q\)，HNSW 要找到最接近它的 Chunk。

1. 从图中的入口节点开始，通常从最高层可用的入口开始。
2. 在当前层查看相邻节点。如果发现某个邻居更接近查询向量，就移动过去。
3. 重复这个过程，直到当前层无法通过局部移动找到更接近的节点。
4. 进入下一层，以刚才找到的位置作为新的起点，继续搜索。
5. 到达第 0 层后，探索更多候选节点，选出最终的 Top K 结果。

这是一种分层的贪心导航策略。实际实现还会维护候选队列和已访问集合，不是简单地只保留一个当前节点。

## 2. 为什么这种方法有效？

因为高层帮助搜索迅速靠近目标的大致区域，底层则负责细化结果。

可以把它理解成：

**先确定城市，再确定城区，最后确定街道。**

但要注意，这是一种近似搜索策略。即使搜索路径很聪明，也可能因为图的连接方式和探索范围限制，错过某个真正最近的向量。

# 四、HNSW 这张图是怎么建出来的？

前面讲的是查询过程。接下来一个更有意思的问题是：

100 万个向量之间的连接关系，究竟是谁建立的？

答案是：HNSW 在建立索引时自动构建，不需要你手动给每个向量指定邻居。

## 1. 新向量插入时，会发生什么？

假设数据库中最初只有 4 个 Chunk 向量：

- A：讨论营业收入。
- B：讨论净利润。
- C：讨论经营现金流。
- D：讨论行业竞争。

现在新增一个向量 E，它讨论“营业收入增长但现金流下降”。

建立 HNSW 索引时，算法大致会执行以下操作：

1、**选择 E 所属的层级**：HNSW 使用随机化规则为新节点选择最高层级。并不是每个节点都会进入高层。

2、**寻找附近的候选节点**：从已有图的入口开始搜索，找到与 E 比较接近的节点，例如 A、C。

3、**选择邻居并建立连接**：算法会从候选节点中选择合适的邻居，让 E 能够进入已有的图结构。

4、**维护已有连接**：必要时也会调整邻居之间的连接，使图保持适合导航的结构。具体规则比单纯选择最近的几个点更复杂。

因此，HNSW 不是把所有向量按照相似度排成一条直线，而是建立一张可以从不同方向接近目标的图。

这也是为什么建立索引本身需要时间和额外内存。

## 2. 为什么不直接把每个节点连向最近的几个节点？

这是一个很值得思考的问题。

假设每个节点都只连接最近的 3 个邻居。看起来很合理，但如果这些邻居全部挤在一个很小的局部区域，图就可能缺乏跨区域的连接。

搜索可能在局部区域里绕来绕去，不容易快速到达其他区域。

HNSW 的连接选择算法会考虑候选邻居之间的相对位置，尽量兼顾局部连接和导航能力，而不只是机械地挑选最近的若干节点。

它并不能保证每条搜索路径都是最优的，但好的连接结构能够让搜索更高效。

# 五、三个核心参数，终于可以真正理解了

你之前看到的 `m`、`ef_construction`、`ef_search`，分别影响图怎么建、建得多仔细，以及查询时搜得多仔细。

## 1. `m`：每个节点可以建立多少连接？

可以把它理解成路网中每个地点可以连接多少条路。

<img src="C:\Users\67564\AppData\Roaming\Typora\typora-user-images\image-20261021000608054.png" alt="image-20261021000608054" style="zoom:80%;" />

在 pgvector 中，`m` 是每个节点的连接数量相关参数，并不意味着每个节点在每一层都恰好有 `m` 条边。不同层的连接上限和实际连接数会有所区别。

常见起始值是 `m = 16`。是否要增大，应该根据召回率、内存和查询延迟的实际测试结果决定。

## 2. `ef_construction`：建图时，寻找邻居要仔细到什么程度？

假设新向量 E 插入时，算法需要寻找它的合适邻居。

如果只检查少量候选节点，就可能错过更合适的连接；如果探索更多候选节点，就有机会建立更好的连接，但建索引会更慢。

这就是 `ef_construction` 的作用。

- 数值较小：建索引通常更快，但图的质量可能较差。
- 数值较大：建索引通常更慢，但可能提高后续检索的召回率。

它主要影响索引构建阶段，不是直接控制每次查询检查多少个候选节点。

## 3. `ef_search`：查询时，要探索多少候选节点？

这是在线检索时特别重要的参数。

假设最终只需要 Top 10 个 Chunk，但不能只检查 10 个候选节点。因为 HNSW 不一定已经访问到真正最相关的 10 个。

所以，它会维护一个候选集合，探索更多节点，再从中挑选最终结果。

可以用下面这个简单例子理解：

| 查询设置           | 探索范围     | 可能的结果                 |
| ------------------ | ------------ | -------------------------- |
| 较小的 `ef_search` | 较少候选节点 | 更快，但可能漏掉相关 Chunk |
| 较大的 `ef_search` | 更多候选节点 | 通常召回率更高，但延迟更大 |

注意，`ef_search` 不是最终返回的条数，也不等于实际计算距离的精确次数。它控制的是搜索的候选探索规模。

例如：

```
SET hnsw.ef_search = 100;
```

这个配置可以作为测试起点，但不是说系统只会计算 100 个向量，也不是说一定能返回最准确的 100 个结果。

### 把三个参数放在一起

| 参数              | 发生阶段 | 你可以把它理解为       |
| ----------------- | -------- | ---------------------- |
| `m`               | 建索引   | 路网有多少连接         |
| `ef_construction` | 建索引   | 修路时探索得有多仔细   |
| `ef_search`       | 查询     | 找路时检查多少候选节点 |

它们不是越大越好。你的目标是用合适的建索引成本、内存和查询时间，换取足够好的召回率。

# 六、HNSW 为什么会漏掉真正最相似的向量？

这是理解 HNSW 最关键的部分之一。

我们先区分两件事：

- 距离计算是否准确：给定两个向量，计算它们的余弦距离，可以是精确的。
- 候选向量是否找全：HNSW 不一定会访问所有向量，所以可能根本没检查到真正最近的那个。

HNSW 的近似性主要来自第二点。

## 1. 一个简单例子

假设查询向量是 \(Q\)，真实最近邻是节点 T。

但是 HNSW 搜索时，当前访问的节点 A 有两条可选路径：

- 路径一通向区域 B，局部看起来越来越接近 Q。
- 路径二需要先经过一个距离 Q 较远的节点，再进入包含 T 的区域。

贪心搜索可能沿着路径一前进，而不愿意经过那个看起来更远的节点。

<img src="C:\Users\67564\AppData\Roaming\Typora\typora-user-images\image-20261021000649711.png" alt="image-20261021000649711" style="zoom:80%;" />

这就是为什么 HNSW 的检索结果可能和暴力搜索的 Top K 不完全一样。

提高 `ef_search`，通常可以让算法探索更多候选节点，减少漏检的概率，但不能保证彻底消除漏检。

## 2. 为什么不把 `ef_search` 无限调大？

当然可以考虑增大搜索范围，但这会带来成本：

- 需要计算更多向量距离。
- 需要维护和处理更多候选节点。
- 查询延迟通常会上升。
- 并发较高时，CPU 和内存压力也会增加。

所以实际工程上通常是在召回率和延迟之间寻找平衡。

对于金融研报 RAG，漏掉一个关键 Chunk 可能导致答案缺少重要依据；但为了召回更多内容而把查询延迟提高数倍，也未必合理。

正确做法是用一批人工标注的金融问题做基准测试，对比不同参数下的 Recall@K、P95 延迟和资源消耗。

# 七、HNSW 在 pgvector 中还有一个容易忽略的问题：过滤条件

这部分和你的项目特别相关。

假设你有 100 万个研报 Chunk，用户提出：

> 查询某公司 2024 年的经营现金流分析。

你可能有以下条件：

```
WHERE company_id = 1001
  AND report_year = 2024
```

同时还要按向量距离取 Top 10。

## 1. 为什么加过滤条件后，结果可能不够？

因为 HNSW 主要根据向量距离寻找候选节点，而公司和年份属于结构化元数据条件。

假设搜索过程中先找到了 100 个向量，其中：

- 70 个来自其他公司。
- 20 个来自其他年份。
- 只有 10 个满足公司和年份条件。

如果这些过滤是在候选向量被找到之后执行，那么符合条件的结果可能少于你希望的数量。

实际行为取决于 PostgreSQL 的执行计划、pgvector 版本和查询配置；上面只是为了说明风险的简化例子。

## 2. 可以怎么解决？

常见思路包括：

1. 迭代索引扫描：在支持的 pgvector 版本中，允许搜索继续探索更多节点，以便过滤后仍能得到足够结果。
2. 增大 `ef_search`：扩大候选探索范围，通常有助于减少过滤后结果不足的问题。
3. 使用合适的元数据索引：例如给 `company_id`、`report_year` 建 B-tree 索引，让 PostgreSQL 在合适的查询计划下利用结构化条件。
4. 按业务分区或隔离检索范围：如果不同公司的数据规模很大、过滤条件很稳定，可以评估分区、分区内索引或其他数据组织方式。

需要注意：B-tree 元数据索引不一定会和 HNSW 索引在一次查询中完美协同。最终执行计划和检索效果都要通过 `EXPLAIN ANALYZE` 与实际数据验证。

# 八、HNSW 的性能代价：它为什么吃内存？

前面讲了 HNSW 为什么快，现在换个角度：它为什么不能免费获得这种速度？

因为它需要提前建立和维护一张图。

这张图除了原始向量，还需要保存节点之间的连接信息，以及索引本身的辅助结构。

假设你的 Embedding 是 1536 维、使用 32 位浮点数：

\[ 1536 * 4 = 6144 bytes \]

也就是说，每个原始向量仅数值部分就大约占 6 KB。

| Chunk 数量 | 仅向量数值的理论大小 |
| ---------- | -------------------- |
| 10 万      | 约 586 MiB           |
| 100 万     | 约 5.72 GiB          |
| 1000 万    | 约 57.2 GiB          |

这些数字不包含表记录、索引连接、数据库页和其他存储开销。实际 HNSW 索引会额外占用空间，因此不能简单地把上表当成完整的内存需求估算。

这也解释了为什么 HNSW 在大规模场景下需要认真规划内存。

## 1. 建索引和插入数据也需要成本

HNSW 不仅在查询时需要资源，建索引时也需要寻找合适邻居、维护图连接。

在 PostgreSQL 中，尤其需要考虑：

- 初次创建索引所需的时间。
- 大量 Chunk 批量导入时的资源消耗。
- 新增向量时的索引维护成本。
- 更新和删除向量时的处理方式。
- 数据库重启、备份恢复和索引重建所需的时间。

因此，HNSW 特别适合需要大量相似度查询的场景，但并不意味着它对所有数据库工作负载都是最佳选择。

## 十、最后用一句话总结 HNSW

你可以把 HNSW 记成三个概念：

- 图：把向量组织成可以沿边访问的网络。
- 分层：高层快速导航，底层精细搜索。
- 近似：减少需要检查的向量数量，以一定的漏检风险换取速度。

它不是让向量距离计算变得更快，而是让系统有办法**尽量少计算一些不必要的向量距离**。

这才是 HNSW 在 RAG 中最核心的价值。
