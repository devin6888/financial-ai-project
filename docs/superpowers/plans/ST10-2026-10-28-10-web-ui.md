## 0. 为什么要有这一阶段

### 0.1 现状：能力齐全，但没有一个能点的界面

截至阶段 9，后端已经是「上传 PDF → 解析切块 → 混合召回 → 重排 → 带页码引用的回答 → 多轮会话 → 长期偏好」的完整链路，
但**全仓库没有一行前端代码**（README 在阶段 9 一节明确写着「前端：全仓库无前端，接口用 curl 演示」）。
这带来三个具体问题：

| 问题 | 表现 | 影响 |
| --- | --- | --- |
| 不会用 | 每个动作都要手写 curl，参数（scope 的三种模式、conversationId、Bearer token）记不住 | 演示时只能念命令，不能「打开就能用」 |
| 看不见 | 引用里有 documentId / pageStart / sectionPath / evidenceType，但 curl 输出是长 JSON | 面试官看不到「带页码引用」这个卖点 |
| 验不了 | warnings / trace / gateHit / SCOPE_EMPTY 这些都是给机器看的 | 出问题时无法用界面复现与解释 |

### 0.3 一次问答返回什么（前端的全部素材）

| 字段 | 含义 | 前端怎么用 |
| --- | --- | --- |
| `sufficient` / `confidence` | 是否答得出 / high·medium·low·insufficient·error | 顶部状态徽标；insufficient 用黄色而不是红色（是业务结果不是故障） |
| `answer` | 正文（含 [E1] 这种编号） | 正文渲染，编号点击高亮对应引用卡 |
| `facts` | 结构化数字（metric/period/value/unit/scope/evidence） | 单独一张「数值表」，方便对数 |
| `citations` | documentId / pageStart / pageEnd / sectionPath / docTitle / evidenceType / unit / scope / bbox | 引用卡片：文档名 + 第 N 页 + 章节 + 类型徽标 |
| `note` | 拒答或证据不足的解释 | 灰色提示框 |
| `warnings` | 机器可读降级原因（`query_inferred_from_context` / `company_from_scope` / `evidence_insufficient` / `scope_acl_hidden` …） | 「诊断」折叠区，默认收起 |
| `scope` | 本轮实际用了哪些文档（resolvedDocumentIds） | 答案上方一行「本轮范围：2 份文档」 |
| `trace` | traceId / 检索段 / 记忆段（gateHit, longTermItems）/ 耗时 / 块数与 token | 「诊断」折叠区 |
| `conversationId` / `messageId` | 落库结果 | 有会话时用于刷新消息列表 |

### 0.4 后端缺的三样东西（前端绕不过去，必须补）

| 缺什么 | 为什么非补不可 | 补法 |
| --- | --- | --- |
| `GET /api/me` | 界面要显示「当前是谁、什么角色、哪个租户」；否则用户不知道自己的 token 是谁的，也解释不了「为什么看不到某份文档」 | 一个 5 行的控制器，返回 `TenantContext.require()` 的 userId/tenantId/username/displayName/roles |
| `PATCH /api/conversations/{id}` | `renameTitle` 已经在 ConversationRepository.java:127 存在，但没有 REST 入口；会话列表只有「新会话」这种自动标题，用户改不了名 | 加一个只接受 `{title}` 的 PATCH，复用 `titleFrom` 的截断规则 |
| `GET /api/documents` | 现在只有 `/api/scope/documents`（**只含 DONE 且可检索**的文档）。上传后 PENDING / PARSING / FAILED 的文档在界面上「消失」，用户不知道该等还是该重传 | 加列表端点（带 parseStatus、pagesParsed、activeChunkVersion、公司），按 created_at 倒序 |

### 1.2 本阶段不做（并写清理由）

| 不做 | 理由 |
| --- | --- |
| SSE / WebSocket 流式输出 | 需要改后端为流式接口（ChatService 目前是同步返回 + 四层校验后才产出答案）。先把「能用」做出来；流式属于体验优化，放阶段 11 之后 |
| PDF 原文预览与 bbox 高亮 | 需要新增「取对象」端点（COS 预签名 URL）+ pdf.js 渲染 + 坐标换算。引用卡片先给「文档名 + 页码 + 章节 + 原文片段所在块」，够用 |
| 用户注册 / 登录页 | 没有登录接口，也不该有：token 是运维预置的（V8 种子），界面只做「粘贴 token」。真要做账号体系属于权限阶段 8 的延伸，不在本期 |
| 仪表盘 / 评测报表页 | 评测数据是测试产物（target/eval-*.json），不是运行时数据；硬做成页面等于把测试结果当业务数据 |
| 移动端适配 | 定位是本地演示与自用，按 ≥1280px 桌面布局；窄屏只保证不横向溢出 |
| 国际化 | 全中文界面；文案集中在 `src/labels.ts`，将来要英文只改一个文件 |
| axios 等 HTTP 库 | 全同源 + 13 个 JSON 端点，`fetch` 够用；实测 axios +21.0 kB gzip 只省 12 行（§2.6.1） |
| marked / markdown-it 等渲染库 | answer 逐字含 PDF 原文，走 innerHTML 就必须再上 DOMPurify；自写 tokenizer 只产出文本节点，从结构上无 XSS（§2.6.2） |
| Playwright 浏览器 e2e | 需要下载浏览器二进制（本机 npm 直连不可用，见 §2.4），先把 Vitest 单测与手工清单做扎实 |

### 2.1 结论

| 层 | 选型 | 版本（本机 npmmirror 实测可安装） | 为什么 |
| --- | --- | --- | --- |
| 框架 | Vue 3（Composition API + `<script setup>`） | vue 3.5.44 | 单文件组件、模板语法对后端同学最直观；本项目页面少、状态简单，不需要 React 生态那套 |

### 2.3 为什么不是别的

| 备选 | 否决理由 |
| --- | --- |
| 纯 HTML + 原生 JS（或 HTMX） | 会话列表、消息流、引用卡片、上传轮询都是「状态驱动」的交互，手写 DOM 更新会散落一地；模板 + 响应式是这类界面的最小成本方案 |
| React + Ant Design | 不是不行，但你（使用者）不是前端方向，Vue 的模板更像 HTML，学习曲线最短；Element Plus 的中文文档更完整 |
| Next.js / Nuxt（SSR） | 本项目界面全部在登录后，SEO 无意义；SSR 只会带来额外的构建与部署复杂度 |
| 直接用 Spring Boot + Thymeleaf 服务端渲染 | 每次交互都要整页刷新，「提问 → 等 3~10 秒 → 局部更新」这种体验做不出来 |

### 2.4 网络前提（本机实测，2026-10-28）

| 项 | 结果 |
| --- | --- |
| `registry.npmjs.org`（默认） | `npm view vue version` 约 18 秒后失败（超时） |
| `registry.npmmirror.com`（阿里镜像） | 正常，vue/vite/element-plus/pinia/vue-router/vitest/typescript 全部可查 |
| Node / npm | v24.18.0 / 11.16.0（pnpm 10.24.0 也在） |

**因此**：`financial-ai-web/.npmrc` 固定写 `registry=https://registry.npmmirror.com`，README 里也说明「默认源不可用」。
这一步不做的话，`npm install` 会卡在超时，且报错信息看不出来是源的问题。

### 2.5 脚手架：用官方 `create-vue`，不用后台管理模板（2026-10-28 实测对比）

问题：前端要不要拿市面上的脚手架直接做？答案是「要脚手架，不要后台模板」——这两件事经常被混成一件事。

| 方案 | 本机实测获取方式 | 实际拿到什么 | 一次性成本 | 结论 |
| --- | --- | --- | --- | --- |
| A. 官方 `create-vue@3.24.0 --bare` | `npx create-vue@3.24.0 web --ts --router --pinia --vitest --eslint --bare`，5 秒生成 | **23 个文件**：4 个 tsconfig（app/node/vitest/base）、eslint 10 flat config + oxlint、vitest.config、vite.config、vue-tsc、index.html、空路由表、App.vue/main.ts 各 200 字节。**零业务代码、零业务假设** | 依赖 3 个运行时（vue/pinia/vue-router）+ 21 个开发依赖；`npm install` **244 秒 / 379 包 / node_modules 166 MB**（镜像源）；`npm run build`（含类型检查）**3.9 秒** → dist **110 KB**（gzip 39 KB） | **采用** |
| B. 成熟后台模板（`vue-pure-admin@7.0.0`，GitHub `git clone --depth 1` 5.6 秒） | 只能 clone（**不在 npm**：vue-pure-admin / soybean-admin / art-design-pro / @vben/admin 全部 E404） | **636 个文件、255 个 .vue、src 下 412 个 ts/vue 共 41,250 行**；**64 个运行时依赖**（echarts、mqtt、wangeditor、logicflow、高德地图、甘特图、二维码、webcam 裁剪、codemirror、i18n、mock…）+ 61 个开发依赖 | 要先把「用户名密码登录 + access/refresh 双 token + RBAC 菜单 + mock 拦截器 + 多布局/主题切换 + i18n」拆掉，再接我们的「固定 Bearer token + `GET /api/me`」 | **不采用** |
| C. npm 上的 element-plus 后台模板（`vue-element-plus-admin@1.9.9`） | `npm view` 可查到 | 最后一次发布 **2023-08-13**，vite 4 / vue 3.2 时代 | 与 Node 24 + vite 8 + TS 6 的工具链代际冲突，升级成本高于重写 | **不采用** |

判断标准只有一条：**模板给的是不是「我们本来就要写的那部分」。**

| 对比项 | 后台模板给的 | 本项目实际需要 | 差在哪 |
| --- | --- | --- | --- |
| 构建/类型/测试/格式化配置 | 有（但它绑定自己的目录约定与别名） | 有（23 个文件里的 16 个） | 正好是脚手架 A 的产出 |
| 登录 | 用户名密码 → 双 token + 刷新 + 权限码 | 粘贴一个预置 token → `GET /api/me` | 模板这套要整段删掉 |
| 权限 | 前端路由级 RBAC 菜单 | 后端 RLS + ACL 已经在服务端裁决，前端只显示「看不到就是空列表」 | 前端 RBAC 是重复实现且会造成「前端隐藏 ≠ 后端拒绝」的错觉 |
| 业务组件 | 表格/表单/图表/富文本/地图 | **引用卡（页码+章节+类型徽标）、数值表、证据不足块、诊断折叠** | 这四样模板里没有，必须自己写 |
| 代码量 | 41,250 行既有代码 | 我们自写的约 1,500 行（4 页 + client + 6 组件） | 读模板的成本 > 写业务组件的成本 |

**结论**：骨架用官方 `create-vue --bare`（它就是这个生态里最主流的脚手架，Vue 官方团队维护），UI 库用 Element Plus，业务页面自己写。
后台模板里值得抄的只有「布局常识」（顶栏 + 左导航 + 内容区 + 面包屑），照样子写 60 行 `App.vue` 即可，不必为了布局引入 4 万行代码。

补充两条实测事实：

- **镜像源**：本机 `registry.npmjs.org` 超时，`registry.npmmirror.com` 正常；但 `npm_config_registry` 环境变量在这里**不生效**（`npm view` 仍打 npmjs 并 404），必须在 `financial-ai-web/.npmrc` 写死 registry 或命令里带 `--registry=`。
- **GitHub 可通**（`github.com` / `codeload.github.com` 均 200），所以「clone 模板」技术上可行 —— 否决它是工程判断，不是网络限制。
### 2.6 第三方依赖的取舍（2026-10-28 本机实测体积）

基线：`create-vue --bare` 空工程 `npm run build` → `dist/assets/index-*.js` **102.06 kB（gzip 39.45 kB）**。下表每一行都是在本机同一个工程里加依赖后重新 build 得到的**实测增量**，不是估算。

| 场景 | JS（raw / gzip） | CSS（raw / gzip） | 相对基线 |
| --- | --- | --- | --- |
| 空工程（基线） | 102.06 / 39.45 | 4.05 / 1.27 | — |
| + axios 1.21.0 | 159.84 / 60.43 | 4.05 / 1.27 | **+57.8 / +21.0** |
| + marked 18.1.2 + DOMPurify 3.4.17 | 178.44 / 64.73 | 4.05 / 1.27 | **+76.4 / +25.3** |

#### 2.6.1 不引入 axios，用原生 `fetch`（+ 25 行 XHR 只给上传用）

| 判断维度 | axios | 原生 fetch | 本项目取谁 |
| --- | --- | --- | --- |
| 我们实际要发的请求 | — | — | 13 个同源 JSON 端点 + 1 个 multipart 上传 |
| 跨域 / cookie / CSRF | 拦截器方便 | 不需要处理 | 都同源（生产同端口，开发走 Vite proxy），**没有跨域问题** |
| 超时 | `timeout: 120000` | `AbortSignal.timeout(120000)`（Chrome 103+ / Node 18+） | 平手 |
| 错误归一 | `error.response?.data` 是 axios 自己的形状 | 自己判 `res.ok` + 解析 `{error,message,warnings}` | 都要手写，axios 省不了 |
| 上传进度 | `onUploadProgress` 开箱可用 | 不支持（浏览器 fetch 不能读请求体进度） | **这一条是 axios 真占优**，用 XHR 包一层解决 |
| 体积 | +57.8 kB raw / **+21.0 kB gzip** | 0 | fetch |
| 依赖数量 | 1 个包 + 25 个传递依赖 | 0 | fetch |

结论：**不装 axios**。它替掉的大约是下面这 12 行代码，代价是 21 kB gzip 与一层额外的错误形状：

```ts
async function request<T>(path: string, init: RequestInit = {}, timeoutMs = 15_000): Promise<T> {
  const res = await fetch(`${baseUrl}${path}`, {
    ...init,
    headers: { ...authHeader(), ...jsonHeader(init), ...init.headers },
    signal: AbortSignal.timeout(timeoutMs),      // 问答传 120_000，其余 15_000
  })
  const text = await res.text()
  const body = text ? JSON.parse(text) : null
  if (!res.ok) {
    throw new ApiError(res.status, body?.error ?? `HTTP_${res.status}`, body?.message ?? res.statusText, body?.warnings ?? [])
  }
  return body as T
}
```

上传唯一的例外用 XHR（约 25 行）：`xhr.upload.onprogress = e => progress.value = e.loaded / e.total`。**只此一处**，其余全部走 `request()`。

什么时候该换成 axios：接第三方**跨域** API、需要「401 后刷新 token 并重放队列」、需要请求/响应拦截器统一切换签名。这三件事本期都没有，将来有了再换，`request()` 是唯一改动点。

#### 2.6.2 不引入 markdown 渲染器（自写 ~80 行 tokenizer，永不产生 innerHTML）

三条理由，按重要性排序：

1. **安全**。`answer` 里逐字包含 PDF 原文片段（规则 1 就是「每个数字必须逐字来自证据」），PDF 是 COS 上的第三方文件。用 `marked` → 得到 HTML → 只能 `v-html` 插入 → 一旦有人在 PDF 里塞 `<img src=x onerror=...>`，这条链路就是可执行脚本。自写渲染器只产出 **Vue 文本节点**（`{{ }}`），结构上不可能 XSS，也就不需要 DOMPurify。
2. **反正要切引用号**。`[E1]` 必须变成可点击的 chip → 必须把 answer 切成 token。既然 tokenizer 已经存在，加「换行 / 粗体 / 列表」只是三个分支。
3. **体积与收益不成比例**。+76.4 kB raw / +25.3 kB gzip，换来的是一堆我们永远不会渲染的语法（表格、代码块、脚注、HTML 内联）。

实际支持的子集（写死在这里，超出的一律按纯文本显示，**不猜结构**）：

| 语法 | 渲染成 | 依据 |
| --- | --- | --- |
| `\n\n` 分段、单 `\n` 换行 | `<p>` / `<br>` | 模型偶尔分行写要点 |
| `**粗体**` | `<strong>` | 模型最常用的强调 |
| 行首 `- ` / `* ` | `<ul><li>` | 列举多个数字时会用 |
| 行首 `1. ` | `<ol><li>` | 同上 |
| `[E1]`、`[E1][E3]` | 引用 chip（可点击，滚动到对应引用卡） | 本项目的核心交互 |
| 其余（`<` `>` `&` 等） | 原样转义显示 | 防注入 |

不支持并写清理由：表格（模型若真输出 `|`，按纯文本等宽显示，比猜错列更诚实）、代码块、链接、图片、内联 HTML、脚注。将来若 `facts` 之外真的需要表格，用**结构化数据**渲染（像 `facts[]` 那样），而不是让模型写 markdown 表格 —— 后者列宽与对齐不可控，还会把数字塞进字符串里，绕开数值校验。

#### 2.6.3 Element Plus 必须按需引入（不能 `app.use(ElementPlus)`）

实测全量引入 **+917.6 kB JS（gzip +289.7）+ 364 kB CSS**，是本项目基线的 10 倍；按需只装用到的组件后回到几百 kB 量级。
做法：`unplugin-vue-components@32.1.0` + `unplugin-auto-import@21.1.0`（镜像源均可查）配 `ElementPlusResolver({ importStyle: 'css' })`，模板里直接写 `<el-button>` 即可，不用手动 import。

#### 2.6.4 最终运行时依赖只有 4 个

| 依赖 | 版本（实测可安装） | 用途 |
| --- | --- | --- |
| vue | 3.5.44 | 框架 |
| vue-router | 5.4.0 | 路由（hash） |
| pinia | 4.1.0 | 两个 store |
| element-plus | 2.14.7 | UI 组件（按需） |

**没有 axios、没有 markdown 库、没有 lodash、没有 dayjs**（日期只需 `Intl.DateTimeFormat` 一行）。开发依赖由脚手架给（oxlint / eslint 10 / vitest / vue-tsc / vite-plugin-vue-devtools）+ 上面两个 unplugin。
## 3. 页面与交互

### 3.1 信息架构（4 个页面，hash 路由）

| 路由 | 页面 | 干什么 |
| --- | --- | --- |
| `#/login` | 登录 | 粘贴 API token → 调 `/api/me` 验证 → 存 localStorage |
| `#/chat` / `#/chat/{id}` | 问答 | 左：会话列表；中：消息流 + 提问框；右（可折叠）：作用域与诊断 |

### 3.2 提问到引用的流程（一次交互的完整时序）

~~~text
用户输入问题
   │  （未建会话时先 POST /api/conversations，标题留空由后端首轮自动命名）
   ├─ POST /api/chat {question, conversationId, scope}
   │      ↓ 3~10 秒（同步）：QU → 检索 → 上下文 → 答案 → 四层校验
   │      ↓ 期间界面：气泡内骨架 + 已等待秒数 + 「检索中/生成中」提示（无流式，只给等待感）
   └─ 200 ChatResponse
         ├─ sufficient=false → 黄色「证据不足」块 + note + warnings
         ├─ answer 里的 [E3] → 点击滚动到第 3 张引用卡并高亮
         ├─ citations[] → 卡片：docTitle · 第 pageStart 页 · sectionPath · 类型徽标 · 单位/口径
         ├─ facts[] → 数值表（指标 / 期间 / 数值 / 单位 / 口径）
         └─ trace/warnings → 右侧「诊断」折叠区（默认收起）
~~~

### 3.3 作用域选择器（三模式，对应 ScopeKind）

| 模式 | 请求体 | 界面 | 边界提示 |
| --- | --- | --- | --- |
| CORPUS（全库） | `{kind:'CORPUS'}` | 单选「全部可检索文档」 | 只统计当前账号**可读**的份数 |
| DOCUMENTS（指定） | `{kind:'DOCUMENTS', documentIds:[...]}` | 多选表格（标题/公司/年份/类型/页数/块数） | 空选 = 前端拦住（后端会 409） |
| FILTER（条件） | `{kind:'FILTER', query:{companyCodes, years, docTypes, industries}}` | 四个筛选框 | 说明「条件之间是 AND，全空等于全库」 |

三种越权/空集响应必须有专门界面：`401`（token 问题 → 引导重新填）、`409 SCOPE_EMPTY`（范围不可用 → 换范围，不是「换个问法」）、`404`（会话不存在 → 回列表）。
这三条如果混成一个「请求失败」弹窗，用户会以为是系统坏了 —— 这正是阶段 8 契约 C11 花大力气区分语义的原因。

### 3.4 会话与上下文

- 会话列表按 `updatedAt` 倒序；点击切换；右侧 ⋮ 菜单：重命名（新端点）、删除（204 后回列表）。
- 上下文面板展示 `companyName(companyCode) / yearFrom~yearTo / currentMetric / documentIds`，可改、可清空（`clear:true`）。
- 追问时如果 `warnings` 含 `query_inferred_from_context`，在该条回答上打「主语来自上文」的小标记 —— 这是把阶段 9 的机制显式展示给用户。

## 11. 登录完善：账号密码 + 默认用户（2026-10-28 晚，用户指令）

> 用户原话（m06921）：「把登录继续完善，你默认创建一个用户，并把现有的 company 和 document 等数据关联到该用户，我后续用该用户去操作」。

### 11.1 现状与问题

| 现状 | 问题 |
| --- | --- |
| 登录 = 粘贴 `dev-analyst-token` 这类**预置明文 token** | 演示时说不清「用户从哪来」；token 泄了不能单独撤销；界面上没有「账号」概念 |
| `app_user.api_token_hash` 一列一个 token | 一个用户只能有一个 token，换设备就得改库 |
| 库里没有任何密码字段 | 无法做「用户名 + 密码」登录 |
| 现有 2 份文档、4 条记忆的 `owner_user_id` / `subject_id` 是旧演示账号 | 新用户登录后看不到自己名下的数据 |

### 11.2 方案（不引入 Spring Security、不引入 JWT）

**认证继续走 Bearer token，但 token 变成「登录后签发」的会话 token**：

1. `POST /api/auth/login {username, password}` → 校验密码 → 签发一个 32 字节随机 token（base64url），**库里只存 SHA-256**，写 `api_session`（含过期时间）。
2. 前端把 token 存 localStorage，后续请求继续 `Authorization: Bearer <token>` —— 与 C11 的认证链路完全一致，RLS / TenantContext / 审计都不用改。
3. `AuthenticationFilter` 先查 `app_user.api_token_hash`（保留三个种子 token，测试与老链接继续可用），再查 `api_session`（未撤销、未过期）。
4. `DELETE /api/auth/session` 撤销当前 token（登出）。会话 token 可撤销，这正是当初不选 JWT 的理由（见 `docs/技术选型.md` §2.8.1）。
5. 密码哈希用 **PostgreSQL pgcrypto 的 bcrypt**（`crypt(pw, gen_salt('bf', 10))`）：校验也在库里做（`password_hash = crypt(?, password_hash)`），Java 侧不引 bcrypt 依赖、不自己实现 KDF。
6. 登录失败按「用户名 + 来源 IP」计数（内存，10 次 / 15 分钟）→ 429 `AUTH_TOO_MANY`；失败响应统一 401 `AUTH_INVALID`，不区分「用户不存在」与「密码错」。
