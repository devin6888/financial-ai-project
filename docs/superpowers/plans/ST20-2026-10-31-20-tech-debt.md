## 2. 债 #1：EXACT 打分（`PgSparseRetriever.exact`）

### 2.1 改法

`ORDER BY score DESC, pos ASC, id ASC`，其中：

- `score = Σ over terms: (内容命中 ? char_length(term) : 0) + (标题或 section_path 命中 ? 3 : 0)`
- `pos = LEAST over terms: (strpos(content, term) > 0 ? strpos(...) : Integer.MAX_VALUE)`

三档信号的理由写在 `docs/关键契约.md` 的 **C31.2**：长度是「具体程度」的廉价代理（这一路没有 IDF）、
标题加分说明整块都在讲这件事、位置只做同分兜底（位置≠相关性）。

### 2.2 为什么不引第三方（BM25 / ParadeDB）

- 这一路的价值是**不过分词器**（实测「每股收益」精确子串 6 条 vs 分词后 86 条），换成 BM25 就回到分词问题上；
- 自建 BM25 需要 `unnest(tsvector)` 算 tf、`count(*)` 算 df、`avg(length)` 算 avgdl，约 150 行 SQL/Java，
  而收益只在「同一路内部的排序」——最终排序本来就交给 RRF + Rerank。

## 3. 债 #2：精准事实跳过 Dense（`HybridRetriever`）

### 3.1 改法

编排从「固定 Dense → Sparse」改成「**可能先跑 Sparse**」：

```
exactFactQuery = qu.queryType == EXACT_FACT && sparseMode == EXACT && qu.metrics 非空
if (exactFactQuery):
    sparseHits = sparse.retrieve(...)
    if (3 <= sparseHits.size() < 30): denseSkipped = true; warnings += dense_skipped_exact_fact
if (!denseSkipped): denseHits = dense.retrieve(...)
if (sparseHits == null): sparseHits = sparse.retrieve(...)   // 没先跑过才跑
```

### 3.2 区间为什么是 [3, 30)

| 命中数 | 含义 | 决策 |
| --- | --- | --- |
| `< 3` | 实体写法与文档对不上（「每股收益」vs「基本每股收益(元/股)」） | 保留 Dense（语义兜底） |
| `[3, 30)` | Sparse 已足够准 | 跳过 Dense |
| `>= 30` | 过滤没真正收窄，排序会退化成位置排序 | 保留 Dense（参与融合增加区分度） |

### 3.3 不跳的另外两种情况

- EXACT 落空回退 `FTS_OR`：此时 `sparseHits` 来自词级召回，不是精确子串；
- `qu_filter_empty_fallback` 放宽过滤后的重试：那一路照旧两路都跑。

## 5. 债 #3：旧 chunk 版本保留策略（已实施，方案 A）

### 5.1 问题规模（实测）

document 7 曾有 11 个版本：v1~v11 每版 758 行，共 8338 行，而检索只读 `active_chunk_version = 11`。
也就是说 **91% 的行永远不会被检索到**，却一直占着 `vector(1024)` 的 4100 字节/行。

### 5.2 为什么不能一删了之

| 约束 | 具体表现 |
| --- | --- |
| 历史答案的引用 | `conversation_message.citations_json` 里存着 `childChunkId`，前端点引用要取原文 |
| 事实表外键 | `financial_fact.chunk_id` 直接指向 `document_chunk(id)`，删了会被数据库拒绝 |

### 5.3 三个候选与选择

| 方案 | 做法 | 结论 |
| --- | --- | --- |
| **A（采用）** | 保留 `active` + 最近 3 版；其余版本的行删除，但**被引用的行单独保留** | 省行数、不破坏历史引用；被引用的那一行仍然能取原文 |
| B | 只留 active + 最近 1 版，历史引用降级为「原文已随重新切块失效」 | 省得更多，但要改前端 404 文案，属于产品决策 |
| C | 加 `retired_at` 软删 | 行数一点不省 —— 堆的是行，不是可见性 |

选 A 的关键细节：**保护到「行」而不是「版本」**。如果按版本整体保留，document 7 的 11 个版本几乎全要留（引用散落多版），
等于没清；按行保留既能点开旧引用，又能清掉同版本的其余行。

### 5.4 实现

| 文件 | 职责 |
| --- | --- |
| `src/main/java/com/finagent/chunk/ChunkRetentionService.java` | `plan(documentId)` 算计划（不写库）、`apply(plan)` 真删；常量 `CITED_CTE` 汇总三处引用 |
| `src/main/java/com/finagent/chunk/RetentionPlan.java` | 计划 record：keep / delete 版本号、`rowsToDelete`、`rowsSpared`、`rowsToFree()` |
| `src/main/java/com/finagent/chunk/ChunkRetentionRunner.java` | 人工触发入口（`ApplicationRunner` + `@ConditionalOnProperty`），默认干跑 |

| `src/test/java/com/finagent/chunk/ChunkRetentionDbTest.java` | 5 例真库：计划正确、按行保留、被引用行存活、无可删时为空、active 是旧版也不删 |

### 5.5 实测（2026-10-31 21:31~21:36，document 7）

```text
干跑：document=7 active=v11 keep=[11, 10, 9] delete=[1..8] rows=6064 spared=0 willDelete=6064
执行：清理 document 7 的旧 chunk：8 个版本 / 删除 6064 行 / 保留被引用 0 行
```

| 指标 | 清理前 | 清理后 |
| --- | --- | --- |
| document 7 行数 | 8338（11 版） | **2274（3 版）** |
| 全库 chunk 行数 | 9072 | **3008** |
| 表 + 索引总大小 | 113 MB | **87 MB**（VACUUM + REINDEX 后） |
| `idx_chunk_embedding` | 16 MB | 10 MB |
| `idx_chunk_content_trgm` | 18 MB | 5 MB |
| `idx_chunk_tsv` | 7.5 MB | 1.3 MB |

注意两个容易踩的点：

1. **`DELETE` 不等于空间回来了**：先 `VACUUM` 清堆，HNSW/GIN 的死条目还要 `REINDEX` 才释放（113 → 112 → 87 MB 就是这个过程）。
2. **`spared=0` 不是「没保护」**：document 7 被引用的 16 个 chunk 都落在 v9/v11（保留集里），所以待删版本里没有被引用的行。

清理后回归：`PgSparseRetrieverTest` 11 + `ComplexEvidenceDbTest` 1 全绿（12/12），检索结果不受影响。

## 8.5 附：图的编译与复用（2026-11-02，用户提出）

### 8.5.1 现象

`AgentRunService` 每次请求都调 `graph.fastGraph()` / `graph.hitlGraph()`，而它们直通 `build(hitl)` ——
一次问答会新建并编译两张图（起 + 人批恢复），**每查一次运行状态（刷新页面 / 轮询）还会再编译一张**。

### 8.5.2 先量，再改

| 指标 | 实测 |
| --- | --- |
| 建图 + `compile()`（fast / hitl） | **0.112 ms / 0.058 ms**（300 次均值，已预热） |
| 一张编译好的图常驻内存 | **≈ 4.9 KB**（留住 2000 张 → 堆涨 9.5 MB） |
| 一次问答的节点耗时（库里 184~214 次样本） | answer **10,506 ms** / understand **3,680 ms** / retrieve 1,551 ms / 其余 < 150 ms |

结论：建图不是性能问题（占比 0.001%，5 KB 垃圾对象）；但它是设计问题 —— 见下。

### 8.5.3 为什么可以共享（字节码级证据）

`CompiledGraph` 的五个字段全 `final`：`stateGraph` / `nodes` / `edges` / `processedData` / `compileConfig`。
`javap -c` 扫全部方法，对这五个字段的 `putfield` 只出现 5 次，**全在构造器里**；`stream()` / `getState()` 一个都不写。
每次运行的变量走 `RunnableConfig(threadId)` + 检查点 saver，节点 lambda 只从 state 读身份。

### 8.5.4 改法

- `AnalysisGraph` 新增两个 `volatile` 字段 + 双检锁：`fastGraph()` / `hitlGraph()` 各只编译一次；
- 新增 `warmUp()`，`AgentGraphConfig` 建 bean 时调一次 —— 图定义写错（少边、节点名错、条件边目标不存在）会在**启动期**抛错，而不是每个请求 500；
- `mermaid()` 与 `AgentRunService.stateOf()`（原来各建一张）自动走缓存，无需改调用点；
- 缓存**必须实例级**，不能 static：测试用 `FakeAnalysisNodes` + `MemorySaver` 另建实例，静态缓存会把假节点带进生产。

### 8.5.5 验收

| 层 | 用例 / 操作 | 结果 |
| --- | --- | --- |
| 单测 | 新增 `AnalysisGraphCacheTest` 8 例：fast 只编一次 / hitl 只编一次 / 两张不同（`interruptsBefore` 各自正确）/ 实例级缓存 / warmUp 幂等 / mermaid 不重编 / 缓存图连跑两次状态互不干扰 / 8 线程并发拿到同一实例 | 8/8 绿 |
| 既有 | `AnalysisGraphTest` 14 例（拓扑、条件边、中断） | 14/14 绿 |
| 真启动 | `spring-boot:run`（web=none） | 启动日志只出现两条「Agent 图已编译：fast / hitl」，都在 `Started` 之前 |
| 真链路 | 1 次 `POST /api/chat` + 3 次 `GET /api/agent/runs/{id}` | 编译日志**始终 = 2 条**（改前这两个动作会各编 1~4 张） |

> 唯一代价：进程启动多约 2 ms，换来「图定义错误在启动期暴露」。

## 9. 债 #4：重索引的三种模式（2026-11-01）

### 9.1 问题：想换模型，却只能整份重来

原来的 `ReindexMode` 有四个值，但只有 `RECHUNK` 能用：

| 模式 | 原意图 | 改前实际 |
| --- | --- | --- |
| `RECHUNK` | 重新切块 + 重嵌 | 能用 |
| `RETRIEVAL_ONLY` | 不切块，只重建检索侧数据（tsv / 向量） | **抛 `UnsupportedOperationException`** |
| `REEMBED` | 保留切块，强制重嵌 | 同上（没有入口） |
| `FULL_REPARSE` | 从解析开始重来 | 仍然抛（这条本来就不该走重索引，入口是上传 / `document.parse`） |

代价很具体：换 embedding 模型、或者想给 chunk 补一个元数据字段后重算 `content_tsv`，
都得**重跑 Docling**（实测 12 页 PDF 解析 201 秒、181 页年报更久）—— 而这两件事都不需要解析。

### 9.2 改法：从库里把块搬回内存，按 C1 重拼 embedding_text

`RETRIEVAL_ONLY` 走的路：

```
读 active_chunk_version 的所有行（findVersionChunks）
  → 按 parent_id 还原 ParentGroup / 子块分组（ReindexService.group）
  → ChunkWriter.writeVersion(..., forceReembed=false)  ← 新版本号，不切块
      → EmbeddingReuseService 按 embedding_text_hash 匹配旧向量
      → 只对 hash 变了的块调 embedding API
  → 切 active_chunk_version 到新版本（原子）
```

三个关键决定：

1. **复用靠 hash，不靠"块序号对上"**：`embedding_text_hash` 是 `embedding_text` 的 SHA-256（C1 的组成：文档标题 + section_path + caption + 正文）。hash 没变就说明送进模型的那段文字一字不差，向量必然相同，可以整段跳过 API。
2. **section_path 要拆回 List 再拼**：库里存的是 `"第一节 § 营业收入"`，而 C1 拼接用 `" > "`。拆错一个字符，hash 全变，就会退化成"654 块全量重嵌"——最贵的失败方式，而且不报错。
3. **新增流程模板 `RETRIEVAL`（3 步）而不是复用 `REINDEX`（4 步）**：`REINDEX` 的第一步叫「切块中」，而这几种模式恰恰不切块，文案会说谎。新模板是 已沿用现有切块 → 向量化 → 切换 ACTIVE。

`REEMBED` 与它的差别只有一行：`forceReembed=true` 等价于"把旧向量当成空"，于是 654 块全部重嵌。

### 9.3 迁移 V18：放开 flow 枚举

`document_ingest_run.flow` 的 CHECK 在 V17 里写死了 `('PARSE','REINDEX','RESUME')`。
新模板第一次写库就被拒（`Failing row contains (... RETRIEVAL ...)`），后续所有语句都在同一个失败事务里连带报 `25P02 current transaction is aborted`。
V18 只做两件事：DROP 旧约束、ADD 带 `'RETRIEVAL'` 的新约束，并更新 `flow` / `total_steps` 的 COMMENT。

> 教训：**枚举值也是 schema**。写 CHECK 的时候要想到"以后会不会多一种"，或者干脆用外键表；至少不要在 CHECK 里留下"三个值就是全部"的暗示而不在注释里说明。

### 9.4 验收：证明"零成本"，而不是"能跑"

| 层 | 用例 | 结果 |
| --- | --- | --- |
| 单测（mock） | `ReindexServiceTest` 8 例：REPARSE 明确报错 / 未解析拒绝且不建 run / RECHUNK 读 COS 写新版本 / 不碰解析服务 / RETRIEVAL 无旧版本时报错 / RETRIEVAL 从库重建且不切块 / REEMBED 传 forceReembed=true / 孤儿块拒绝重建 | 全绿 |
| 真库 | `ReindexRebuildDbTest` 2 例：重建后的每个 hash 都在旧版本里找到向量（`toEmbedTexts()` 为空）/ 新版本父子数与旧版一致且没有空向量 | 2/2 绿（20.75 s） |
| 真链路 | `--finagent.reindex.document-id=7 --finagent.reindex.mode=RETRIEVAL_ONLY` | 日志「复用 654 / 新嵌 0」，v11 → v12 |
| 库内核对 | v11 与 v12 的 CHILD `embedding_text_hash` 集合双向 EXCEPT | **0 行差异** |
| 执行记录 | `document_ingest_run` 新 run 156 | flow=`RETRIEVAL`、3 步全 DONE、`summary_json={"chunks":654,"reused":654,"version":12,"embedded":0}`；REUSED 15 ms → EMBEDDING 30 ms → SWITCHED 12 ms |

**"零 API 调用"怎么证明**：不是看日志写"新嵌 0"（那是我们自己的计数），而是 `ReindexRebuildDbTest` 里那条 `toEmbedTexts()` 必须为空的断言 —— 它直接检查"要送进模型的那一批"是空集合。

### 9.5 一个必须记住的事实：654 个块只有 652 个不同的 embedding_text

第一次跑真库用例时断言红了：`hasSize(654)` 实际 652。查了数据侧（758 行 = 104 + 654、无孤儿、父块 chunk_index 互不相同）之后才确认：
**v11 里有 3 个块的 `embedding_text` 一字不差**（同一个 hash），所以复用表（hash → 向量）天然只有 652 个键。

这反过来说明复用策略的另一个好处：**重复块只算一次嵌入**。

## 10. 债 #5：删掉兼容构造器（2026-11-01）

### 10.1 债是什么

三个 record 一路加字段，为了不改老调用点，就一路补"少几个参数"的构造器：

| record | 组件数 | 兼容构造器 | 调用点 |
| --- | --- | --- | --- |
| `QueryUnderstanding` | 13 | 12 / 11 / 10 / 9 参共 4 个 | 52（生产 13 / 测试 39） |
| `ChatResponse` | 12 | 10 参 1 个 | 8（生产 3 / 测试 5） |
| `MemoryContext` | 4 | 3 参、2 参共 2 个 | 7（生产 4 / 测试 3） |

真正的风险不是"多几行"，而是**位置传参错位**：`QueryUnderstanding` 里 `companyCodes` 与 `companyMentions` 都是 `List<String>`，
把后者错当后者传进去，编译器一声不响，运行时表现为"公司名被当成证券代码去查库"。

### 10.2 改法：一个全参构造器 + 具名工厂 + wither

```java
QueryUnderstanding qu = QueryUnderstanding.of(QueryType.EXACT_FACT, "2025年营业收入")
        .withCompanyCodes(List.of("300059"))
        .withYears(2025, 2025)
        .withMetrics(List.of("营业收入"))
        .withRoute("LLM");
```

- `of(type, query)` 给出全部默认值（无实体、无年份、路由 `RULE`、不降级）；
- 新增 wither：`withYearRange / withYears / withMetrics / withRoute / withDegraded / withDocType / withCompanyMentions / withNeedMultiQuery / withNeedDecompose`（已有 `withCompanyCodes / withInferredFromContext / withNeedLongTermMemory`）；
- `ChatResponse`、`MemoryContext` 直接删兼容构造器，7 + 5 处调用点补尾参（`null, null` / `List.of(), null`）。

### 10.3 验收

| 层 | 用例 | 结果 |
| --- | --- | --- |
| 新增单测 | `QueryUnderstandingFactoryTest` 5 例：默认值 / 代码与公司名不串位 / 两种年份入口等价 / wither 只改一个字段且不可变 / `none()` 与 `failed()` 仍可区分 | 5/5 绿 |
| 受影响类 | 19 个类（RouterService、HybridRetriever、MemoryGate、AnswerService…） | 209 例全绿 |
| 全量 | `mvn -o test`（排除 e2e / db） | 见 §11 |

### 10.4 差点埋进去的坑：批量改写把"变量年份"弄丢了

39 处测试调用点是脚本改写的（把位置参数映射成 wither）。第一版只认 `new int[]{2025, 2025}` 这种字面量，
遇到 helper 里的 `int[] years` **直接跳过**，于是年份静默变成 `null` —— 编译通过、7 个用例红（`HybridRetrieverTest` 2 / `HybridRetrieverScopeTest` 3 / `ScopeFilteringTest` 2），
全部是"年份过滤没生效"。

修法是补一个 `withYearRange(int[])`，三处 helper 显式传数组。教训：**机械改写要按"参数类型"而不是"参数长相"决定落点**，
而"编译通过"对静默丢字段毫无防御力 —— 只有断言能抓到。
