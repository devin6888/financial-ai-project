# 阶段 13 · 首屏时延优化（状态行 + 证据先行）

> 计划日期：2026-10-28　｜　状态：**待确认执行**（本文只整理方案，未动代码）
> 前置：阶段 12 已完成（`docs/阶段12-体验补强报告.md`），流式链路已上线，实测首字 7,870 ms。
> 契约影响：新增 C16（stage 事件与首屏时延口径），C15 只加不改。

## 0. 为什么做这一步

### 0.1 阶段 12 留下的那句实话

阶段 12 验收表第 3 项写的是「流式首字 < 2.5 秒」，实测 **7,870 ms**，标记为未达标。报告里给的判断是：差的不是流式实现，而是**检索与模型首 token 的固定成本**；下一步应该「先发状态行 + 证据先到」，而不是硬压模型。这份计划就是把那句话变成可执行的东西。

### 0.2 一次真实请求，时间到底花在哪（实测拆解）

下表 6 行来自 `logs/chat-trace.jsonl` 的真实记录（2026-10-28 18:49~19:39，同一问题「东方财富2025年营业总收入是多少」问了 5 次 + 1 次追问）：

| 时刻 | Dense | Sparse | 融合 | 精排 | 上下文装配 | 生成整段 | 一次总耗时 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 18:49:27 | 697 ms | 61 ms | 1 ms | 486 ms | 94 ms | 7,280 ms | 8,519 ms |
| 18:57:23 | 536 ms | 31 ms | 3 ms | 479 ms | 35 ms | 7,116 ms | 8,165 ms |
| 18:58:14 | 463 ms | 16 ms | 0 ms | 432 ms | 761 ms | 6,623 ms | 8,295 ms |
| 19:00:31 | 698 ms | 37 ms | 2 ms | 524 ms | 33 ms | 7,167 ms | 8,160 ms |
| 19:03:09 | 932 ms | 27 ms | 3 ms | 484 ms | 140 ms | 7,730 ms | 9,176 ms |
| 19:39:39（追问） | 1,175 ms | 182 ms | 26 ms | 1,219 ms | 66 ms | 3,813 ms | 6,481 ms |

把「首字 7,870 ms」按段摊开（前四段实测，后一段推算）：

| 段 | 耗时 | 口径 |
| --- | --- | --- |
| ① 理解问题（QU，一次 LLM 调用） | **约 2,900 ms** | 阶段 6 的 A/B 对照：开 QU 每题多花 3 秒（`docs/阶段6-评测报告.md:243`）；本期新增 `quMs` 埋点后改为直接测量 |
| ② 双路召回（Dense + Sparse） | 500~1,360 ms | 上表 Dense + Sparse 列（Dense 占九成） |
| ③ RRF 融合 | 0~26 ms | 上表融合列 |
| ④ 精排（qwen3-rerank，一次外部调用） | 430~1,220 ms | 上表精排列 |
| ⑤ 上下文装配 | 33~761 ms | 上表装配列 |
| ⑥ 模型首 token | **约 3,300 ms（推算）** | 7,870 − (①+②+③+④+⑤) |

**结论**：7,870 ms 里，**系统自己算的部分约 4,500 ms（①②③④⑤，其中 QU 占三分之二）**，模型首 token 约 3,300 ms。也就是说：即使把模型换成更快的，用户仍然要静止 4 秒以上。

### 0.3 用户看到的 vs 系统在做的

| 时间 | 系统在做什么 | 用户看到什么 |
| --- | --- | --- |
| 0 ms | 收到请求，开始 QU | 三个省略号的「正在检索并生成」 |
| 0~2,900 ms | QU 的 LLM 调用 | 同上（没有任何变化） |
| 2,900~4,300 ms | 双路召回 + 融合 + 精排 | 同上 |
| 4,300~5,000 ms | 装配上下文 | 同上 |
| 5,000 ms | **证据早已确定**（8 条，4 条会被引用） | 仍然什么都不显示 |
| 5,000~7,870 ms | 等模型首 token | 同上 |
| 7,870 ms | 第一个 delta | 终于有反应 |

两个浪费：

1. **前 7.8 秒没有任何「进度」信号**，用户无法区分「在算」与「卡死」；
2. **证据在 5 秒时就已确定**（`meta` 事件里就带着），却要等到 7.9 秒后跟着答案一起出现 —— 先给证据，用户至少能开始读。

### 0.4 为什么不做「压模型」那一类优化

| 方案 | 收益 | 为什么不选 |
| --- | --- | --- |
| 换更快的模型（qwen-turbo） | 首 token 可能从 3.3 s 降到 1.5 s | 答案质量是这套系统的卖点，数值落地校验与引用全靠它；为了 1.8 秒换掉最强的理解能力，面试时反而是减分项 |
| 关掉 QU | 省 2.9 s | 多轮追问（「那净利润呢」）与公司名解析全靠它；阶段 9 实测这是核心能力 |
| 关掉精排 | 省 0.5~1.2 s | 引用准确率与 top-1 相关性直接下降，评测有门槛（`EvalGateTest`） |
| **并行 QU 与检索** | 省 2.9 s | 做不到：检索的过滤条件与查询改写都来自 QU 的输出，是硬依赖 |
| **先发状态行 + 证据先行** | 把「7.9 秒静止」变成「0.1 秒有反应、5 秒看到证据」 | **选这个**：不动质量、不动模型、不改检索，只改「什么时候告诉用户什么」 |

## 1. 范围

### 1.1 做（6 项）

1. 后端新增 `stage` SSE 事件：`understanding` / `retrieving` / `reranking` / `generating` 四个阶段，进入某段代码时才发；
2. 后端把 QU 计时（`quMs`）与各段耗时一起落 trace，日志一行能看全；
3. 前端把写死的「正在检索并生成」换成**真实阶段状态行**（阶段名 + 已用秒数，秒数是本地真实计时，不是动画）；
4. 前端在 `meta` 到达时**立刻渲染证据条**（文档名 · 页码 · 类型），不等答案；
5. 前端在证据已到、答案未到时显示「证据已就绪，正在生成答案」+ 答案骨架；首字到达即替换骨架；
6. e2e 断言三个数字并落盘：`firstStageMs`、`metaMs`、`firstTokenMs`；报告记录优化前后对比。

### 1.2 不做（6 项，各有理由）

| 不做 | 理由 |
| --- | --- |
| 逐 token 之外再发「dense 完成 / sparse 完成」这类子阶段 | 用户不需要知道内部召回细节，事件多了前端每秒重渲染，反而更卡 |
| 前端伪造进度条 / 循环动画 | 一旦进度和真实耗时脱钩，就是在骗人；面试被问「这个进度是真的吗」会很难看 |
| 把 `meta` 提前到精排之前发 | `meta` 里的 E1..En 是上下文装配后的块（含邻居与整段展开），检索候选与最终证据不是同一批；提前发会出现「证据条 8 条、引用 4 条对不上」 |
| 服务端 Streaming 分片写入数据库（边生成边存） | 本轮不涉及持久化语义；`final` 之后再落库与现在一致 |
| WebSocket 或 HTTP/2 推送 | 已有 SSE 够用，换协议成本远大于收益 |
| 首字压到 2 秒以内 | 见 0.4：那要靠降模型/砍 QU/砍精排，属于「用质量换时延」，本阶段明确不做 |

## 2. 契约 C16（草案）

### 2.1 `stage` 事件

| phase | 什么时候发（代码位置） | label（前端直接显示） | detail |
| --- | --- | --- | --- |
| `understanding` | `ChatService.askStreaming` 第一行，**在 `prepare()` 之前** | 正在理解问题 | 无 |
| `retrieving` | QU 与作用域解析完成、进入检索之前 | 正在检索证据 | `{documents: N}`（作用域内可读文档数） |
| `reranking` | `HybridRetriever` 融合完成、调用 rerank 之前 | 正在精排证据 | `{candidates: N}` |
| `generating` | `meta` 发出之后、调用模型之前 | 正在生成答案 | `{evidence: N, contextTokens: N}` |

payload 统一为 `{phase, label, detail}`；`detail` 可以为空对象，但**不允许**出现答案文本、证据正文、页码、chunk id。

事件完整顺序（正常路径）：

```
stage(understanding) → stage(retrieving) → stage(reranking) → meta → stage(generating) → delta* → final
```

拒答路径：`stage(understanding) → stage(retrieving) → final`（没有 `generating`：没调用模型）。
错误路径：`stage(...)* → error`。

五条硬规则：

1. **stage 只能说「正在做什么」**，不能携带任何答案内容与证据正文；
2. **stage 必须由真实进入该段的代码发出**，禁止用定时器补发、禁止前端按时间伪造；
3. **发过 stage 就必须有终止事件**（`meta` / `final` / `error` 至少一个），不允许停在「正在精排」；
4. **stage 可以丢**（网络抖动丢了不影响正确性），`meta` / `final` 不能丢；丢了 `final` 前端按 `STREAM_INCOMPLETE` 回落；
5. **旧前端不许崩**：SSE 解析器按事件名分发，未知事件忽略即可（`web/src/utils/sse.ts:54-68` 已有此行为，本期只加测试守住）。

### 2.2 证据先行

- `meta` 到达 = 证据集合已确定 → 前端**立即**渲染证据条（每条：`[E#]` + 文档名 + 第 N 页 + 类型）；
- 证据条与最终 `citations` 的对应关系：`meta.evidence` 是**候选全集**（通常 8 条），`final.citations` 是**模型实际用到的**（通常 2~4 条）。因此：
  - 生成阶段证据条显示全部，超出 4 条折叠成「+N」；
  - `final` 到达后按 `citations` 重绘（这是唯一真相，C15 §15.1 规则 1 不变）；
- 证据条与答案区之间**不得跳动**：证据条高度固定（一行 chip，超出折叠），答案区骨架提前占位。

### 2.3 时延口径（这一节是为了以后能对比）

| 指标 | 定义 | 采集点 | 目标 |
| --- | --- | --- | --- |
| `firstStageMs` | 请求发出 → 收到第一个 `stage` | 前端 `onStage` 时间戳 | **≤ 300 ms**（本地回环，实测应 < 50 ms） |
| `metaMs` | 请求发出 → 收到 `meta`（证据可读） | 前端 `onMeta` 时间戳 | ≤ 5,000 ms（现状约 4,400~5,000 ms，**回归门限**） |
| `firstTokenMs` | 请求发出 → 收到第一个 `delta` | 前端 `onDelta` 首次 | ≤ 8,000 ms（现状 7,870 ms，不得变慢） |
| `quMs` | QU 全段耗时 | 后端 `ChatService` 埋点 → `ChatTrace.quMs` | 只观测，不设门槛 |

### 2.4 与 C15 的关系

- C15 §15.1 的 `meta` / `delta` / `final` / `error` 语义**一个字不改**；
- `stage` 是**新增的可选事件**，因此 C15 不需要改，只在 C16 里声明「stage 与 C15 四事件的关系」；
- C15 规则 1「final 是唯一真相」在 C16 里继续适用：`meta.evidence` 只是预览，`final.citations` 才是引用。

## 4. Task 1：后端 `stage` 事件

### 4.1 步骤

1. `ChatStreamEvent`：`public static final String STAGE = "stage"`；`public static ChatStreamEvent stage(String phase, String label, Map<String, Object> detail)`。
2. `RetrievalProgress`：`onPhase(String phase, int count)`；`NONE` 常量。
3. `HybridRetriever`：`doRetrieve` 增加 `RetrievalProgress progress` 参数，四处埋点（dense / sparse / fuse / rerank），`retrieve(req, qu, scope)` 委托给新重载并传 `NONE`。
4. `ChatService.askStreaming`：**第一行**发 `understanding`（此时连 `prepare` 都还没进）；再调 `prepare(request, sink)`。
5. `ChatService.prepare(request, stageSink)`：
   - 作用域解析完成后、检索前：`retrieving`（`{documents: scope.size()}`）；
   - 检索内部由 `RetrievalProgress` 转成 `reranking`；
   - 装配完成、`meta` 之前不再发；`askStreaming` 在 `meta` 之后发 `generating`。
6. `ChatTrace.quMs`：围绕 `router.understand(...)` 计时；`compose()` 里传入；日志行加 `qu=…ms`。

### 4.2 为什么 stage 回调要下到 `HybridRetriever`

「精排中」只有 `HybridRetriever` 自己知道（它内部先融合、再截断、再调 rerank）。如果只在 `ChatService` 层埋点，就只能给出「检索中」，无法区分「召回」与「精排」—— 而精排恰恰是用户等待感最强的一段（430~1,220 ms，且是外部 HTTP 调用，抖动大）。

### 4.3 验收

| # | 断言 |
| --- | --- |
| 1 | 正常路径事件序列 = `stage(understanding) → stage(retrieving) → stage(reranking) → meta → stage(generating) → delta+ → final` |
| 2 | 拒答路径（作用域外公司）= `stage(understanding) → stage(retrieving) → final`，且**没有** `generating` |
| 3 | 检索无候选时：`stage(reranking)` 不出现（没东西可精排），`meta` 仍然发 |
| 4 | `stage` 的 detail 不含答案文本 / chunk id / 页码 |
| 5 | 既有 60 条流式相关用例不回归 |

## 5. Task 2：前端状态行

### 5.1 要解决的问题

现状 `web/src/components/MessageBubble.vue:63` 是写死的：

```vue
{{ message.text ? '正在生成' : '正在检索并生成' }}<span class=dots><i /><i /><i /></span>
```

它有两个毛病：① 检索和生成混成一句，用户不知道卡在哪；② 没有时间感，7 秒和 70 秒看起来一样。

### 5.2 设计

- `StageLine.vue`：四个小圆点（理解 / 检索 / 精排 / 生成）+ 当前阶段中文 + `已用 3.2s`；
- 秒数由 `setInterval(200)` 本地累计，`final` / `error` 时清理定时器；
- 阶段切换时圆点依次点亮（已过的阶段保持灰实心，不再动）；
- 文案只用后端 `label`，前端**不自己编**阶段名（避免两边说法不一致）。

### 5.3 验收

| # | 断言 |
| --- | --- |
| 1 | 点发送后 ≤ 300 ms 出现「正在理解问题」+ 计时开始 |
| 2 | 阶段切换时文案跟着变，不会出现「检索中」直接跳「生成中」而中间漏掉（后端没发就不显示） |
| 3 | `final` 后状态行消失、计时器停止（用 `clearInterval` 断言，避免内存泄漏） |
| 4 | 失败（error / 回落同步）后状态行换成错误提示，不残留计时 |

## 6. Task 3：证据先行渲染

### 6.1 设计

- `onMeta` 时写入 `message.evidencePreview = meta.evidence`，`EvidenceStrip` 立即渲染（最多 4 条 + 「+N」）；
- 同时把状态行文案切到「证据已就绪，正在生成答案」（若后端已发 `generating`，用后端的 label，不重复）；
- 答案区：`delta` 未到时显示 3 行骨架（固定高度，避免首字到达时页面跳动）；
- `final` 到达后：证据条按 `citations` 重绘，正文整段替换（C15 规则 1）；若 `meta` 8 条而 `citations` 4 条，被丢的 4 条不保留（它们没进答案）；
- 滚动：仅当用户已在底部 40 px 内才自动滚到底（用户向上翻证据时不打断）。

### 6.2 验收

| # | 断言 |
| --- | --- |
| 1 | `meta` 到达后 ≤ 200 ms 出现证据条，此时正文仍是骨架 |
| 2 | 首字到达时骨架消失、正文出现，布局无跳动（证据条与正文顶端 Y 坐标差 < 2 px） |
| 3 | `final` 后证据条数量 = `citations.length` |
| 4 | 用户向上滚动时不被自动滚动打断 |

| D2 | `stage` 是新增可选事件，`meta/delta/final/error` 语义不变 | 已部署的静态包遇到未知事件只会忽略（`sse.ts` 默认分支），不需要前后端同时升级 |
| D3 | 阶段粒度 4 个（理解 / 检索 / 精排 / 生成），不细到 dense/sparse | 用户关心「卡在哪一段」，不关心内部两路召回；事件越少前端越稳 |
| D4 | 秒数用本地真实计时，不做假进度条 | 假进度在演示时被追问会崩；真实计时即使慢也诚实 |
| D5 | 证据先行走 `meta.evidence`，不新增端点 | 数据已经在 meta 里，加端点等于把同一份数据发两遍 |

| D7 | 不做 QU 预取 / 缓存 | QU 依赖上一轮会话状态，预取会读到旧槽位，正确性优先 |
| D8 | 门槛用「不回归」而不是「必须更快」 | 本期改的是感知，不是真实耗时；真实耗时优化（QU 缓存、rerank 候选裁剪）留到后续单独评估 |

## 11. 风险与回滚

| 风险 | 表现 | 处置 |
| --- | --- | --- |
| 代理缓冲 | 加了 stage 但浏览器仍是「一次性全到」 | 响应头 `X-Accel-Buffering: no`；本地 Tomcat 不受影响 |
| 事件过多导致重渲染 | 状态行闪烁 | 只在 phase 变化时改 DOM；秒数用独立 ref，不触发整条消息重渲染 |
| 拒答路径漏终止事件 | 前端一直转圈 | 单测覆盖拒答 / 错误两条路径；前端 180 秒超时兜底 |
| `meta` 与 `citations` 数量不一致让用户困惑 | 「证据 8 条，引用 2 条」 | 证据条在 `final` 后按 `citations` 重绘，并在折叠处标「其余未引用」 |
| 回滚 | 需要退回「只有 7.9 秒静止」的旧行为 | 后端删 4 处 `sink.send(stage)` 即可；前端对无 stage 的流天然兼容（一直显示 `understanding`） |
