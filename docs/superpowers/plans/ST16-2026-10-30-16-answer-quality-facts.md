## 1. 现象与证据（2026-10-30 实测）

### 同一个问题，两种答案

问题：`分析下2024年和2025年的营业总收入，然后看下是什么原因导致的`

| | 腾讯 ima 知识库 | 本系统 |
| --- | --- | --- |
| 结构 | 四节：总体对比 / 结构对比 / 增长原因 / 总结 | 一段连续文字 |
| 表格 | 两张表（含占比、同比列） | 无 |
| 归因 | 按业务线拆成 4 类，落到可核查指标（股基交易额、基金销售额、保有规模、手续费净收入） | 只有「收入结构复述」 |
| 换算 | 全部换算成亿元（116.04 亿 / 160.68 亿） | 原样搬 14 位数字 |
| 计算 | 2024 增速 +4.72%、手续费 +48.85%、利息净收入 +44.29% | 无（只有一处占比差，是模型自己减的） |
| 结论句 | 「证券业务为主引擎、基金销售为稳定器」 | 无 |

逐条核对过 ima 的 12 个数字：**全部能在两份 PDF 里找到出处，零幻觉**（核验表见 `docs/阶段15-多路检索证据覆盖报告.md` §8 与本计划 §1.3）。
所以差距不是模型能力，是四项工程能力：**要素覆盖、事实层与计算、跨年份取证、结构化输出**。

## 2. 目标与非目标

### 目标（可验收）

1. 问「原因」的问题，答案必须有归因段，且归因要落到**可核查的经营指标**（交易额、保有规模、销售额、手续费及佣金收入、利息净收入、成本构成）。
2. 金额类事实默认同时给「亿元」与「元」，增长率/占比/百分点由**确定性代码**算，答案里标「系统计算」。
3. 问题提到 N 个年份，证据里必须每年至少一块来自该年年报（`document.doc_year`）。
4. 答案可以输出小标题与表格，前端能正确渲染，引用 chip 仍然可点。
5. 答案可一键复制为 Markdown：粘到飞书/GitHub 里标题是标题、表格是表格，且正文 `[E3]` 能在文末附录里查到是哪份文件哪一页。

### 非目标（这次明确不做）

| 不做 | 原因 |
| --- | --- |
| 接入 XBRL / tushare 等结构化数据源 | 是阶段 17 的候选，本次先把「从 PDF 里确定性抽事实」做扎实 |
| 引入外部（网页/宏观库）信息 | 破坏「引用必须能回到 PDF 页」这条契约（C6/C7） |
| 让模型自己心算 | 15 位数字除法不可靠、不可复现 |
| 多轮指代消解 | 属阶段 9 记忆范畴，本次只做单轮 |
| 图表（柱状图/折线图） | 表格已经够用，图表要另建数据管道 |

## 3. 任务清单

### Task 1 · 答案骨架与要素覆盖（1 天）

#### 1.1 为什么

答案的形状由问题决定：问「多少」要数字，问「为什么」要归因，问「结构」要占比，问「趋势」要同比。
现在的提示词只有「只依据证据、每个数字带引用」，**没有一句关于结构**，模型自然按最省力的方式复述表格。

#### 1.2 新增 `AnswerShape`（规则判定，不花 token）

新文件 `src/main/java/com/finagent/understanding/AnswerShape.java`：

```java
public enum AnswerShape {
    /** 要原因：原因 / 为什么 / 驱动 / 因素 / 归因 / 拉动 */
    ATTRIBUTION,
    /** 要结构：结构 / 构成 / 占比 / 分行业 / 分产品 / 分地区 */
    BREAKDOWN,
    /** 要对比：对比 / 相比 / 同比 / 环比 / 较 */
    COMPARISON
}

public static EnumSet<AnswerShape> detect(String question, int[] yearRange);
```

| 形态 | 触发词 | 额外条件 |
| --- | --- | --- |
| ATTRIBUTION | 原因、为什么、为何、驱动、因素、归因、得益于、受益于、拉动、带动、贡献 | 无 |
| BREAKDOWN | 结构、构成、占比、分行业、分产品、分地区、明细、拆开 | 无 |
| COMPARISON | 对比、相比、同比、环比、较、变化 | 无 |

「增长 / 下降」**不算**触发词 —— 「分析增长的原因」是 ATTRIBUTION，不是趋势题，加了会让骨架跑偏。

#### 1.3 状态与节点接线

- `AnalysisState` 新增 `ANSWER_SHAPES = "answerShapes"`，访问器 `answerShapes()` 返回 `List<String>`（状态里只放 JDK 类型，C17 硬规则 1）。
- `RealAnalysisNodes.plan` 写入（与 `companyMentions` 同一节点，都是「问题的结构」）。
- `AnalysisGraph` 的 stage `plan` 的 `detail` 增加 `shapes`（前端不消费，仅供排障）。

#### 1.4 `verify` 增加第三道检查：要素覆盖

现在的 verify 只查两件事（`RealAnalysisNodes:276-297`）：证据条数够不够、指标字面有没有出现。
它对「问原因、但命中的全是财务附注」无感 —— 这次的现象就是它放过的。

新增：

```java
/** 归因类问题必须命中「驱动类证据」，否则证据不完整（不等于答案错，但要走一次改写重检）。 */
private static boolean attributionCovered(AnalysisState state);
```

| 判定 | 规则 |
| --- | --- |
| 驱动章节 | 命中块 `sectionPath` 含「管理层讨论」「主营业务分析」「行业情况」「经营情况」之一 |
| 驱动词 | 命中块 `snippet` 含「交易额」「保有」「销售额」「手续费及佣金」「利息净收入」「同比增减」「主要原因」之一 |
| 结论 | 任一成立即算覆盖；都没有 → `insufficient=true` + `warnings += "coverage_missing:attribution"` |

关键设计：`insufficient` 只用来**触发一次 rewrite**（复用现有重试机制），不改答案生成路径。改写后仍缺，就照常生成，由骨架第 ④ 段写明缺口 —— 不能把「缺归因」变成「整题拒答」。

`rewrite` 追加驱动关键词：`" 原因 驱动 交易额 保有规模 手续费"`（只加一次，`retryCount` 已有上限）。

#### 1.5 提示词：答案骨架

`AnswerPrompts.SYSTEM` 追加（放在规则之后）：

```
答案骨架：answer 必须按四段写，段首用「一、二、三、四」；
① 结论：一句话给结论，带关键数字与引用；
② 数据：逐年或逐项列出，金额同时给「亿元」与「元」；
③ 归因：按业务线或按科目拆开，每条都必须落在证据里出现过的经营指标上
   （交易额、保有规模、销售额、手续费及佣金净收入、利息净收入、成本构成）；
   证据里只有定性描述时，写「仅有定性表述，报告未给出定量归因」，
   不要用「市场回暖」这类没有出处的判断代替；
④ 口径与缺口：写清单位、期间、口径（合并/母公司）、本次不可得的项。
```

`AnswerPrompts.USER_TEMPLATE` 在【证据】之前插入 `【回答要求】` 段，把 shapes 渲染成清单：

| shape | 渲染文本 |
| --- | --- |
| ATTRIBUTION | 必须回答「为什么」：归因按业务线拆开，引用证据里出现的经营指标 |
| BREAKDOWN | 必须给出结构：分项金额、占比、占比变化（百分点） |
| COMPARISON | 必须给出对比：两期并列 + 变化量 + 变化率 |

为兼容已有调用点，`AnswerPrompts.user(...)` 增加重载；旧的重载传空 shapes，模板里该段整段省略（与 `background` 的处理方式一致，不占位）。

#### 1.6 验收

| 项 | 标准 |
| --- | --- |
| ima 那条问题 | 四段结构齐全；归因至少命中 2 个经营指标块（7237 / 7531 / 7239）；每段有引用 |
| 纯取数问题（「2025年营业总收入是多少」） | 不出现归因段，仍然一句话 + 引用（不为了凑结构而编归因） |
| 测试 | `AnswerShapeTest`（≥8 例）、`AnswerPromptsTest`（骨架段名存在、占位符不残留）、`RealAnalysisNodesTest`（覆盖检查 3 例） |

#### 1.7 风险

| 风险 | 对策 |
| --- | --- |
| 骨架让答案变长，挤占上下文 | 骨架只约束「怎么写」，不增加证据；6000 token 预算不动 |
| 规则形态误判 | 词表故意保守；误判只影响提示词里的一句话建议，不影响检索 |
| 覆盖检查把好答案逼成 rewrite（多 5~15 秒） | 只在 ATTRIBUTION 且完全无驱动证据时触发；最多 1 次 |

### Task 2 · 事实层与派生指标（1.5 天）

#### 2.1 为什么

两个问题必须在同一个任务里解决，否则会打架：

1. **`facts` 经常为空**：模型只写正文不填 facts，`FactGuard` 也放过空数组 → 结构化数据没了，前端「关键数据」卡片是空的。
2. **答案不能换算、不能算比率**：规则 1 禁止换算（防幻觉），代价是只能搬 15 位数字；而 ima 的「专业感」一半来自 `160.68 亿元`、`+38.46%`。

正确做法不是放开规则，而是**把换算与计算搬进确定性代码**，模型只负责叙述。

#### 2.2 新包 `com.finagent.fact`

| 类 | 职责 | 关键约束 |
| --- | --- | --- |
| `ReportedFact` | 证据里**直接写着的**事实（record：metric / period / value:BigDecimal / unit / chunkId / evidenceNo / rowText） | 值必须能在该块正文里逐字找到 |
| `ComputedFact` | 由公式算出来的事实（record：metric / period / value / unit / formula / inputs:List<ReportedFact> / evidenceNos） | 必须带 `formula` 与 `inputs`，否则不许出 |
| `TableRowParser` | 解析 markdown 表格行 → 标签 + 数值列表（千分位、括号负数、空单元格） | 解析失败一律返回空，不猜 |
| `FactCollector` | 上下文块 + QU → `List<ReportedFact>` | 只在「表头能唯一确定列→期间」时出事实 |
| `UnitConverter` | 元 → 万元 / 亿元（`BigDecimal` HALF_UP，2 位小数） | 保留原值；|value| < 1e7 不换算 |
| `MetricRegistry` | 公式登记表（见 2.3） | 每条公式带口径说明 |
| `MetricCalculator` | 按 registry 算 `ComputedFact` | 上期为 0 / 缺输入 → 跳过并记 `compute_skipped:原因` |

#### 2.3 公式登记表（第一版只这四条）

| 名称 | 公式 | 需要的输入 | 单位 | 口径说明 |
| --- | --- | --- | --- | --- |
| 同比增长率 | (本期 − 上期) / abs(上期) × 100 | 同一指标两期 | % | 上期为负时用绝对值做分母，并在 note 里标注 |
| 结构占比 | 分项 / 合计 × 100 | 分项 + 合计（同期） | % | 合计必须与分项同期、同口径 |
| 占比变动 | 本期占比 − 上期占比 | 两期占比 | 百分点 | 输出用「百分点」，不是「%」 |
| 收入贡献度 | (分项本期 − 分项上期) / (合计本期 − 合计上期) × 100 | 分项两期 + 合计两期 | % | 合计增量为 0 时跳过 |

**不做**：毛利率、净利率、ROE、人均指标 —— 这些的分母口径有争议（券商没有制造业口径的营业成本，见阶段 15 报告 §6），要么接结构化数据源，要么单独定义口径，不在本任务范围。

#### 2.4 图里新增 `compute` 节点

位置：`verify`（或 `rewrite`）之后、`answer` 之前。

```
understand → plan → retrieve → verify ─┬→ rewrite → retrieve → verify
                                       └→ compute → answer → cite_check → final
```

节点职责：

1. `FactCollector` 从上下文块抽 `ReportedFact`；
2. `MetricCalculator` 按「问题形态 + 指标」算出 `ComputedFact`（只算需要的，不算全套）；
3. 把两类事实渲染成 `【已报事实】` / `【已计算事实（系统计算，可直接引用）】` 两段，注入 answer 提示词；
4. 写回状态 `FACTS`（供 answer 之后的合并与前端展示）。

提示词里每个 `ComputedFact` 渲染成一行，带公式与输入，例如：

```
[F3] 营业总收入同比增长率 = 38.46%（= (16,067,741,039.51 − 11,604,343,090.16) / 11,604,343,090.16；系统计算）
```

#### 2.5 `facts` 兜底与三态来源

`AnswerResult.Fact` 增加两个字段：

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| `origin` | `REPORTED` / `COMPUTED` / `EXTRACTED` | 证据直给 / 系统计算 / 系统从证据抽取 |
| `formula` | 可空 | 只有 COMPUTED 有 |

合并规则（answer 之后）：

1. 模型给的 facts 里，能被证据逐字核到的 → `REPORTED`；核不到的沿用 `FactGuard` 现有处理（丢弃 + 警告）；
2. `compute` 节点的 `ComputedFact` 全部进 facts（`COMPUTED`）；
3. 模型一条 facts 都没给、但问题有明确指标 → 用 `FactCollector` 的 `REPORTED` 事实兜底（`EXTRACTED`），并记 `facts_backfilled` 警告。

`ChatResponse.facts` 增字段 `origin` / `formula`（可选，旧客户端忽略即可）。**不新增接口、不改端点。**

#### 2.6 换算规则（写进提示词 + 由代码保证）

| 场景 | 输出 |
| --- | --- |
| 金额 ≥ 1 亿元 | `160.68 亿元（16,067,741,039.51 元）`，首次出现给括号原值，后文只用亿元 |
| 1000 万 ≤ 金额 < 1 亿 | `3,527.51 万元` |
| 金额 < 1000 万 | 原样，元 |
| 比率 | 2 位小数 + `%` |
| 占比变动 | 2 位小数 + `个百分点` |

换算值一律由 `UnitConverter` 产出并作为「已计算事实」注入，**模型不许自己换**。

#### 2.7 验收

| 项 | 标准 |
| --- | --- |
| 问「2025年营业总收入同比增长多少」 | 答案出现 `160.68 亿元`、`38.46%`（标「系统计算」）；facts 含 2 条 REPORTED + 1 条 COMPUTED（带 formula） |
| 问「2025年各业务板块收入结构」 | facts 含 3 条分项 + 占比（COMPUTED）；占比之和 = 100.00% |
| 上期为 0 / 缺一期 | 不出 COMPUTED，答案里写明缺口，`warnings` 有 `compute_skipped:*` |

### Task 3 · 跨年份与章节定向多路（1 天）

#### 3.1 为什么

现在的跨年问句等于「不按年份过滤」：`HybridRetriever:324-326` 在 `yearRange` 跨年时只记一条 `qu_year_range_no_filter` 警告，然后把年份条件丢掉。
结果能不能拿到 2024 年报的段落，取决于 `DocumentQuotaBalancer` 有没有顺手带进来 —— 这是运气，不是设计。
ima 那条答案之所以能把 2024 年报的「股基交易额 24.24 万亿」写出来，是因为它两份文件都读了；我们只是碰巧也读到了。

#### 3.2 检索车道（lane）模型

把「一路检索」从 `String query` 升级为一条车道：

```java
// com.finagent.agent.RetrievalLane（record，包内可见）
record RetrievalLane(String text, Integer docYear, String sectionPrefix, int topK) {}
```

| 车道 | 什么时候加 | 过滤条件 | topK |
| --- | --- | --- | --- |
| 整句 | 永远 | 空 | 默认 8 |
| 子问题 | `needDecompose` 且拆出 ≥1 条（现状） | 空 | 默认 8 |
| 按年份 | `yearRange` 跨年（`range[0] != range[1]`），每年一条，最多 3 年 | `docYear = Y` | 4 |
| 归因章节 | `AnswerShape.ATTRIBUTION` 命中 | `sectionPathPrefix = "第三节"` | 4 |
| 结构章节 | `AnswerShape.BREAKDOWN` 命中 | `sectionPathPrefix = "第三节"`（主营业务分析在第三节内） | 4 |

过滤条件用 `new RetrievalFilters(null, null, year, null, null, null)`（该 record 所有字段可空，见其类注释），
再通过已有的 `RetrievalRequest.of(text, filters)` 传入。**不要新开检索方法**：`HybridRetriever` 里 `base.docYear()` 优先级最高（`:310`），车道不会被 QU 覆盖。

#### 3.3 年份覆盖校验（关键）

合并之后（沿用 ST15 的「同一 chunkId 取最高分」），检查每年是否真的拿到证据：

```java
/** 返回「一条来自该年 doc_year 的块都没有」的年份。 */
private static List<Integer> missingYears(List<Map<String, Object>> hits, ResolvedScope scope, int[] range);
```

判定依据：命中块的 `documentId` 对应的 `document.doc_year`（作用域里已有这份映射，`scope.docYearOf(documentId)`；执行时若没有就补一个只查 `document` 的轻量方法）。

| 情况 | 处理 |
| --- | --- |
| 缺某年 | 该年再补一条 lane，`topK=8`，重跑一轮（**全局最多 1 轮**，用 `warnings` 里的标记判断是否已补过） |
| 补完仍缺 | `warnings += "year_coverage_missing:2024"`，**不拒答**（答案第 ④ 段写缺口） |
| 作用域里本来就没有该年文档 | 不补，直接记警告（例如用户只勾了 2025 年报） |

#### 3.4 `stage(retrieve).detail` 口径

现在是 `{hits, queries}`（`queries` = 实际检索路数，ST15 改过）。本任务加 `lanes`：

```
{ hits: 23, queries: 6, lanes: ["full", "sub:0", "sub:1", "year:2024", "year:2025", "attr"] }
```

前端不消费（已 grep 确认 `queries` 无消费方，`lanes` 同理），只用于排障。

#### 3.5 验收

| 项 | 标准 |
| --- | --- |
| 问「2024年和2025年营业总收入及原因」 | `hits` 里 doc 7 与 doc 38 **各 ≥1 条**；`lanes` 含 `year:2024`、`year:2025`、`attr`；`warnings` 无 `year_coverage_missing` |
| 问「2025年营业总收入是多少」 | 不产生年份 lane（range 单年），不产生 attr lane（无归因形态） |
| 作用域只含 2025 年报、问两年 | 记 `year_coverage_missing:2024`，答案第 ④ 段写「作用域内无 2024 年报」 |
| 测试 | `YearLaneTest`（纯函数：range 跨年/单年/三年以上/作用域缺年）+ 真库 `CrossYearCoverageDbTest`（`@Tag("db")`，断言两个 document_id 都在 hits 里） |

#### 3.6 风险

| 风险 | 对策 |
| --- | --- |
| 车道变多 → 每次答案多花 2~4 次 rerank 调用（钱与延迟） | 年份/章节 lane 的 `topK=4`（默认 8 的一半），且只在形态命中时加；实测记进报告 |
| `docYear` 过滤把候选集压小，rerank 分变高但相关性不一定更好 | 覆盖校验只看「有没有」，最终排序仍由合并后的分数决定 |
| 三年以上的区间（如 2022~2025）车道爆炸 | 最多 3 年，超出退化为「不加年份过滤」并记 `year_range_too_wide` |

### Task 4 · 结构化输出与复制为 Markdown（1.5 天）

#### 4.1 为什么

答案里三列以上的对比（本期/上期/增减）用散文写必然难读，ima 的「专业感」有相当一部分来自表格。
但前端渲染器是自写的（`D:/Project/myproject/financial-ai-web/src/utils/answer.ts`，113 行），不认标题与表格；
**引入 marked + v-html 是不可接受的**（XSS 面变大，且现有引用 chip 的下标逻辑会失效）。
所以做法是：**后端只输出极简 markdown 子集，前端加两个块类型**。

#### 4.2 自写渲染器还是引库（这是 Task 4 的第一个决定）

「要支持表格和标题」有两条路：**扩现有自写渲染器**，或**引入现成 markdown 库**。两条路都评估过，结论是这次选自写，理由不是「不想加依赖」，而是**引用 chip 的交互形态决定了引库并不省事**。

| | 扩现有自写渲染器 | 引库（marked / markdown-it + DOMPurify） |
| --- | --- | --- |
| 现在的代码量 | 113 行（段落 / 粗体 / 无序 / 有序 / 引用 chip） | — |
| 本任务要加的量 | 约 +80 行（表格块、标题块、单元格内联复用） | 约 +40 行接入，**但还要另写 chip 桥接** |
| 引用 chip 怎么点 | 本来就是 Vue 组件，`@click` 直接绑到 PDF 页 | v-html 里绑不了事件 → 只能事件委托 + `data-` 属性，或者事后把 HTML 再拆回 segments（等于又走回自写） |
| XSS 面 | 无（全是文本节点，`v-text` 级别） | 必须每次流式增量都跑 DOMPurify，且白名单要收到只剩十几个标签 |
| 打包体积 | +0 KB | marked ≈ 40 KB min + DOMPurify ≈ 20 KB min（gzip 后约 +25 KB），当前 ChatView chunk 已是 135 KB / gzip 45.6 KB |
| 流式行为 | 每次 delta 整段重解析，半张表自然降级成段落 | 同样要整段重解析；且 sanitize 失败时会整块空白 |
| 支持范围 | **只支持我们提示词里允许的子集**（见 4.4） | 支持完整 markdown，但模型多写的语法会变成我们没测过的渲染路径 |

结论：两条路的**本期工作量接近**（都是约 1 天），但自写这条的长期形态更可控 —— 引用 chip 是我们最核心的交互（C6/C7：能回到 PDF 页），不能交给 v-html。

顺带说明：这不是新立的规矩，仓库里本来就没用 marked（`src/utils/answer.ts` 的注释写了「刻意不用 v-html」），本任务只是把这条隐含约定**写进计划与契约**，避免以后有人再问一遍。

#### 4.3 什么时候该换成库（决策规则，写死在这）

自写渲染器有明确的天花板。命中下面任意一条，就停下来换成 `markdown-it` + `DOMPurify` + 事后 chip 桥接，并把这次的决定记录进契约：

| 触发条件 | 为什么它意味着「该换」 |
| --- | --- |
| 需要 3 层以上嵌套列表 / 行内代码 / 链接 / 引用块 / 脚注 | 自写解析器会迅速变成 300 行以上的状态机，测试成本超过引库 |
| `answer.ts` 超过 300 行 | 同上（现在 113 行，本任务后约 190 行，还有余量） |
| 一个阶段内新增块类型 ≥ 3 种 | 说明模型输出形态已经超出「极简子集」的假设 |
| 出现 2 次以上「渲染 bug 但解析逻辑看不出问题」 | 说明边界情况已超出人工维护能力 |

换算成钱与体积：引库方案 = 60 KB 源 / 约 25 KB gzip + 一次安全评审；自写方案 = 0 KB 但每加一种块类型约 30 行 + 4~8 个测试。以我们目前「答案只输出四段 + 表格」的形态，自写更划算；一旦答案要变成「报告体」（多级标题、脚注、目录），立刻换库。

#### 4.4 允许的输出子集（写进 `AnswerPrompts.SYSTEM`）

| 语法 | 用途 | 限制 |
| --- | --- | --- |
| `## 标题` | 分段（二~四级标题用 `###`） | 最多 6 个 |
| 段落 | 正文 | 不加行首缩进 |
| `- 项` / `1. 项` | 列表 | 最多两层（第二层用两个空格缩进） |
| 管道表格（表头行 + 分隔行 + 数据行） | 表格 | 最多 6 列、12 行；单元格里禁止换行、禁止再嵌表格；管道符用反斜杠转义 |
| `[E3]` | 引用 | 不变（C7） |

同时加两条硬规则：

1. 表格只用于「同一指标多期并列」或「多分项同期并列」，**不要**把整段文字塞进单元格；
2. 表格前后各留一个空行（否则解析器会当成段落的一部分）。

#### 4.5 前端解析器改造

`answer.ts` 的块模型扩展为：

```ts
type BlockKind = 'paragraph' | 'bullet' | 'ordered' | 'heading' | 'table'

interface TableBlock {
  kind: 'table';
  header: Segment[][];   // 复用现有 Segment（文本 / 引用 chip）
  rows: Segment[][];
}
interface HeadingBlock { kind: 'heading'; level: 2 | 3 | 4; segments: Segment[] }
```

解析规则（按行扫描）：

| 当前行 | 下一行 | 判定 |
| --- | --- | --- |
| 以管道符开头且结尾 | 是分隔行（每格只含减号） | 开表格：第一行做表头，跳过分隔行，后续管道行做数据行 |
| 以管道符开头 | 不是分隔行 | **当普通段落**（防止把残缺表格渲染成一行乱码） |
| 两个及以上 # 开头 | — | heading（level = # 的个数，上限 4） |

单元格切分：按未转义的管道符切；转义符还原；每格再走现有的内联解析（粗体 + 引用 chip），**所以表格里也能点引用**。

#### 4.6 渲染

`AnswerText.vue` 增加两个分支：

- `heading` → `<component :is="'h' + level">`（样式由 class 控制，不用默认 h2 的巨大字号）；
- `table` → `<table>` + `<thead>`/`<tbody>`，外面包一层 `overflow-x: auto`，窄屏可横向滚动；单元格仍是内联渲染（chip 可点）。

流式安全：现有实现每次收到 delta 就整段重新 parse，半张表（还没收到分隔行）会落到「当普通段落」分支，收到分隔行后自动变成表格 —— 不需要额外处理。

#### 4.7 复制为 Markdown（0.5 天，2026-10-30 新增需求）

复制按钮看起来是十行代码，但**复制出去的内容在别的工具里能不能用**，取决于三个决策。做错的表现是：粘到飞书里一堆 `[E3]` 死编号，或者表格散成一行管道符。

##### 决策 1：以「后端原文」为基底，不从渲染块反序列化

答案原文本来就是 markdown 子集（见 4.4），**直接复制原文**，表格与标题零精度损失。
从 `blocks` 重新序列化会丢三样东西：模型写的细微空白、表格列结构、以及我们特意降级掉的语法。所以复制路径是：

```
后端 answer 原文 → 最小归一化（引用编号 + 空白）→ 追加引用附录 → 写剪贴板
```

**不走** `blocks → markdown`，因为那条路的唯一收益是「修正不合规的 markdown」，而我们已经有提示词约束（4.4）与解析降级（4.6）。

##### 决策 2：引用编号必须归一化，并附证据附录（这是最大的兼容点）

`[E3]` 是**站内编号**，复制到外部就是死符号。三种处理的取舍：

| 方案 | 结果 | 取舍 |
| --- | --- | --- |
| 原样保留编号 | 外部只看到 `[E3]` | 不可接受（读者不知道 E3 是什么） |
| 删掉编号 | 引用能力丢失 | 不可接受（C6/C7 的核心价值） |
| **保留编号 + 文末附录** | 正文 `[E3]`，附录解释 E3 是哪份文件哪一页 | **采用** |

归一化规则（与后端 `renumberCitations` 保持同一套口径）：

| 原文写法 | 复制时 |
| --- | --- |
| `[E5]` / `[ E5 ]` / `［E5］` | 统一成 `[E5]` |
| 正文有、`citations` 里没有的编号 | **删除**（与页面角标一致，不制造指向不存在证据的编号） |
| 多个编号 | 按首次出现顺序重排为 E1..En，与页面角标编号一致 |

附录格式（只列正文真正用到的）：

```
---

### 引用

- [E1] 东方财富2025年年度报告 · 第 11 页 · 第三节 管理层讨论与分析 § 一、经营情况讨论与分析（chunk 7237）
- [E2] 东方财富2025年年度报告 · 第 74 页 · 第十节 财务报告 § 合并利润表（chunk 7531）
```

| 细节 | 决定 |
| --- | --- |
| 附录标题层级 | `###`（不能用 `##`，否则和答案骨架的分节标题同级，在外部文档里乱序） |
| 定位信息 | 文件名 + 页码 + 章节路径 + chunk id；**不写 `[E1]` 之外的内部 id** |
| 站内链接 | 若前端已有文档路由（形如 `/documents/7?page=11`）就给相对链接；执行时先确认路由，没有就只给文字定位（不影响可用性） |
| 编号越界 | 删除该角标，并在附录里不出现 |

##### 决策 3：空白与换行

| 规则 | 原因 |
| --- | --- |
| 统一 `\n`（不用 `\r\n`） | CRLF 会让部分 markdown 工具多出空行 |
| 表格前后各保证一个空行 | 否则被当成段落的一部分（4.4 已约束模型，这里兜底） |
| 行尾空格全部去掉 | 两个以上行尾空格在 markdown 里是「强制换行」，粘到别处会变形 |
| 连续空行压到最多 1 个 | 附录与正文之间固定一个空行 |

| 车道变多导致延迟上升 | 单次答案 > 25 秒 | 年份/章节 lane 的 topK 降到 3；或只在 `QUECOMPLEX` 时启用 |
| 前端表格渲染破版 | 窄屏溢出/单元格挤成一列 | `overflow-x: auto` + 单元格 `white-space: normal`；实测 375px 宽 |

## 8. 契约更新（执行时同步写）

### 8.1 C20 · 答案骨架与事实三态

| 规则 | 内容 |
| --- | --- |
| 20.1 | 每轮答案只允许一种骨架：`结论 / 数据 / 归因 / 口径与缺口`；骨架由 `AnswerShape` 决定要不要段落，不是无脑四段 |
| 20.2 | 事实三态：`REPORTED`（证据直给）/ `COMPUTED`（系统按公式算）/ `EXTRACTED`（系统从证据行抽取）；`COMPUTED` 必须带 `formula` 与 `inputs` |
| 20.3 | 冲突时 REPORTED 优先；COMPUTED 与 REPORTED 不一致时在 facts 里加 note，不静默覆盖 |
| 20.4 | 不可得就写缺口，禁止用定性判断替代定量归因 |

### 8.2 C21 · 换算与派生指标口径

| 规则 | 内容 |
| --- | --- |
| 21.1 | 换算只由 `UnitConverter` 做（元→万元/亿元，BigDecimal HALF_UP，2 位），并保留原值 |
| 21.2 | 派生指标只允许 `MetricRegistry` 登记的四条公式；新增公式必须同时加测试与口径说明 |
| 21.3 | 分母为 0、缺一期、口径不明 → 不出 COMPUTED，记 `compute_skipped:原因` |
| 21.4 | 比率 2 位小数 + `%`；占比变动 2 位小数 + `个百分点`（不要写 `%`） |

### 8.3 C22 · 答案渲染子集与依赖约束

| 规则 | 内容 |
| --- | --- |
| 22.1 | 后端只输出 `##/###` 标题、段落、列表、管道表格、`[E编号]` 五类语法；其它 markdown 一律不保证渲染 |
| 22.2 | 前端**禁止** `v-html` 渲染答案；禁止为渲染答案引入 markdown 库，除非命中 Task 4 §4.3 的任一触发条件，并在契约里记录这次换库 |
| 22.3 | 表格解析失败（缺分隔行、列数不齐）一律降级为段落，不抛异常、不出现空白块 |
| 22.4 | 表格单元格内的引用 chip 必须与正文同样可点（回到 PDF 页），这是 C6/C7 的延伸，不是新能力 |

### 8.4 C23 · 复制为 Markdown 的口径

| 规则 | 内容 |
| --- | --- |
| 23.1 | 复制基底是**后端 answer 原文**，只做最小归一化；禁止从渲染块反序列化（会丢表格结构与空白） |
| 23.2 | 引用编号归一化为紧凑写法，越界编号删除，并按首次出现顺序与 `citations` 对齐；文末固定追加「### 引用」附录，只列正文用到的编号 |
| 23.3 | 换行统一 `\n`；表格前后各 1 个空行；行尾无空格；连续空行 ≤1 |
| 23.4 | 流式生成中禁用复制；剪贴板不可用时必须降级（`execCommand`）并在失败时给出可操作提示，不允许静默失败 |
| 23.5 | C7 里「复制后丢括号不是缺陷」的旧表述作废：现在复制要保留编号**并且**给附录 |
