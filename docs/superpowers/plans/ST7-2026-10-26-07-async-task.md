# ST7 · 阶段 7：异步与任务化

> 日期：2026-10-26　前置：阶段 2（docs/阶段2-解析结果报告.md）+ 阶段 3（docs/阶段3-切块与入库报告.md）
> 目标一句话：**把「上传 PDF → 解析 → 切块 → 嵌入」从手动/CLI 驱动改成 Kafka 事件驱动，带上幂等、重试与 DLQ，并让重切块只重嵌真正变了的块。**

> 📖 术语：本文出现的缩写（Kafka、Producer/Consumer、Worker、幂等、DLQ、KRaft、事件驱动……）在 docs/术语表.md 有中文全称、为什么需要它、在本项目里长什么样。写法约定见 docs/文档写作规范.md。

## 0. 为什么这一阶段值得单独做

**现状（两条手动链路）：**
1. 解析 = `DocumentParseService.parseAndStore()` 的**同步 submit + poll**（提交作业 → 轮询结果），没有 REST 入口，也没有事件；
2. 切块/嵌入 = `ReindexRunner` 这个 CLI（`mvn spring-boot:run -D...--finagent.reindex.document-id=7`）**手动触发**，重切时 654 个块**全量重嵌**（上一阶段实测，407 张表只变了 45 张，却全量调了 654 次 embedding API）。

**改造前 · 两条互不相关的手动链路：**

```
链路 A · 解析（无生产入口，靠测试触发）
  手动取 PDF → parseAndStore()
    ├─ sha256(pdf) → content_hash
    ├─ upsertDocument 登记（parse_status=PENDING）
    ├─ parser.submit(...) → jobId
    ├─ markRunning（RUNNING）
    ├─ parser.fetchResult(jobId)   ★ 同步轮询，卡住线程几十分钟
    └─ persistResult → 写 normalized.json 到 COS + mark DONE

链路 B · 切块 + 嵌入（CLI 触发）
  mvn spring-boot:run -D...--finagent.reindex.document-id=7
    → ReindexService.reindex(7, RECHUNK)
      ├─ 查 parse_status == DONE
      ├─ 从 COS 读回 NormalizedDocument
      ├─ ParentChunker.split → ChildChunker.splitAll
      └─ ChunkWriter.writeVersion   ★ 全量重嵌 654 块

两条链路之间没有连接：解析完不会自动切块，得再人工跑一遍 CLI。
```

**改造后 · 一条事件串起来：**

```
上传链路（parse → chunk → embed 一条龙，异步）
  POST /api/documents（multipart 上传）
    → 存 COS + 登记 document(PENDING) + 投递 document.parse 事件
    → 秒回 documentId（不等解析）
  ↓
  [Kafka: document.parse, key=documentId]
  ↓
  DocumentParseListener（worker 消费）
    ├─ task_message=PROCESSING（eventId 幂等去重）
    ├─ 解析（submit+poll）→ 写 COS → mark DONE
    ├─ 切块 + 嵌入（复用 ReindexService 的 chunk+embed）
    └─ 成功 SUCCESS / 失败三分类：瞬时重试 · 业务 FAILED · 数据进 DLQ
  ↓
  客户端轮询 GET /api/documents/{id}

重索引链路（reindex，增量）
  投递 document.reindex 事件（REST/CLI 触发）
  ↓
  [Kafka: document.reindex, key=documentId]
  ↓
  DocumentReindexListener（worker 消费）
    ├─ 从 COS 读回 NormalizedDocument → 切块
    ├─ 增量重嵌：按 embedding_text_hash diff，未变块复用旧向量
    └─ 写新版本（旧版本 SUPERSEDED）
```
**设计文档 §13 已经画好了目标形态**：`document.parse` / `document.reindex` 两个 topic，Document Worker 消费后编排「解析 → Parent-Child 切块 → Embedding → 入库」。本阶段把这条链路落地，并解决三个面试必问的问题：

1. **幂等**：同一条消息重投（网络抖动、消费者崩溃重放）不能产生重复 chunk / 重复向量；
2. **重试与 DLQ**：瞬时错误（网络、COS 超时）要重试；业务错误（解析失败）要进死信而不是无限重试；坏消息要能人工重放；
3. **增量重嵌入**：用已存的 `embedding_text_hash` 做 diff，只重嵌真正变了的块。

## 2. 契约

### C9 · 文档任务、幂等与错误分类

**Topic 定义（沿用设计文档 §12 的 topic 表，本阶段只建前两个）：**

| Topic | Key | 消费者 | 用途 |
|---|---|---|---|
| `document.parse` | documentId | document-worker | PDF 解析 → Parent-Child 切块 → Embedding → 入库（一条龙） |
| `document.reindex` | documentId | document-worker | 从已存 NormalizedDocument 重切 + 增量重嵌（不重新解析） |

**消息体（JSON，两个 topic 同构）：**

```json
{ "eventId": "uuid", "documentId": 7, "mode": "RECHUNK", "occurredAt": "2026-10-26T21:00:00Z" }
```

- `eventId`：本次投递唯一标识，落 `task_message` 表做消息级去重。
- `mode` 仅在 `document.reindex` 用（对齐 `ReindexMode`，本阶段只支持 RECHUNK）；`document.parse` 无此字段。

**幂等键（业务级，设计文档 §13.1「解析结果采用 document_version + content_hash」）：**

- 解析幂等：`document` 行 `(content_hash, parse_status)`。同一 documentId 重投 `document.parse` 且已 `DONE` 且 `content_hash` 未变 → 直接跳过（不重复解析）。
- 切块/嵌入幂等：`(active_chunk_version, chunk_strategy_version, content_hash)`。重切走版本化（新版本原子切换，旧版本 SUPERSEDED），重复 `document.reindex` 不会在「当前 ACTIVE 版本」上重复写。

**状态机（复用现有 `document` 表字段，不新造轮子）：**

- `document.parse_status`：`PENDING → RUNNING → DONE | FAILED`（已存在）。
- 新增 `task_message.status`：`RECEIVED → PROCESSING → SUCCESS | FAILED | DLQ`，`retry_count` 记重试次数。

**错误分类（`RetryClassifier`，三分类，设计文档 §13.1「区分瞬时错误、业务不可恢复错误和数据错误」）：**

| 类别 | 例子 | 处理 |
|---|---|---|
| 瞬时 transient | 网络超时、COS 5xx/451、连接拒绝 | 有限次重试 + backoff，重试仍失败进 DLQ |
| 业务 business | Docling 解析失败（`parse_error`）、PDF 损坏 | 不重试，直接 `FAILED`，可人工重放 |
| 数据 data | 解析产物（normalized.json）损坏/不可读 | 直接进 DLQ，人工修复后重放 |

### C10 · 增量重嵌入

**规则：** 重切块生成新版本 N+1 时，对每个新 Child chunk：
1. 先按 C1 的拼法算 `embedding_text_hash`（`embedding_text` 本身不落库，只落 hash，规则不变）；
2. 在同一 document 的**旧 ACTIVE 版本**里找「同 `embedding_text_hash` 且同 `embedding_model` + `embedding_version`」的块；
3. 找到 → **复制该块的 embedding 向量**（不调 API）；找不到 → 调 `text-embedding-v4` 生成。

**硬约束：**

- `embedding_text` 拼法（C1）一旦变，等于 hash 全部失效 → 必须全量 REEMBED，禁用增量；
- `embedding_model` 或 `embedding_version` 任一变 → 必须全量 REEMBED，禁用增量；
- 增量重嵌后必须校验：新版本 ACTIVE 块数与旧版本一致（或按预期变化），且日志输出「复用向量 X 块 / 新嵌入 Y 块」占比，可观测。

**实测基线（上一阶段重切 document 7）：** 407 张表只有 45 张变了内容，却全量重嵌 654 个块。增量落地后，同一次重切的 API 调用应从 654 降到「新增 + 变化的块数」（几十个量级）。

## 4. 验收口径

| 项 | 标准 |
|---|---|
| Kafka 起来 | `docker compose up -d kafka` 后 `document.parse` / `document.reindex` 能建 |
| 上传异步 | `POST /api/documents` 秒回 documentId，解析在 worker 里异步完成 |
| 幂等 | 同一事件重投不产生重复 chunk/向量（集成测试断言版本号不重复 +1） |
| DLQ | 坏消息进 `.dlt` topic，可重放恢复 |
| 增量重嵌 | 重切 document 7 时「复用向量」占比 > 80%（654 块里只有 ~几十块真的变） |
| 全量测试 | 非 e2e 全绿 + e2e 冒烟绿 |
