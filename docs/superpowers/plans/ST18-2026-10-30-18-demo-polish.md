## 5. D 批：解析进度百分比（需求 2）

**现状**：`document.parse_status` 只有 PENDING/RUNNING/DONE/FAILED（`DocumentRepository.java:67-98`），没有百分比；上传进度是**浏览器到后端**的字节进度（`DocumentView.vue:158`）。

**改法**：
1. 解析服务（Python）的 job 状态里若已带 `pages_done/total` 就直接用；若没有，按 Docling 的逐页进度补（`document-parser-service` 侧改一行，属跨仓改动）；
2. 后端 `document` 加 `parse_progress SMALLINT DEFAULT 0`（`V14__doc_parse_progress.sql`），`DocumentParseService` 轮询 job 时更新；
3. `GET /api/documents/{id}` 返回 `parseProgress`；
4. 前端：上传后卡片显示 `解析中 42%` + 细进度条（不是 indeterminate），3 秒轮询一次，DONE 后换成「已就绪」。

**验收**：上传一份 180 页 PDF，能看到 0→100 的百分比（至少 5 个不同数值）。

### 5.1 实施记录（2026-10-30 14:0x）

**结论先说**：计划第 1 条（让 Python 服务报页级进度）**做不到**，所以退化为方案 2 ——
「阶段检查点 + 向量化按条数插值」。这不是偷懒，是解析服务的真实能力边界，理由与实测见下。

**为什么拿不到页级进度**：`document-parser-service/app/main.py` 里 Docling 的转换是一次阻塞调用
（`converter.convert(...)`），作业对象只有 `status / elapsed_seconds / pages_parsed` 三个字段，
而 `pages_parsed` **只在作业完成时**赋值（`job.pages_parsed = doc.meta.page_count`）。
转换过程中没有任何回调，Java 侧轮询 `GET /jobs/{id}` 只能看到「还在 running、已跑 N 秒」。
要拿真实页级进度，得改 Docling 的调用方式（page_range 分批转换再合并），那是解析引擎层面的重构，
与「阶段 18 演示前打磨」不是一个量级 —— 记入 §9 风险，留作后续阶段。

**实际落地的六个检查点**（`src/main/java/com/finagent/document/DocumentProgress.java`）：

| 百分比 | 阶段文案 | 埋点位置 | 说明 |
| --- | --- | --- | --- |
| 2 | 排队中 | `DocumentUploadService.upload` 投递事件后 | 用户上传完立刻有反馈，不再是 0% |
| 8 | 提交解析作业 | `DocumentParseService.parseAndPersist` 调 `parser.submit` 前 | 从 COS 读回 PDF 的耗时在这之前 |
| 12 | 解析中 | `documents.markRunning` 之后 | **这一段最久**（180 页约 20 分钟） |
| 45 | 解析完成 | `persistResult` 里 `backfillPeriod` 之后 | 产物已落 COS、document 已 DONE |
| 50 | 切块中 | `DocumentParseService` 调 `reindex` 前 | Parent + Child 切分，纯 CPU 几秒 |
| 55 → 95 | 切块完成 → 向量化 x/y | `ChunkWriter.writeVersion` 第 4 步 | 按**条数**插值（最后一批常不满 10 条） |
| 100 | 已完成 | `persister.persistAndSwitch` 返回后 | 与 active_chunk_version 可见性同时成立 |

**三个设计决定**：

1. **只增不减**：`DocumentRepository.updateProgress` 用 `GREATEST` + `CASE WHEN ? >= parse_progress`
   一条 SQL 完成「进度前进 + 阶段文案同步」。分两条语句会出现「60% + 切块中」的错配；
   只写进度不写文案回退保护，重试时进度条会倒退。
2. **进度写失败不能让文档失败**：`DocumentProgress.step` 吞掉异常只记 warn。
   进度是观测，不是状态 —— 文档已经入库了，只是百分比没写进去，不该标成 FAILED。
3. **前端轮询判据换成进度**：原来判 `parseStatus === 'PENDING' | 'PARSING'`，
   但解析完成（DONE）之后还有切块 + 向量化几十秒，那一段状态已经是 DONE、
   进度却只有 55%。判据必须是 `parseProgress < 100 && parseStatus !== 'FAILED'`，
   否则「语料」页会在 45% 就停止自动刷新。

**改动清单**：
- 新增 `V16__document_parse_progress.sql`（两列 + CHECK + 存量回填：DONE→100、FAILED→失败、在途→排队中）
- 新增 `src/main/java/com/finagent/document/DocumentProgress.java`（检查点常量 + 吞异常的 step + 插值）
- `DocumentRepository`：`updateProgress`、`DocumentRow`/`DocumentDetail` 加 `parseProgress`/`progressStage`、
  `markFailed` 追加 `progress_stage='失败'`
- `EmbeddingService.embedAll(texts, IntConsumer)`（旧单参重载保留）
- `ChunkWriter` / `DocumentParseService` / `DocumentUploadService` 埋点
- 前端 `DocumentView.vue`：表格新增「进度」列（细进度条 3px + 百分比 + 阶段文案）、详情弹窗加「进度」行
- 测试：`DocumentProgressTest`（5 例，含插值与吞异常）、`DocumentProgressDbTest`（4 例，真库验单调性与回填）

**实测（2026-10-30 14:13~14:17，上传 12 页一季报，后端 2 秒轮询一次，抓到的不同取值）**：

```
14:13:39   8%  失败        status=PENDING   ← 上一轮解析服务没起，库里留着上次的失败记录
14:13:42  12%  解析中      status=RUNNING
14:17:03  55%  切块完成    status=DONE      ← Docling 单次转换 190.54 秒
14:17:05  76%  向量化 20/38
14:17:09  95%  向量化 38/38
14:17:11 100%  已完成
```

一共 **6 个不同值**（验收要 ≥5）。注意 **45%（解析完成）与 50%（切块中）没被看到**：
从 `persistResult` 到 `reindex` 再到 `ChunkWriter` 第 4 步，整段不到 1 秒，2 秒轮询必然跳过。
这不是 bug，但说明「检查点数量」不等于「用户能看到的取值数」——
要让人看到更多取值，要么提高轮询频率（代价是更多请求），要么在快阶段之间留一拍。
本轮不改，记入 §9。

**踩坑**：给 `DocumentRow`/`DocumentDetail` 加字段后，`DocumentQueryControllerTest`、
`StatsControllerTest`、`DocumentControllerTest` 里的 `new DocumentRow(...)` 全部编译不过 ——
record 加字段是破坏性变更，测试里的构造点必须一起改（一次编译就会全报出来，不要逐个试）。

## 10. 环境坑：前端改了但页面没变（2026-10-30 现场踩到）

**现象**：`npx vite build` 成功、文件也写进了 `src/main/resources/static/`，刷新浏览器还是旧界面。

**原因**：后端是用 `mvn spring-boot:run` 起的，它服务的是 `target/classes/static/`（编译期从 src 拷过去的副本），不是 src 目录。`vite build` 只写 src，`target/classes` 里仍是上一次 `mvn` 时的旧 `index.html` + 旧 hash 的 js。

**两条修法**（任选）：
1. 每次前端 build 后同步一次：
   `robocopy src/main/resources/static target/classes/static /MIR`（不用重启，Spring 直接从目录读）；
2. 或者 `mvn -o -q process-resources`（效果相同，顺带走一遍资源过滤）。

**验证办法**：`Invoke-WebRequest http://127.0.0.1:8080/` 看 `<script src>` 的 hash 与 `src/main/resources/static/index.html` 里的是否一致；不一致就是没同步。

**浏览器侧**：`index.html` 会被缓存，同步后仍需 Ctrl+F5 强刷一次；之后新 hash 的 js 会走正常缓存。
