# 文档写作规范

> 目标：**让一个从没做过 RAG / Agent 的人，只读文档也能跟下来，并且学到东西。**
> 这份规范约束本仓库所有报告、计划、设计文档。已知术语的解释统一放 docs/术语表.md。

---

## 1. 三条硬规则

### 规则 1：第一次出现的术语，必须「中文全称 + 英文 + 缩写 + 一句人话」

反例（以前的写法）：

> e2e 测试 2 个类 8 条。

正确写法：

> 端到端测试（end-to-end，以下简称 e2e）2 个类 8 条 —— 即从真实 PDF 一路跑到生成答案，中间不 mock 任何组件。

**为什么**：缩写只有在读者脑子里已有对应概念时才是缩写，否则是噪声。第一次出现的成本是几个字，省下来的是读者反复搜索的时间。

### 规则 2：每个术语第一次出现，除了「是什么」，还要给「为什么需要它」

反例：

> 我们用 RRF 融合两路结果。

正确写法：

> 两路结果用 RRF（Reciprocal Rank Fusion，倒数排名融合）合并：每路按名次给分 1/(60+名次)，相加排序。
> 为什么不用分数直接相加 —— 向量距离是 0~1 的小数，全文检索分数能到 10 以上，量纲不同，相加等于让数值大的那一路独占权重。

**为什么**：知道「叫什么」只能应付考试，知道「为什么不用别的方案」才是工程能力。每个设计选择背后都有一条被否决的路，那条路值得记一笔。

### 规则 3：每个数字必须带「口径 + 样本量 + 时间」

反例：

> 检索耗时 400 ms。

正确写法：

> 单次检索 388~623 ms（10 题 × 1 遍，2026-10-20，本机热缓存，不含 QU 与答案生成）。

**为什么**：没有口径的数字无法复现，也无法判断好坏。133 和 0.13 说的是同一件事，取决于单位。

## 2. 报告的标准结构

每份阶段报告按这个顺序写，缺一节就说明有东西没想清楚：

| 节 | 必须回答的问题 |
| --- | --- |
| 0. 一句话结论 | 这一阶段到底做成了什么？没做成什么？ |
| 1. 结果总览 | 用表格给出核心数字（测试数、指标、耗时） |
| 2. 做了什么 | 交付清单：文件 + 职责，一行一个 |
| 3. 实测数据 | 真实跑出来的数字，带口径 |
| 4. 踩到的坑 | 越具体越好：报错原文、误判方向、修法 |
| 5. 与预期的偏差 | 计划里写错的、实际上不一样的 |
| 6. 未决问题 | 现在没解决、以后必须解决的 |
| 7. 复现 | 完整命令，能照抄跑起来 |

### 第 4 节「踩到的坑」是整份报告最有价值的部分

网上教程只写成功路径，所以你照着做必然卡住。把卡住的原因写下来，是对未来的自己最有用的东西。写法：

> **现象**：报错原文 / 错误的输出。
> **原因**：为什么会这样（机制层面）。
> **修法**：改了什么。
> **教训**：以后怎么避免（一句话）。

### 第 5 节「与预期的偏差」不是自我批评

计划是坐在桌前写的，执行是在真实数据上做的，必然有偏差。**记偏差的目的不是追责，而是让后来的人知道「计划里的那段代码不能直接抄」**。

## 3. 语言风格

### 3.1 先给结论，再给推理

段落第一句就是结论，后面的句子解释「为什么」和「具体怎么做」。不要写成「让我们先看看……然后我们发现……」的流水账。

### 3.2 可以用比喻，但必须紧跟一句精确描述

比喻帮助理解，但不能替代定义。正确写法：

> 切块像把一本书拆成卡片（比喻）：每张卡片要能独立看懂，但也不能太碎 —— 我们要求 Child 块 300~700 token，一张表原则上不拆（精确定义）。

### 3.3 不写「显然」「众所周知」

第一次做的人不觉得显然。凡是需要三步推导才能得到的结论，就写三步。

### 3.4 允许写「我一开始以为 X，实际是 Y」

这类句子对读者价值极高 —— 它标出了一个真实的认知陷阱。比正确的教科书式陈述更有用。

### 3.5 中文优先，代码标识符保留原文

正文用中文；类名、方法名、SQL、配置项保留英文原样，必要时用「」括起来并解释。例如：
「所有过滤条件都在 DenseRetriever.appendFilters 里拼，它被 Dense 和 Sparse 两条路共用」。

## 4. 图表约定

| 想表达 | 用什么 |
| --- | --- |
| 流程、链路 | 纯文本 ASCII 框图（三行以内），超过就拆成两图 |
| 对比（方案 A vs B） | 两列表格，一行一个维度 |
| 规模变化（行数 → 耗时） | 表格，不要画 ASCII 曲线 |
| 目录结构 | 树形缩进 + 行尾注释说明职责 |
| 错误现象 | 引用原文，用代码块包住，不要改写 |

### 表格的三条要求

1. 第一列是「被比较的对象」，不是序号；
2. 数字右对齐，单位写在表头；
3. 空值写「—」，不写「无」或留空（留空会被误读成漏填）。

---

## 5. 计划文档（ST*.md）的额外要求

计划是「写给执行者看的施工图」，所以除了任务清单，还要有：

1. **每个任务的文件清单**：新增哪些文件、修改哪些文件、每个文件负责什么；
2. **关键代码骨架**：不是完整实现，但要有签名与关键分支（否则执行者会自由发挥）；
3. **验收标准**：可执行、可判定（「测试 X 通过」而不是「功能正常」）；
4. **偏差登记表**（执行时填）：计划写的 vs 实际做的 vs 原因；
5. **未决问题**：现在不解决但必须记下来的；
6. **明确写出「不做什么」**：范围外的东西写清楚，比写清楚范围内容更重要 —— 否则执行时会顺手扩scope。

---

## 6. 术语清单的维护

新增一个概念时，按这个顺序做：

1. 在 docs/术语表.md 加一条（是什么 / 为什么需要 / 我们项目里长什么样 / 常见误解）；
2. 在报告的第一次出现处给「中文全称（English, 缩写）」并指向术语表；
3. 如果这个概念有「我们踩过的坑」，同时在报告的踩坑节写一条。

**不要把术语解释散落在各份报告里各写一遍** —— 三份报告各写一版，三版就会慢慢不一致。

---

## 7. 检查清单（提交文档前逐条过）

- [ ] 每个缩写第一次出现都有中文全称和一句解释
- [ ] 每个关键术语都回答了「为什么需要它」
- [ ] 所有数字都有口径与样本量
- [ ] 每个坑都写了现象、原因、修法、教训
- [ ] 复现命令能照抄运行（含前置条件，比如「先启动 Docker」）
- [ ] 表格有单位、空值用「—」
- [ ] 没有「显然」「众所周知」「很简单」
- [ ] 未决问题一节不为空（如果不为空说明还有边界没想清楚）
