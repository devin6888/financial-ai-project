## 3. 链路实测（分阶段耗时，NO-QU 十题）

| 阶段 | 耗时 | 说明 |
|---|---|---|
| dense | **154 ~ 235 ms** | 其中 PostgreSQL 精确 kNN 只占约 10 ms，**其余是百炼 embedding 的网络往返** |
| sparse | **1 ~ 10 ms** | 纯 SQL，无外部调用 |
| fuse | **0 ~ 1 ms** | 内存计算 |
| rerank | **208 ~ 403 ms** | 一次 HTTP，30~58 条候选 |
| 合计 | **388 ~ 623 ms** | — |

QU 路径下叠加一次路由：规则快路径 < 1 ms，LLM 路径约 +300 ms。**Q1 出现 1263 ms 的离群值**，Trace 显示 `qu=SEMANTIC_EXPLANATION/DEGRADED:weak_evidence`，dense 572 ms + rerank 679 ms —— 降级重试把两段都跑了两遍。这是「宁可多花 600 ms 也不返回错答案」的代价，属预期行为，但要记在账上。

一条完整 Trace（第 9 题 QU 模式）：

    dense=30 sparse=5 fused=32 returned=8 rerank=APPLIED qu=SEMANTIC_EXPLANATION/LLM cost=497ms
    #1 id=861 TABLE p16 dense=1 sparse=3 rrf=0.0323 rerank=0.741  第三节 § 四、主营业务分析（研发投入表）
    #2 id=846 LIST  p17 dense=8 sparse=2 rrf=0.0308 rerank=0.710  （研发投入相关说明）
    #3 id=845 TEXT  p14 dense=null sparse=1 rrf=0.0164 rerank=0.647（主要客户情况）

一眼可见三个机制在同时工作：**id=845 只被 Sparse 捞到**（dense=null），**id=861 靠 RRF 从 dense=1 与 sparse=3 的双路共识拿到最高 rrf**，**最终顺序由 rerank 决定**（861 恰好两路共识最高、rerank 也最高；但 #2 与 #3 的 rrf 差距 0.0144、rerank 差距仅 0.063——同一份候选换一种打分，排序就不再由「哪一路先捞到」说了算）。

## 4. 机制层实测（不是估算，是跑出来的）

| 事实 | 实测值 | 对设计的影响 |
|---|---|---|
| 带过滤时走精确 kNN 还是 HNSW | **bitmap 过滤 + top-N 排序 3.1 ms（热缓存）**，不走 HNSW | 候选集只有 654 行时，精确排序比图遍历快；交叉点实测 **1,200~1,500 行**（合成数据无过滤，41,856 行时 276.3 vs 0.66 ms） |
| `plainto_tsquery`（AND）对自然语言长问题 | **0 条** | 必须有 AND→OR 回退，否则 Sparse 路半瘫 |
| 同一个 OR 查询 | 372 / 654 条 | 召回够但精度低，靠 RRF 排名与 rerank 收敛 |
| `ILIKE '%每股收益%'` vs FTS | **6 条 vs 86 条** | 精确子串适合「代码/专名」，不适合长指标名 |
| 一条 1024 维向量占多少字节 | 4100 bytes（正文平均 115 bytes） | 向量是存储大头，将来扩到多文档要先算容量 |
| RRF k=60 时的分数比 | rank1 = 0.016393，rank5 = 0.015385；两个列表都排第 5 时合计 0.030769 > 单列表第 1 | 「两路共识」天然压过「单路第一」，这是融合该有的性格 |

计数：**严格口径 QU 7/10、无 QU 6/10；宽松口径 8/10 vs 7/10**。验收标准 #14（top-1 相关 ≥7 且 QU 不差于无 QU）以严格口径满足，且**唯一净胜题是第 7 题**。

第 7 题为什么是 QU 赢：QU 把问题判成「风险」类，走 LLM 路由后 Sparse 只捞到 1 条，dense 第 1 名直接命中风险章节；无 QU 时 rerank 被第一节那句「保证年度报告内容真实、准确、完整……不存在虚假记载」骗到 0.636，压过了真正的风险章节 0.609。**这是「语义路由」的价值，也是 rerank 的盲区**。

为什么不写自动化相关性断言：全库 0 条标注数据，任何自动打的「相关性」都是自欺欺人。冒烟测试只守不变量（两遍都非空、returned == chunks.size()、结果全属 documentId=7），排序质量靠本表人工判定，逐条可回溯到 target/smoke2.log。

## 6. 三个真实缺陷（不粉饰）

### 6.1 rerank 偏爱「提到数字的叙述」，压过「装着数字的表格」

第 1 题，关键审计事项（1109，文本，0.844）排到了合并利润表（1133，表格，0.739）前面。前者只是在一段讲融出资金减值的文字里**提到**了「贵集团营业总收入金额为人民币……」，后者才是真正列出 16,067,741,039.51 的表。QU 与无 QU 同时中招，说明问题在 rerank 模型本身的偏好，不在路由。

### 6.2 短实体词在长表里出现次数多，就被抬高

第 5 题，子公司注册资本表（882，0.594）压过公司信息表（811，0.529）。「注册资本」在子公司表里出现 20+ 次，在公司信息表里 0 次（该表的注册资本一行在别的 chunk），rerank 按词面共现打分，自然选前者。

### 6.3 财务报表里「营业收入」与「营业总收入」是两个口径

合并利润表 id=1133 里同时有「一、营业总收入 16,067,741,039.51」和「其中：营业收入 ……」；母公司利润表 id=1137 的「一、营业收入 4,531,884,934.72」也被召回（第 3 名）。用户问「营业收入是多少」时，**这题本身有歧义**，阶段 5 的答案生成必须显式说明口径，否则会答出一个「对但答非所问」的数字。

## 7. 与预期的偏差（详见 ST4 偏差登记表，共 14 条）

- **没有用上 HNSW**：真实查询的计划是 bitmap 过滤 654 行 + top-N 排序（热缓存 3.1 ms）。索引建了、也在（`Enable Seq Scan` 关掉就能强制走）。原因是**访问模式**而不是数据量：候选集被 `document_id + chunk_version` 压到一份报告的 654 个 Child，与总语料规模无关。带过滤的 HNSW 实测反而更慢（4 万行时 31.8 ms vs 5.6 ms），详见 docs/pgvector-工作机制.md §6。
- **Sparse 必须双模式**：有实体走精确子串（命中计数打分），无实体走 FTS 且 AND 不行要回退 OR。
- **QU 的规则路只覆盖完整三元组**：「净利润」这种单指标问题会落到 LLM 路径（Trace 里 `SEMANTIC_EXPLANATION/LLM`）。是否让「只命中指标字典」也走规则快路径，留给阶段 6 决定。
- **两级渐进放松是必需的**：Sparse 精确路 0 命中、QU 过滤后 0 命中，都会把结果清零。现在的做法是先摘过滤再降级模式，Trace 里各留一条 warning。
- **Rerank 没有现成轮子**：Spring AI 2.0.1 上游没有 rerank 抽象（issue #4343 / #5776 仍是 feature request），Spring AI Alibaba 有但默认模型 gte-rerank 已于 2026-05-30 下线，且编译自 2.0.0-M1。结论：保留自研 `RerankModel`（两个方法，约 190 行，真正有价值的是边界处理），真要换写个 20 行适配器即可。
- **`degraded` 单布尔语义不够**：拆成 `RerankStatus`（APPLIED / SKIPPED / FAILED），否则「没开 rerank」和「rerank 挂了」分不清。
- **计划里的 @ConditionalOnProperty 成对装配是错的**：api-key 为空串时两个条件同时命中，2 个 Bean 启动即失败，改为单工厂方法。

## 8. 未决问题（带入阶段 5 / 6）

1. **表格与叙述的排序偏好**（6.1）：是否在 rerank 前给 TABLE 类型加一个小的先验加权？先看阶段 5 的答案质量再决定，避免在检索层拍脑袋。
2. **短实体词的词频偏置**（6.2）：候选是「rerank 前把同质候选去重（同一 section_path 只留最高分）」，尚未验证。
3. **母公司 vs 合并口径**（6.3）：属答案生成层职责，阶段 5 必须在 prompt 与引用里强制标注。
4. **单指标问题走不走规则快路径**：影响延迟（少一次 LLM）与稳定性，阶段 6 用 10~20 题对照测。
5. **要不要自己维护 BM25**：PostgreSQL 只有 ts_rank，没有 BM25。三条路（接受 ts_rank / 用 tsvector 自算 BM25 / ParadeDB pg_search）留到阶段 6，前提是 Sparse 路的质量真的成为瓶颈。
6. **多文档评测缺位**：目前只有 1 份年报，`docs/东方财富2024年年度报告.pdf` 已入库未解析，跨文档的「同一指标不同年份」检索还没测过。
