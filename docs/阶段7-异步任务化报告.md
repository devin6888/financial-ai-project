# 阶段 7 · 异步与任务化报告

> 执行日期：2026-10-26。本阶段新增组件：Apache Kafka 3.7.0（KRaft 单节点，跑在 Docker 里）。
> 所有数字来自一次真 Kafka、真 PostgreSQL 16 + pgvector、真阿里云百炼（text-embedding-v4）运行，不是估算。
> 计划文件：`docs/superpowers/plans/ST7-2026-10-26-07-async-task.md`。

## 怎么读这份报告（先看这 8 个词）

| 词 | 一句话解释（完整版见 docs/术语表.md） |
| --- | --- |
| 事件驱动 | 不直接调用「去做某事」的方法，而是往队列里投一条「应该做某事」的消息，由另一方取走执行。上传接口因此能秒回，解析在后台慢慢做 |
| topic（主题） | Kafka 里消息的分类频道。本项目建了两个业务 topic：`document.parse`（拆解这份 PDF）、`document.reindex`（重新切块并嵌入） |
| producer / consumer（生产者 / 消费者） | 往 topic 投消息的一方 / 从 topic 取消息的一方。本项目 REST 接口是生产者、Kafka listener 是消费者，两个角色在同一个应用里共存 |
| at-least-once（至少一次投递） | Kafka 只保证消息不丢，不保证只送一次。消费者崩溃、网络抖动、手动重放都会让同一条消息再来一遍 —— 所以消费端必须自己幂等 |
| 幂等（idempotent） | 同一件事做一遍和做十遍，最终结果一样。本项目两道防线：eventId 唯一（消息级）+ content_hash 已解析完成就跳过（业务级） |
| ack（确认）与位点（offset） | 消费者处理完一条消息后「确认」它，Kafka 才把位点前移；不确认就会重投。本项目用手动 ack：处理成功才确认 |
| DLQ（dead letter queue，死信队列） | 「怎么重试都处理不好」的消息的去处。本项目用原 topic 名加 `.dlt` 后缀，例如 `document.parse.dlt` |
| 增量重嵌 | 重切文档时不重新算全部向量，只算内容真的变了的块，其余按内容哈希复用旧向量 |

## 1. 一句话结论

阶段 7 把「上传 PDF → 解析 → 切块 → 嵌入」这条链，从**两段互不相连、只能由测试手动调用**的代码，改成了**REST 上传秒回 + Kafka 事件 + worker 异步执行一条龙**，并给出三条可复现的保证：

1. **幂等**：同一份 PDF 重复上传只解析一次（实测第二次上传 0 秒返回原 documentId，不落 COS、不投递、不解析）；
2. **增量重嵌**：重切时未变块零 API 调用（实测复用 **654 / 654 = 100%**，0 次 embedding API 调用，全程 **6.7 秒**，改造前是全量重嵌约 **62 秒**）；
3. **DLQ 可恢复**：坏消息进 `document.reindex.dlt` 后，改掉消息里的 documentId 重投，`task_message` 从 `FAILED` 走到 `SUCCESS`，文档版本正常 +1。

过程中抓到两个真问题：

- **一个潜伏了四个任务的配置缺陷**：listener 方法声明了 `Acknowledgment` 参数，但 `application.yml` 从没配 `spring.kafka.listener.ack-mode`。Spring Kafka 启动时**不报错**，只有真收到第一条消息时才抛 `IllegalStateException`。此前所有 listener 单测都直接调 `process()` 绕过了 Kafka，所以这个洞一直没暴露，直到 Task 8 的集成测试真的发了一条消息。
- **重切会让阶段 6 的整份评测集失效**：`golden-set.json` 里的证据块是按 chunk id 硬编码的，而每次重切 chunk id 全变。阶段 7 让「重切」从偶发操作变成常规操作，所以这个问题必须在阶段 7 修掉，否则阶段 6 的满分结果再也复现不出来。

## 2. 为什么阶段 6 之后还要做这一步

### 2.1 改造前：两条断开的链路

| 环节 | 怎么触发 | 谁能用 |
| --- | --- | --- |
| PDF 解析（→ NormalizedDocument 存 COS） | `DocumentParseService.parseAndStore()` 同步 submit + 轮询，**只有测试在调**（`FullDocumentPipelineTest`、`IngestReportTest`） | 只有开发者，写代码或跑测试 |
| 切块 + 嵌入（→ document_chunk） | `ReindexRunner` 命令行：`mvn spring-boot:run -Dspring-boot.run.arguments=--finagent.reindex.document-id=7` | 只有开发者，敲命令行 |

两条链路之间**没有连接**：解析产物落 COS，但没人自动去触发切块；切块只能对「库里已经登记过的 document 行」手动跑。换句话说，阶段 3~6 的所有能力都已经建好了，但**外面的人没法用** —— 这正是「demo 和产品」的差别。

### 2.2 改造后：一条事件驱动的链路

~~~text
POST /api/documents（multipart：PDF + 公司代码 + 年份 + 标题）
        │
        ├─ 1. 算 SHA-256(content_hash)
        ├─ 2. 幂等快路径：同 hash 已 DONE + 有 ACTIVE chunk → 直接返回旧 id（0 秒，不落盘不投递）
        ├─ 3. 上传 PDF 到 COS（samples/{code}-{year}-{docType}.pdf）
        ├─ 4. upsert company + document（parse_status=PENDING）
        └─ 5. 投递 document.parse（key=documentId）→ 立刻返回 {documentId, parseStatus:PENDING}
                    │
                    ▼  Kafka: document.parse
        DocumentParseListener（同一个 JVM 里的 @KafkaListener）
        ├─ task_message 落行（event_id UNIQUE）+ 置 PROCESSING
        ├─ 从 COS 读回 PDF → Docling 解析 → 结果存 COS → document 置 DONE
        ├─ 触发 ReindexService(RECHUNK) → 切块 → 增量嵌入 → 新版本原子切换
        └─ task_message 置 SUCCESS → 手动 ack（位点前移）
                    │
                    ▼  客户端轮询
GET /api/documents/{id} → parseStatus / activeChunkVersion / 公司名 …

失败路径：
  瞬时错误（超时/COS 5xx）→ DefaultErrorHandler 重试 max-retries 次（间隔 backoff-ms）
  仍失败 或 业务/数据错误 → 消息投到 document.parse.dlt，task_message 置 FAILED
  人工修好后把 .dlt 里的消息重投 → 同一个 eventId 会命中幂等，改掉 documentId 即可复用
~~~

### 2.3 为什么不能就做一个同步接口

| 同步接口的后果 | 具体的量级 |
| --- | --- |
| 请求挂 50 分钟 | 一份 181 页年报在 CPU 上跑 Docling 约 50 分钟（阶段 2 实测 8 页 10 分钟量级），HTTP 连接、网关、浏览器全部超时 |
| 失败没有第二次机会 | 网络抖一下、COS 返回一次 5xx，整次解析白做，只能人工重新点一次 |
| 没有留痕 | 「这份 PDF 到底被处理过几次、为什么失败」无从查起 |
| 不能限流 | 三个人同时上传就把 CPU 打满，解析服务互相拖死 |

事件驱动把「接受请求」和「执行请求」解耦，这三个问题各自有了出路：接口秒回、失败可重试、失败有 DLQ 留痕。

## 4. 两个契约

### 4.1 C9 · 文档任务、幂等与错误分类

**topic 定义**（沿用设计文档 §12 的 topic 表，本阶段只建前两个）：

| Topic | Key | 消费者 | 用途 |
| --- | --- | --- | --- |
| `document.parse` | documentId | document-worker | PDF 解析 → 切块 → 嵌入 → 入库（一条龙） |
| `document.reindex` | documentId | document-worker | 从已存 NormalizedDocument 重切 + 增量重嵌（不重新解析） |
| `document.parse.dlt` / `document.reindex.dlt` | 原 key | 人工 | 死信，等人工处理或重放 |

为什么 key 用 documentId：同一文档的事件进同一分区，天然保序 —— 「先解析后重切」不会被重排成「先重切后解析」。

**消息体**（两个业务 topic 同构）：

~~~json
{ "eventId": "uuid", "documentId": 7, "mode": "RECHUNK", "occurredAt": "2026-10-26T21:00:00Z" }
~~~

`eventId` 是本次投递的唯一标识，落 `task_message.event_id`（UNIQUE）；`mode` 只在 `document.reindex` 用。

**两级幂等**（这是本阶段最需要讲清楚的一点）：

| 级别 | 键 | 防什么 | 实现在哪 |
| --- | --- | --- | --- |
| 消息级 | `task_message.event_id` UNIQUE | 同一条 Kafka 事件被重投（消费者崩溃重放、DLQ 重放） | `TaskMessageRepository.upsert`：先 insert，撞唯一约束就回查已有行返回同 id |
| 业务级（解析） | `document.content_hash` + `parse_status='DONE'` | 同一份 PDF 换了 eventId 再传一遍 | `DocumentUploadService` 的幂等快路径 + `findCompletedIdByContentHash` |
| 业务级（切块） | `chunk_version` 版本化 + 原子切换 | 重复 reindex 在「当前 ACTIVE 版本」上重复写 | 阶段 3 已有的 `ChunkPersister.persistAndSwitch`（新版本写入并校验通过才切 ACTIVE，旧版本置 SUPERSEDED） |

为什么不只靠一级：只有消息级会漏「用户重新上传同一份 PDF」（新 eventId、旧内容）；只有业务级会漏「消息重放时中间状态已经被改过」。两级都要。

**状态机**：`document.parse_status`：`PENDING → RUNNING → DONE | FAILED`（阶段 2 已有）；新增 `task_message.status`：`RECEIVED → PROCESSING → SUCCESS | FAILED | DLQ`。

**错误三分类**（设计文档 §13.1「区分瞬时错误、业务不可恢复错误和数据错误」）：

| 类别 | 例子 | 处理 |
| --- | --- | --- |
| TRANSIENT（瞬时） | 网络超时 `SocketTimeoutException`、连接拒绝 `ConnectException`、COS 服务端异常 `CosServiceException`/`CosClientException` | 固定间隔重试 `max-retries=3` 次，仍失败进 DLQ |
| BUSINESS（业务不可恢复） | 文档没有 PDF 对象键、documentId 不存在 | 不重试，直接进 DLQ 等人工 |
| DATA（数据坏） | 消息体反序列化失败 `JacksonException` | 不重试，直接进 DLQ，必须人工修正 |

**一个必须沿 cause 链找的理由**：`CosObjectStorage.get()` 会把 COS SDK 的瞬时异常包成 `NoSuchElementException`。只判顶层类型，就会把「网络超时」误判成「对象不存在」这种业务错误，于是本该重试的消息直接进 DLQ。`RetryClassifier.classify` 沿 `getCause()` 链往上找，`transientTypes()` 暴露同一份白名单给 `KafkaErrorHandlerConfig` 复用，两处不会漂移。

### 4.2 C10 · 增量重嵌入

复用键是 `embedding_text_hash`（契约 C1 的 SHA-256，覆盖 doc_title + section_path + caption + content）。**三个条件缺一不可**：

1. hash 相同 —— 送进模型的文本一模一样，向量必然相同；
2. `embedding_model` 相同 —— 换了模型，旧向量和新模型不在同一个向量空间；
3. `embedding_version` 相同 —— 同一模型但改了调用参数（维度、归一化、instruction），同理不能混用。

数据流（`ChunkWriter.writeVersion` 六步，切块与嵌入仍在事务外）：

~~~text
1. 事务外：对新块算 embedding_text 与 hash（复用键）
2. 读旧 ACTIVE 版本的 CHILD 向量（embedding::text，一次 ~654 行约 2.6MB）
3. plan()：按三条件建 hash → 旧向量索引，把新块分成「复用」与「待嵌入」
4. 只对「待嵌入」调 embedding API（未变块零调用）
5. assemble()：按新块原顺序填回向量（复用的直接拷贝）；末尾校验条数一致，不符抛异常
6. 事务内：写新版本 → 校验 → 原子切换 ACTIVE
~~~

第 5 步那个「校验条数」不是多余的：顺序错位**不会报错**，只会让块 A 挂上块 B 的向量，检索结果悄悄变差。所以必须显式断言 `cursor == freshVectors.size()`。

首次索引（无旧版本）时 `oldVersion == 0`，复用源为空，退化为全量嵌入，行为与阶段 3 完全一致。

## 5. 实测结果

### 5.1 e2e 四个用例（32~35 秒跑完）

| 用例 | 断言 | 实测 |
| --- | --- | --- |
| 上传同一份 PDF 幂等 | 返回 `{documentId:7, parseStatus:"DONE"}`；document 表同 hash 只有 1 行 | 通过。上传的 `docs/东方财富2025年年度报告.pdf` 共 4,982,101 字节，SHA256 = `a5edb330…c1737`，与 document 7 的 `content_hash` 逐字一致 → 命中快路径，**没落 COS、没投递、没解析** |
| 查详情 | parseStatus=DONE、activeChunkVersion≥3、title 含「东方财富2025年年度报告」、companyCode=300059、companyName=东方财富 | 通过（`GET /api/documents/7`） |
| 真重索引 | 版本恰好 +1；新版本 CHILD=654 / PARENT=104；`embedding IS NULL` 的 CHILD=0；复用块数占比 | 通过。**复用 654 / 新嵌 0**，耗时 **6.7 秒**，0 次 embedding API 调用 |
| DLQ 重放恢复 | 坏消息进 `.dlt`；改 documentId 后重投；`task_message` 从 `FAILED` → `SUCCESS`；版本再 +1 | 通过 |

第 3 个用例的复用数不是直接读日志的，而是用 SQL 反查的：

~~~sql
SELECT count(DISTINCT b.id)
FROM document_chunk a
JOIN document_chunk b
  ON a.document_id = b.document_id
 AND a.embedding_text_hash = b.embedding_text_hash
 AND a.chunk_level = 'CHILD' AND b.chunk_level = 'CHILD'
 AND a.chunk_version = ? AND b.chunk_version = ?
 AND a.embedding::text = b.embedding::text
WHERE a.document_id = ?
~~~

### 5.2 为什么这次是 100% 复用，而不是「大部分复用」

验收口径写的是「复用占比 > 80%」，实测是 100%。原因不神秘：这次 reindex **没有改切块代码、没有改 PDF、没有改解析产物**，所以 654 个块的 `embedding_text` 逐字节相同，hash 全部命中。

真正发生「部分复用」的场景是阶段 7 之前那次修复 `TableRenderer` 之后的重切（document 7 的 v3）：那时只有几百个表格块的内容变了，其余正文块本可以复用，但当时还没有增量重嵌，654 块全部重算（约 62 秒）。增量重嵌上线后，同类改动的耗时应当落在「几十块 × 单条 API 延迟」这个量级。

**所以 100% 这个数字证明的是「复用逻辑没漏、没多算」，不是「收益上限」**。真正的收益要等下一次内容变更才能测出来，这一点本阶段没有样本，如实记录在此。

### 5.3 幂等与 DLQ 的实测细节

- 幂等快路径的耗时：第二次上传同一份 PDF，从 `POST` 到返回约 **0 秒**（只有一次 SHA-256 计算 + 一次索引查询）。改造前若照常走解析，是 50 分钟量级 + 一次 embedding 费用。
- DLQ 消息体就是原始 payload（`DeadLetterPublishingRecoverer` 不改造消息），所以「重放」= 从 `.dlt` 读出来、改掉 `documentId`、投回原 topic。`eventId` 保留原值，正好命中消息级幂等 —— 这是刻意的：重放不应该产生第二条 task_message 记录。
- 但要注意：DLQ 用例里那条坏消息 `documentId=999999998` 的 `task_message` 状态是 **FAILED 而不是 DLQ**。原因是 listener 自己 catch 了异常、置 FAILED 后重新抛出，异常才交到 `DefaultErrorHandler` 去发 DLQ；`task_message` 这一层不知道「我已经被判死刑了」。这是当前实现的粗糙点，见 §7。

## 6. 这次抓到的 3 个问题

### 6.1 listener 声明了 Acknowledgment 却没配 ack-mode（潜伏四个任务）

**现象**：Task 8 的集成测试第一次真发消息，listener 立刻抛异常，`task_message` 卡在 RECEIVED。

~~~text
IllegalStateException: No Acknowledgment available as an argument,
the listener container must have a MANUAL AckMode to populate the Acknowledgment.
~~~

**原因**：`@KafkaListener` 方法签名里有 `Acknowledgment ack` 参数，但 `application.yml` 的 `spring.kafka` 下没有 `listener.ack-mode`。Spring Kafka 默认 `BATCH` 模式，容器不会注入 `Acknowledgment`。启动期不校验方法签名，只有真正调用时才炸。

**修法**：`application.yml` 加 `spring.kafka.listener.ack-mode: manual`。语义是「处理成功才提交位点」→ at-least-once；失败交 `DefaultErrorHandler` 重试/进 DLQ。

**教训**：**mock 掉框架的单元测试证明不了接线正确**。此前 `DocumentParseListenerTest` 直接调 `process()`，容器、ack、序列化、反序列化全绕过了，所以绿得毫无意义。凡是有「配置驱动的行为」，至少要有一条测试真的走一遍框架。

### 6.2 重切让阶段 6 的整份评测集失效

**现象**：阶段 7 重切几次之后跑 `GoldenSetTest`，报「Q07 证据块不可用：818」等一片红。

**原因**：`golden-set.json` 的 `evidenceChunkIds` 是手写的 chunk id，而 chunk id 每次重切都会变（旧版本被标 SUPERSEDED、新版本重新生成）。阶段 7 之前重切是偶发操作，所以这个脆弱点没被踩到；阶段 7 之后重切是常规操作，它就成了「评测永远只能跑一次」的死结。

**修法**：把版本无关的稳定锚点换成 `embedding_text_hash`（契约 C1 的 SHA-256，内容不变则哈希不变）。新增 `src/test/java/com/finagent/eval/EvidenceResolver.java`，走「历史 id → 它的 hash → 当前 ACTIVE 版本里同 hash 的 CHILD 块 id」这条链；`GoldenSetTest` 与 `RetrievalEvalTest` 都改成先解析再判分。

另外有两题的证据块因为 `TableRenderer` 修好了表头，内容本身变了、旧 hash 在 ACTIVE 版本里已不存在，只能重新指定：Q07/Q19 的 848 → 5712（主营构成表，第 13 页），Q08/Q20 的 1146 → 6010（所有者权益变动表，第 81 页）。

**修复后**：`GoldenSetTest` 3/3 通过；`RetrievalEvalTest` 恢复满分 —— `EVAL-RET-SUM|QU|cases=27 recall@5=1.000 recall@10=1.000 docRecall@10=1.000 mrr=0.782`（阶段 6 原值 MRR=0.779，差异来自重切后的块边界微调）。

**教训**：**测试数据里凡是「数据库自增 id」，都是定时炸弹**。能换成内容哈希、业务主键的，一律不要用自增 id 当锚点。

### 6.3 复用率算成了 100.92%

**现象**：第一次写断言用 `count(*)` 算复用块数，得到 660 / 654 = 100.92% —— 超过 100%，明显错。

**原因**：同一个版本里存在 content 完全相同的重复块（同一段文字在两个章节都出现），join 时一对多把行数放大了。

**修法**：改 `count(DISTINCT b.id)`。

**教训**：**比率超过 100% 是 join 扇出的信号，不是「恰好复用得很充分」**。任何 join 后的计数，先问一句「这张表有没有重复行」。

| # | 限制 | 后果 | 打算什么时候处理 |
| --- | --- | --- | --- |
| 1 | `document_chunk` 没有保留策略 | 每次重切 +1516 行（约 +7MB），旧版本永远留着。当前 **6040 行 / 69MB**，其中只有 2 个 ACTIVE 版本（1516 行）是有用的 | 阶段 8 或之后加「保留最近 N 个版本」的清理任务；现在体积无害，先不动 |
| 2 | **`.dlt` 死信 topic 没有消费者** | 坏消息投进去后无人处理，只能人工 `kafka-console-consumer` 捞；没有任何告警。当前 `document.parse.dlt` 与 `document.reindex.dlt` 各积压 1 条（跑 e2e 时产生的 `documentId=999999998/999999999`） | 已决定按方案 B 做（见 §7.1），排在阶段 8 之后 |
| 3 | 坏消息的 `task_message` 状态是 FAILED 而不是 DLQ | listener 先置 FAILED 再抛异常，发 DLQ 的动作在它之外；`markStatus` 三个调用点只写 PROCESSING/SUCCESS/FAILED，`DLQ` 这个 CHECK 枚举值没有任何写入方 | 与 #2 一起改：DLQ listener 里置 DLQ |
| 3b | `task_message.retry_count` 永远是 0 | `incrementRetry()` 只有测试在调；真实重试由 Kafka 的 `DefaultErrorHandler` 在内存里做，没回写数据库 | 需要精细化运维时，用 `CommonErrorHandler` 回调回写 |
| 3c | `TaskMessageRepositoryTest` 的 `@AfterEach` 是**无 WHERE 的 `DELETE FROM task_message`** | 全量跑一次测试就把 e2e 留下的任务历史一起清掉，「查库看历史」这条路会失效 | 加 `WHERE document_id IN (...)` 或按 `created_at` 截断，改动很小，排进 #2 的同一批 |
| 4 | worker 单实例、无并发控制 | listener 默认并发度 1，一个 50 分钟的解析会堵住后面所有解析任务 | 水平扩容是多实例部署的问题（同一 consumer group 天然分摊分区）；本阶段按「单实例够用」推进 |
| 5 | `document.parse` 的真链路没有自动化覆盖 | 181 页解析 50 分钟，做不进 CI。e2e 只覆盖了幂等快路径（不真的解析）。真解析由 `FullDocumentPipelineTest`（`@Tag("e2e")`、需手动跑）覆盖 | 可以用一份 5 页的小 PDF 做自动化冒烟；本阶段没做 |
| 6 | 没有监控/告警/延迟指标 | 消息堆积、消费延迟、DLQ 条数都只能手动查 | 属于运维范畴，不进 V1 功能范围 |

> 说明：#2/#3/#3b/#3c 是同一坨问题（死信链路只写不读），2026-10-27 讨论后决定**按方案 B 一起做**，不零敲碎打。

### 7.1 待办：DLQ 消费链路（方案 B，暂缓到阶段 8 之后）

**现状（代码事实）**

- 全仓库只有 2 个 `@KafkaListener`，都在业务 topic 上：`DocumentParseListener.java:43`、`DocumentReindexListener.java:43`。
- `.dlt` 的两个 `NewTopic` bean（`KafkaTopicConfig.java:36-44`）只创建 topic，不读。
- 唯一读 `.dlt` 的代码是测试 `DocumentTaskE2ETest.pollDlq()`（第 278 行），自己 new 一个 `KafkaConsumer` 读一次就关。
- 于是「死信只有人捞、没有告警、24 小时后连同证据一起消失」（保留期见 §8）。

**要做的三件事**

| # | 内容 | 关键实现点 |
| --- | --- | --- |
| 1 | `DlqListener`：`@KafkaListener` 订阅两个 `.dlt`，把 `task_message` 置为 `DLQ`、写日志与计数指标，**不自动重试** | **不能复用默认的 `DefaultErrorHandler`** —— 它会把失败消息投到 `document.parse.dlt.dlt`。要么单独给一个 `containerFactory` + 只记录不抛的 errorHandler，要么在方法内 catch 到底（死信处理不能再产生死信） |
| 2 | `POST /api/tasks/{eventId}/replay`：从 `task_message` 取回原始 payload 重投业务 topic | **保留原 `eventId`**：命中消息级幂等，重放不产生第二条 `task_message`；只改 `documentId` 等业务字段 |
| 3 | `task_message` 状态机补齐：`FAILED → DLQ →（重放）→ PROCESSING → SUCCESS` | 顺带把 `retry_count` 用 `CommonErrorHandler` 回调回写（#3b），并修掉测试里无 WHERE 的 `DELETE`（#3c） |

**为什么不选自动重放**：解析一份年报 50 分钟，自动重放会把 CPU 打满；而且需要 `replay_count` 上限才防得住无限循环。手工重放（方案 B）在这个项目里性价比最高。

## 8. 附：Kafka 资源占用优化（2026-10-27 补）

阶段 7 交付后 `docker stats` 显示 Kafka 常驻 **955.9 MiB / 12.25%**、CPU **69.34%**，对一个「只存几条文档任务消息」的开发用 broker 明显过重。定位到三个根因，改完后 **258.4 MiB / 3.31%**。

### 8.1 改前改后

| 指标 | 改前 | 改后 | 降幅 |
| --- | --- | --- | --- |
| 常驻内存 | 955.9 MiB | **258.4 MiB** | **-73%** |
| CPU（空闲） | 69.34% | **2.69%** | -96% |
| 满载后内存（跑完 7 个 e2e 用例） | — | **283.1 MiB** | — |
| `__consumer_offsets` 分区数 | 50 | **1** | -98% |
| 日志段大小 | 1 GB | **64 MB** | — |
| 日志保留 | 168 小时 | **24 小时** | — |

### 8.2 三个根因（都不是「Kafka 本来就吃内存」）

| # | 根因 | 证据 | 修法 |
| --- | --- | --- | --- |
| 1 | **堆默认 1G**。`apache/kafka` 镜像不设 `KAFKA_HEAP_OPTS` 时用 `-Xmx1G -Xms1G`，而 RSS ≈ 堆 + 100MB 左右。单节点、4 个 topic、每 topic 1 分区、数据量 KB 级，1G 纯浪费 | `cat /proc/1/cmdline` 里就是 `-Xmx1G -Xms1G` | `KAFKA_HEAP_OPTS: -Xmx256m -Xms256m` |
| 2 | **健康检查每 10 秒起一个新 JVM**。`kafka-broker-api-versions.sh` 不是轻量脚本，它是 Java 客户端程序 —— 每跑一次就起一个 JVM、连一次 broker、打印版本、退出 | CPU 尖峰 69%，且每 10 秒一段内存抖动 | 换成 `nc -z localhost 9092`（一次 TCP 握手），间隔 15s |
| 3 | **数据根本没落在 volume 上**。镜像默认 `log.dirs=/tmp/kafka-logs`，`KAFKA_LOG_DIRS` 环境变量为空；我们挂的 `kafkadata:/var/lib/kafka/data` 因为没人写，一直是 **4.0K** 的空目录 | `du -sh /var/lib/kafka/data` = 4.0K，而 `find / -name partition.metadata` 指向 `/tmp/kafka-logs` | `KAFKA_LOG_DIRS: /var/lib/kafka/data` |

顺带把两个「默认值偏大」的参数按开发场景收了口：`__consumer_offsets` 默认 50 分区（每个分区都要开一组日志 + 索引文件），单消费者组用 1 个就够；日志保留从 7 天收到 1 天、段大小从 1GB 收到 64MB。

### 8.3 验证

| 验证项 | 结果 |
| --- | --- |
| 重建容器后健康 | `Up (healthy)`，`/proc/1/cmdline` 里是 `-Xmx256m -Xms256m` |
| 数据落在 volume | `/var/lib/kafka/data` 里有 `__cluster_metadata-0`、checkpoint 文件；跑完 e2e 后 192 KB；`/tmp/kafka-logs` 不存在 |
| 任务链路仍然通 | `DocumentTaskFlowIntegrationTest` 3/3 + `DocumentTaskE2ETest` 4/4，共 7 个 e2e 用例全绿（61.7s + 31.8s） |
| 重启不丢 topic | `docker compose restart kafka` 后 `kafka-topics.sh --list` 仍是 5 个 topic（4 业务 + `__consumer_offsets`） |
| 全量非 e2e | 306 通过 / 0 失败 / 1 跳过 |

### 8.4 副作用与注意

- **DLQ 只留 24 小时**：`KAFKA_LOG_RETENTION_HOURS=24` 对业务 topic 和死信 topic 一视同仁。想长期保留死信，要么把这条改回 168，要么给 `.dlt` topic 单独设 `retention.ms`。
- **这次重建丢掉了旧数据**（旧数据本来在容器可写层 `/tmp` 里，随容器一起销毁）。现在数据在 volume 上，之后再重建容器不会丢。
- **没有加 `mem_limit`**：硬性封顶是「掩盖」不是「优化」—— 真要封顶，先把堆调对，再考虑上限。
