## 一、端到端链路

```
COS(取 PDF) → Java 编排 → POST /jobs → Python/Docling
                                  ↓ 轮询 GET /jobs/{id}
COS(写产物) ← Java ← result → UPDATE document
```

这条链路是**生产路径**。阶段 2 之初，全量解析放在 Python 脚本里、Java 只测 3 页 ——
等于测了一条生产中不存在的路。现在完整走通。

| 指标 | 计划估算 | **实测** |

**估算偏差 3.7 倍。** 原因：前 8 页是封面 / 目录 / 短章节，而正文有大量密集财报表格，

## 五、异常统计（诚实呈现）

标题 anomaly 共 **224 / 581 = 38.6%**，但需要分开看：

| 类型 | 数量 | 是否真问题 |
|---|---|---|
| **错误归属**（章标题排在自己子节之后） | **6（1.0%）** | ❌ **是真问题**，决策门看这个 |
| 层级跳变（父级标题缺失） | 218（37.5%） | ⚠️ **多数不是问题** |

层级跳变高的原因：年报本身会省略中间层级，例如 `七、境内外会计准则下会计数据差异`
下面**直接**跟 `1、`、`2、`，没有 `（一）`。这种路径是正确的，只是层级号偏深。

**结论：真正的归属错误率是 1.0%，达标。**

## 六、本阶段踩到的坑（都已固化进计划）

| # | 问题 | 影响 |
|---|---|---|
| C | 原计划用"解析目录页反查归属"，但问题在**页内**（目录只给页间位置） | 改用**坐标重排**，错误归属 5.9% → 0% |
| C 补 | 只修标题树不够，**正文块的归属也必须按坐标** | 加了 `_SectionResolver` |
| D1 | Spring Boot 4 把 Flyway 自动配置拆成独立模块 | 只加 `flyway-core` → **迁移静默不执行** |
| D2 | Spring Boot 4 默认用 Jackson 3 | 包名变了，**且编译期看不出来** |
| D3 | 编排层依赖 `ObjectStorage` 导致无凭据时应用起不来 | 加条件装配 |
| **E** | **`parse()` 把 job_id 吞在适配器内部** | **客户端断线后无法恢复** —— 改成 submit / fetchResult 两步 |

### E 的详细说明（本阶段最有价值的发现）

初版实现里适配器这样包：

```java
ParsedDocument parsed = parser.parse(pdf, ...);   // 内部 submit + poll，job_id 从未传出
```

编排层拿不到 job_id，也就无法 `markRunning` 落库。后果：客户端轮询期间断开时，
数据库里那行是 `PENDING` 且无 job_id，恢复流程只能判定"作业从未提交"——
**而实际上作业正在服务端跑得好好的**。

这个缺陷**只有真跑长链路才会暴露**：短任务 16 秒就跑完，根本来不及断线。

## 七、恢复机制的真实验证（意外的收获）

这次恰好上演了恢复机制存在的意义那一个场景：

1. E2E 客户端提交作业并开始轮询
2. 解析远慢于预期，**在 60 分钟超时前我主动杀掉了客户端**（避免它把状态标成 FAILED）
3. Python 服务端的作业**继续在跑**
4. 修复 job_id 落库的缺陷后重启应用
5. `DocumentParseRecovery` 发现在途行 → 凭 job_id 接回 → 轮询
6. 92 分钟时作业完成，恢复流程**取回结果、写入 COS、更新 document**

日志证据：

```

[parse-recovery] 解析作业 04f23b5e... 状态: running (已用 3140.4s)
[parse-recovery] 解析作业 04f23b5e... 状态: done (已用 5517.8s)
[parse-recovery] 解析完成 document_id=7
                 产物=parsed/a5edb330.../docling-2.138.0/normalized.json
[parse-recovery] document_id=7 已从作业 04f23b5e... 恢复完成
```

**这不是模拟——是真实的 92 分钟作业，客户端中途死亡，重启后自动接回完成。**

## 八、已知局限

- **作业状态在进程内存**：单 worker、服务重启即失。阶段 7 交给 Kafka。
- **无细粒度进度**：只有 status + elapsed。Docling 不提供页级回调；要真实进度需分片解析
  再拼接，那会破坏章节树，本阶段不做。
- **无取消能力**：作业一旦提交只能等它跑完。
- **表格质量未评估**：345 张表的结构正确性要等阶段 4 的召回评估来反推。
- **同文档重解析是"替换"**：库里只保留最新一次（产物版本由 COS key 承载）。
