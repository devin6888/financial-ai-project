# 关键契约

> 这里记录**跨阶段、跨模块的隐含约定** —— 那些"代码里看不出来、改了就静默出错"的规则。
>
> 与设计文档的区别：设计文档写**方案**，这里写**实现层面必须遵守的契约**，以及为什么。

---

## C1 · embedding_text 的组成（阶段 3 起）

### 规则

向量不是对 `content` 直接嵌入，而是对一段**临时拼接**的文本嵌入：

```
{document_title}\n
{section_path 用 " > " 连接}\n
{caption}\n            ← 为空则整行省略
{content}
```

实现：`com.finagent.embedding.EmbeddingService#embeddingText(String documentTitle, Chunk chunk)`

### 这个字符串**不落库**

`document_chunk` 里只有 4 个相关字段：

| 字段 | 内容 |
|---|---|
| `embedding` | 1024 维向量 |
| `embedding_model` | 服务商模型名，如 `text-embedding-v4` |
| `embedding_version` | 本项目的接入版本，如 `v1` |
| `embedding_text_hash` | **拼接串的 SHA-256**，不是原文 |

**没有 `embedding_text` 这一列。** 它只存在于内存，嵌完即丢。

### 为什么要把标题与章节路径拼进去

单看 `content` 会丢掉「这段属于哪一章」的信息。比如：

> 「注：本报告中若出现总数与各分项数值之和尾数差异的情况，均属四舍五入原因所致。」

脱离上下文它什么都不是；拼上「第一节 重要提示、目录和释义 > 释义」之后，
向量才知道它属于**释义**章节。

财报里同一句话在不同章节含义可能完全不同。

### 为什么不把 embedding_text 存下来

1. 它比 `content` 更长 —— 存两份让表膨胀近一倍
2. 更重要的是：**它是「给模型看的 Prompt」，不是事实源**。存下来会诱导后续逻辑把它当内容使用
3. 存 hash 已经够用 —— 模板或模型变了，hash 就变，能**精确圈出需要重嵌入的 chunk**

### 已知的不一致（有意为之，但要小心）

| 场景 | 分隔符 |
|---|---|
| 库里 `section_path` 的**存储**形式 | ` § `（因为章节标题本身可能含 `>`） |
| 拼 `embedding_text` 时的**连接** | ` > ` |

**这意味着**：任何「从库里读出 section_path 再重建 embedding_text」的代码，
必须先把 ` § ` 拆开、再用 ` > ` 拼回去。少了这一步，向量会和不入库时不一致，
**但不会报错** —— 只会让重嵌入后的检索质量悄悄下降。

### 如何验证

`src/test/java/com/finagent/embedding/EmbeddingTextRoundTripTest.java`：

1. 从库里读 `doc_title / section_path / caption / content`
2. 用同一个 `embeddingText()` 重建
3. 重新调 API 嵌入
4. 与库里存的向量算余弦

实测：**1.000000**。

**这是一个回归保护** —— 以后若有人改了拼接顺序、分隔符或字段来源，这条会立刻从 1.0 掉下来。

### 改动流程

| 改了什么 | 必须同时做什么 |
|---|---|
| 拼接模板（顺序/分隔符/字段） | 升 `EmbeddingService.VERSION` → 所有 chunk 需要 REEMBED |
| 换嵌入模型 | 改 `EmbeddingService.MODEL` + 升 VERSION → 全量 REEMBED |
| 只改 `content` 切分 | 与 embedding_text 模板无关，走 RECHUNK 即可 |

## C2 · section_path 的存储格式

- 存储：用 ` § ` 分隔（`Chunk#sectionPathText()`）
- 为什么不用 `>`：章节标题本身可能含 `>`（如「A > B 类业务」），会造成歧义
- 用于过滤时：`section_path LIKE '第八节%'`（前缀匹配）

**注意**：与 C1 中 embedding_text 用 `>` 连接不同，两者不要混淆。

## C3 · chunk_index 在版本内全局唯一

- 切块时 `chunkIndex` 是**每个 Parent 内部**从 0 编号（对 sibling 扩展最自然）
- 入库前由 `WritePlan.assemble` **统一重编号**成版本内全局序号
- 原因：`uq_chunk_version_index (document_id, chunk_version, chunk_level, chunk_index)`
  要求唯一。不重编号会撞唯一索引 —— 单测里每个 Parent 只有一个 Child，**测不出来**，
  只有端到端跑真实数据才会暴露

## C4 · 检索只读 active 版本的 ACTIVE 行

任何检索 SQL 都必须带：

```sql
WHERE dc.status = 'ACTIVE'
  AND dc.chunk_version = coalesce(?, d.active_chunk_version)
```

- 不传版本时用**每篇文档自己的** `active_chunk_version`
- 写法必须用 `JOIN document d`，不要用相关子查询（逐行执行）
- 重索引期间新版本以 ACTIVE 写入但归属新版本号，**事务提交前对检索不可见**

## C5 · 作用域是检索的**上界**，不在其内部回退越过（阶段 5 起）

### 规则

1. 作用域（`ResolvedScope`）解析成 `documentIds` 之后，**一路带进 SQL**；
2. QU 推出的 company / year / docType 只能**收窄**作用域，越界就丢弃该字段并记 warning
   （`qu_company_out_of_scope` / `qu_year_out_of_scope` / `qu_doc_type_out_of_scope`）；
3. 命中为 0 时的两级回退：
   - `qu_filter_empty_fallback`：只清 **QU 带来的**条件，**保留** `documentIds`；
   - `no_evidence_in_scope`：清完仍为 0 → 返回空 + 该 warning，**不跨作用域兜底**。

### 为什么不能用「空列表」表示空集

`dc.document_id IN (...)` 在列表为空时是**语法错**，而「不加这个条件」等价于**全库**。
所以 `HybridRetriever.EMPTY_DOCUMENT_SET = -1L`：用一个永不匹配的 id 表达「作用域是空集」。
把空列表当「不过滤」写，会让「范围内没证据」悄悄变成「全库检索」。

### 与授权的关系

`ScopeAuthorizer` 在**解析阶段**完成权限过滤（`AllowAllAuthorizer` 是阶段 5 的占位实现）。
检索层不再做第二遍鉴权 —— 一旦两处都判，任何一处漏判都会让越权检索看起来「正常」。

## C6 · 上下文只放原文，且引用只能来自上下文（阶段 5 起）

### 规则

1. `ContextBlock.content` **永远是原文**，绝不塞 `embedding_text`
   （那里面有标题与章节路径的副本，既浪费 token，又会让模型把「检索用的拼接串」当内容引用出去）；
2. 每块带 `[E1]..[En]` 编号，模型**只输出编号**，后端映射成 chunk_id / 页码 / bbox；
3. 预算用库里的 `token_count` 累加，**整块出局**，不截断字符串（截断会把表格切成半行）；
4. 邻居按「该 Parent 的 children 排序后的位置 ± radius」，不按 `chunkIndex` 差
   —— chunkIndex 是全局编号，同 Parent 内可能跳号。
5. **拒答与证据不足都必须可读、可判**（阶段 9 补，ST9 §17.2）：模型判 `sufficient=false` 时，
   响应必须同时有非空 `answer`（可展示的说明）、非空 `note`（为什么答不了）与
   `evidence_insufficient` 警告（机器可读）。三条缺一，客户端就只能看到「空答案 + 一个 confidence」。

### 为什么编号比让模型写 id 可靠

模型不知道 chunk_id（也不该让它猜）。编号天然受限于本轮上下文，
于是 `CitationValidator` 遇到越界编号时**只能剔除**，不可能「反解析出一个不存在的块」。
这是结构性保证，不是概率性校验。

## C7 · 引用必须能反解析回真实行（阶段 5 起）

`Citation` 的每个字段都来自 `ContextBlock`（也就是库里的行），**不采信模型输出**：

| 字段 | 来源 |
|---|---|
| `childChunkId / parentChunkId / documentId` | ContextBlock |
| `pageStart / pageEnd` | ContextBlock（库里可空，null 渲染「页码未知」） |
| `bbox` | 库里单框 `{top,left,right,bottom}` → `{page,x,y,w,h}`；`x=left, y=top, w=right-left, h=bottom-top` |
| `evidenceType` | chunkType：TABLE→TABLE，其余→TEXT |
| `scope`（合并/母公司） | 正文出现「归属于母公司」→ 母公司；出现「合并…表/口径」→ 合并；判断不了→null |
| `tableRef` | 恒 null（库里没有 tableId，**不猜行范围**） |

### 降级而不是拦截

| 情况 | 处理 |
|---|---|
| 编号越界 | 剔除该条，记 `citation_dropped:N`；过半数记 `citations_mostly_dropped` |
| 引用被剔除 | `confidence` 上限降到 medium，记 `answer_citations_dropped` |
| 一条引用都没有 | 不拦截答案，但 `confidence` 降 medium + `answer_without_citation` |
| 模型输出非 JSON | `confidence=error` + `answer_generation_failed`，**不返回无引用的自由文本** |

最后一条是底线：金融场景里没有引用的答案等于谣言，宁可返回"生成失败"。

### 正文里的编号怎么认（2026-10-30 补）

| 模型可能写成 | 处理 |
|---|---|
| `[E5]` | 正常引用 |
| `[ E5 ]`（括号内空格） | 同样算引用，重排时统一写成 `[En]`；不认的话前端 `AnswerText.vue` 只匹配 `\[E(\d+)\]`，会渲染成一段点不开的纯文本 |
| `［E5］`（全角括号） | 同 `[ E5 ]` |
| 正文写了、`usedEvidence` 里没有 | **补进 citations**（按首次出现顺序）。只信 `usedEvidence` 等于把这句的出处扔掉：2026-10-30 线上答案写「增长贡献最大[ E5 ][E3]」而 `usedEvidence` 只有 `[E1,E2,E3]`，那次 E5 就点不开 |
| 越界（`[E99]`，块数不够） | 删除正文里的标记，记 `citation_dropped`；与上面两条不冲突 |

**提示词里禁止用真实数字做示例。** `AnswerPrompts.USER_TEMPLATE` 曾用 `"value":"12,084,594,947.22"` 做示例，而这个数正好是东方财富 2025 年**净利润**（chunk 7216）。
模型看到示例把净利润标成「营业总收入」，于是判定「证据被误标」并整题拒答（2026-10-30 实测）。现在示例统一用 `"<照抄证据里的数字>"` 这类占位符。

## C8 · Parent-Child 的语义与上下文展开规则（阶段 5 起）

### Parent 的定位：分组键 + 章节锚点

`document_chunk` 里 `chunk_level='PARENT'` 的行**不是**「这一节的完整内容」，也不是元数据源：

1. **分组键**：子块的 `parent_id` 指向它。邻居扩展、组内二次选择都按 `parent_id` 分组。
2. **章节锚点**：章节级 `chunk_index` 是重切重编号的锚点；切块以它为单位，版本切换做原子替换。
3. **不是内容容器**：`parent.content` 只拼正文、**不含表格**（表格都在子块里）。
4. **不是元数据源**：`section_path`/`title` 是父块在切块时定一次、再**冗余写进每个子块**（不是继承）。
   这样既保证同一节的兄弟块一致，又让子块读时自包含——检索、过滤、引用都不用 join 父表。

### 三条不可违反的规则

1. **检索永远只查 CHILD**（Dense/Sparse 都 `WHERE chunk_level='CHILD'`）；父块 0 embedding、`content_tsv` 不被搜。
2. **`parent.content` 永不进提示词**：它只做诊断展示 + parent 缺失兜底。整段展开用子块组装，不用它。
3. **引用来自子块**：上下文里每块对应一个 CHILD 行，`Citation.childChunkId` 永远是子块 id，不存在「引用一个 PARENT 块」。

### 上下文装配的两条路径（ContextBuilder）

| 路径 | 触发条件 | 给什么 |
|---|---|---|
| 精确路径（默认） | 任何 queryType | 命中子块 + 同 parent 内 ±neighborRadius 邻居（按 chunkIndex 排序） |
| 整段展开 | 仅 `COMPLEX_ANALYSIS` 且该父块**全部子块 token 和 ≤ `parentWholeMaxTokens`(1500)** | 该父块下**全部子块按 chunkIndex 排序**（正文+表格）；命中子块标 HIT，其余标 SIBLING |

- 整段展开**超上限时自动退回精确路径**，绝不截断、也绝不退回 `parent.content`。
- 不变量：一个父块的全部子块**完整覆盖该节的正文 + 表格**，且**每个表格至少出现一次**在某个子块里。

## C9 · 文档任务、幂等与错误分类（阶段 7 起）

### topic 与消息体

| Topic | Key | 消费者 | 用途 |
|---|---|---|---|
| `document.parse` | documentId | document-worker | PDF 解析 → 切块 → 嵌入 → 入库（一条龙） |
| `document.reindex` | documentId | document-worker | 从已存解析产物重切 + 增量重嵌（不重新解析） |
| `document.parse.dlt` / `document.reindex.dlt` | 原 key | 人工 | 死信，等人工处理或重放 |

~~~json
{ "eventId": "uuid", "documentId": 7, "mode": "RECHUNK", "occurredAt": "2026-10-26T21:00:00Z" }
~~~

`eventId` = 本次投递的唯一标识；`mode` 只在 `document.reindex` 用（对齐 `ReindexMode`）。
**key 必须是 documentId**：同一文档的事件进同一分区、天然保序，
「先解析后重切」不会被重排成「先重切后解析」。

### 两级幂等（缺一不可）

| 级别 | 键 | 防什么 | 实现 |
|---|---|---|---|
| 消息级 | `task_message.event_id` UNIQUE | 同一条 Kafka 事件被重投（消费者重放、DLQ 重放） | `TaskMessageRepository.upsert`：先 INSERT，撞唯一约束就回查返回同 id |
| 业务级（解析） | `document.content_hash` + `parse_status='DONE'` | 同一份 PDF 换了 eventId 再传一遍 | `DocumentUploadService` 幂等快路径 + `DocumentRepository.findCompletedIdByContentHash` |
| 业务级（切块） | `chunk_version` 版本化 + 原子切换 | 重复 reindex 在 ACTIVE 版本上重复写 | `ChunkPersister.persistAndSwitch`（新版本校验通过才切 ACTIVE） |

只有消息级会漏「用户重新上传同一份 PDF」（新 eventId、旧内容）；
只有业务级会漏「重放时中间状态已被改过」。所以两级都要。

### 状态机

- `document.parse_status`：`PENDING → RUNNING → DONE | FAILED`（阶段 2 起）
- `task_message.status`：`RECEIVED → PROCESSING → SUCCESS | FAILED | DLQ`（CHECK 约束枚举）

### 错误三分类（`RetryClassifier`）

| 类别 | 判定 | 处理 |
|---|---|---|
| TRANSIENT | cause 链上有 `SocketTimeoutException` / `ConnectException` / `CosServiceException` / `CosClientException` | 重试 `max-retries` 次、间隔 `backoff-ms`，仍失败进 DLQ |
| DATA | cause 链上有 `JacksonException` | 不重试，直接进 DLQ |
| BUSINESS | 其余 | 不重试，直接进 DLQ |

**必须沿 `getCause()` 链找，不能只判顶层类型**：`CosObjectStorage.get()` 会把 COS 的瞬时异常
包成 `NoSuchElementException`。只判顶层就会把「网络超时」误判成「对象不存在」这种业务错误，
于是本该重试的消息直接进 DLQ。

**`transientTypes()` 是唯一白名单来源**：分类逻辑与 `KafkaErrorHandlerConfig` 共用它，两处不许各写一份。

### 三条不可违反的规则

1. **listener 方法带 `Acknowledgment` 参数 → 容器必须 `ack-mode: manual`。** 否则启动不报错、
   收到第一条消息才抛 `IllegalStateException: No Acknowledgment available as an argument…`。
2. **`task_message.document_id` 不加外键。** 坏消息（documentId 不存在）也必须能落表留痕，
   否则失败本身就查不到。
3. **DLQ 消息体必须是原始 payload 原样保留**（含 `eventId`）。重放时改 `documentId` 不改 `eventId`，
   才能命中消息级幂等，不产生第二条 task_message。

## C10 · 增量重嵌入（阶段 7 起）

### 复用必须同时满足三个条件

1. `embedding_text_hash` 相同 —— 送进模型的文本一模一样，向量必然相同；
2. `embedding_model` 相同 —— 换模型后旧向量与新模型不在同一空间；
3. `embedding_version` 相同 —— 同模型但改了调用参数（维度 / 归一化 / instruction）同理。

少任何一条都不许复用。另外 `embedding IS NULL` 的旧块不算可复用（否则 `containsKey` 为真但取值为空，
回填时会与新向量数量错位）。

### 数据流（`ChunkWriter.writeVersion`）

~~~text
1. 事务外：对新块算 embedding_text 与 hash
2. 读旧 ACTIVE 版本的 CHILD 向量（embedding::text，一次约 654 行 2.6MB）
3. EmbeddingReuseService.plan：按三条件建 hash→旧向量索引，分出「复用」与「待嵌入」
4. 只对「待嵌入」调 embedding API
5. assemble：按新块原顺序回填；末尾校验 cursor == freshVectors.size()
6. 事务内：写新版本 → 校验 → 原子切换 ACTIVE
~~~

### 不可违反的规则

1. **回填顺序错位不会报错**，只会让块 A 挂上块 B 的向量、检索结果悄悄变差 —— 必须显式校验条数。
2. **首次索引（无旧版本）必须退化为全量嵌入**，行为与阶段 3 完全一致，不许走特殊分支。
3. **hash 的计算口径就是 C1**。改了 `embedding_text` 的拼法，等于让全部旧向量失效 —— 这是
   `embedding_version` 需要跟着改的信号。

## C11 · 认证、租户与可见性（阶段 8 起）

### 身份的唯一起点

身份 = `Authorization: Bearer <token>` 经 SHA-256 查 `app_user` 得到的 `CurrentUser(userId, tenantId, username, roles)`，
写进 `TenantContext`（ThreadLocal），请求结束时清掉。**请求体 / 查询串里的 `tenantId`、`userId`、`roles` 一律不读。**

| 位置 | 必须守的规则 | 破坏后的现象 |
|---|---|---|
| `AuthenticationFilter` | `shouldNotFilter` 只放行 `/error`；`finally` 必须 `TenantContext.clear()` | 拦 `/error` 会 401 套 401；不清上下文，Tomcat 复用线程会把上一个人的身份带进下一个请求 |
| `ApiTokenRepository` | 库里只存 `SHA-256(token)`，不存明文 | 拖库即拿到全部可用 token |
| 控制器 / 服务层 | 身份只能来自 `TenantContext.require()` | 客户端传什么就是什么，跨租户读写零成本 |

### 三道防线（各管一件事，缺一层就漏一类）

| 层 | 管什么 | 实现 | 明确挡不住什么 |
|---|---|---|---|
| ① 认证 | 有没有身份、token 是否有效 → **401** | `AuthenticationFilter` + `app_user.api_token_hash` | 同一租户内的串号（都是合法用户） |
| ② 租户（硬边界） | 跨租户读写 | V8 的 5 条 RLS 策略 + `TenantAwareDataSource`（`SET ROLE finagent_app` + `set_config('app.tenant_id', …)`） | 租户内互相可见；表 owner 连接直接绕过 RLS |
| ③ 租户内可见性（软边界） | 公司级授权、私有文档 | `AclScopeAuthorizer.filterReadable` + `ScopeResolver` 三条路 | 授权之后「这一轮取多少」由 C5 的作用域上界管 |

「硬 / 软」是相对的：②破了是**数据事故**（跨客户泄漏）；③破了是**越权事故**（同客户内多看几份）。
两者都要测：②由 `RlsEnforcementTest`，③由 `AclScopeAuthorizerTest` + `ScopeResolverAclTest`，
合起来由 `TenantIsolationE2ETest` + `ZeroLeakGateTest` 走真 HTTP 验收。

### fail closed / fail loud

| 场景 | 行为 |
|---|---|
| 无 token / token 无效 | **401** `AUTH_REQUIRED` / `AUTH_INVALID`（两者措辞不同，但都不透露用户是否存在） |
| 有身份，但 ACL 过滤后为空（CORPUS / FILTER） | **409** `SCOPE_EMPTY`「知识库中没有当前账号可检索的文档」 |
| DOCUMENTS 模式里请求的 id 都不可读 | **409** `SCOPE_EMPTY`「所选文档均不可检索（未解析完成或不存在）」+ warning `scope_unauthorized` |
| 借连接时设不上租户变量 | 关闭该连接并抛异常，**绝不**把「无租户状态」的连接借出去 |
| 无 `TenantContext`（CLI / Flyway / e2e 造数） | `RESET ROLE`（回到 owner）+ fallback 租户。这是**受信路径**，不得用于对外请求 |

### 空集语义（最危险的一条）

作用域解析出的空集，在检索层等于「不过滤 = 全库」（`documentIds.isEmpty()` / `EMPTY_DOCUMENT_SET` 哨兵）。所以：

1. ACL 过滤后为空必须抛 `ScopeEmptyException`，**不许**返回空列表；
2. CORPUS 被 ACL 收窄后必须把 id 下推 SQL（`ResolvedScope.aclNarrowed = true`），否则 ACL 只影响提示词、不影响真正取到哪些块 —— 那就是「看得见的没拿到、拿到的可能是看不见的」。

### 写路径的租户从哪来

| 表 | tenant_id 来源 | 为什么 |
|---|---|---|
| `document` | `CurrentUser.tenantId()` | 上传动作属于某个登录用户 |
| `document_chunk` / `financial_fact` | 从 `document` 行查（`ChunkPersister` 先 `SELECT tenant_id FROM document WHERE id = ?`） | 父子一致性不能靠调用方保证；查不到就抛异常 |
| `task_message` | 子查询 `(SELECT tenant_id FROM document WHERE id = ?)`，可为空 | 坏消息推不出租户，但失败本身必须留痕（见 C9 规则 2） |

### 四条不可违反的规则

1. **响应正文不许出现**：对象存储键（`object_key` 原文、`parsed/`、`cos.`、`myqcloud.com`）、
   调用方不可读文档的标题与正文片段、以及「你有 N 份看不见的文档」这种计数。
   所以 warning 只写 `scope_acl_hidden` / `scope_unauthorized`，**不带数字**（条数进服务端日志）。
2. **跨租户查详情返回 404，不返回 403**：403 等于确认「这个 id 存在」。
3. **枚举端点（`GET /api/scope/documents`）必须过同一个 `filterReadable`**：不过就等于把全库清单送出去，
   攻击者连 id 都不用猜。
4. **唯一约束按租户内**：`uq_company_tenant_code (tenant_id, code)`、`uq_document_tenant_hash (tenant_id, content_hash)`。
   全局唯一会让两个租户抢同一个公司代码 / 同一份 PDF 哈希（V9 已改）。

### 与其它契约的关系

- C4（只读 ACTIVE 版本）、C5（作用域是上界）在 ACL **之后**执行：
  ③ 决定「这个租户里你能看哪几份」，C5 决定「这一轮实际查哪几份」。
- C8（Parent 不进提示词）不受影响：ACL 只做文档级过滤，不改变块的角色。
- 关掉 ACL 的唯一合法场景是**测试 profile**（`finagent.tenant.acl-enabled=false`）：300 多个既有测试
  不该为了每个用例造授权行。代价是「测试环境不验 ACL」，所以 ③ 必须有独立的数据库级测试与真 HTTP 越权用例。

## C12 · 会话、四层记忆与指代消解（阶段 9 起）

### 分层与真相源（每层只回答一个问题）

| 层 | 回答什么问题 | 真相源 | 进 Prompt 的位置 | 可引用 |
|---|---|---|---|---|
| 短期记忆 | 刚才几轮说了什么 | `conversation_message`（追加，永不改写） | 【背景信息 · 不可引用】最近 6 轮 | 否 |
| 会话摘要 | 更早的对话压缩后是什么 | `conversation_summary`（每会话 1 行，覆盖写 + version） | 同段「此前对话摘要」 | 否 |
| 结构化上下文 | 这一轮在聊哪家公司 / 哪几年 / 哪份文档 | `conversation_context`（每会话 1 行，`ON CONFLICT DO UPDATE`） | 同段第一行 | 否 |
| 长期记忆 | 用户明确表达过的偏好与关注点 | `long_term_memory`（每 key 一条 ACTIVE，冲突版本化） | 同段最后 | 否 |
| 本轮证据 | 这次从文档里取到了什么 | `document_chunk`（C4：只读 ACTIVE 版本） | 【证据 E1..En】 | **是** |

四层记忆都是「背景」，只有证据块能产出引用 —— 这是 C12 与 C7 的交界。

### 每会话有几行（行基数是设计的一部分，不是实现细节）

| 表 | 行数 | 为什么 |
|---|---|---|
| `conversation` | 1 | 会话本体；删除是 `status='DELETED'`（逻辑删除，消息留作审计） |
| `conversation_message` | 每轮 +2（USER / ASSISTANT） | 追加型；摘要不删消息，只前移指针 |
| `conversation_summary` | **恒定 1**（PK = `conversation_id`） | 摘要是「当前状态」不是「事件」；可由消息重算，不必存历史 —— 每次变化写一条 `memory_event` |
| `conversation_context` | **恒定 1**（PK = `conversation_id`） | 同上 |
| `long_term_memory` | 每 key 1 条 ACTIVE + N 条 SUPERSEDED/DELETED | 版本化保留「改过什么」，ACCEPT 与撤回都可回放 |
| `memory_event` | 追加（只能 INSERT） | 审计：谁在什么时候把哪条改成了什么 |

### 三条硬规则

1. **记忆永不产生引用**（D4）。`[E1..En]` 的序号是 `ContextBlock` 数组下标（`CitationValidator`），
   记忆没有 `documentId` / `pageStart` / `bbox`。把记忆塞进证据数组会让编号整体错位，
   并产出「看起来有出处却点不开」的引用 —— 比没有引用更有害。记忆只在 `ChatTrace.memory` 留统计。
2. **预算只能整条丢，不能截断**。半句话会让模型自行补数字（幻觉的高发来源）。
   裁剪顺序固定：证据（低分先丢）→ 短期（最旧的一轮成对丢）→ 摘要 → 结构化 → 长期记忆。
   例外：**INSTRUCTION 不参与 5% 配额**，它有独立的 `instruction-tokens`（默认 600），
   超了只合并压缩、**不丢弃**；压不下则带 `instruction_overflow` 警告照常注入（D10）。
3. **越权一律 404 / 空结果，不泄漏存在性**：他人会话 → 404 `CONVERSATION_NOT_FOUND`；
   他人记忆查不到（`WHERE tenant_id = ? AND subject_id = ?`，靠 RLS + 主体双重条件，不是 403）。

### 会话与作用域

| 规则 | 细节 |
|---|---|
| 请求里的 `scope` 优先，其次会话配置 | `ConversationService.effectiveScope(requested, conversation)`；两者都空 = CORPUS |
| 归属校验必须在作用域解析**之前** | 否则别人会话里的文档范围会被当成自己的授权（`ChatService.ask` 第 91-96 行） |
| `conversation_message.scope_snapshot` 记四个字段 | `{session, effective, chunkVersions:{docId:版本}, resolverVersion}`；`chunkVersions` 让历史回答能指回**当时那一版**的块（重切后 id 全变） |
| 无 `conversationId` = 单轮 | 不装配记忆、不落库、不写 trace 的记忆段；这条是与阶段 8 完全一致的回归门限 |

### Prompt 装配（不是把四层拼一起）

固定顺序：**System（规则）→ 背景信息·不可引用（① 结构化 → ② 摘要 → ③ 短期 → ④ 长期）→ 证据 E1..En → 当前问题**。
记忆不进 `ContextBuilder`，由 `MemoryPromptRenderer` 纯函数渲染，两者只在 `AnswerPrompts` 汇合。

| 层 | 配额（默认） | 空层的处理 |
|---|---|---|
| 结构化上下文 | `structured-ratio` 5% | 整段省略（不写「（无）」占位） |
| 摘要 | `summary-ratio` 10% | 整段省略 |
| 短期 | `short-term-ratio` 15%，最多 `short-term-rounds` 6 轮 | 整段省略 |
| 长期（CONTEXTUAL / WATCHLIST） | `long-term-ratio` 5%，最多 `long-term-max-items` 3 条 | 整段省略 |
| 长期（INSTRUCTION） | `instruction-tokens` 600，独立 | 无记忆则省略 |
| 证据 | `evidence-ratio` 40% | 由检索层的 `ContextPackage` 决定 |

基数 `context-window-tokens` 默认 8000，合计 75%，剩下 25% 留给 System、问题与输出。
配额按**百分比**而非条数：模型换窗口时自动放大。

### 长期记忆：只写两类高置信来源（D2）

| 来源 | 触发 | 落库 |
|---|---|---|
| 显式命令（规则解析） | 句首「以后…」「记住…」「别再…」「重点关注 300059」 | `source_type='EXPLICIT_COMMAND'`，`confidence=1.0`，`source_ref` 记原句 |
| 显式 API | `POST /api/memories {type,key,content}` | `source_type='USER_API'` |

**不做模型自动提炼**：写错一条偏好会污染之后每一轮，而「模型判断用户在不在下指令」的准确率无法离线评估。
宁可漏（漏了用户用 API 显式写），也不误写。

冲突规则：同 `(tenant_id, subject_id, memory_type, memory_key)` 只允许一条 ACTIVE —— 靠**部分唯一索引**
`uq_memory_active ... WHERE status='ACTIVE'`，且 `ON CONFLICT` 也要带同样的 WHERE。
内容相同 → 幂等返回旧行（不写事件）；内容不同 → 旧行 `SUPERSEDED`、新行 `version = old.version + 1`、
`memory_event` 记 `SUPERSEDE` 与新旧值。**先降级再插入**，顺序反了会撞唯一索引。

### 召回闸门（Gate）与零调用

判定顺序：`gateEnabled=false` 或 `memory.enabled=false` → 不召回；问题为空 → 不召回；
QU 的 `needLongTermMemory=true` → 召回；命中词典（以后 / 以前 / 上次 / 照旧 / 还是按 / 格式 / 偏好 / 习惯 /
记住 / 一贯 / 历来 / 按我的 / 照我 / 之前说）→ 召回；否则**不召回**。

两道「零开销」闸门，缺一个都会多花一次外部调用：

1. Gate 不通过 → **不查库**；
2. Gate 通过但候选行为空 → 直接返回空，**不起 embedding**（先精确 key 规则命中，命中不足才向量补）。

召回阈值 `long-term-min-score` 0.6 ⇔ 余弦距离 `<= 0.4`（`<=>` 返回的是距离，写反就变成「越不相关越入选」）。
排序键：importance 降序 → 相似度降序 → id 降序；`touchAccessed` 放最后（失败不影响回答）。

### 摘要（D3 / D9）

触发：未汇总消息数 > `summary-trigger-messages`（默认 12）→ 取最旧**一半**（偶数化、最少 2 条）+ 旧摘要一起交给 LLM，
指针前移到这一半的最后一条。只压一半而不是全量：全量会让摘要每轮重写，「改了什么」失去意义。
失败只加警告 `summary_failed`，指针不动、下一轮自然重试。摘要文本 ≤ 200 字，渲染时标「不可引用」。

### 与其它契约的关系

- **C11**：会话与记忆的 `tenant_id` 只来自 `TenantContext`；子表也带 `tenant_id` + 各自 RLS 策略（RLS 不会替你 join 父表）。
- **C4 / C5 / C8**：检索仍然只读 ACTIVE 版本的 CHILD 块；记忆在作用域**之内**做，不会把范围撑大。
- **C7**：引用只能来自证据块，记忆与摘要永不参与编号。

## C13 · 公司名 → 公司代码的解析（阶段 9 起，ST9 §16）

### 13.1 三个名字，不许混用

| 名字 | 类型 | 含义 | 谁产生 |
| --- | --- | --- | --- |
| `QueryUnderstanding.companyMentions` | `List<String>` | **问题原文里的公司名字面**（如「东方财富」）。必须是原文逐字子串 | 模型抽取 + 子串校验 |
| `QueryUnderstanding.companyCodes` | `List<String>` | **证券代码**（6 位数字，如 300059）。不是数据库主键 | 原文里写了代码才是模型抄的；否则由 CompanyResolver 查库得到 |
| `ResolvedScope.companyIds()` | `Set<Long>` | **数据库 `company.id` 主键**（如 7） | 作用域解析 |

### 13.2 为什么这么分工

让模型把「东方财富」翻译成「300059」，等于让它凭训练记忆背答案 —— 没有权威源可查，出错是概率问题。
2026-10-28 的多轮 e2e 实际抓到一次：模型把东方财富翻成 **600519（贵州茅台）**，作用域里没有它 → 整轮被拒答（3.34 秒、零检索）。

正确的分工是**抽取交给模型，实体链接交给数据库**：模型只被允许抄原文里的公司名（抄不出原文没有的字符串），代码一律查 `company` 表得到。

### 13.3 四条硬规则

1. `companyMentions` 必须是问题原文的子串；不是的一律丢弃（`RouterService.validate`）。
2. `companyCodes` 必须在问题原文里字面出现；没出现的一律丢弃 —— 这是根治编造代码的那一刀。
3. 代码为空时由 `CompanyResolver` 用 mentions 在**当前作用域**内匹配（先逐字，再归一化双向 contains）；
   匹配不到且「像公司名」→ **拒答**（不允许退化成无公司约束检索，那是阶段 6「问五粮液答东方财富」的根因）。
4. 解析后仍为空、且**作用域里只有一家公司** → 用它的代码兜底并记 `company_from_scope`（ST9 §17.1）；
   作用域里有两家以上则**不兜底** —— 替用户选主体就是主体错配。
   顺序也是硬规则：**用户原话 > 会话上下文 > 单公司作用域 > 无约束**，前一层有值就不看后一层。

### 13.4 「像公司名」判定

| 判定 | 规则 |
| --- | --- |
| 是实体 | 长度 ≥ 3，或含后缀词（公司/股份/集团/银行/证券/保险/控股/实业/科技/药业/能源/汽车/地产/电力/传媒/基金/信托/航空/钢铁/煤炭/化工/医药/食品/家电） |
| 不是实体（不拒答） | 代词表：该公司、上述公司、本公司、母公司、子公司、公司、企业、行业、市场、这些公司、上市公司、其他公司、同行业 |
| 也不拒答但要留痕 | 其他短泛称（如「报告」）→ 只加 `company_mention_ignored` 警告 |

### 13.5 与 C12 的关系

多轮追问「那净利润呢」时，公司来自**会话结构化上下文**（`fillFromContext` 补 `companyCodes`），
这条路径不经过 mentions 校验（值来自数据库，本身可信），但同样要经过 `CompanyResolver` 的作用域匹配。
## C14 · 登录、会话 token 与默认用户（阶段 10 起，ST10 §11）

### 14.1 两条进入方式，产物是同一个 Bearer token

| 方式 | 入口 | 产物 | 谁的场景 |
| --- | --- | --- | --- |
| 账号密码 | `POST /api/auth/login` | 会话 token（32 字节随机，43 字符 base64url），写 `api_session` | 人用的默认路径：界面登录、演示、换设备 |
| 预置 token | V8 种子的 `dev-*` | 无（本来就是 token） | 机器：既有 500+ 用例与 e2e 的地基 |

两条路的后续完全一致：`Authorization: Bearer <token>` → `AuthenticationFilter` → `TenantContext` → RLS。
所以**认证层以下（租户、RLS、ACL、审计）一行都不用改** —— 这也是当初不选 JWT / 不引 Spring Security 的收益。

### 14.2 硬规则

1. **库里只存哈希**：`app_user.api_token_hash` 与 `api_session.token_hash` 都是 SHA-256 十六进制（同一口径 `ApiTokenRepository.sha256Hex`）。明文只在签发那一刻出现在响应体里。
2. **密码哈希与校验都在数据库**：`pgcrypto` 的 bcrypt（`crypt(pw, gen_salt('bf', 10))`），Java 侧不引 KDF、不自己实现。代价是数据库不可用时登录失败 —— fail closed，方向正确。
3. **失败报文逐字相同**：用户不存在 / 密码错 / 账号 DISABLED 都返回 `401 AUTH_INVALID` 同一句话。否则登录接口就是用户枚举器。
4. **登出是软撤销**：`DELETE /api/auth/session` 写 `revoked_at`，不物理删 —— 保留行才能回答「这个 token 哪天被撤销的」。撤销后同一 token 立刻 401。
5. **登录是唯一匿名 API**：`AuthenticationFilter.shouldNotFilter` 只放行 `/api/auth/login`；登出、`/api/me`、其余全部要求已登录。
6. **身份只来自 token**：请求体 / 查询串里的 `tenantId`、`userId` 一律忽略（与 C11 同一条规则，`RestAuthContractTest` 有断言）。

### 14.3 会话生命周期

| 事件 | 行为 |
| --- | --- |
| 登录 | `INSERT api_session`，`expires_at = now() + interval '168 hours'`（`finagent.auth.session-ttl-hours`） |
| 每次请求 | 只读校验（`revoked_at IS NULL AND expires_at > now()`），顺带 `touch` 更新 `last_used_at`；**最多 5 分钟写一次**，避免每请求一条 UPDATE |
| 登出 | `UPDATE ... SET revoked_at = now()` |
| 过期 | 不做定时任务：过期由查询条件自然淘汰（`expires_at > now()`），过期行留作审计 |
| 节流 | 内存计数「用户名 + 来源 IP」，15 分钟内失败 10 次 → `429 AUTH_TOO_MANY`；成功登录清零 |

### 14.4 默认演示用户

| 项 | 值 | 理由 |
| --- | --- | --- |
| 账号 / 密码 | `demo` / `demo123456` | 演示时可念；密码随时可在库里改（`crypt` 重算即可） |
| 角色 | `ADMIN` + `ANALYST` | ADMIN 让它看到本租户全部文档；ANALYST 继承已有的 300059 公司授权 |
| 数据归属 | `document.owner_user_id` / `long_term_memory.subject_id` / `conversation.owner_user_id` → demo | 现有数据全部挂在它名下，登录即见 |
| 公司 | 不动 | `company` 是租户级共享数据，没有 owner 列；权限来自「租户 + 角色授权」 |

### 14.5 与 C11 / C13 的关系

- **C11**：四道门（认证 / 租户 / 租户内可见性 / 查询范围）不变；C14 只替换第一道门的「凭证从哪来」。
- **C13**：登录用户与公司解析无关 —— 解析出的公司仍要过作用域与 ACL；换成哪个账号登录，作用域链条都不动。

### 14.6 已知限制

1. 用户名在**租户内**唯一；登录按 username 全局匹配，若同一用户名存在于多个租户，登录直接失败（fail closed），需要时再补「先选租户」。
2. 节流计数在内存里：重启清零、多副本不共享。
3. 没有找回密码 / 改密码接口：演示账号密码写死在迁移里，改密码 = 改库。

## C15 · 流式输出、原文页图与切块可视化（阶段 12 起）

### 15.1 SSE 事件协议（`POST /api/chat/stream`）

| 事件 | 时机 | data（JSON） | 前端义务 |
| --- | --- | --- | --- |
| `meta` | 检索 + 上下文装配完成、模型开始生成前 | `{traceId, scope:{kind,documentIds}, evidence:[{no,childChunkId,documentId,pageStart,pageEnd,sectionPath,docTitle,evidenceType}], contextTokens}` | 只能用来「先占位」；不得据此下结论 |
| `delta` | 模型每吐一段 | `{text}` | 追加显示；**编号是提示词编号，会被 final 重排**，不得据此建引用 |
| `final` | 四层校验全部完成 | 与 `POST /api/chat` 逐字段相同的 `ChatResponse` | **必须整条替换**本地消息 |
| `error` | 任何阶段失败 | `{code, message}`，code ∈ `BAD_REQUEST` / `SCOPE_EMPTY` / `AUTH_*` / `INTERNAL` | 显示错误并允许重试 |
| `: ping` | 每 15 秒 | 注释行，无 data | 忽略（防中间层 60 秒空闲断流） |

四条硬规则：

1. **`final` 是唯一真相**：引用、confidence、warnings、facts、trace、messageId 全部以它为准；delta 只负责「字在动」。
2. **租户上下文必须跨线程重建**：SSE 在虚拟线程里跑，进入任务先 `TenantContext.set(user)`，`finally` 里 `clear()`；丢了上下文 = RLS 返回 0 行 = final 里没有引用。
3. **拒答也走同一条流**：作用域外公司等拒答只发一个 `final`，不发 `meta`（没有证据可展示）。
4. **失败回落一次**：前端在「接口不存在 / 流中断 / 5xx / 网络错」时改调 `POST /api/chat`；`409 SCOPE_EMPTY` 与 `401` 是业务结论，不回落。

### 15.2 引用编号重排（与 C7 配套）

- 模型引用的是**提示词里的证据号**（E1..E20）；`citations` 只收「用到的」且按首次出现顺序。
- 因此 `AnswerService` 在 `CitationValidator` 之后必须把正文角标重写成 `[E1..En]`，n = `citations.size()`：
  - 越界 / 编造的编号在正文里**直接删除**（留着就是点不开的死链）；
  - 重排只改编号，不改文字与数字。
- 不变量：**正文里出现的最大编号 ≤ citations.size()**；这条由 `AnswerServiceTest` 的两条用例守住。

### 15.3 原文页图（`GET /api/documents/{id}/pages/{page}?dpi=150`）

| 项 | 规则 |
| --- | --- |
| 鉴权 | 先 `ScopeAuthorizer.filterReadable`，不可读 → **404**（不是 403，403 等于确认存在） |
| 入参 | 只接受 `documentId` + 页码；**永不接受对象键**（否则等于任意文件读取） |
| 输出 | 固定 `image/png`；`X-Page-Width` / `X-Page-Height` 给前端算高亮框 |
| dpi | 服务端夹紧到 72~300，默认 150（1080p 下表格可读，单页约 280 KB） |
| 缓存 | 进程内 LRU 48 页，key = documentId + contentHash + page + dpi；重新上传自动失效 |
| 404 合并 | 文档不存在 / 无权限 / 无对象键 / 页码越界 **全部同一个 404**，不确认页数 |

高亮坐标：库里 `document_chunk.bbox` 是 `{top,left,right,bottom}` 归一化值（0~1，原点左上），
`CitationValidator` 转成 `BBox{page,x,y,w,h}`，前端直接按百分比定位，**后端不再按 dpi 换算**。

### 15.4 切块列表（`GET /api/documents/{id}/chunks?limit=800&offset=0`）

- 只读当前 `active_chunk_version` 且 `status='ACTIVE'` 的块；没有 ACTIVE 版本 → 空数组。
- 返回**扁平列表**（不是嵌套树）：Parent 在前、Child 紧随其后，排序键
  `CASE chunk_level WHEN 'PARENT' THEN 0 ELSE 1 END, parent_id NULLS FIRST, chunk_index`。
  嵌套会让「limit 算 Parent 还是 Child」变得含糊，扁平列表前端用 `Map` 分组即可。
- 每行只带 `left(content, 220)` 的缩略与 `content_length`，不传完整正文。
- 不可读文档 → 空数组（抽屉已经打开过详情，再回 404 只会让前端多一套错误分支）。

### 15.5 与 C6 / C7 / C11 的关系

- **C6**（答案四层校验）不变：流式只是把同一份 JSON 的 `answer` 字段边生成边推，`evaluate()` 仍是唯一校验入口。
- **C7**（引用可反解析）由 15.2 强化：编号必须与 `citations` 下标一一对应。
- **C11**（四道门）由 15.3 / 15.4 延续：两个新端点都先过 ACL，且都用「不可读 = 404 / 空」而不是泄漏存在性。

## C16 · 首屏反馈：阶段事件与证据先行（阶段 13 起，ST13）

### 16.1 `stage` 事件（`POST /api/chat/stream` 上的第 5 种事件）

| phase | 谁在哪发 | label | detail |
| --- | --- | --- | --- |
| `understanding` | `ChatService.askStreaming` **第一行**（还没进 `prepare`） | 正在理解问题 | `{}` |
| `retrieving` | `ChatService.prepare`：作用域解析完、检索之前 | 正在检索证据 | `{documents:N}` |
| `reranking` | `HybridRetriever.doRetrieve`：融合完、调 rerank 之前（只在真的有候选且启用精排时才发） | 正在精排证据 | `{candidates:N}` |
| `generating` | `ChatService.askStreaming`：`meta` 之后、调模型之前 | 正在生成答案 | `{evidence:N, contextTokens:N}` |

事件顺序（正常路径）：

```
stage(understanding) → stage(retrieving) → stage(reranking) → meta → stage(generating) → delta* → final
```

- 拒答：`stage(understanding) → stage(retrieving) → final`（**没有** `generating` —— 没调模型）；
- 错误：`stage(...)* → error`；
- 检索无候选：没有 `reranking`（没东西可精排），`meta` 仍然发。

五条硬规则：

1. **只表达「正在做什么」**：不带答案文本、证据正文、页码、chunk id。detail 只允许计数。
   （`ChatServiceStageTest.stagePayloadCarriesCountsOnly` 断言 data 的 key 恰为 `phase` / `label` / `detail`，且不含任何数字答案。）
2. **必须由真实进入该段的代码发出**：禁止用定时器补发、禁止前端按时间伪造进度。
   「精排中」只能由 `HybridRetriever` 自己发 —— 它是唯一知道「何时开始调 rerank」的地方。
3. **发过 stage 就必须有终止事件**：`meta` / `final` / `error` 至少一个，不允许停在「正在精排」。
4. **stage 可以丢，`meta` / `final` 不能丢**：丢 stage 只是少一行提示；丢 final 前端按 `STREAM_INCOMPLETE` 回落一次。
5. **旧前端不许崩**：SSE 解析器按事件名分发，未知事件忽略（`web/src/utils/sse.ts` 默认分支，`sse.spec.ts` 有专门用例守）。

### 16.2 证据先行（`meta` 不是 `final`）

| 事件 | 含义 | 前端义务 |
| --- | --- | --- |
| `meta.evidence` | **候选全集**（送进模型的证据块，本语料 16 条） | 立即渲染证据条，最多 4 条 + 「+N」；不可点（点开也没有引用映射） |
| `final.citations` | **模型实际用到的**（通常 2~4 条），下标即 `[E#]` | 按它**重绘**证据条，可点，联动原文页高亮 |

- 证据条与答案区之间不允许跳动：证据条固定单行（`nowrap` + 折叠），答案区先用骨架占位。
- `meta` 比 `final` 多出来的条数要显式说明（「其余 N 条未被引用」）—— 否则观众会以为证据丢了。
- **`final` 仍是唯一真相**（C15 规则 1 不变）：`meta` 只是预览。

### 16.3 时延口径（2026-10-28 实测，热路径）

| 指标 | 定义 | 目标 | Java e2e | 真浏览器（headless） |
| --- | --- | --- | --- | --- |
| `firstStageMs` | 请求发出 → 第一个 `stage` | ≤ 300 ms | **19 ms** | **59 ms** |
| `metaMs` | 请求发出 → `meta`（证据可读） | ≤ 5,000 ms | **4,563 ms** | **4,904 ms** |
| `firstTokenMs` | 请求发出 → 第一个 `delta` | ≤ 8,000 ms | **5,275 ms** | **5,555 ms** |
| `totalMs` | 请求发出 → `final` | 观察值 | 11,377 ms | 12,459 ms |

优化前（阶段 12）用户在这 7.9 秒里看到的是一个静止的骨架屏；现在是
**0.06 秒出现状态行 → 3.5 秒「正在检索证据」→ 4.3 秒「正在精排证据」→ 4.9 秒证据条出现 → 5.5 秒首字**。

冷启动（进程刚起、Tomcat 异步响应与 Hikari 首次初始化）`firstStageMs` 实测 1,209 ms，属已知冷启动成本，e2e 用「先跑一轮预热再断言」处理。

### 16.4 `quMs`：把「理解问题」这一段单独计时

`ChatTrace` 新增 `long quMs`（第 11 个字段，保留 10 参兼容构造器），
`totalMs() = quMs + retrieval.totalMs() + contextMs + answerMs`。

为什么单列：QU 是唯一「不是必然要花」的一段（规则命中就不调模型），实测 2.9~3.4 秒，
占了首字延迟的一半左右。要优化它（预取 / 缓存 / 跳过）必须先能量它。本期只观测，**不设门槛**（决策 D8）。

### 16.5 与 C15 的关系

- C15 的 `meta` / `delta` / `final` / `error` 语义**一个字不改**；`stage` 是新增的可选事件，旧前端忽略即可。
- C15 规则 1（`final` 是唯一真相）在 16.2 继续适用。
- C15 规则 2（租户上下文跨线程重建）不受影响：stage 也走同一个 `SseEmitter`，在同一个虚拟线程里发。

## C17 · 深度分析图（Agent 工作流，阶段 11 起，ST11）

### 17.1 状态只有 JDK 类型，且节点只写自己的键

「深度分析」不是另一套问答，而是把既有八步（QU → 作用域 → 检索 → 装配 → 生成 → 校验）搬进一张图里跑。
状态是节点之间唯一的交换面，所以规则必须死：

| 规则 | 为什么 |
| --- | --- |
| 状态值只用 JDK 类型（String / 数字 / Boolean / List / Map） | LangGraph4j 默认用 `ObjectStreamStateSerializer`（JDK 序列化）落检查点；塞 Spring Bean 会在**第一次存档**时才炸 |
| 节点只写自己的键，返回的是「补丁」不是整份状态 | 状态靠通道合并（appender 追加 / base 覆盖），整份返回会把别人写的覆盖掉 |
| `question` 永不改写 | 原话要能让用户核对；改写只写进 `rewrittenQuery` |

键分四组：输入（question / scope* / conversationId / memoryText / 身份四键）、中间（queryType / companyCodes / yearFrom / yearTo / plan / subQuestions / hits / evidenceCount / insufficient / retryCount）、输出（answer / citationIssues / citeAttempts / decision / decisionNote / status / warnings）、诊断（runId）。

**身份四键（TENANT_ID / USER_ID / USERNAME / ROLES）不是业务状态**，是 ThreadLocal 的搬运工：节点跑在 LangGraph4j 自己的线程上，`TenantContext` 过不去，不搬就会在第一处查库抛
`UnauthorizedException: 缺少认证上下文`（2026-10-29 真跑时抓到，见 ST11 §17.5）。进入节点前 `TenantContext.set`、退出后 `clear`，这条由 `AnalysisGraph.node()` 统一包，节点自己不管。

### 17.2 图的形状（两张图，同一个节点集合）

```text
START → understand → plan ─┬─ DIRECT / DECOMPOSE ─▶ retrieve
                           └─ REFUSE ─────────────▶ respond_insufficient
retrieve → verify ─┬─ ENOUGH ──────────────▶ approve → answer
                   ├─ RETRY（retryCount<1）──▶ rewrite → retrieve
                   └─ INSUFFICIENT ─────────▶ respond_insufficient
answer → cite_check ─┬─ 通过 ────▶ END
                     └─ 不过且未重试 ─▶ answer（不再经过 approve）
```

```text
hitlGraph = fastGraph + interruptsBefore("approve")
```

**为什么中断点是 approve 而不是 answer**（2026-10-29 收尾修正，ST11 §19）：cite_check 不过会沿回边重跑 answer，
中断点若挂在 answer 上，**每重试一次就再弹一次审批**（真链路实测复杂问题批了两次）。approve 是纯透传节点，
只在 verify 通过后进入一次，所以「一次运行只批一次」；引用校验重试自动进行，不再打扰人。

三条硬规则：

1. `interruptsBefore` 是**编译期**配置，所以「要不要人批」只能编译期决定 → 两张图（`fastGraph()` / `hitlGraph()`），不能按请求切。
2. **中断不抛异常**：流会在 `answer` 之前停下，判据是 `compiledGraph.getState(cfg).nextNodeId()` 等于中断点 —— 别等 `GraphInterruptException`（那是节点内部主动中断的路径）。
3. 用了检查点就必须 `releaseThread(false)`：库默认 `true`，跑到 END 就把线程释放掉，之后 `getState` 抛 `Missing Checkpoint!`，刷新页面再也看不到这次运行。

### 17.3 检查点表由 Flyway 建（本仓库 schema 规则的唯一例外）

`LG4JThread` / `LG4JCheckpoint` 两张表是 LangGraph4j 的存储格式，**DLL 原文照抄**库自带脚本
（`langgraph4j-postgres-saver-1.9.7.jar!db/migration/v1.1__init.sql` → `V12__langgraph_checkpoint.sql`），运行时 `createTables(false)`。

- 为什么不交给库自建：本仓库「schema 只由 Flyway 管」；库自建会绕过版本历史，升级时也没法回滚。
- 为什么不手写 DDL：列名/索引是库的私有契约，升级就跟不上。
- 换来的代价：升级 LangGraph4j 时必须 diff 它的迁移脚本再补一个 `V*`。

这两张表**不带 tenant_id、不加 RLS**：它们是基础设施表（与 `flyway_schema_history` 同类），只由 owner 连接读写；
租户隔离靠 `agent_run.run_id = thread_name`（UUID 不可猜）+ 应用层归属校验（他人 run 一律 404）。

检查点连接**不能复用应用主池**：主池带 `SET ROLE finagent_app`，而 LG4J 表只授权给 owner；
给运行时角色授权又等于让它能读所有租户的检查点。所以单独一个不池化的 `DriverManagerDataSource`（8 节点约 80 ms）。

### 17.4 人批（HITL）三决定与五条硬规则

| 决定 | 含义 | 理由 |
| --- | --- | --- |
| APPROVE | 照计划生成 | 理由可空 |
| EDIT | 按意见改后再生成 | 理由**必填**（空 EDIT 等同 APPROVE，等于白停一次） |
| REJECT | 不生成 | 理由**必填**，要能解释为什么这次分析不该继续 |

1. `resume` 的入参（decision / decisionNote）**会合并进状态**，节点直接 `state.decision()` 读，不需要另存表。
2. 停下时写库：`agent_run.status=WAITING_APPROVAL`、`current_node` = **`approve`**、`plan_json` = 计划、`agent_run_step` 追加一行 SKIPPED「等待人工审批」。
3. **超时不自动通过**：超过 `finagent.agent.approval-timeout-minutes`（默认 30）→ FAILED(`approval_timeout`)，并让接口报错。自动放行等于把「人批」变成装饰。
4. 幂等：已 DONE / REJECTED 再 resume → 直接返回既有结果；RUNNING 时 resume → 400（还没停，没什么可批）。
5. **一次运行只批一次**：中断点挂在只走一次的 `approve` 节点上，`cite_check` 不过沿回边重跑 `answer` 时不再弹审批（ST11 §19）。`approve` 是控制流锚点，**不写进 `agent_run_step`、不发 `stage`**，时间线里只留 `approval` 的 SKIPPED（等待）+ OK（人工决定）两行。

### 17.5 事件协议：复用 C15/C16，只多一个 `approval`

| 事件 | 载荷 | 时机 |
| --- | --- | --- |
| `stage` | `{phase,label,detail}`，`phase` 就是**节点 id** | 每个业务节点跑完一次；`approve` 不发（人批已由 `approval` 表达） |
| `delta` | `{text}` | 只有 `answer` 节点会发 |
| `approval` | `{runId,status,plan,evidence,steps}` | 停在 `approve` 之前；**此时还没有答案**，且**每次运行只出现一次** |
| `final` | `{runId,status,answer,warnings,plan,evidence,steps,currentNode,decision,decisionNote,error}` | 结束（含拒答、驳回、失败） |
| `error` | `{code,message}` | 传输层错误 |

与问答链路的差别只有两条：**不发 `meta`**（证据在 `approval`/`final` 里给），**`final` 不是 `ChatResponse`**。
前端因此要自己合成一个 `ChatResponse` 才能复用气泡与证据面板（ST11 §17.3：`citations` 由 `evidence` 映射，
`bbox` 为空所以「原文」页签对 agent 轮次不可用 —— 不假装能点开）。

### 17.6 与 C12 / C15 / C16 的关系

- C12（会话与记忆）：`conversationId` / `memoryText` 进状态；图的节点**不写会话表**，落库仍由 `ChatService.finishTurn` 那一层负责（本期 agent 轮次不落 `conversation_message`，见 ST11 §17.4 已知限制）。
- C15（流式）：SSE 语法、`: ping` 心跳、`TenantContext` 跨线程重建全部照用。
- C16（首屏）：`stage` 的语义（只表达「正在做什么」、必须由真进入该段的代码发出）同样适用；agent 的 `stage` 更细，直接按节点发。

### 17.7 拒绝结论必须进控制流（2026-10-29 补，ST11 §18）

**事故**：问「五粮液 2025 年净利润」，`understand` 已经判出「公司不在作用域」并写下 `REFUSE_REASON`，但 `plan` 的条件边只判「问题是否为空」，于是图继续检索 —— 检索层拿到空 `companyCodes`（= 无公司约束），在唯一的东方财富语料里召回 8 条，生成出
「五粮液 2025 年净利润为 12,084,594,947.22 元」——**拿东方财富的数字回答五粮液**。

四条硬规则：

1. **判定结论必须变成控制流**：`REFUSE_REASON` 非空时，`plan` 与 `retrieve` 之后都必须直接去 `respond_insufficient`；`verify` 也要先看它，再判「证据够不够」。
2. **「没命中」与「不可答」必须分开**：`ScopeEmptyException`（一份都看不到）不能被吞成「检索没命中」。前者是权限/范围问题，重试无意义；后者才可能靠改写检索式补救。
3. **生成节点必须兜底**：`answer` 开头 `REFUSE_REASON` 非空 → 直接拒答，不调模型。边可以被将来新增的节点绕过，兜底不能。
4. **空 `companyCodes` 有两种含义**：用户没点名公司（可以无约束检索）与点名了但不在范围（必须拒答）。区分它们只能靠节点写下的原因标记，不能靠字段是否为空。

响应形态（两条链路必须同义）：

| 情形 | chat（`/api/chat/stream`） | agent（`/api/agent/runs/{id}/resume`） |
| --- | --- | --- |
| 没身份 | 401 | 401（同一个过滤器） |
| 一份文档都看不到 | 409 `SCOPE_EMPTY` | `error` 事件 `SCOPE_EMPTY`（SSE 头已发，改不了状态码） |
| 点名主体不在范围 | 200 + 拒答文案 + `company_unresolved` | `final` + `status=REJECTED` + `company_unresolved` |
| 检索到但证据不足 | 200 + `evidence_insufficient` | `final` + `status=REJECTED` + `evidence_insufficient` |

拒答文案对「没有这份文档」与「没被授权」必须一致（C11 不确认存在性）：统一说「不在当前可检索范围内」。

## C18 · 唯一执行路径：所有问答都走图（阶段 14 起，ST14）

阶段 11 之前有两条链路：直链（`ChatService`）与图（`LangGraph4j`）。阶段 14 把直链删掉，图成为唯一引擎。

### 18.1 端点与实现的对应

| 端点 | 实现 | 说明 |
| --- | --- | --- |
| `POST /api/chat` | `AgentStreamService.ask` → 图（`hitl=false`） | 同步语义：一次返回标准 `ChatResponse` |
| `POST /api/chat/stream` | `AgentStreamService.startStream` → 图 | 歧义时停在 `approve` 前发 `approval` |
| `POST /api/agent/runs/{id}/resume` | `AgentStreamService.resumeStream` | 聊天流与人批共用这一个续跑入口 |
| `GET /api/agent/runs/{id}` | `AgentRunService.view` | 刷新页面 / 排障 |

`finagent.agent.enabled` 不再是入口闸门：图是唯一引擎，该配置项保留只为兼容旧配置文件。

### 18.1.1 2026-10-30：删掉冗余的开流端点

`POST /api/agent/runs/stream` 在阶段 14 之后与 `POST /api/chat/stream` 完全等价（都调 `AgentStreamService.startStream`，
事件契约都出自 `ChatStreamEvent`），前端从未调用（`startAgent` 无引用），已删除；
前端 `src/api/agent.ts` 只剩 `resumeAgent` 与 `getAgentRun`。

顺带把两个 controller 里各写一遍的 SSE 外壳抽成 `com.finagent.chat.SseStreamTemplate`（建 emitter / 心跳 / 换线程 / 重建 `TenantContext` / 三类异常映射），
端点专属的异常由调用方在 body 里自己 catch（agent 的 `AgentRunNotFoundException` → `AGENT_RUN_NOT_FOUND` 事件）。
**不做「异常类型 → 错误码」映射表**：一张表会把两个端点的差异藏起来。

### 18.2 三条硬规则

1. **一轮只收尾一次**：任何路径跑完都必须经过 `TurnRecorder.record`（消息 → 上下文 → 记忆命令 → 摘要）。节点内不写会话表，收尾不参与检索。
2. **结果不进状态**：`AnswerResult` / `Citation` / `Fact` 不是 `Serializable`，进 `AnalysisState` 会在「停下等审批」写检查点那一刻炸。它们走 `AnswerStreamBridge`（按 runId 的旁路），生命周期是一次请求。
3. **空作用域仍是 409**：图内部把它写成 `scope_empty` + `REJECTED`，同步接口必须再翻回 HTTP 409；流式接口发 `error` 事件（SSE 头已发，改不了状态码）。这是 C11「fail loud」在图里的延续。

### 18.3 `final` 的载荷

`final` 是**运行视图**，不是 `ChatResponse`：

~~~text
{ runId, status, answer, warnings, plan, evidence, steps, currentNode, decision, decisionNote, error,
  response: ChatResponse | null }
~~~

`response` 是标准 `ChatResponse`（`sufficient/answer/facts/citations/confidence/note/scope/warnings/trace/conversationId/messageId`），与同步接口逐字段同源（同一个 `synthesize`）。

### 18.4 `stage.phase` 取值（替换 C16 的四阶段）

`understand` / `plan` / `retrieve` / `verify` / `rewrite` / `answer` / `cite_check` / `respond_insufficient`。

- `understand` 在**开跑前**先发一条（首屏不能等一次 QU，约 4 秒），节点完成时不重发。
- `approve` 不发 stage（它由 `approval` 事件表达），也不写 `agent_run_step`（C17 §17.4）。
- `verify` 完成后发 `meta`（证据先行，沿用 C16 §16.2 的语义）。

### 18.5 与其它契约的关系

- **C15 / C16**：SSE 语法、心跳、`: ping`、`stage` 只能表达「正在做什么」全部照用；C16 的四个中文阶段名被 18.4 的节点 id 取代。
- **C17**：图的形状、检查点、HITL 三决定、「拒绝结论进控制流」不变。
- **C12**：多轮仍靠会话表 + 记忆装配；图是一次运行，不做图内重入。
- **C11**：401 / 409 / 404 语义不变；空作用域与越权仍是两种响应。

## C19 · 多路检索：子问题必须自包含，整句永远占一路（阶段 15 起，ST15）

> 触发这次契约的原因见 `docs/阶段15-多路检索证据覆盖报告.md`：拆出的碎片子问题把 2025 年主表挤出了上下文，
> 模型只能在「2025 | 2024」两列并排的表里挑列，答成了 2024 年的数。

### 19.1 三条规则

1. **子问题必须能独立回答。** 复杂问题按连接词切开后，每个片段要剥掉句首连接词（`并且/并/结合/同时/以及/还有/且/而且/另外/再/和/与/及/、/，/；/;`），
   再补上「公司名字面 + 年份」前缀。片段里已经出现的不重复补。
   - 前缀来源是 **QU 的 `companyMentions`（字面名，如「东方财富」）**，不是 `companyCodes` —— 把 6 位代码拼进检索式会把向量拉向无关方向。
   - 没有字面名（规则路由路径）时只补年份；年份也抽不到时与改动前等价。
2. **整句永远占第一路。** 有子问题时，检索路数 = 整句 + 子问题（整句在最前）。拆解是「多路召回」，不是「只召回碎片」。
   - 检索轨迹（`RetrievalTrace`）取第一路，即整句那一次（`AnswerStreamBridge` 用 `putIfAbsent`）。
3. **同一块在多路里出现，保留最高分**，不是先到先得。先到先得会让块带着某一路的低分一路走到装配，名次被低估。

### 19.2 为什么不做「每路配额」

配额（每路保底 top-k 进上下文）解决的是「某一路一条都进不去」；本次是「某一路的第 4 名（主表 0.523）进不去」——
按分数排队被高分噪声挤掉，配额无效（诊断实验 D：整句 + 3 个原始片段，主表仍然不在）。
真正的修法是让片段本身可检索（规则 1），把主表的 rerank 从 0.523 抬到 0.572。

### 19.3 与其它契约的关系

- **C1**：embedding_text 的组成不变；本条只改「送进检索的那个 query 字符串」。
- **C6**：上下文仍然只放原文，不摘要、不改写。
- **C17**：状态新增键 `companyMentions`（understand 写、plan 读），符合「节点只写自己负责的键」。
- **C18**：改动对 SSE 事件协议无影响；`plan` 的 `detail.subQuestions` 数量不变（仍是 3），但内容变成自包含片段。

### 19.4 `retrieve` 阶段事件的 `detail.queries` 口径

改成**实际检索路数** = 整句 1 路 + 子问题 N 路（未拆解时为 1）。改动前它是「子问题数」，
现在整句固定占一路，若继续只报子问题数就会少报一次（3 子问题实际发 4 次检索）。
前端未消费该字段（已 grep 确认），只影响排障时看日志/事件的人。

## C20 · 答案骨架、答案形态与覆盖检查（阶段 16 起，ST16）

> 背景见 [阶段16-答案质量报告.md](阶段16-答案质量报告.md)：同一份证据、同一个问题，
> 改动前是一句话把结论/数据/归因挤在一起，改动后是「结论 / 数据 / 归因 / 口径」四段。
> 20.2 / 20.3（事实三态）在 Task 2 落地，本文件先记规则。

### 20.1 四段骨架与「按形态取舍」

| 段 | 写什么 | 什么时候写 |
| --- | --- | --- |
| 结论 | 一句话给答案 + 关键数字 + 引用 | 永远写 |
| 数据 | 逐年/逐项并列，数字**逐字照抄证据**（单位精度不变） | 有多个数字时写 |
| 归因 | 按业务线或科目拆开，每条落在证据里出现过的经营指标（交易额、保有规模、销售额、手续费及佣金净收入、利息净收入、成本构成） | 形态含 `ATTRIBUTION` 时写 |
| 口径与缺口 | 单位、期间、口径（合并/母公司），以及本次证据里不可得的项 | 有歧义或缺口时写 |

**没有对应内容就整段省略**：只取一个数时只有「结论：」一段，禁止为了凑结构编归因。

### 20.2 形态判定（`AnswerShape`）

- 三种形态：`ATTRIBUTION`（归因）/ `BREAKDOWN`（结构）/ `COMPARISON`（对比）。
- 判定是**纯词表**，不调模型：归因 = 原因/为什么/为何/驱动/因素/归因/得益于/受益于/拉动/带动/主因；
  结构 = 结构/构成/占比/分行业/分产品/分地区/明细/拆开/板块；对比 = 对比/相比/同比/环比/较/变化/差异。
- `yearRange = [2024, 2025]`（跨年）时自动补一个 `COMPARISON`——问题里不一定写「对比」两个字。
- **故意不收录**「增长 / 下降」（会把纯取数题判成归因题）与「贡献」（会把「各板块贡献度」判成结构题）。
- 判定在 plan 节点写入状态 `answerShapes`（字符串列表，C17 要求状态只放 JDK 类型）；
  `AnswerService` 用同一个纯函数再算一次，不读状态（避免为传状态改方法签名）。

### 20.3 覆盖检查（verify 的第 4 条防线）

- 只在 `形态含 ATTRIBUTION` 且 `retryCount == 0` 且前两道防线（hits 数、指标名）已通过时判。
- 判据（任一成立即算覆盖）：命中块 `sectionPath` 含驱动章节（管理层讨论 / 主营业务分析 / 行业情况 / 经营情况），
  或 `snippet` 含驱动词（交易额、保有、销售额、手续费及佣金、利息净收入、同比增减、主要原因）。
- 不覆盖 → `insufficient = true` + `warnings += "coverage_missing:attribution"`，触发一次 rewrite（追加「原因 驱动 交易额 保有规模 手续费」）。
- **改写后不再判**：缺口应由答案第 ④ 段写明，不能升级成整题拒答。

### 20.4 排版规则（当前阶段）

- answer 字段内部段落之间空一行，每段以「结论：」「数据：」「归因：」「口径：」开头。
- **不用 markdown 标题符号（`#`）**：前端渲染器在 Task 4 才支持标题，现在写 `#` 会显示成字面量（C22 记渲染子集）。
- 多期数字用「2025 年 / 2024 年」行首并列，禁止为了排版重新四舍五入（规则 1 仍然有效，换算在 C21）。

### 20.5 与其它契约的关系

- **C6**：骨架只约束「怎么写」，仍然只用证据原文，不摘要不改写。
- **C7**：正文引用必须带 `[E编号]` 且可点；骨架不改变引用规则。
- **C17**：新增状态键 `answerShapes`，plan 写、verify/rewrite 读。
- **C19**：归因段的证据来源依赖「整句 + 自包含子问题」多路召回。
- **C21**：换算与派生指标（Task 2）；**C22** 渲染子集与依赖约束（Task 4）。

## C21 · 换算与派生指标口径（阶段 16 起，ST16 Task 2）

### 21.1 四条硬规则

| 规则 | 内容 |
| --- | --- |
| 21.1 | 换算只由 `UnitConverter` 做（元 → 万元/亿元，`BigDecimal` + HALF_UP + 2 位），并且**保留原值**（`Fact` 里 value 是原值，display 才是换算值） |
| 21.2 | 派生指标只允许 `MetricFormula` 登记的五条公式：同比增长率、结构占比、占比变动、收入贡献度、增长额；新增公式必须同时加测试与口径说明 |
| 21.3 | 分母为 0、缺一期、合计增量为 0、与披露值冲突 → **不出 COMPUTED**，记 `compute_skipped:原因` / `compute_conflict:指标` |
| 21.4 | 比率 2 位小数 + `%`；占比变动 2 位小数 + `个百分点`（不要写 `%`） |

### 21.2 事实的三种来源（`origin` 字段）

| origin | 谁给的 | 什么时候出现 |
| --- | --- | --- |
| `REPORTED` | 证据原文直给 | 表格行解析出的金额 / 披露的同比 / 披露的占比 |
| `COMPUTED` | 系统按公式算 | `compute` 节点产出，带 `formula` 与 `inputs` |
| `EXTRACTED` | 后端兜底抽取 | 模型一条 `facts` 都没给时用，并记 `facts_backfilled` |

**为什么必须区分**：用户看到「38.46%」时要能知道这是报告里印的，还是系统算的；
前者可以被原文复核，后者只能被公式复核。混在一起，就等于把「可审计」变成了「看起来可审计」。

### 21.3 与披露值冲突时披露优先

算出来的值与证据里披露的值相差 > 0.011 时，**放弃计算值**并记 `compute_conflict:*`。
理由：同一段提示词里同时出现 41.00% 与 38.46%，模型必然挑一个，而它挑错了没人能发现。

### 21.4 提示词里的两段清单与数字白名单

| 段 | 写法 | 用途 |
| --- | --- | --- |
| 【已报事实】 | `[F1] 营业总收入 / 2025 = 16,067,741,039.51元（≈160.68 亿元）〔E2〕` | 让模型照抄，不许自己换算 |
| 【已计算事实】 | `[F9] 营业总收入同比增长率 / 2025vs2024 = 38.46%（= 公式；系统计算）` | 让模型直接引用，不许自己再算 |

- 行首 `[F…]` **只是清单序号，不是引用编号**：正文里禁止出现，后处理一律删除（`AnswerService.FACT_MARK`）；
- 【已报事实】行末的 `〔E4〕` 才是它的出处，正文引用要写 `[E4]`；
- 所有计算值与换算值的数字串进 `FactPack.allowedValues` 白名单 —— 落地校验时白名单里的数字算「已核对」，
  否则系统算出来的每个比率都会被判成幻觉（这是 2026-10-30 实测踩到的）。

### 21.5 事实卡的配额

- 对外 `facts` 最多 `MAX_FACTS=8` 条；其中 COMPUTED 最多占 `MAX_COMPUTED_IN_ANSWER=5` 格，其余留给 REPORTED；
- 顺序：COMPUTED 在前（用户最想核对的是新算出来的比率），REPORTED 在后；同一「指标 + 期间」只留一条。

### 21.6 与 C6 / C7 / C20 的关系

- C6 说「上下文只放原文」—— 事实层不改变这一点：事实是从原文表格里抽的，不是外部知识；
- C7 说「引用必须能反解析回真实行」—— 事实的 `evidence` 记的是证据号，最终仍映射到 chunk；
- C20 的四段骨架里，第 ② 段（数据）优先用 REPORTED，第 ③ 段（归因）优先用 COMPUTED 的贡献度与占比变动。

## C22 · 答案渲染子集与依赖约束（阶段 16 起，ST16 Task 4）

### 22.1 后端只输出这五类结构

| 语法 | 用途 | 限制 |
| --- | --- | --- |
| `### 小标题` | 段内分项（如「### 分行业」） | 最多 6 个；**不允许 `#` / `##`**，四段骨架仍用中文标签 |
| 段落 | 正文 | 空行分隔，不加行首缩进 |
| `- 项` / `1. 项` | 列表 | 单层（本期的答案不需要嵌套列表） |
| 管道表格 | 多期 / 多分项并列 | ≤6 列、≤12 行；表头行 + 分隔行 + 数据行；单元格禁止换行与嵌套；竖线写 `\|` |
| `[E3]` | 引用 | 不变（C7） |

### 22.2 前端禁止 v-html，也禁止擅自引 markdown 库

`answer.ts` 只产出**数据结构**（`Block` / `Segment`），由 Vue 模板渲染成文本节点，结构上不可能 XSS。
改 `v-html` 等于把「PDF 原文里的 `<img onerror>`」变成可执行脚本，而且 chip 的点击要重新用事件委托做一遍。

### 22.3 解析失败一律降级，不抛异常、不出空白块

| 输入 | 处理 |
| --- | --- |
| 只有表头、没有分隔行 | 当普通段落 |
| 数据行列数与表头不一致 | 多的丢、少的补空 |
| 未知语法（`#` 一级标题、代码块、HTML） | 按纯文本保留 |

### 22.4 换库的触发条件（命中即换 `markdown-it` + `DOMPurify`）

1. 需要三层以上嵌套列表 / 行内代码 / 链接 / 引用块 / 脚注；
2. `answer.ts` 超过 300 行（本期结束时约 210 行）；
3. 一个阶段内新增块类型 ≥3 种；
4. 出现 2 次以上「渲染 bug 但解析逻辑看不出问题」。

### 22.5 与 C20 / C7 的关系

- C20 的四段骨架用「结论：」「数据：」「归因：」「口径：」标签，**不改成标题** —— 覆盖检查与前端 chip 定位都认这个标签；
- C7 的引用 chip 在表格单元格里同样可点：表格单元格走的是同一套 `AnswerSegments` 内联解析。

## C23 · 复制为 Markdown 的口径（阶段 16 起，ST16 Task 4）

### 23.1 基底是后端原文，不从渲染块反序列化

```
answer 原文 → 引用编号归一 → 空白归一 → 追加引用附录 → 剪贴板
```

为什么不走 `blocks → markdown`：表格列结构、模型写的细微空白、以及我们特意降级掉的语法都会在往返里丢失，
唯一收益是「修正不合规 markdown」，而那条路已经有提示词约束（C22）与解析降级兜着。

### 23.2 编号：归一化 + 文末附录，不重排

| 原文写法 | 复制时 |
| --- | --- |
| `[E5]` / `[ E5 ]` / `［E5］` | 统一 `[E5]` |
| 编号 > `citations.length` | 删除（与页面角标一致，不制造指向不存在证据的编号） |
| 多个编号 | **保持原编号**，不重排 |

不重排的理由：服务端已经按首次出现顺序重排过（C7），前端再排一次会和页面上显示的角标对不上 ——
用户看到页面上是 E5，复制出去变成 E1，附录还指向第 5 条，这才是真正的错位。

附录格式（只列正文用到的，按编号升序）：

```
---

### 引用

- [E1] 东方财富2025年年度报告 · 第 11 页 · 第三节 管理层讨论与分析 § 一、经营情况讨论与分析（chunk 7237）
```

附录标题用 `###`（与答案小标题同级），定位信息只写文件名 / 页码 / 章节 / chunk id。

### 23.3 空白规则

统一 `\n`；行尾空格全去；连续空行压到 1；表格前后各保证 1 个空行（模型漏写时兜底）。

### 23.4 交互

| 状态 | 行为 |
| --- | --- |
| 流式生成中 | 按钮禁用 |
| 复制成功 | 「已复制」2 秒后复位，`aria-live` 播报 |
| 剪贴板不可用（http / 权限拒绝） | 降级 `document.execCommand('copy')`，仍失败提示手动选择 |
| 拒答 / 空答案 | 按钮不渲染 |

### 23.5 与 C7 的关系（一条作废）

C7 里「复制后丢括号不是缺陷」的表述**作废**：复制路径必须产出合法 markdown，编号必须在附录里有条目。

## C24 · 检索车道与年份覆盖（阶段 16 起，ST16 Task 3）

### 24.1 一次问答的检索是「一组车道」，不是「一次查询」

| 车道 id | 何时开 | 过滤 | topK |
| --- | --- | --- | --- |
| `full` | 永远第一路 | 无 | 检索器默认 |
| `sub:N` | 问题被拆成子问题（N 从 0 起，空片段跳过） | 无 | 默认 |
| `attr` | 答案形态含 `ATTRIBUTION` 或 `BREAKDOWN` | `sectionPathPrefix="第三节"` | 4 |
| `year:YYYY` | 年份数 2~3 | `docYear=YYYY` | 4（补跑 8） |

### 24.2 四条硬规则

1. **整句永远占一路**（C19 的延续）：车道顺序固定 `full` → `sub:N` → `attr` → `year:YYYY`；
2. **合并按 chunkId 取最高分**，不是先到先得 —— `attr` 车道的低分不能覆盖 `full` 的高分；
3. **年份数 > 3 不开车道**，记 `year_range_too_wide`，退化为只有 `full`。上限 `MAX_YEAR_LANES=3` 是成本约束：每多一年 = 多一次 embedding + rerank + 一次 SQL；
4. **缺年份先补跑、再告警、不拒答**：补跑一次（topK 4 → 8），补到只留 `year_lane_retried`；仍缺记 `year_coverage_missing:YYYY`，**不影响 `sufficient`**。

### 24.3 「缺一年」的两种来源，别混

| 来源 | 何时记 | 记在哪 |
| --- | --- | --- |
| 作用域里根本没有该年文档 | `plan` 阶段就知道 | `year_coverage_missing:YYYY`（不建车道） |
| 有文档但检索没命中 | `retrieve` 阶段补跑后仍空 | `year_coverage_missing:YYYY`（建了车道） |

两种都只进 `warnings`，都**不拒答** —— 少一年不等于答不了，答案第 ④ 段「口径与缺口」正好写它。
判「有没有命中」用 `scope.documents()` 的 docId→docYear 映射，不要用问题里的年份直接比。

### 24.4 `stage.retrieve` 的字段口径

| 键 | 含义 |
| --- | --- |
| `hits` | 合并去重后的候选数 |
| `queries` | **实际检索路数** = `lanes.size()`；没有车道（老路径）时按 1 算 |
| `lanes` | 车道 id 列表，按执行顺序 |

前端不消费 `lanes`，它只用于排障与评测。

### 24.5 与 C19 / C20 / C21 的关系

- C19 说「整句 + 子问题都要发」—— C24 把「发几次」显式化成车道；
- C20 的答案形态决定 `attr` 车道开不开，形态判定仍然只在 `AnswerShape.detect` 一处；
- C21 说「比率只由系统算」—— 24.2 的补跑与合并只影响拿到哪些证据，不产生任何数字。

## C26 · 引用角标与悬浮原文（阶段 18 起，ST18 需求 5）

### 26.1 显示口径

正文里的引用统一渲染为**纯数字角标**（`1`、`2`…），不再显示 `E1`。理由：`E1` 读起来像编号系统，而用户要的是「第 1 条证据」。数字角标 15×15px、`--accent-soft` 底、`--accent` 字、圆角 3px，不参与行高（`vertical-align: 1.5px`）。

后端产出的仍是 `[E1]` 形式（提示词与 `AnswerService.CITE_MARK` 不变）；数字化只发生在渲染层 `AnswerSegments.vue` → `CiteChip.vue`。

### 26.2 悬浮卡的数据来源

新增 `GET /api/chunks/{id}`（`DocumentQueryController.chunk`）：

- 返回 `{id, documentId, docTitle, sectionPath, title, chunkType, pageStart, pageEnd, tokenCount, caption, unit, content}`；
- 走 `ScopeAuthorizer.filterReadable`，**不可读与不存在都返回 404 `CHUNK_NOT_FOUND`**（403 等于承认「这个块存在」）；
- 不校验 `status`/`chunk_version`：引用指向的块就在当前 ACTIVE 版本里，版本切换后返回旧行也比「凭空少一条」好。

为什么不把正文塞进 `citations`：一轮只用 2~5 条引用，但证据包要发给模型；引用带全长正文会让每轮响应多几十 KB，而用户可能一次都不悬停。

### 26.3 前端行为

- 号码 → chunkId 的映射由 `MessageBubble` 用 `provide(CITE_SOURCE, computed(...))` 下发（`citations[i].childChunkId`），不走 props：AnswerText → 表格单元格 → AnswerSegments → CiteChip 有四层；
- 悬停 200ms 才发请求（防手快扫过），离开有 160ms 宽限（否则移向卡片就消失）；卡片 `Teleport` 到 body + `position: fixed`（正文容器有 overflow，absolute 会被裁）；
- 会话级 `Map<chunkId, ChunkDetail>` 缓存，同一块只取一次；
- **取不到正文不影响点击**：`dead` 只等于「编号越界」，`chunkId` 缺失只是没有悬浮卡。这一条是被 `AnswerText.spec.ts` 抓出来的（第一版把两者绑在一起，组件在无 provide 的测试里点不动）。

### 26.4 点击行为不变

点击角标 → 打开右侧证据面板并定位到该条的原文页（C6/C7）。悬浮卡只做「先看一眼」，不替代原文页。

### 26.5 与其它契约的关系

- **C6/C7**：引用编号与正文重排逻辑不变，本契约只改显示与悬浮；
- **C22**：渲染子集仍只认 `[E编号]` 作为输入格式，数字角标是渲染产物，不改变后端输出；
- **C23**：复制为 Markdown 时仍输出 `[E3]`（可移植），不输出裸数字 —— 裸数字粘到飞书里没有附录可查。

## C27 · 管理端边界（阶段 18 起，ST18 需求 11）

### 27.1 谁能进

只有 `ADMIN`。守卫在 `AdminController.requireAdmin()`，每个端点第一行：

- 没有身份 → **401**（该重新登录）；
- 有身份但不是 ADMIN → **403 `ADMIN_REQUIRED`**（该换账号，不该把人踢回登录页）；
- 前端 `AppRail` 按 `session.user.roles` 隐藏「权限」入口，直接输 URL 时页面显示 403 说明。

### 27.2 能改什么

| 端点 | 作用 | 不能做 |
| --- | --- | --- |
| `GET /api/admin/overview` | 四个计数（用户 / 角色 / 文档 / 授权） | — |
| `GET/POST /api/admin/users` | 分页列表（`q` 搜账号或姓名、`status` 过滤、带 `docCount`）/ 建号（用户名 3~32 位、密码 ≥8 位、角色必须存在） | 不能建到别的租户 |
| `PUT /api/admin/users/{id}` | 改显示名、启停、换角色 | 不能改密码、不能删用户 |
| `GET /api/admin/users/{id}/documents` | 该用户**实际可读**的文档（分页，每行带来源 `ADMIN/OWNER/USER/ROLE`） | — |
| `GET /api/admin/roles` | 角色列表 + 成员数 + 可读文档数 + `system` 标记 | — |
| `POST /api/admin/roles` | 新建**自定义角色**（`code` 2~32 位、大写字母开头、只含大写字母/数字/下划线、同租户唯一；`name` ≤64 字） | 不能指定 `is_system` |
| `PUT /api/admin/roles/{id}` | 改显示名（内置角色也允许） | 不能改 `code`（授权、审计、代码都按 code 认） |
| `DELETE /api/admin/roles/{id}` | 删自定义角色，连带清掉它的 `resource_grant` | 系统内置角色 400；还有成员 409 `ROLE_IN_USE` |
| `GET /api/admin/roles/{id}/members` | 该角色成员（分页） | — |
| `GET /api/admin/roles/{id}/documents` | 该角色可读文档（授权按公司展开成文档；ADMIN 角色为 `ALL`） | — |
| `GET /api/admin/grants` | 授权记录（分页 + `q` 搜主体名/文档名） | — |
| `GET /api/admin/documents` | 授权选择器（分页 + 标题/公司名搜索） | — |
| `POST /api/admin/grants` | `ROLE`/`USER` × `DOCUMENT`/`COMPANY` 的 READ 授权，授权前校验对象存在 | 见 27.5：TENANT 文档不接受单份授权 |
| `DELETE /api/admin/grants/{id}` | 撤销授权 | — |

分页口径：`page` 从 1 起（<1 归 1），`size` 默认 20、上限 100（`MAX_PAGE_SIZE`），响应统一 `{items,total,page,size}`。

不删用户：会话、`document.owner_user_id`、`resource_grant.granted_by` 都挂着外键，物理删会把这些历史一起打断；停用（`DISABLED`）已经能让 `AuthenticationFilter` 拒绝登录与 token 校验。

### 27.3 为什么新增 V14 / V15 授权

V9 把 `tenant / app_user / role / user_role / resource_grant` 对运行时角色 `finagent_app` 收成了**只读**，理由是这五张表没有 RLS，SQL 注入就能读走 `api_token_hash`。

管理端点需要写，但**不恢复** V8 的 `GRANT ... ON ALL TABLES`，而是按用途精确开（`V14__admin_write_grants.sql`、`V15__admin_role_write_grants.sql`）：

- `app_user`：INSERT、UPDATE（**不含 DELETE**）；
- `user_role`、`resource_grant`：INSERT、DELETE；
- `role`：INSERT、UPDATE、DELETE（角色是纯数据，删除不连带成员）；
- 三个 sequence 的 USAGE / SELECT（否则 `nextval` 会让 INSERT 失败）。

漏掉 V15 的现象是建角色报 500，日志里 `permission denied for table role` —— 与阶段 18 首版建账号时报 `permission denied for table app_user` 是同一类问题。

### 27.4 与其它契约的关系

- **C11**：身份仍只来自 Bearer token（`AuthenticationFilter`），管理端点读 `TenantContext`，不接受请求体里的租户；
- **C13**：租户是硬边界，管理员不是跨租户超管；
- **C26**：`/api/chunks/{id}` 走的是 `ScopeAuthorizer`，与本契约的管理权限是两套判断，不要混用。

### 27.5 全租户文档只能按公司授权

`AclScopeAuthorizer` 判定「这份文档能不能看」时分两种资源：

- 文档 `visibility = 'TENANT'` → 只查 `resource_type='COMPANY'` 且 `resource_id = d.company_id`；
- 其它文档（私有等）→ 查 `resource_type='DOCUMENT'` 且 `resource_id = d.id`。

所以「给某个角色授某一份 TENANT 文档」在检索侧**什么都不改变**——授权接口返回 201，用户却还是看不到，属于静默无效。

处理方式：`AdminController.createGrant` 在 `resourceType='DOCUMENT'` 时先读该文档的 `visibility`，若是 `TENANT` 直接 **400**：

> 该文档是全租户可见，单份授权不会生效；请改为对所属公司授权（resourceType=COMPANY）

前端同步：授权弹窗里选中 TENANT 文档时默认「整家公司」，并把「仅这一份文档」置灰，下面一行说明原因。

### 27.6 「能看哪些文档」必须与检索同源

管理页上「这个用户能看几份、分别是哪几份」如果自己写一套 SQL，就会和检索侧的判定慢慢漂移（管理页说有 5 份、实际检索只能召回 2 份）。

因此 `AdminRepository.VISIBLE_TO_USER` 只写一段 SQL，`searchUsers` 的 `doc_count` 子查询和 `documentsOfUser` 共用它，四档判定与 `AclScopeAuthorizer` 一一对应：

| 来源 | 条件 |
| --- | --- |
| `ADMIN` | 该用户是管理员 → 全租户文档 |
| `OWNER` | `d.visibility='PRIVATE' AND d.owner_user_id = 该用户` |
| `USER` | `resource_grant` 直授给该用户（`permission IN ('READ','READ_WRITE')`、未过期） |
| `ROLE` | 授权给该用户所属角色（经 `user_role`） |

`AdminAccessDbTest` 用真库断言「管理页列出的文档集合 == `new AclScopeAuthorizer(jdbc).filterReadable(allDocs)` 的结果」，改任一处的 SQL 都会红。

### 27.7 授权前先校验对象存在

`POST /api/admin/grants` 会先验证主体（`roleExists`/`userExists`）与资源（`documentExists`/`companyExists`），不存在就 400。理由：`resource_grant` 只有 `subject_id`/`resource_id` 两个裸列（`subject_type`/`resource_type` 决定去哪张表查），数据库层没有外键能兜住「角色 5 不存在」，悬空授权会安静地留在表里，撤销页面上还显示成一条正常记录。

### 27.8 角色为什么分内置与自定义

`role.is_system = true` 的三个（`ADMIN` / `ANALYST` / `VIEWER`）由 V11 种子数据写入，是代码的一部分：

- `ADMIN` 被 `CurrentUser.isAdmin()` 与 `AclScopeAuthorizer` 按 **code** 识别（不看 id），删掉或改 code 会让管理员判定失效；
- 所以内置角色的 `code` 与存在性由迁移保证，接口只允许改 `name`，删除一律 400。

自定义角色（`is_system = false`）是纯数据：**角色本身不带任何权限**，能力完全来自「角色 → 文档」的授权记录，与内置角色走同一套判定。由此两条管理侧规则：

- 删角色前必须没有成员（否则成员会安静地失去全部文档权限），接口返回 409 `ROLE_IN_USE`；
- 删角色时连带删除 `resource_grant`（该表只存裸 `subject_id`，没有外键能级联），在 `AdminRepository.deleteRoleWithGrants` 的同一事务里完成。

## C28 · 解析入库进度的口径（阶段 18 需求 2）

演示时用户第一句就问过「我传完了吗，卡在哪」，而当时页面只有四个状态词。
进度条的价值不在于精确，而在于**让人相信系统还在动**。由此定下口径：宁可是粗的阶段进度，
也不要一个会和事实矛盾的假精确数字。

### 28.1 是「阶段检查点」，不是「页级百分比」

`document.parse_progress` 记录的是链路上真实存在的检查点，不是「已解析页数 / 总页数」。

原因：Docling 的转换是一次阻塞调用，`document-parser-service` 在作业完成前拿不到任何页级回调
（`pages_parsed` 只在完成时赋值）。硬凑页级进度只能靠「已耗时 / 预估耗时」这类外推，
一旦文档排版复杂就会停在 60% 二十分钟 —— 那比没有进度更伤信任。

检查点表（数值是契约，前端文案与后端常量必须一致）：

| 值 | 阶段 | 触发点 |
| --- | --- | --- |
| 2 | 排队中 | 上传接口投递 `document.parse` 之后 |
| 8 | 提交解析作业 | 调解析服务 `POST /jobs` 之前 |
| 12 | 解析中 | `markRunning` 之后（最久的一段） |
| 45 | 解析完成 | 产物落 COS、`markDone` + `backfillPeriod` 之后 |
| 50 | 切块中 | 调 `ReindexService.reindex` 之前 |
| 55 | 切块完成 | `ChunkWriter` 第 4 步之前 |
| 55~95 | 向量化 x/y | 每个 embedding 批次回调，按**条数**插值 |
| 100 | 已完成 | chunk 版本原子切换成功之后 |

### 28.2 三条硬规则

1. **只增不减**：`GREATEST(parse_progress, ?)`；阶段文案用 `CASE WHEN ? >= parse_progress`
   同一条语句写，避免「60% + 切块中」的错配。重试、恢复、回退阶段都不会让进度条倒退。
2. **进度写库失败不能冒泡**：`DocumentProgress.step` 吞异常只记 warn。进度是观测不是状态：
   文档已经入库、只是百分比没写进去，绝不能因此把文档标成 FAILED。
3. **100 与「可检索」同时成立**：100 只在 `persistAndSwitch` 返回之后写。
   因此「进度 100%」与「active_chunk_version 指向新版本」是同一个时间点，不会出现
   「显示完成但检索不到」。

### 28.3 与 `parse_status` 的关系（为什么两个字段都要）

`parse_status = DONE` 只表示**产物可读**；切块 + 向量化仍在进行时状态就已经是 DONE、进度却只有 55%。
所以：

- 前端轮询判据是 `parseProgress < 100 && parseStatus !== 'FAILED'`，**不能**用 `parseStatus`；
- 失败时 `markFailed` 把阶段文案写成「失败」，进度**保留最后值**（55% + 失败，比 0% + 失败更能说明卡在哪）；
- 可检索性仍只由 `active_chunk_version` 决定（C4），进度不参与任何检索判定。

### 28.4 与 C1 / C4 / C7 / C26 的关系

- 与 **C4**：进度与「哪些块可被检索」无关；C4 的「只读 active version 的 ACTIVE 行」不因进度改变。
- 与 **C1/C7**：切块与嵌入的内容口径不变，`embedding_text_hash` 仍按 C1 计算，进度只是旁路观测。
- 与 **C26**：引用悬浮卡取的是 chunk 正文，本契约只管文档级进度，两者不交叉。

## C29 · 入库执行记录的口径（阶段 19）

C28 回答「现在到哪一步了」，本契约回答「这一趟到底发生了什么」：一次入库被拆成固定模板的若干步，每步都有状态、耗时、附注，失败时能看出卡在哪一步、重试过几次。

### 29.1 两张表的分工

| 表 | 一行代表 | 关键列 |
| --- | --- | --- |
| `document_ingest_run` | **一次入库尝试**（一个 attempt，横跨 HTTP/MQ/CLI 全链路） | `attempt`、`flow`（PARSE/REINDEX/RESUME）、`total_steps`、`current_step`、`status`（RUNNING/DONE/FAILED）、`summary_json`、`error` |
| `document_ingest_step` | **模板里的一个步骤** | `seq`、`step`（枚举名）、`status`（RUNNING/OK/FAILED/SKIPPED，接口补的 PENDING 不落库）、`detail`、`retry`、`duration_ms` |

`UNIQUE(document_id, attempt)` 与 `UNIQUE(run_id, seq)` 是两条结构事实，规则都从它们推出来。

### 29.2 四条硬规则

1. **步数由模板决定，不由行数决定**。`flow.totalSteps()` 是常量（PARSE/RESUME 8、REINDEX 4），前端「第 N/8 步」直接用它；心跳、重试、跳过都不会让分母漂移。
2. **一步一行：重跑复用原行**。`beginStep` 是 `INSERT … ON CONFLICT (run_id, seq) DO UPDATE`，重跑只把 `retry+1` 并把该行改回 RUNNING。若改成「重跑就再插一行」，总步数会膨胀成 15/8。
3. **心跳只改 detail**，不加行、不推 `current_step`，且 30 秒节流（解析器 10 秒回调一次，不节流等于 3 倍无效写）。
4. **所有写语句都只影响 `status='RUNNING'` 的行**（`fail`/`succeed`/`finishStep`/`heartbeat` 全带这个条件）。因此「心跳与收尾撞车」「两次重试撞车」时第二条语句影响 0 行，天然幂等，不需要加锁。

### 29.3 attempt 的语义：内部重试不算新一次

- 用户点一次上传 = 一个 attempt。上传接口先开 run（第 1 步 RECEIVED 立刻可见），MQ worker 用 `startOrResume` 复用，不新开。
- **5 分钟宽限窗（`IngestTracker.RETRY_GRACE`）内的 FAILED 也算同一次**：MQ 重投、消费重试都是同一次入库的内部重试，`reopen` 把 run 改回 RUNNING，`retry` 计数记在同一步上。不加这条的实测后果：一次失败上传会在界面上显示「第 4 次」（Kafka 3 次重投各开一条 run）。
- 只有 `POST /retry`（用户显式点重试）才走 `start` → attempt + 1。

### 29.4 接口形状（`GET /api/documents/{id}/ingest`）

| 状态 | 返回 |
| --- | --- |
| `NONE` | 没有 run（老文档、幂等快路径复用的 DONE 文档）→ 前端整块不渲染 |
| `RUNNING` / `FAILED` | 按模板补齐 **完整 N 行**：已有行用库里的值，缺的行补 `PENDING`（前端显示「未执行」），`label` 由枚举报，前端不维护对照表 |
| `DONE` | `steps=[]`，只给 `summary`（`totalMs/parseMs/chunkMs/embedMs` 由后端按步耗时现算，不冗余存列） |

`POST /api/documents/{id}/retry` 只接受 `parse_status='FAILED'`，否则 409 `NOT_RETRYABLE`；成功后把 `parse_progress` 归零（否则 C28 的「只增不减」会让 8% 写不进去）。

### 29.5 与 C28 / C4 / C7 的关系

- 与 **C28**：进度列给卡片（时间加权检查点），步骤表给详情；两者都由同一批埋点写入，但**不是同一份数据**——进度可能停在 55%，步骤却已到 7/8。谁的文案改口径，两边要一起改。
- 与 **C4**：可检索性只由 `active_chunk_version` 决定；`SWITCHED` 这一步只是把「已经切换完成」写进流水，不参与判定。
- 与 **C7/C1**：`CHUNKED` 的 `Parent x / Child y` 与 `EMBEDDING` 的 `新嵌 n / 复用 m` 是观测值，不影响切块与嵌入口径。

### 29.6 已知边界

- DONE 的文档查不到历史步骤（接口有意不返回），只能看摘要；要复盘必须看库。
- `PENDING` 不落库：它是「模板里有、这次没跑到」的展示态，落库会让「模板」与「实际」两套事实互相污染。
- 一个文档同时只允许一条 RUNNING（`start` 会先把遗留的 RUNNING 收成 FAILED，文案「被新的入库尝试取代」）。

## C30 · 证据判定与期间标注的口径（阶段 19 收尾，2026-10-31）

2026-10-31 全量测试暴露三条 e2e 红与两项评测门槛不达标（引用准确率 0.726、valueAccuracy 0.889、periodRate 0）。逐条查下来**没有一条是「测试过期」**：要么是阶段 14 把逻辑搬进图引擎时丢了调用点，要么是判定写得比事实窄。本契约把修完之后的判定口径固定下来。

### 30.0 先记住这一条：定义存在 ≠ 在用

| 类 | 曾经的状态 | 现象 |
| --- | --- | --- |
| `ConversationContextService.applyTurn` + `RouterService.understand(question, TurnContext)` | 只有定义，图里只调单轮重载 | 多轮追问「那净利润呢」不会继承公司/年份，`query_inferred_from_context` 永不出现 |
| `MemoryGate` / `LongTermMemoryRecaller` / `MemoryAssembler.withLongTerm` | 只有定义，无调用点 | 长期记忆召回整条链失效，`memory.gateHit` 恒 false |
| `PeriodLabeler` | 只有定义，无调用点 | 问 2023、证据来自 2024 年报也无声无息，periodRate 恒 0 |

三处都在阶段 14「唯一执行路径」重构里丢的。**验收只能靠真链路或 e2e**：单测各自绿，链路照样断。

### 30.1 指标命中按「同义组」，不按字面

`MetricDictionary.VARIANTS` 六组：归母净利润（4 种写法）／员工总数（5 种）／经营活动现金流量净额（4 种）／总资产·资产总额·资产总计／净资产·所有者权益合计／研发投入（4 种）。

- **只做同义词，不做上下位词**：`净利润` 与 `归母净利润`／`扣非净利润` 是三个口径，合并会把「扣非」当「归母」，属于错配。宁可漏判（走 rewrite 再试一次），不可错判。
- **为什么不进库**：它与指标词表同源，都是业务词汇，不是业务数据；进库只会多一次查询并失去版本控制。
- 实测：问「归母净利润」表头写「归属于上市公司股东的净利润」、问「员工总数」表里写「在职员工的数量合计」，字面比对必然落空 → 整题被 verify 判成「证据不足」拒答，而数值就在证据里。

### 30.2 指标命中要读命中块的全文

状态里每块只留 `SNIPPET_CHARS = 160` 字，而「主要会计数据和财务指标」那张表有 801 字：目标行分别落在第 156 / 631 字。只看片段会把「明明检索到了」判成「没检索到」。

规则：先判 `sectionPath + snippet`；不命中再按 `chunkId` 回库 `findViewsByIds` 读全文（**不过滤 status/version** —— 命中的块本来就在本轮证据里）。读的量是本轮 ≤8 块，与装配上下文同一数量级。

### 30.3 期间标注在 answer 之后，只加 warning 与 note，绝不改数字

- 触发条件（三条同时）：问题是**单一年份**（`yearFrom == yearTo`）、有 citations、引用文档的 `docYear` 与该年不同。
- 产物：warning `evidence_period_mismatch:<问题年>@<文档年>`（每个不同年份一条）+ 一句 note「部分证据来自 X 年年度报告的上年同期对比列，数值口径请核对期间」。
- **为什么放在 answer 节点之后**：得先有 citations 才知道「引用了哪几年」，而 Citation 列表不能进状态（C17 硬规则），只能在拿到 `AnswerResult` 的这一处补。
- **为什么不改数字**：从 2024 年报的上年同期列取 2023 的数是正确来源，缺的只是「这个数出自哪一年报告」这句话。替用户改数是越界。

### 30.4 答案形态里的「变化」只在问变化本身时算「对比」

`AnswerShape` 的 COMPARISON 词表移除裸「变化」，改由 `CHANGE_ASK` 正则判定：
`(有什么|有何|哪些|什么|多大|多少)变化` 或 `变化(了)?(多少|多大|几何|率|幅度|趋势|情况)`。

理由（Q18 实测）：「2024年公司应对行业**变化**的措施是什么？」被判成 COMPARISON → 提示词要求「两个期间并列、给出变化量」→ 模型面对一堆定性的应对措施表述直接拒答。**它被要求回答一个没人问的问题。** 跨年区间（`yearTo > yearFrom`）仍然无条件补 COMPARISON，那条不受影响。

### 30.5 与 C12 / C20 / C21 / C24 的关系

- 与 **C12**：多轮补全仍走 `TurnContext`；本契约只管「证据年份 vs 问题年份」这一条独立判断。
- 与 **C20**：只改「变化」一个触发词，三形态（归因/结构/对比）本身不变；ATTRIBUTION 的覆盖检查照旧。
- 与 **C21/C6**：指标命中只决定 verify 放不放行，不改变事实抽取、上下文内容与引用映射。
- 与 **C24**：车道里「某年一条都没命中」由年份补跑负责；本契约的指标命中是最后一道闸，两者互补。
