# 技术选型表

> 一份「选了什么 / 没选什么 / 为什么 / 什么时候该改主意」的清单。
> 每条都尽量给可验证的细节（文件、行号、实测数字），而不是「业界最佳实践」这种无法证伪的话。
> 实测环境：Windows 本机 + Docker，Java 21 / Spring Boot 4.0.8 / PostgreSQL 16.15，数据截至 2026-10-27。
> 如果只想看「为什么不用 MyBatis-Plus / JPA」，直接跳 **附录 A**（A.1 五层拆解 → A.4 各生态现状 → A.7 四条路线）。

## 0. 五条选型原则（先看这个，后面每条都能对回来）

| # | 原则 | 具体含义 |
|---|---|---|
| 1 | **能就地扩展就不引入新组件** | PostgreSQL 装个扩展能解决的事，不新起一个中间件（这就是没用 ES 的原因） |
| 2 | **一个事实只有一个真相源** | 表结构只认 Flyway；租户只认连接上的会话变量；作用域只认 `ResolvedScope` |
| 3 | **SQL 是核心逻辑时，用最薄的访问层** | 向量检索 / 全文检索 / 版本原子切换都写在 SQL 里，所以选 `JdbcTemplate` 而不是 ORM |
| 4 | **每个选型都写「什么时候该换」** | 没有触发条件的选型，半年后没人敢动 |
| 5 | **本地全可跑** | 学习项目要能反复复现；凡是「必须买服务才能验证」的方案都降级 |

## 2. 逐项说明

### 2.1 数据库：为什么是 PostgreSQL 一个就够

| 需求 | 用 PG 自带能力 | 换成别的组件要多做什么 |
|---|---|---|
| 向量检索 | `pgvector` 扩展 | 起 ES/Milvus，还要做「元数据 → 向量库」双写与一致性 |
| 中文分词 + 全文检索 | `zhparser` + `tsvector` 生成列 + GIN | 起 ES，装 IK 分词器，再写同步管道 |
| 模糊匹配（兜底） | `pg_trgm` 的 `gin_trgm_ops` | 无 |
| 版本原子切换 | 同一张表同一事务里改指针 | 向量库无事务 → 「切一半」的中间态无法回滚 |

最关键的一条不是性能，而是**一致性边界**：`document_chunk` 里既有 `content`（元数据与正文）也有 `embedding`（向量），所以「新版本写完 + 指针切换 + 旧版退役」可以在**一个本地事务**里完成。拆成两个存储，就必须面对「向量库写成功、元数据写失败」这种补偿逻辑。

**实测（2026-10-21，1,516 行）**：查询计划走的是精确 kNN（`Seq Scan` + `Sort`）**9.8 ms**；强制 `enable_seqscan=off` 走 HNSW 是 **31.4 ms**。交叉点约 1 万行 —— 也就是说这个规模下「不上 ANN」反而更快，但索引已经建好，等数据长大自动切换。细节见 `docs/pgvector-工作机制.md`。

**代价**：向量与业务表同库，写放大与 vacuum 压力都落在主库；超过千万级 chunk 时需要分区或独立向量库。

### 2.2 稀疏检索：为什么是 zhparser，而不是自己维护 BM25

| 方案 | 状态 | 说明 |
|---|---|---|
| `ts_rank` + `plainto_tsquery`（当前） | 已用 | 打分口径是词频+距离，不是 BM25；够用但不理想 |
| 自己算 BM25（`unnest(tsvector)` 取 tf + `count(*)` 取 df） | 备选 | 约 150 行 SQL，阶段 6 的候选方案 |
| ParadeDB `pg_search` | 备选 | 有预编译包，但**中文分词未验证**，需要 1~2 小时 spike |

**实测坑**：`plainto_tsquery`（AND 语义）对自然语言长问题返回 **0 条**；`ILIKE '%每股收益%'` 只 **6 条**，而 OR 模式的 FTS 能召回 **86 条** —— 所以 `PgSparseRetriever` 里做了 AND→OR 回退。

### 2.3 表结构：为什么只认 Flyway

- 9 个迁移脚本（`src/main/resources/db/migration/V1`~`V9`）就是 schema 的完整历史，含注释与「为什么这么改」。
- 禁止 `baselineOnMigrate`、禁止 `docker down -v` 重置：早期踩过「`Found non-empty schema "public" but no schema history`」，用重置库解决等于把历史丢了。
- **代价**：没有实体注解，字段改名只能靠人和测试。

### 2.4 数据访问：为什么是 JdbcTemplate，不是 MyBatis / JPA

#### 现状（可验证）

| 检查 | 结果 |
|---|---|
| `pom.xml:46-48` | 只有 `spring-boot-starter-jdbc`，无 mybatis / jpa / hibernate |
| 全仓 grep `mybatis\|hibernate\|jpa\|@Entity` | **0 命中** |
| 数据访问类 | 4 个 Repository + 3 个直接用 `JdbcTemplate` 的组件 |
| 手写 SQL 调用点 | **45 处**（`ChunkRepository` 18 / `DocumentRepository` 16 / `TaskMessageRepository` 4 / 其余 7） |

#### 写法（三层都很薄）

1. **拼 SQL**：text block 写在 Java 里，可选条件用 `appendIn` 逐个追加（`DocumentRepository.java:271-290`、`:341-349`）。空条件直接跳过，避免 `IN ()` 语法错误。
2. **映射结果**：record + lambda `RowMapper`，不用注解、不反射（`DocumentRepository.java:303-325`）。
3. **拿主键 / 事务 / 锁**：`RETURNING id`（5 处）、`@Transactional`（`ChunkPersister.java:44`）、`SELECT … FOR UPDATE`（同文件 `:49`），并发还有唯一索引兜底。

#### 为什么不用 MyBatis（四条硬理由）

| 理由 | 证据 |
|---|---|
| **核心逻辑是 PG 专属语法，不是 CRUD** | `<=>` 2 处、`::vector` 2 处、`tsquery` 4 处、`ts_rank` 3 处、`FOR UPDATE` 2 处、`RETURNING id` 5 处。JPA/JPQL 表达不了；MyBatis 写原生 SQL 等于「给手写 SQL 再包一层」 |
| **查询是「条件可选」的动态拼装** | `findRetrievable` 有 5 个可选筛选，JdbcTemplate 里 5 行 `appendIn`；MyBatis 要在 XML 里写 5 个 `<if>`，SQL 与代码分家 |
| **向量列是 USER-DEFINED 类型** | `embedding` 是 pgvector 注册的 `vector`，不是 JDBC 标准类型。我们用「传字符串 + `?::vector`」让 PG 自己转；MyBatis 需要自定义 `TypeHandler` |
| **不想引入第二套数据访问栈** | Spring AI 的 `PgVectorStore` 内部也是 `JdbcTemplate`。两套框架=两个连接/事务/缓存模型，收益为零 |

#### 为什么不用 JPA / Hibernate（额外两条）

- `ddl-auto` 会造出「注解」与「迁移脚本」两个真相源，且改一个字段要同时动两处；本项目 DDL 全部在 `V*.sql`。
- 一级缓存/脏检查在「读到自己刚写的向量」这类场景里会增加不确定性；RLS 测试要直接跑 `SET ROLE` 并断言 0 行，这种「SQL 即代码」的风格最直接。

#### 代价与缓解

| 代价 | 缓解 |
|---|---|
| SQL 没有编译期校验，字段改名靠人 | SQL 集中在 4 个 Repository；测试大量连真库（320 个用例，1 个跳过） |
| RowMapper 重复代码 | 每个 Repository 1 个 mapper 常量 + 少量 lambda，映射到不可变 record |
| 复杂对象图要手写 join | 本项目以宽表为主，`document ⨝ company` 一个 LEFT JOIN |
| 分页/批量要自己写 | 当前规模（单文档 654 子块 / 全库 6000+ 行）不需要 |

#### 什么时候该换

| 触发条件 | 换成 |
|---|---|
| 报表/多表动态查询变多、DBA 要直接读 SQL 文件、团队已有 XML 资产 | MyBatis |
| 以对象模型为主、CRUD 密集、需要跨数据库方言 | JPA / Hibernate |
| SQL 继续是核心逻辑（向量/全文/窗口函数） | 保持 JdbcTemplate |

> 完整的 ORM 对照论证见 **附录 A**：MyBatis-Plus 的五层拆解与本机实测、各生态对 `pgvector` 的支持现状（L1~L5）、`hibernate-vector` 的 HQL 距离函数、四条备选路线。那一节回答的是「换上去到底能省什么、要付什么」。

### 2.5 异步：为什么是 Kafka，而不是 RocketMQ / RabbitMQ / DB 轮询

| 方案 | 结论 | 原因 |
|---|---|---|
| Kafka 3.7.0（KRaft，单节点） | 采用 | 设计文档 ADR-004 已定；`DefaultErrorHandler` + DLT（死信 topic）开箱可用，正好对上「重试 3 次后进 DLQ」的需求 |
| RocketMQ | 未采用 | 本机 Docker 里那两个 `rmqbroker`/`rmqnamesrv` 是别的项目的；换栈要重写错误处理 |
| RabbitMQ | 未采用 | 延迟队列/重试要用插件，不如 Kafka 的 DLT 直接 |
| DB 轮询 | 未采用 | 幂等与「至少一次」都要自己实现，且延迟取决于轮询间隔 |

**资源实测（2026-10-27）**：默认镜像堆 `-Xmx1G`，容器 **955.9 MiB / CPU 69%**；改 `KAFKA_HEAP_OPTS=-Xmx256m`、healthcheck 换 `nc -z`（原来每 10 秒起一个 JVM）、修正 `KAFKA_LOG_DIRS` 后降到 **258.4 MiB / CPU 2.7%**。

### 2.6 PDF 解析：为什么是 Docling

| 方案 | 表格结构 | bbox | 中文 | 结论 |
|---|---|---|---|---|
| **Docling 2.138.0** | TableFormer，能识别跨行跨列 | 有 | 好 | 采用（解析服务独立进程） |
| PyMuPDF | 无表格结构（只有文本块） | 有 | 好 | 只用于**核对**原文（本项目用它验证解析结果） |
| pdfplumber | 有基础表格 | 有 | 一般 | 复杂财报表格经常错列 |
| unstructured / MinerU | 有 | 部分 | 一般 | 依赖更重 |

**代价**：CPU 上极慢（实测 8 页要 10 分钟以上，要加载 RapidOCR + TableFormer 模型）。所以「解析」必须异步化（阶段 7 的 Kafka 链路），而且**修解析结果不能靠重跑解析** —— 阶段 6 的员工表丢值 bug 是在 Java 侧 `TableRenderer` 修的。

### 2.7 模型：为什么走第三方 API

| 用途 | 选型 | 备选 | 理由 |
|---|---|---|---|
| Embedding | 百炼 `text-embedding-v4`，1024 维 | 本地 bge-m3 | 中文财报语义好；本地模型显存/速度都不够 |
| 生成 | `qwen-plus` | 本地 Llama | 内网可直连、按量计费 |
| Rerank | `qwen3-rerank` | 自训 cross-encoder | 一次 HTTP 就有；`gte-rerank` 已于 2026-05-30 下线，必须显式指定模型名 |

**硬约束**：`1024` 维已锁定进契约（`embedding vector(1024)`），换模型=重建全库向量。`RerankModel` 是自己写的接口（Spring AI 2.0.1 上游**没有** rerank 抽象），真换供应商只需写一个约 20 行的适配器。

### 2.8 认证与多租户：为什么自己写，且用 RLS

| 选择 | 取舍 |
|---|---|
| 自写 Bearer Filter（不用 Spring Security） | 需求只有三件事，框架会顺带接管过滤器链/CSRF/默认登录页，是负资产；代价是必须自己守住 `@Order` 与 `finally clear()` |
| 库里存 SHA-256(token)（不用 JWT） | 要「随时可撤销」，且不想为此再挂一个 Redis。纯无状态 JWT 撤销不了；JWT + Redis 校验**能**撤销，但每请求成本反而更高、还多一个组件 —— 见 §2.8.1 |
| RLS 做跨租户硬边界（不用「一租户一库」） | 单库最省；策略写一次覆盖所有读路径；代价是「查不到」会静默发生 |
| 应用层 ACL 做租户内软边界 | RLS 只看 `tenant_id`，表达不了「公司级授权 / 私有文档」 |

#### 2.8.1 为什么不用 JWT（以及「JWT + Redis 黑名单」为什么不划算）

先纠正一句容易被读成绝对化的话：**「JWT 无法撤销」只对「纯无状态验证」成立。** 只要在验证链路上加一次状态查询（Redis 白名单 / 黑名单、`jti` 表、`token_version` 计数器），JWT 就能撤销，权限变更也能立刻生效 —— 「删缓存 → 下次请求 401 → 客户端重新登录换新 token」这条路是**可行**的。

所以问题不是「能不能撤销」，而是**撤销要付什么**。三种形态摆在一起：

| 形态 | 撤销能力 | 每请求外部查询 | 状态存在哪 | 本项目 |
|---|---|---|---|---|
| A. 纯 JWT（只在本地验签） | ❌ 只能等 `exp` | 0 次 | 无 | ✗ |
| B. JWT + Redis 校验 | ✅ 删 key 即失效 | 1 次 Redis | Redis | ✗ |
| C. 随机 token + 库里 SHA-256 | ✅ 改 `status` / 删行 | 1 次索引查询 | PostgreSQL | ✓ |

关键点：**B 的每请求成本 ≥ C。** B 除了那一次 Redis 查询，还要多做「验签 + Base64 解码 + 校验 `exp` / `nbf` / `iat` / `aud` / `iss`」；C 只做一次哈希 + 一次索引查询。也就是说，为了买到「可撤销」，B 把 A 唯一的优势（零查询）交了出去，剩下来的只有「token 更大、签名密钥要管、算法与时钟要防」这几项负担。

本项目还多一层理由：**每个请求本来就必开一个数据库连接** —— `TenantAwareDataSource` 要在连接上 `SET ROLE finagent_app` + `set_config('app.tenant_id', …)`，RLS 才有边界。既然 DB 已经在请求路径上，把 token 查询挂在同一条连接上几乎免费：实测（2026-10-27，`EXPLAIN ANALYZE`）**0.080 / 0.084 / 0.119 / 0.124 / 0.125 ms**，计划是 `Index Scan using app_user_api_token_hash_key`，`shared hit = 6`。而 Redis 是**新增的第二个网络跳**加一个新容器。

三个容易被忽略的细节：

| 细节 | 说明 |
|---|---|
| 传播语义 | 「删缓存 → 401 → 重新登录」本质上是**把会话状态放进 Redis**，只是 token 本身变成了自包含的大字符串；生效边界取决于「先删缓存还是先改库」的顺序与原子性 |
| 多副本一致性 | 一旦有任何一个验证方**不查** Redis（比如某个只做本地验签的内部服务），它就会继续接受旧 token —— 这正是无状态 JWT 想避免的问题，在「加校验」之后以另一种形式回来了 |
| 风险形状不同 | HS256 签名密钥泄漏 = 可伪造任意租户任意用户的 token（全局、瞬时）；`api_token_hash` 表被拖走只拿到不可逆的 SHA-256 摘要，撤销是「删一行」 |

#### 2.8.2 什么时候该换成 JWT

| 触发条件 | 为什么那时 JWT 才划算 |
|---|---|
| 要对外发**短期**凭证（第三方接入、OIDC 联邦身份） | `exp` + 签名就能表达「15 分钟有效」，不需要撤销 |
| 拆成多个资源服务器，各自验签 | 验签是本地计算，不必每个服务都连同一个会话库 |
| 边缘 / CDN / 网关要校验身份 | 边缘节点连不到内网 DB，但能拿到公钥 |
| 客户端要离线可用 | 无状态 token 可以带着走 |
| 权限变更频率极低（月级） | 「等过期」的代价可以接受，缓存层就不必存在 |

换句话说：**JWT 真正的卖点是「验证方不需要访问状态存储」**。一旦为了撤销把这个前提推翻，它相对不透明 token 就只剩劣势了。

细节见 `docs/权限与多租户-工作机制.md`。

### 2.9 测试：为什么大量用真数据库

| 手法 | 用在哪 | 为什么不能 mock |
|---|---|---|
| 真库 `@SpringBootTest` | 切块写入、版本切换、RLS、ACL、检索 SQL | 这些行为**就是**数据库行为；mock 掉等于测了个假的 |
| 纯 mock 单测 | 编排类（上传链路、监听器、路由器） | 这些只关心「顺序与分支」 |
| 分级 tag | `-Dgroups=e2e` 跑真 Kafka + 真 HTTP | 默认 `mvn test` 要快（320 例），e2e 单独跑 |
| 不用 Testcontainers | — | 向量/分词扩展要预装，容器启动 1 分钟以上，本机 Docker 常驻更省 |

## 3. 被否决的方案清单（决策日志）

| 阶段 | 被否决的方案 | 否决理由 |
|---|---|---|
| 1 | Elasticsearch / OpenSearch 做向量+全文 | 要多一个中间件，且元数据与向量会分裂成两个存储（用户明确要求只用本地 PG + 分词器） |
| 1~2 | 自建 BERT/CLIP 向量化服务 | 成本远超收益 |
| 2 | 用 PyMuPDF 代替 Docling 做解析 | 没有表格结构，财报的表格全部丢失 |
| 3 | 直接按固定长度切块（不看章节/表格） | 表格会被拦腰切断，引用无法定位 |
| 4 | 一次查询里用 `WHERE 距离 < 阈值` 过滤 | 距离是数值不是布尔谓词，必须放 `ORDER BY`；且阈值会随语料漂移（实测 0.17~0.65 全被拒） |
| 4 | 自己维护 BM25 | 先看 `ts_rank` 够不够；不够再上（§2.2） |
| 5 | 用 `row_number() OVER()` 取名次 | 窗口函数会先对全集排序再截断，HNSW 用不上 |
| 7 | Spring Batch 做异步任务 | 太重；Kafka + 幂等表更贴近真实系统 |
| 7 | per-task git commit | 仓库只有一个初始提交，没有干净基线可增量提交 |
| 8 | Spring Security + Keycloak | 只为三件事引入两套组件 |
| 8 | 一租户一 schema | 迁移要跑 N 次，跨租户运营查询困难 |
| 8 | 无状态 JWT（含「JWT + Redis 黑名单」变体） | 见 §2.8.1：要可撤销就必须每请求查一次状态，成本 ≥ 现在的一次索引查询（实测 0.08~0.125 ms），还要多一个 Redis 容器；而 JWT 的卖点恰好是「不查状态」 |
| 8 | MyBatis-Plus 替换 JdbcTemplate | 见附录 A.1~A.3：45 处 SQL 里约 30 处仍要手写，且要把全仓不可变 record 改成可变 POJO |
| 8 | JPA / Hibernate + `hibernate-vector` | 见附录 A.5~A.7：HQL 已能表达距离排序，但生成列 / `ON CONFLICT` / `FOR UPDATE` / RLS 会话变量仍要原生 SQL，结果是混合形态；当前规模不值得 |

## 4. 这些选型的已知代价（诚实清单）

| 代价 | 影响面 | 缓解 / 何时处理 |
|---|---|---|
| 无 ORM：SQL 改动没有编译期保护 | 全库 45 处 SQL | 测试连真库；SQL 集中存放 |
| pgvector 与业务同库 | 写放大、vacuum 压力 | 千万级 chunk 时分区或拆库 |
| Docling 慢（CPU 8 页 > 10 分钟） | 首次入库 | 已改为事件驱动异步；修复解析问题走 Java 侧而不是重解析 |
| 第三方模型 API | 可用性 / 成本 / 数据出境 | 已确认允许发第三方；`RerankModel` 可换实现 |
| zhparser 分词质量问题 | 稀疏检索召回 | `营业收入`→`营业`+`收入`、`每股收益`→`收益`；已用 `pg_trgm` 兜底，BM25 待评估 |
| 旧 chunk 版本不清理 | 每重切 +1516 行 / 约 7 MB | 保留策略待做（阶段 7 遗留项） |

## 5. 一句话总结

这套选型的形状是「**一个数据库 + 一层薄薄的 SQL + 一条事件驱动链路**」：PostgreSQL 用扩展把向量、分词、模糊匹配都吃进来，Java 侧只写 SQL 和编排，模型能力全部走 API。它牺牲了「框架帮你兜底」的便利，换来的是「每一步都能在 psql 里验证」——对学习型项目，这个交换是划算的。

## 附录 A：为什么不用 MyBatis-Plus / JPA（ORM 论证）

> 这份附录回答两个追问（2026-10-27）：
> ① 「MyBatis-Plus 是不是更能支持 PostgreSQL 的语法？」
> ② 「业界做 RAG 用 PostgreSQL，有没有成熟的 ORM？」
>
> 一句话结论：**有成熟 ORM，但 RAG 的检索 SQL 业界基本不用 ORM 写；而「支持 PG 语法」这件事我们真正需要的那一层（原生 SQL 透传），`JdbcTemplate` 已经 100% 做到。**
>
> 本附录的版本号、类名、行号都是 2026-10-27 在本机 `.m2` 与 Maven Central 上**实测**的（`javap` / `jdeps` / 反查 BOM），不是引述二手资料。

### A.1 先拆「MyBatis-Plus 支持 PG 语法」这句话

这句话要分五层看。**流传的「大部分能支持，复杂 SQL 不支持」对 L4 是对的、对 L1 是错的**，而 L1 才是本项目吃饭的那一层。

| 层 | 能力 | MyBatis-Plus | `JdbcTemplate`（现状） | 本项目要不要 |
|---|---|---|---|---|
| **L1** | 原生 SQL 透传（框架不解析、不改写） | ✅ 完全支持（MyBatis 不解析 SQL 文本） | ✅ 完全支持 | **要，且是核心** |
| **L2** | 动态 SQL（`<if>` / `<foreach>` / `<bind>`） | ✅ 强于现状 | ❌ 自己拼 `StringBuilder` | 只有 4 处 `appendIn`，收益很小 |
| **L3** | 结果映射到对象（含 Java `record`） | ⚠️ record 要写构造器映射；`BaseMapper` 要**可变 POJO** | ✅ 一个 lambda `RowMapper` 直接映 record | 要，现状更顺 |
| **L4** | 框架**自动生成** SQL（`Wrapper` / `BaseMapper` CRUD） | ✅ 但只覆盖标准 CRUD | — | 45 处 SQL 里只有十几处能用上 |
| **L5** | 向量 / 全文 / 行锁 / upsert 等 PG 专属语义 | ❌ 只能手写，或走 `.last(...)` 后门 | ✅ 手写即真理 | **要，且是核心** |

### A.2 逐项对照：本项目真正要写的 SQL，在 MyBatis-Plus 里长什么样

| 现在（`JdbcTemplate`，手写 SQL） | 换成 MyBatis-Plus 要怎么写 | 结论 |
|---|---|---|
| `ORDER BY dc.embedding <=> ?::vector LIMIT ?`（`DenseRetriever.java:52`） | `wrapper.last("order by dc.embedding <=> ?::vector limit ?")` 或 `@Select` 手写 | 两条路都是「绕开框架」，等于放弃 wrapper |
| `content_tsv @@ plainto_tsquery('chinese_zh', ?)` + `ts_rank`（`PgSparseRetriever`） | 只能 `@Select` 手写 | 同上 |
| `SELECT ... FOR UPDATE`（`ChunkPersister.java:49`） | `wrapper.last("for update")` | 后门；行锁语义要靠人记 |
| `INSERT ... ON CONFLICT (tenant_id, code) DO UPDATE` | MP **没有原子 upsert**；`saveOrUpdate` 是「先 select 再 insert / update」，并发下会撞唯一键 | V9 把唯一键改成租户内，正是**靠 `ON CONFLICT` 兜住**的；换 MP 这条防线要自己补 |
| 生成列 `content_tsv GENERATED ALWAYS AS ... STORED` | MP 默认把所有字段写进 `INSERT` → 报 `cannot insert into generated column`，必须给该字段加 `@TableField(exist = false)` | 现状是 `ChunkRepository` 显式列名，生成列**根本不出现在 INSERT 列表里** |
| `RETURNING id`（`ChunkPersister` / `DocumentRepository`） | MP 的 `useGeneratedKeys` 走 JDBC `getGeneratedKeys`；多列 `RETURNING` 仍要手写 | 明显更差 |
| `IN (?, ?, ...)` 动态列表（`DocumentRepository.java:341-349` 的 `appendIn`） | `<foreach>` 确实更短 | **MP 唯一明显更好的点**（还有下一行） |
| PG 数组参数 `setObject(i, list, Types.ARRAY)` | MyBatis 的 `ArrayTypeHandler` 更省事 | `DenseRetriever.java:86-89` 注释记过「JdbcTemplate 变参拿不到这个 API，退回占位符拼接」 |

### A.3 换 MyBatis-Plus 的实际账

| 项 | 内容 |
|---|---|
| 能省的地方 | 45 处 SQL 里的十几处简单 CRUD（`INSERT` / 按 id `SELECT` / `UPDATE status`）+ 4 处 `appendIn` |
| 成本 ①（最重） | 本项目**全链路是不可变 `record`**（`ChunkView` / `DocumentSummary` / `TaskMessage` …），而 MP 的 `BaseMapper` 要**可变 POJO** → 要么加一层 Entity 再映射，要么把 record 改成可变类 |
| 成本 ② | SQL 位置分裂：约 30 处仍然手写（`@Select` 或 XML），于是「哪些在注解里、哪些在 XML 里、哪些在 Wrapper 里」变成三类真相源 |
| 成本 ③ | 生成列 / `vector` 类型 / 数组参数都要写 `TypeHandler` 或注解开关 |
| 成本 ④ | Boot 4 只验到**类级**兼容（见 A.1.1），方法级没验 |

**结论**：收益集中在「少写十几行样板」，成本落在「改掉全仓的不可变模型」。**不划算。**

### A.4 各生态对 `pgvector` 的「成熟 ORM」现状

先说「成熟」怎么量化。对 RAG 来说，一个数据访问框架支持 pgvector 要依次跨过五级：

| 级别 | 能力 | 含义 |
|---|---|---|
| L1 | `vector` 列能读写 | `float[] ↔ vector` 类型映射 |
| L2 | 能用距离**排序** | `ORDER BY embedding <=> ?`（框架必须能表达「操作符 + 排序列」） |
| L3 | 能建 HNSW / IVFFlat 索引 | 索引 DDL |
| L4 | 能批量 upsert | `ON CONFLICT` |
| L5 | 能控执行计划 | 过滤下推、`hnsw.ef_search`、`iterative_scan` |

**绝大多数「我们支持 pgvector」只做到 L1~L2**，而 L3~L5 才是检索的日常。

| 生态 | 组件 | 覆盖到 | 成熟度 |
|---|---|---|---|
| **Python** | `pgvector`（官方）：SQLAlchemy `Vector` 类型 + `HNSW` / `IVFFlat` 索引 + Django `VectorField` / `CosineDistance` | L1~L3 | **最成熟**（LangChain / LlamaIndex 的 PGVector 都建在它上面） |
| **Java / JPA** | **`org.hibernate.orm:hibernate-vector`**（Hibernate 官方孵化模块） | L1~L3，且带 HQL 距离函数 | **已可用**（见 A.5） |
| **Java / JDBC** | `com.pgvector:pgvector`（官方 Java 客户端，只做类型转换） | L1 | 稳定；**已在本机 `.m2`**（Spring AI 的 pgvector starter 传递引入） |
| **Java / MyBatis** | 无官方模块；靠自定义 `TypeHandler` + 原生 SQL | L1（手写可达 L5） | 社区示例级 |
| **Java / jOOQ** | 无官方 vector 类型，要自定义 `DataType` / `Binding`；但 PG 方言覆盖最全 | L1~L5（都要自己写一点） | 中 |
| **Node** | 官方 `pgvector` npm（node-postgres 助手）；Drizzle 有 `vector` 列类型；Prisma 只能 `Unsupported("vector(1024)")` + 原生查询 | L1~L2 | 中 |
| **Go** | 官方 `pgvector-go`（配 pgx）；GORM 要插件或原生 SQL | L1~L2 | 中 |
| **.NET** | 官方 `Pgvector` + `Pgvector.EntityFrameworkCore` | L1~L2 | 中上 |
| **Rust** | 官方 `pgvector` crate（sqlx / diesel） | L1~L2 | 中 |

> 验证口径：Java 三件套（`com.pgvector:pgvector`、`hibernate-vector`、MyBatis-Plus）是本机实测；Python / Node / Go / .NET / Rust 是生态常规认知 —— 本机到 `pypi` / `npm` / `raw.githubusercontent.com` 均超时，未逐项复跑。

### A.5 Java 侧的关键变化：`hibernate-vector`（2026 实测）

| 检查 | 结果 |
|---|---|
| `org.hibernate.orm:hibernate-vector` 版本线 | 从 **6.4.0.Final** 一直到 **8.0.0.Beta3**；7.2 线有 7.2.20 ~ 7.2.25.Final |
| 本项目 Boot 4.0.8 管理的 Hibernate | **7.2.24.Final**（`spring-boot-dependencies-4.0.8.pom` 的 `hibernate.version`） |
| Boot 4.0.8 BOM 是否管理 `hibernate-vector` | **是** → 加依赖**不用写版本号**，天然对齐 |
| `hibernate-vector-7.2.24.Final.jar`（153,178 字节）关键类 | `PGVectorFunctionContributor`、`PGVectorTypeContributor`、`PGSparseFloatVectorJdbcType`，另有 DB2 / Oracle / MySQL / MariaDB / HANA / SQL Server / Cockroach 各自 TypeContributor |

`PGVectorFunctionContributor` 是重点：它把 PG 的距离运算注册成 **HQL 函数**，于是「L2 排序」第一次能在 ORM 里自然表达（伪代码）：

```java
em.createQuery("""
    select c from Chunk c
     where c.documentId in :docs
     order by cosine_distance(c.embedding, :queryVector) asc
    """, Chunk.class)
  .setParameter("queryVector", floatArray)
  .setMaxResults(30)
  .getResultList();
```

两年前问「pgvector 怎么配 JPA」只能得到「用原生 SQL」的答案（StackOverflow 上那批 Hibernate 6 + pgvector 的问题就是这种情况）。**这是这两年 Java 侧唯一实质性的新东西。**

### A.6 业界的真实形状：ORM 管元数据，SQL 管检索

| 实现 | 元数据（文档 / 会话 / 评测） | 向量检索 |
|---|---|---|
| Spring AI `PgVectorStore` | 用户自己决定 | **纯 `JdbcTemplate`**，手写 SQL |
| LangChain `PGVector` | 用户自己决定 | `psycopg` + 手写 SQL |
| LlamaIndex `PGVectorStore` | 同上 | 同上 |

三条原因，每一条都能在本项目代码里找到对应：

| 原因 | 说明 | 本项目的证据 |
|---|---|---|
| 距离不是布尔谓词 | `ORDER BY embedding <=> ?` 是**排序列**，`Wrapper.orderBy` / Criteria 只能拼「列名 + asc/desc」，拼不出操作符 | `DenseRetriever.java:52` 直接写在 SQL 里 |
| 执行计划要可控 | ORM 会顺带加 join / 一级缓存 / `count(*)`；排障时你希望手上是一条能直接丢进 psql 的 SQL | 实测 1,516 行时精确 kNN **9.8 ms**，强制走 HNSW **31.4 ms** |
| 混合检索不是 CRUD | RRF 融合、`ts_rank`、`plainto_tsquery`、`FOR UPDATE`、`ON CONFLICT`、生成列 | `<=>` 2 处、`::vector` 2 处、`tsquery` 4 处、`ts_rank` 3 处、`FOR UPDATE` 2 处、`RETURNING id` 5 处 |

### A.7 如果真要上 ORM：四条路线对比

| 路线 | 依赖 | 能覆盖 | 必须手写 | 主要阻力 |
|---|---|---|---|---|
| **A. 现状 `JdbcTemplate`** | 0 | 全部（45 处手写） | — | 样板多、无编译期校验 |
| **B. Hibernate 7.2 + `hibernate-vector`** | JPA starter + vector 模块（版本由 BOM 管） | 元数据 CRUD、向量排序（HQL 函数） | 生成列、`ON CONFLICT` upsert、`FOR UPDATE`、`ts_rank`、RLS 会话变量 | 要引入实体模型（与「全不可变 record」冲突）；实体与 Flyway 变成两套真相源 |
| **C. MyBatis + `TypeHandler`** | mybatis / mybatis-plus | 原生 SQL 全量 + 更好写的动态 SQL / 数组绑定 | 与现在一样（SQL 仍手写） | 可变实体或额外 DTO；SQL 位置分裂 |
| **D. jOOQ** | jOOQ（含代码生成） | 类型安全 SQL、PG 方言最全、可拼任意操作符 | vector 要自定义 `DataType` / `Binding` | 要从 schema 生成代码（可与 Flyway 配合，但多一步构建） |

**判断**：

| 如果目标是 | 选择 |
|---|---|
| 练 Spring Boot AI + 搞懂 RAG 机制（本项目现状） | **A 最优** |
| 练企业级 Java 数据访问 | **B 最值得试一次**：`hibernate-vector` 的 HQL 距离函数是真正的新东西，且 Boot 4 的 BOM 已在替我们管版本；但要预先接受「生成列 / upsert / 行锁」三处仍回原生 SQL，最终形态必然是「JPA 管元数据 + 原生 SQL 管检索」的混合 —— **而这就是业界的标准形态** |

### A.8 这个决定什么时候该重开

| 触发条件 | 说明 |
|---|---|
| 简单 CRUD 表超过 ~10 张且全是单表读写 | 那时样板代码才真的成为负担 |
| 需要跨数据库方言（比如某天要支持 MySQL） | `JdbcTemplate` 里的 PG 专属 SQL 是最大阻力 |
| 出现「对象图」需求（多表关联 + 级联更新 + 懒加载） | 手写 join 开始比 ORM 贵 |
| 团队要求 SQL 与 Java 分离（DBA 直接审 SQL 文件） | 反而是 MyBatis 的 XML 更合适 |
| 要练企业级 | 单独开分支试 B，不要在主线里换 |

---

**本附录的结论一句话**：ORM 解决的是「对象 ↔ 表」的搬运问题，而本项目的核心逻辑是「在一条 SQL 里用 PG 的方言把召回、排序、过滤、锁、幂等 upsert 一次做完」——这件事 ORM 不擅长，`JdbcTemplate` 反而是最短路径。等哪天枯燥的样板真的压过检索逻辑的复杂度，A.8 的触发条件会先响。
