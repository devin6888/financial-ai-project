# 主流程导读：一次提问，代码到底走了哪条路

> 这份文档只讲**主流程**，不讲细节。目标是让你能在 20 分钟内，从「用户点了发送」一路读到「答案出现」，
> 并且知道每一步在哪个文件、哪个方法、状态里多了哪个键。
>
> 术语见 `docs/术语表.md`；契约见 `docs/关键契约.md`（C17 图引擎、C18 流式端点、C20~C24 答案质量）。

---

## 0. 先记住三句话

1. **LangGraph4j 不是框架，是「带检查点的 switch 语句」**：它只负责「上一个节点跑完，下一个跑谁」，
   以及「跑完把状态存下来，之后能接着跑」。业务逻辑一行都不在它里面。
2. **所有节点读写同一个对象**：`AnalysisState`（本质是一个 Map 的包装）。节点之间不互相调用，
   只往这个 Map 里写自己的键、读别人写的键。想看数据怎么流，就看键。
3. **一次提问 = 一次 run**，有 `runId`。整个流程可中断（等人批）、可恢复、可回放（`agent_run_step` 表）。

## 1. 整体分层：谁调谁

```text
浏览器 / curl
   │  POST /api/chat/stream
   ▼
ChatController            ← 只做 HTTP：建 SSE、把事件写出去（chat/ChatController.java:84）
   │  agentStreams.startStream(request, sink)
   ▼
AgentStreamService        ← 编排「一轮对话」：会话/记忆/歧义判定/落库/组装响应（agent/AgentStreamService.java:74）
   │  runs.execute(runId, ...)
   ▼
AgentRunService           ← 图的宿主：建初始状态、选图（fast/hitl）、跑流、把结果写成终态（agent/AgentRunService.java:77）
   │  compiled.stream(input, cfg)
   ▼
LangGraph4j               ← 只做「节点调度 + 检查点 + 中断/恢复」（agent/AnalysisGraph.java:126 建图）
   │  依次调用
   ▼
RealAnalysisNodes         ← 九个业务节点的实现（agent/RealAnalysisNodes.java）
   │  每个节点调一个能力包
   ├─ understanding/  QU：问题 → 类型/公司/年份/指标
   ├─ retrieval/     混合检索：dense + sparse + RRF + rerank
   ├─ context/       证据 → 上下文包（预算/展开/邻居）
   ├─ fact/          表格 → 事实 → 派生指标（同比/占比/贡献度）
   ├─ answer/        组装提示词 → 调模型 → 引用校验 → 落数字校验
   └─ agent/         RetrievalLanes（车道）、ScopeMapper（作用域 ↔ 状态）
   │  答案增量（delta）走旁路
   ▼
AnswerStreamBridge        ← 节点内部把 token 推给 SSE，不经过状态（agent/AnswerStreamBridge.java）
```

### 1.1 入口现在只剩一个，业务只有一份

| 端点 | 处理类 | 谁在用 | 说明 |
| --- | --- | --- | --- |
| `POST /api/chat/stream` | `chat/ChatController.java:68` | **前端聊天页**（`src/api/chat.ts:82` 的 `askStream`） | 唯一的流式入口 |
| `POST /api/chat` | `chat/ChatController.java:54` | 脚本 / 单测 | 非流式、不走人批 |
| `POST /api/agent/runs/{id}/resume` | `agent/AgentController.java:50` | 前端审批后**必经** | 只有这里能续跑 |
| `GET /api/agent/runs/{id}` | `agent/AgentController.java:65` | 前端刷新恢复 | 运行视图（plan / evidence / steps） |

**2026-10-30 删掉了一个等价入口**：原来还有 `POST /api/agent/runs/stream`（开新运行），它和 `/api/chat/stream` 调的是
同一个 `AgentStreamService.startStream`、事件契约也是同一套（都出自 `ChatStreamEvent`），前端从未调用（`startAgent` 定义完没人用），
于是删掉，只留 `resume` / `view` 这两个真正不可替代的。

顺带把 SSE 外壳收成一份：建 emitter、心跳、换线程、`TenantContext` 重建、三类异常映射全在 `chat/SseStreamTemplate.java`；
两个 controller 现在只剩「校验参数 → 交给 service」。**主流程看 service 层，不看 controller。**

历史原因：ST11 有「普通问答」和「深度分析」两种模式，各一个端点；ST14 合并成一张图后，`ChatController` 也改成调 `AgentStreamService`，
agent 的「开新运行」那半就空了，于是 2026-10-30 清掉。
**记住了这张图，剩下的都是细节。**

## 2. 一张图：九个节点怎么连

（来自 `AnalysisGraph.java:24-33` 的类注释，也是真实边定义）

```text
START → understand → plan ─┬─ direct ────▶ retrieve
                           ├─ decompose ─▶ retrieve
                           └─ refuse ────▶ respond_insufficient
retrieve → verify ─┬─ enough ────────▶ approve → compute → answer
                   ├─ retry ─────────▶ rewrite → retrieve
                   └─ insufficient ──▶ respond_insufficient
answer → cite_check ─┬─ ok ───────────▶ END
                     └─ 不过且 <2 次 ─▶ answer（回边，不再经过 approve）
```

两处细节值得单独记：

- `approve` 是个**空节点**（`AnalysisGraph.java:134` 只有 `Map.of()`）。它存在的唯一理由是：
  LangGraph4j 的「中断点」只能挂在节点上，而中断点不能挂在 `answer` 上——
  `cite_check` 失败会回到 `answer` 重写，挂在那儿就会**每重试一次再弹一次审批**。
- `compute` 在 `approve` 之后：审批不通过时不该白算一遍事实与派生指标。

## 3. 跟着一次真实请求走（12 步）

假设前端发了：`POST /api/chat/stream {"question":"分析下2024年的营收情况"}`。

| 步 | 在哪 | 发生什么 | 状态里新增/改变的键 |
| --- | --- | --- | --- |
| 1 | `chat/ChatController.java:85` `stream()` | 建 `SseEmitter`（超时、`onCompletion` 收尾），把请求交给 service | — |
| 2 | `agent/AgentStreamService.java:74` `startStream()` | 先发一个 `stage(understand, 理解问题)` 事件（**首屏反馈**，因为下一步要 4 秒） | — |
| 3 | 同上 `:80-82` | 装配会话、作用域、`MemoryContext`（在进图之前做，因为节点跑在别的线程，拿不到 ThreadLocal） | — |
| 4 | 同上 `:85-89` | 歧义判定（`AmbiguityDetector`），再 `runs.create()` 落一行 `agent_run`（状态 `RUNNING`） | 数据库一行 |
| 5 | `agent/AgentRunService.java:77` `execute()` | 建初始状态：问题 + 作用域 + 记忆 + **身份快照**（tenant/user/roles） | `question/scope*/tenantId/userId/roles` |
| 6 | 同上 `:94-96` | 选图：有歧义 → `hitlGraph()`（在 approve 前停），否则 `fastGraph()`；然后 `executeStream()` | — |
| 7 | `agent/AnalysisGraph.java:126-190` | 图按边跑：每个节点都是 `node(...)` 包一层（**重建 TenantContext**），跑完把状态合并 | 每个节点各写各的键 |
| 8 | `agent/AgentRunService.java:211` | 边跑边记：`updateCurrentNode`、每节点一行 `agent_run_step`（含耗时）、回调 `progress` 发 `stage` 事件 | — |
| 9 | `agent/AgentRunService.java:249` `settle()` | 三种收尾：停在 approve 前 → `WAITING_APPROVAL`；拒答 → `REJECTED`；否则 `DONE` | `status` |
| 10 | `agent/AgentStreamService.java:190` `synthesize()` | 从 `AnswerStreamBridge` 取完整 `AnswerResult`（facts/citations/confidence），折成 `ChatResponse` | — |
| 11 | 同上 `:164` | `traceWriter.write()` 落轨迹、`turnRecorder.record()` 落两条消息（USER/ASSISTANT） | 数据库 |
| 12 | 同上 `:173` | 发 `final` 事件（含 `answer/facts/citations/trace`），SSE 结束 | — |

审批分支（第 9 步停在 approve 前时）：前端拿到 `approval` 事件 → 用户点「通过」→ 
`POST /api/agent/runs/{id}/resume` → `AgentController.java:71` → `AgentStreamService.resumeStream()` 
（`:140`）→ `AgentRunService.resume()`（`:111`）→ **不是从头跑**，而是 
`compiled.stream(GraphInput.resume(patch), cfg)` 从检查点接着跑，把 `decision/decisionNote` 打进状态。

## 4. 状态里的键谁写谁读（这是最容易乱的地方）

| 键 | 谁写 | 谁读 | 说明 |
| --- | --- | --- | --- |
| `question` | 外部（execute） | understand / plan / answer | **原问永不改写**（改写走 `rewrittenQuery`） |
| `queryType/companyCodes/yearFrom/yearTo/metrics` | understand | plan / retrieve / compute / answer | QU 的结果 |
| `companyMentions` | understand | decompose | 拆解时给子问题补主体名 |
| `plan/subQuestions` | plan | retrieve | route=DIRECT 时 subQuestions 为空 |
| `answerShapes` | plan | verify / compute / answer | 答案形态（归因/结构/对比） |
| `lanes` | retrieve | 前端 stage.detail / 调试 | 这一轮跑了哪些检索车道 |
| `hits` | retrieve | verify / answer / packageOf | 检索命中的候选（Map 形式） |
| `insufficient/retryCount` | verify | 条件边 | 决定走 replace/rewrite/refuse |
| `facts` | compute | answer | 已报事实 + 已计算事实（含公式） |
| `answer/status/warnings` | answer | settle / synthesize | 最终答案与告警 |
| `citationIssues/citeAttempts/citationCount` | cite_check | 条件边 | 引用不合格时回 answer 重写 |
| `decision/decisionNote` | resume（外部 patch） | answer | 人工修改意见会并进提示词 |
| `tenantId/userId/roles` | execute | 每个节点（`node()` 包装） | 只为在别的线程里还原登录身份 |
| `refuseReason` | understand / retrieve | 条件边 | 非空就一律走拒答分支 |

规则只有一条：**节点只写自己的键，不碰别人的**。所以看到某个值不对，先找「谁写的」那一行。

## 5. LangGraph4j 到底做了什么（只有四件事）

很多人一看到 `CompiledGraph`、`StateGraph`、`CheckpointSaver` 就懵。把它们翻译成人话：

| 概念 | 人话 | 我们怎么用 |
| --- | --- | --- |
| `StateGraph` | 一张「谁接谁」的表 | `AnalysisGraph.java:129-190`，10 个节点、6 处条件边 |
| 节点 `addNode(name, action)` | 一个函数：吃状态、吐「要改的键」 | 就是 `RealAnalysisNodes` 里的 9 个方法 |
| 条件边 `addConditionalEdges` | 「跑完看某个键，决定下一个是谁」 | verify 看 `insufficient/retryCount`；cite_check 看 `citationIssues` |
| `CheckpointSaver` | 每跑完一个节点，把状态存档 | `AgentGraphConfig` 提供的存储；`threadId = runId` |
| `interruptsBefore` | 跑到某个节点**之前**停住 | 只有 `hitlGraph()` 在 `approve` 前停（编译期配置，不能按请求开关） |

它**没有**做的事（所以不要在这些地方找逻辑）：没有重试、没有并发、没有事务、没有提示词、没有业务判断。
重试是 `rewrite` 节点 + 条件边；事务在 `AgentRunRepository`；提示词在 `answer/AnswerPrompts`。

### 为什么有两张图

`interruptsBefore` 是**编译期**配置（`AnalysisGraph.java:202-204`）：编译时定了「要不要停」，运行时改不了。
所以 `fastGraph()`（不停）和 `hitlGraph()`（停）在启动时就编译好两份，按请求选。

## 6. 五个常见困惑

### Q1：为什么 `AgentRunService.executeStream` 自己写了个 for 循环？

因为我们要**边跑边产出**：每跑完一个节点就要落一行 `agent_run_step`、发一个 `stage` 事件。
`compiled.stream(...)` 返回的是 `Iterator<NodeOutput>`，循环体就是「记一笔、发一下、继续」（`:211-231`）。
不是 LangGraph4j 要求这么写，是我们要旁路监听。

### Q2：为什么答案的 token 不在状态里？

状态要能**序列化存档**（检查点），而 token 是流式的、几十上百次，写进状态既浪费又没必要。
所以 `answer` 节点里 `answers.answerStreaming(..., delta -> bridge.delta(runId, delta))`，
token 直接通过 `AnswerStreamBridge` 推给 SSE；完整结果用 `bridge.result(runId, result)` 存旁路，
收尾时 `synthesize()` 再取出来（`AgentStreamService.java:191`）。

### Q3：为什么节点里第一件事总是 `packageOf(state, qu, scope)`？

因为检索命中的 `hits` 只有元数据（chunkId、分数、页码），**没有正文**。
正文要按 `chunkId` 回库取、按 parent/child 展开、按 token 预算裁剪 —— 这就是 `ContextBuilder`。`packageOf` 是它的薄包装（`RealAnalysisNodes.java:339` 附近）。
注意 `answer` 与 `cite_check` 各算一次：**必须算出同一份上下文**，否则引用编号会对不上。

### Q4：为什么 `resume` 不用重跑 understand/retrieve？

因为检查点。第一次跑到 `approve` 前就停住，状态已存档；`resume` 用同一个 `threadId(=runId)` 继续，
LangGraph4j 从存档处接着跑 `approve → compute → answer`。`releaseThread(false)`（`:200`）保证跑完线程不释放、状态还能查。

### Q5：改了代码怎么知道图没坏？

三处断言：
1. `AnalysisGraphTest`：用假节点跑出**节点序列**（比如 `approve, compute, answer, cite_check`）；
2. `AgentRunServiceDbTest`：真跑一遍，断言 `agent_run_step` 的顺序；
3. `ChatStreamE2ETest`：真 HTTP + 真模型，断言 SSE 的事件顺序。
改图以后这三处都会红，按报错把它们同步即可（阶段 16 就漏过一次，见报告 12.5 #24）。

## 7. 建议的阅读顺序（每步 10~20 分钟）

| 顺序 | 读什么 | 目标 | 关键行 |
| --- | --- | --- | --- |
| 1 | `agent/AnalysisGraph.java` | 只看类注释的 ASCII 图和 `build()` 的边，**不要**看 `node()` 包装 | `:24-33`、`:126-190` |
| 2 | `agent/AnalysisState.java` | 知道状态是个 Map，键名都在这里 | 常量区 |
| 3 | `agent/RealAnalysisNodes.java` 的 9 个节点方法 | 每个方法只做一件事：读状态 → 调能力 → 写状态 | `:113/169/244/354/404/431/498/525/549` |
| 4 | `agent/AgentRunService.java` | 初始状态怎么拼、流怎么消费、终态怎么定 | `:77-98`、`:204-236`、`:249-273` |
| 5 | `agent/AgentStreamService.java` | 一轮对话的周边：首屏事件、记忆、落库、final 载荷 | `:74-101`、`:148-178` |
| 6 | 能力包（按需） | 哪一步看不懂就去那个包 | `retrieval/`、`context/`、`fact/`、`answer/` |

**不要**从 `ChatController` 开始读：它只有 30 行 HTTP 代码，读完也建立不了整体感。
也**不要**先读 `RealAnalysisNodes` 的私有方法（`decompose`、`runLanes`、`attributionCovered`）：那是细节，卡住时再看。

## 8. 三个调试入口（比读代码快）

| 想知道 | 看哪里 |
| --- | --- |
| 这次跑了哪些节点、每个多久 | 数据库 `agent_run_step`（`select node, summary, duration_ms from agent_run_step where run_id='...' order by seq`） |
| 每个节点看到了什么 | 前端 SSE 的 `stage` 事件（`detail` 里有 hits/lanes/shapes/facts 数） |
| 检索为什么没召回到 | 同题的 `meta` 事件（证据清单）+ `GET /api/agent/runs/{id}` 的 `evidence` |

要在节点里打断点，`AnalysisGraph.node()`（`:101`）是**唯一入口**：所有节点都从这里进。
