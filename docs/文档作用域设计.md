# 文档作用域设计 v0.2

> 目标：把「这次对话基于哪些文档」从隐含行为变成有契约、有界面、可审计的产品参数。
> 状态：**v0.3 定稿**（2026-10-21 用户确认）。P1~P5 按建议采纳，另定「主动建议切 B」规则（见 2.6）。

## 0. 结论摘要

1. **三种对话模式**：A 指定文档（≤5 份）、B 条件筛选（公司/年份/类型/行业，不限份数）、C 全库智能检索。新对话默认 C。
2. **两个作用域概念必须分开**：`sessionScope`（会话配置，可改）与 `effectiveScope`（本轮实际检索范围，含临时扩展）。
3. **范围外文档不自动扩张**：检测到「问题需要、但不在范围内」的文档时，给三选一（仅本轮 / 加入会话 / 不扩展），默认仅本轮。
4. **三种模式共用一套检索引擎**，只换过滤条件；差异体现在「作用域怎么解析」和「候选集多大时启用文档级路由」。
5. **每轮重新检索**：上一轮召回的 chunk 只是临时证据，绝不当作后续轮次的检索范围。

## 1. 概念与术语

| 术语 | 定义 | 生命周期 |
|---|---|---|
| `sessionScope` | 用户在界面上配置的研究范围 | 会话级，用户显式修改才变 |
| `effectiveScope` | 本轮实际用于检索的范围 = sessionScope ± 临时扩展 | 单轮，随消息落快照 |
| `resolvedDocumentIds` | 作用域解析后的具体文档集合（B/C 模式需要解析） | 单轮 |
| 证据（evidence） | 本轮召回的 chunk，临时、可取替 | 单轮，不进范围 |

**为什么必须分开 sessionScope 和 effectiveScope**：用户点「仅本轮使用五粮液年报」时，如果不落 effectiveScope，后端就无法在下一轮复原「这一轮到底查了什么」；如果直接改 sessionScope，又违背了用户「别改我会话范围」的意图。两者混成一个字段，产品选项就无法实现。

三者的关系：

```
sessionScope ──(本轮是否临时扩展)──> effectiveScope ──(解析/权限过滤)──> resolvedDocumentIds
                                                                        │
                                                                        └──> 检索 ──> 证据
```

## 2. 三种模式

### 2.1 对照表

| | A 指定文档 | B 条件筛选 | C 全库 |
|---|---|---|---|
| 用户给什么 | 1~5 份具体文档 | 公司 / 年份 / 报告类型 / 行业 | 什么都不给 |
| `scope.kind` | `DOCUMENTS` | `FILTER` | `CORPUS` |
| 份数上限 | **5（软上限）** | 不限 | 不限 |
| 典型问题 | 「分析这份年报的现金流」 | 「宁德时代近三年盈利能力变化」 | 「哪些行业盈利在恶化」 |
| 检索前要做 | 无（直接过滤） | 解析成文档集合 | 文档级路由 |
| 候选集规模 | 5 × 每份 Child 数 | 解析结果 × 每份 Child 数 | 全库 |
| 引用可追溯性 | 最强（用户自己指定） | 强（每份都有元数据） | 依赖引用约束 |
| 默认 | 否 | 否 | **是（新对话）** |

### 2.2 模式 A：指定文档

- 用户勾选 1~5 份，Agent 只在这些文档里检索。
- **5 是软上限**：超过 5 份不阻止，提示「超过 5 份会降低精排效果，建议改用条件筛选」。
- 5 的算式：`fusionLimit=50 ÷ 5 = 10 条/文档`，少于 10 条 Reranker 没有足够样本判断「这份文档里有没有答案」。

### 2.3 模式 B：条件筛选

- 用户选「公司 + 年份 + 报告类型（+ 行业）」，系统把这些条件解析成文档集合，再在该集合内检索。
- **不等于「过滤掉其他文档」那么简单**：必须先解析成 `resolvedDocumentIds`，因为：
  1. 解析结果为 0 时要能明确报「没有符合条件的文档」，而不是静默返回空；
  2. 解析出的份数决定后面走单池还是文档级路由；
  3. 权限过滤（阶段 8）要在解析这一步做，不能等检索出来再剔除。
- 解析出 1 份时，等价于模式 A 单文档；解析出 200 份时，必须先做文档级路由。

### 2.4 模式 C：全库智能检索

- 不指定文档，Agent 在有权限的整个知识库里检索。
- **必须依赖文档级路由（L2）**，否则 chunk 级检索会在全库范围里被长文档主导。
- 现阶段语料只有 2 份文档，L2 未实现前允许退化为单池检索，但要在 trace 里标记 `doc_routing=unavailable`，避免以后忘了它没做。

### 2.5 模式切换规则

| 触发 | 行为 |
|---|---|
| A 模式选了 6 份以上 | 提示「改用条件筛选」，不阻止 |
| B 模式解析出 1 份 | 内部按 A 处理，界面上仍显示 B（不改用户设置） |
| B 模式解析出 0 份 | `SCOPE_EMPTY`，提示放宽条件 |
| C 模式问题里点名了具体公司/年份 | **不自动切模式**，只作为 QU 条件收窄；同时按 2.6 主动建议切 B |
| 用户中途切换模式 | 允许，只影响后续轮次 |

### 2.6 主动建议切 B（不自动切）

C 模式下，若 QU 同时抽出**明确对象**（公司代码/名称）与**明确期间**（年份或报告期），说明用户已经开始「具体研究」，
此时返回一条非错误的提示：

```
「要精确到这家公司这两年，可以切到条件筛选模式，能保证只检索它的年报。」  [ 切换 ]  [ 不用 ]
```

- 只在**本轮问题第一次出现明确对象 + 期间**时提示，同一会话最多提示一次（避免打扰）；
- 不自动切：模式是用户的研究配置，改了会改变后续所有轮次的语义；
- 用户忽略不提示第二次，除非他明确问「怎么限定范围」。

**理由**：默认 C 是为了降低门槛，但用户一旦开始做精读，B 才是正确工具 —— 主动引导比让他自己发现 chip 更有效。

## 3. 检索语义

### 3.1 作用域是上界，QU 不得越界

```
scope=[2025年报] + QU 抽出 docYear=2024
  → 作用域内无匹配 → 不静默回退 → SCOPE_EXTENSION_SUGGESTED
  → 「当前范围是《2025年年度报告》，不含 2024 年报告」+ 三选一
```

这条要改现有行为：现在 `qu_filter_empty_fallback` 是「去掉 QU 条件重来」，在单文档场景下会**悄悄跑到全库**。回退只允许发生在同一作用域内（如「每股收益」在文中写作「基本每股收益(元/股)」，子串落空退回词级召回）。

### 3.2 多文档时的配额

| 问题类型 | 检索方式 |
|---|---|
| 普通（解释/事实） | 单池 top-k：`document_id IN (...)` 统一排序 |
| 比较类（COMPARISON 或跨公司/跨年） | **按文档配额**：每份至少 `ceil(fusionLimit/N)` 条进入精排候选池 |

配额不是讲公平，是防止「A 文档召回 50 条、B 文档 0 条，答案里只有 A」。对比题失败最典型就是这个样子。

### 3.3 对比列陷阱

同一家公司的 2024 年营收，在 2025 年报的对比列里也有。两份都命中时引用该指谁？

**规则：优先取「该数值属于本期」的那份文档**，判据是 `document.period_start / period_end` 与问题所指期间的匹配度，而不是谁的得分高。

| 文档 | 12.64% 出现在 | 引用优先级 |
|---|---|---|
| 2024 年报 | 本期列 | **高** |
| 2025 年报 | 上期对比列 | 低（仅兜底） |

这就是 V6 必须补 `period_start / period_end` 的原因：只有 `doc_year` 分不出「本期」和「上期」。

### 3.4 文档级路由（L2）的触发阈值

| 条件 | 处理 |
|---|---|
| 可检索文档 ≤ 20 且 chunk ≤ 50,000 | 单池 chunk 检索（现状） |
| 超过阈值 | 文档级召回 top-3 → 再在 3 份内做 chunk 检索 |

阈值取 20 的理由：20 份 × 600 chunk = 12,000，仍在精确扫描舒适区（实测 1,284 条 16.6 ms，41,856 条才 276 ms）。

## 4. 界面

### 4.1 新建对话页

```
┌──────────────────────────────────────────────────────┐
│  新建金融研究对话                                     │
│                                                       │
│  你希望 Agent 从哪里查找资料？                        │
│                                                       │
│  ● 整个知识库（默认）                                 │
│    从你有权访问的全部研报中自动检索                    │
│                                                       │
│  ○ 指定公司和时间范围                                 │
│    公司 ▾   年份 ▾   报告类型 ▾   行业 ▾              │
│                                                       │
│  ○ 仅限我选择的文档                                   │
│    ☑ 东方财富 2025 年年度报告            654 段       │
│    ☑ 东方财富 2024 年年度报告            630 段       │
│    已选 2 份 · 超过 5 份会降低精排效果                 │
│                                                       │
│                                   [ 开始对话 ]        │
└──────────────────────────────────────────────────────┘
```

**默认选中 C（整个知识库）**，这是降低首次使用门槛的关键 —— 初学者不该先做文档管理。

### 4.2 会话页常驻 chip

```
┌──────────────────────────────────────────────────────┐
│  [🌐 全库]  ·  [过滤：东方财富 / 2024–2025]  [+ 改]   │
├──────────────────────────────────────────────────────┤
│  用户：2024 年营业收入是多少？                         │
│  AI：11,604,343,090.16 元                             │
│      来源：《东方财富2024年年度报告》p.7 表 5-1  [1]   │
└──────────────────────────────────────────────────────┘
```

chip 必须始终可见 —— 用户任何时候都要知道「系统在哪找资料」。

### 4.3 范围外文档提示卡（核心交互）

```
┌──────────────────────────────────────────────────────┐
│  ⚠ 五粮液 2024 年年度报告不在当前范围内                │
│                                                       │
│  它已存在于你的知识库中。要如何使用？                  │
│                                                       │
│  ● 仅本轮使用（推荐）  不修改会话范围，这轮答完即止    │
│  ○ 加入当前会话        后续问题也可使用                │
│  ○ 不扩展范围          仅用当前文档回答，可能证据不足  │
│                                                       │
│                                   [ 继续 ]            │
└──────────────────────────────────────────────────────┘
```

三选项的语义必须**精确落到后端**：

| 选项 | 后端行为 | 落库 |
|---|---|---|
| 仅本轮使用 | `effectiveScope` = sessionScope ∪ {该文档}，**不改 sessionScope** | 消息快照记 `TURN_ONLY_EXTENSION` |
| 加入当前会话 | sessionScope 更新，后续轮次可见 | 更新会话配置 + 记一条 scope 变更事件 |
| 不扩展范围 | 原范围检索，证据不足就明说 | 无变更 |

**永远不自动扩展**。自动扩展会让「同一问题两次问出不同范围」这种不可复现的行为发生，金融场景不能接受。

### 4.4 「改研究范围」与「改知识库」是两个入口

| 操作 | 入口 | 影响 |
|---|---|---|
| 改模式 / 改范围（加文档、换公司） | 会话页 chip | 只影响本会话后续轮次 |
| 上传 / 删除 / 重新解析文档 | 知识库管理页 | 影响所有会话与用户 |

**从会话中移除一份文档 ≠ 从知识库删除它。** 两个操作在 UI 上不能放在一起，否则用户会误删。

## 5. API 契约

### 5.1 请求

```json
POST /api/chat
{
  "question": "对比贵州茅台和五粮液 2024 年的营收",
  "scope": { "kind": "CORPUS" },
  "extensionPolicy": "ASK",          // ASK | NEVER（AUTO 不提供）
  "scopeOverride": null              // 用户选了「仅本轮」后，前端把合并结果放这里
}
```

三种 scope：
```json
{ "kind": "DOCUMENTS", "documentIds": [7, 38] }
{ "kind": "FILTER", "companyCodes": ["600519","000858"], "years": [2024], "docTypes": ["ANNUAL"], "industries": [] }
{ "kind": "CORPUS" }
```

### 5.2 响应

```json
{
  "answer": "...",
  "sessionScope":   { "kind": "CORPUS" },
  "effectiveScope": { "kind": "DOCUMENTS", "documentIds": [2, 9], "reason": "TURN_ONLY_EXTENSION" },
  "resolvedDocumentIds": [2, 9],
  "citations": [
    { "index": 1, "documentId": 2, "documentTitle": "贵州茅台2024年年度报告",
      "pageStart": 8, "pageEnd": 8, "chunkId": 2101, "quote": "营业收入 ..." }
  ],
  "extensionSuggested": {
    "documents": [{ "id": 9, "title": "五粮液2024年年度报告", "reason": "问题点名了该公司" }],
    "defaultAction": "TURN_ONLY"
  },
  "warnings": ["doc_routing_unavailable"]
}
```

### 5.3 状态码与错误码

| code | 触发 | 前端处理 |
|---|---|---|
| `SCOPE_EMPTY` | B 模式解析出 0 份 | 提示放宽条件 |
| `SCOPE_UNAUTHORIZED` | 解析出的文档无权限（阶段 8） | 提示无权限，不透露标题 |
| `NO_EVIDENCE_IN_SCOPE` | 范围内检索无结果 | 明说没找到 + 「扩大范围」 |
| `extensionSuggested`（非错误） | 范围外有相关文档 | 弹三选一卡片 |
| `MODE_SUGGESTION`（非错误，warning） | A 模式超 5 份 | 提示改用 B |

注意 `SCOPE_EXTENSION_SUGGESTED` 是**正常响应**而不是错误 —— 用户没做错事，只是范围可以更好。

## 6. 数据模型

### 6.1 V6 迁移（阶段 5 前）

```sql
ALTER TABLE document ADD COLUMN period_start date;
ALTER TABLE document ADD COLUMN period_end   date;
-- doc_type 收敛为固定枚举，历史脏值先订正
UPDATE document SET doc_type = 'ANNUAL' WHERE doc_type = 'ANNUAL_REPORT';
ALTER TABLE document ADD CONSTRAINT ck_document_doc_type
  CHECK (doc_type IN ('ANNUAL','SEMI_ANNUAL','Q1','Q3'));
-- 同年同类型不允许重复入库（version 用于重新解析后的多版本）
ALTER TABLE document ADD CONSTRAINT uq_document_identity
  UNIQUE (company_id, doc_year, doc_type, version);
-- B 模式的行业筛选需要
ALTER TABLE company ADD COLUMN industry varchar(64);
```

`doc_year` 保持可空但在应用层强制：年报/半年报/季报必须能推导出 `doc_year`，否则拒绝入库。

### 6.2 阶段 9：会话持久化

```sql
CREATE TABLE conversation (
    id         bigserial PRIMARY KEY,
    title      text,
    scope_kind varchar(16) NOT NULL,     -- DOCUMENTS / FILTER / CORPUS
    scope_json jsonb       NOT NULL,     -- 完整的 sessionScope
    created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE message (
    id              bigserial PRIMARY KEY,
    conversation_id bigint NOT NULL REFERENCES conversation(id) ON DELETE CASCADE,
    role            varchar(16) NOT NULL,
    content         text NOT NULL,
    scope_snapshot  jsonb NOT NULL,      -- 见 6.3
    created_at      timestamptz NOT NULL DEFAULT now()
);
```

### 6.3 scope_snapshot 结构

```json
{
  "session":   { "kind": "CORPUS" },
  "effective": { "kind": "DOCUMENTS", "documentIds": [7, 38], "reason": "TURN_ONLY_EXTENSION" },
  "chunkVersions": { "7": 2, "38": 1 },
  "resolverVersion": "scope-v1"
}
```

`chunkVersions` 必须存：文档会被重新解析（`chunk_version` 递增），历史回答的引用要能指向**当时**那一版。`resolverVersion` 记录作用域解析算法版本，便于解释「为什么当时解析出这几份」。

## 9. 不做什么

- **不做**「用 LLM 自动决定该查哪份文档」—— 不可审计，出错无法复现；文档级路由用向量 + 元数据，不用 LLM；
- **不做**跨租户权限（阶段 8，`scope` 里预留 tenantId 即可）；
- **不做**多轮指代消解（「它」「那份报告」需要短期记忆，阶段 9）；
- **不做**自动扩展范围（见 4.3）；
- **不做**把上一轮检索结果缓存成下一轮的候选集 —— 每轮重新检索，只继承范围与对话上下文。
