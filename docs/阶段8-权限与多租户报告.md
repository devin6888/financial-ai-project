## 怎么读这份报告（先看这 8 个词）

| 词 | 一句话解释（完整版见 docs/术语表.md §9） |
| --- | --- |
| 认证 / 授权 | 认证回答「你是谁」（失败给 401，再登有用）；授权回答「你能干什么」（失败给 409，再登没用） |
| 租户（tenant） | 一个客户的数据边界。本项目租户 1 = 演示数据（东方财富年报），另造一个 `other-test` 租户专门验「什么都看不到」 |
| RLS（Row Level Security） | PostgreSQL 的功能：给表配一条策略后，数据库自己给每条查询补上 `AND tenant_id = 当前租户`，漏写的 SQL 也被兜住 |
| ACL（Access Control List） | 「谁对哪个资源有什么权限」的清单，管**租户内部**（分析师只看自己负责的公司、私有文档只看 owner） |
| 可信上下文 | 服务端从 token 查出来的身份（`TenantContext`）。请求体里塞的 `tenantId` / `userId` 不算数 |
| 401 / 409 | 401 = 没身份或身份无效；409 `SCOPE_EMPTY` = 有身份但一份文档都看不到（语义与「范围内没答案」不同） |
| 越权（broken access control） | 做了没权限做的事，OWASP 排名第一。本项目把 4 类越权都落成可执行用例 |
| 零泄漏门限 | 一条机器可判的门槛：把各类响应正文拼起来扫对象键 / 他人标题 / 他人正文片段，命中数必须是 0 |

## 1. 一句话结论

阶段 8 之前，这个系统的**每一个**接口都是裸奔的：任何人只要能访问 `localhost:8080`，就能拉走全库文档列表、
问出任何一份年报里的数字、拿到 `documentId` 后直接查对象存储键。现在有**三道防线 + 一条可复现的门限**：

1. **身份只从 token 来**：`Authorization: Bearer <token>` → SHA-256 查库 → `TenantContext`。请求体里塞 `tenantId:1, userId:1` 对结果零影响（有专门用例）；
2. **跨租户读 = 0 行**：靠 PostgreSQL 的行级安全策略，不是靠我们每条 SQL 都记得写 `where tenant_id`。证据是 `EXPLAIN` 里数据库自己补出来的过滤条件；
3. **越权 4 类全绿 + 零泄漏门限命中数 = 0**：枚举、传他人 id、语义相关但无权限、对象直链，各有可执行用例。

过程中抓到三个真问题（详见 §6）：

- **空集 = 全库**：作用域被 ACL 过滤成空之后，检索层把空集理解成「不过滤」，等于放开全库。这是本阶段最危险的一个语义陷阱；
- **计数本身是泄漏**：警告里写 `scope_acl_hidden_2`，等于告诉调用方「你还有 2 份看不见的文档」；
- **成对条件装配**：用两个 `@Profile` / `@ConditionalOnProperty` 选实现，会导致两个 Bean 同时存在（启动直接失败）。

## 2. 为什么阶段 7 之后还要做这一步

### 2.1 改造前：所有端点裸奔

| 端点 | 改造前谁能访问 | 泄漏什么 |
| --- | --- | --- |
| `POST /api/chat` | 任何人 | 任何一份年报的任何数字，带页码引用 |
| `GET /api/scope/documents` | 任何人 | **全库文档清单**（不用猜 id） |
| `POST /api/documents` | 任何人 | 能往别人库里塞文档 |
| `GET /api/documents/{id}` | 任何人 | 标题、公司、解析状态，甚至 `object_key`（对象直链的入口） |

「本地跑着玩」时这些都不算问题。但设计文档 §15 把多租户与 ACL 列为 V1 范围，理由很实在：
只要这套系统将来服务第二个客户，「谁能看哪份文档」就必须是**数据层**保证的，
而不是「记得在每条 SQL 里加条件」。

### 2.2 改造后：四道门

~~~text
请求进来
  │
  ├─ ① 认证（AuthenticationFilter）
  │     有没有 Authorization: Bearer <token>？→ 没有：401 AUTH_REQUIRED
  │     SHA-256(token) 查 app_user → 查不到：401 AUTH_INVALID
  │     查到 → CurrentUser(userId, tenantId, roles) 写进 TenantContext
  │
  ├─ ② 租户（TenantAwareDataSource + RLS）
  │     借连接时：SET ROLE finagent_app + set_config('app.tenant_id', 1)
  │     之后任何 SQL 都被数据库补上 AND tenant_id = 1  ← 跨租户在这里被拦住
  │
  ├─ ③ 租户内可见性（AclScopeAuthorizer）
  │     这批 documentId 里，哪些这个账号能读？
  │     管理员 → 本租户全可见；其他人 → 自己的私有文档 OR 显式授权（用户级 / 角色级，可带过期）
  │     过滤完为空 → 409 SCOPE_EMPTY（绝不返回空列表）
  │
  └─ ④ 查询范围（C5 的「作用域是上界」）
        这一轮实际查哪几份文档 → 下推成 SQL 的 document_id IN (…)
~~~

### 2.3 为什么不能只靠应用层 where 条件

| 只靠应用层 | 靠 RLS |
| --- | --- |
| 每条新 SQL 都得记得写 `where tenant_id = ?`，漏一条就是漏洞 | 数据库自己补，漏写也被兜住 |
| 一个 `SELECT *` 的调试代码就能把全库拉出来 | 同一条 SQL 在运行时角色下只返回本租户行 |
| 靠 code review 保证（人会累） | 靠一条策略保证（不会累） |

代价是**必须让运行时用非 owner 角色**：表 owner 默认绕过 RLS。所以 V8 建了 `finagent_app` 角色，
连接借出时 `SET ROLE`，而 Flyway 迁移仍用 owner（否则迁移会被自己的策略拦住）。

## 4. 契约 C11 摘要

完整版见 `docs/关键契约.md` 的 C11。四条最容易被写错、也最容易被改回去的：

| 规则 | 为什么 |
| --- | --- |
| 身份只来自 `TenantContext`；请求体/查询串里的 `tenantId` 一律不读 | 否则客户端传什么就是什么，跨租户只是一个 JSON 字段的事 |
| ACL 过滤后为空必须抛 `ScopeEmptyException`，**不许**返回空列表 | 空列表在检索层的语义是「不过滤 = 全库」 |
| CORPUS 被 ACL 收窄后必须把 id 下推 SQL（`ResolvedScope.aclNarrowed`） | 否则 ACL 只影响提示词，不影响真正取到哪些块 |
| 跨租户查详情返回 404，不返回 403 | 403 等于确认「这个 id 存在」，本身就是信息泄漏 |

另外两条与写路径有关：`document.tenant_id` 来自当前用户；`document_chunk` / `financial_fact` 的 `tenant_id`
从所属 `document` 行查出来（不让调用方传）——父子一致性不该靠调用方保证。

## 5. 实测

### 5.1 认证的成本

每次请求查一次令牌表，实测（`EXPLAIN ANALYZE`，5 次取后 4 次）：

| 次数 | 执行时间 | 计划 |
| --- | --- | --- |
| 首次（含解析/生成计划） | 4.922 ms | `Nested Loop Left Join` + `Index Scan using app_user_api_token_hash_key` |
| 2~5 次 | **0.080 / 0.084 / 0.119 / 0.124 / 0.125 ms** | 同上，`shared hit = 6` |

这个数字是「要不要换 JWT」的判据：我们每个请求本来就要开数据库连接（RLS 需要会话变量），
所以查一次索引几乎免费；换来的是「改权限立刻生效」。详见 `docs/技术选型.md` §2.8.1。

### 5.2 RLS 的三条探针

库里租户 1 有 4 份文档（id 2 / 4 / 7 / 38）。同一张表、同一条 SQL，只换角色和会话变量：

| 连接 / 会话变量 | `SELECT count(*) FROM document` |
| --- | --- |
| 表 owner（Flyway / 测试夹具） | **4**（RLS 绕过） |
| `SET ROLE finagent_app`，未设 `app.tenant_id` | **0** |
| `SET ROLE finagent_app` + `app.tenant_id = '1'` | **4** |
| `SET ROLE finagent_app` + `app.tenant_id = '2'` | **0** |

决定性证据是执行计划里数据库自己补的条件：

~~~text
EXPLAIN (COSTS OFF) SELECT id FROM document WHERE id = 7
→ Seq Scan on document
    Filter: ((id = 7) AND (tenant_id = (NULLIF(current_setting('app.tenant_id'::text, true), ''::text))::bigint))
~~~

我们只写了 `where id = 7`，`tenant_id` 那半句是数据库加的。

## 6. 抓到的 7 个问题

### 6.1 空集 = 全库（最危险的一个）

**现象**：ACL 把 CORPUS 作用域过滤成空之后，代码走的是「空集就不加过滤」的分支，检索直接扫全库。
表面上接口返回了 409，但只要有任何一条路径把空列表传下去，ACL 就完全失效。

**原因**：检索层的「空 documentIds」本来表示「调用方没指定文档」（= 全库），这是一个合法的默认值；
而 ACL 过滤后的空集是「一份都不能看」，两者语义相反，却共用同一个表示。

**修法**：`ResolvedScope` 增加 `aclNarrowed` 标记，作用域解析时若「过滤后比候选少」就置 true；
`HybridRetriever.applyScope` 只在 `CORPUS && !aclNarrowed` 时保持「不过滤」，否则把 id 下推 SQL。

**教训**：一个字段承担两种相反语义时，迟早会有一边被解释错。要么加标记，要么换类型。

### 6.2 计数本身是泄漏

**现象**：拒答响应里带着 `scope_acl_hidden_2`，测试断言「正文无数字」直接失败。

**原因**：warning 是为了排查方便写的 `scope_acl_hidden_` + 条数，但它会原样进响应体。
「你有 2 份看不见的文档」也是信息 —— 攻击者靠它就能确认库里有多少数据。

**修法**：警告改成不带数字的 `scope_acl_hidden` / `scope_unauthorized`，精确条数写服务端 debug 日志。

**教训**：凡是要进响应体的字符串，都按「给外部看」的标准审一遍；排查信息和对外信息不该同源。

### 6.3 成对条件注解选实现 → 两个 Bean

**现象**：`@Profile("!test")` 与 `@Profile("test")` 两套实现，在非 test profile 下同时注册（一个来自组件扫描、一个来自测试配置），
启动报 `NoUniqueBeanDefinitionException`；换成成对的 `@ConditionalOnProperty` 又有空串双命中的坑（api-key 为空串时两个条件都成立）。

**修法**：`ScopeAuthorizerConfig` 里一个 `@Bean` 工厂方法，用 `properties.aclEnabled()` 二选一。

**教训**：「选哪个实现」是一个 Java 分支，不是一个注解组合。注解表达不了「互斥」，工厂方法能。

### 6.4 Hikari 绑不上 `url`

**现象**：`@ConfigurationProperties("spring.datasource")` 打在 `HikariDataSource` 上，启动报
`IllegalArgumentException: dataSource or dataSourceClassName or jdbcUrl is required`。

**原因**：配置文件里写的是 `url`，Hikari 的属性叫 `jdbcUrl`，宽松绑定不会跨名字映射。

**修法**：用 Spring Boot 的 `DataSourceProperties.initializeDataSourceBuilder()` 构建（它认 `url`），再包一层 `TenantAwareDataSource`。

### 6.5 Flyway 单独给账号就必须同时给 url

**现象**：为了用 owner 跑迁移、运行时用 `finagent_app`，给 Flyway 单独配了 `user` / `password`，
启动报 `Unable to find suitable method for url`。

**修法**：`spring.flyway.url` 也得显式给（一旦自己配账号，Flyway 就不再复用 `spring.datasource` 的 url）。

### 6.6 V9 的 REVOKE 打断了测试夹具

**现象**：ACL 测试要插 `resource_grant` 行，报权限不足。

**原因**：V9 把认证表的写权限从 `finagent_app` 收走了；而测试主线程如果设了 `TenantContext`，
借到的连接就是运行时角色，写认证表必然被拒。

**修法**：`@AfterEach` 第一行 `TenantContext.clear()`，夹具的增删都在「无上下文（owner）」下做。

**教训**：双角色模型下，「谁在写」比「写什么」更容易出错。测试夹具也要明确自己站在哪个角色上。

### 6.7 `uq_document_identity` 是部分唯一索引，`pg_constraint` 里查不到

**现象**：造测试文档时撞 `duplicate key value violates unique constraint "uq_document_identity"`，
但按 constraint 名去查元数据查不到。

**原因**：它是 `UNIQUE (tenant_id, company_id, doc_year, doc_type, version) WHERE company_id IS NOT NULL AND doc_year IS NOT NULL`，
属于**部分索引**（index），不是约束。

**修法**：测试文档用 `doc_year = 1999` 之类不会与真实年报冲突的年份。

## 7. 已知限制

| # | 限制 | 影响 | 什么时候必须改 |
| --- | --- | --- | --- |
| 1 | ACL 过滤在「取到候选之后」做，没下推进 SQL | 文档几百份时每次作用域解析都要把候选全捞出来 | 单租户文档数 > 200 |
| 2 | 后台任务（Kafka worker）没有租户上下文，`parseDocumentAsync` 走 fallback 租户 1 | 多租户上线后，异步任务会写到租户 1 | 接第二个租户之前 |
| 3 | RLS 没有 `FORCE`，表 owner 绕过 | 任何用 owner 连接跑的代码（CLI、测试、将来的报表脚本）不受租户约束 | 出现「用 owner 跑业务代码」时 |
| 4 | 没有令牌缓存（每请求一次索引查询） | 0.1 ms 级开销，当前可忽略 | QPS 上千时加 Redis 缓存 |
| 5 | 没有登录 / 刷新 token / 用户管理接口，token 只能直接改库 | 只能演示 | 要做「多用户自助」时 |
| 6 | 角色只有 ADMIN / ANALYST / VIEWER 三个 code，没有权限点（permission）粒度 | 细粒度只能靠 `resource_grant` | 需要「同一角色不同能力」时 |
| 7 | 没有审计日志（谁在什么时候看了哪份文档） | 合规场景不够 | 设计文档 §17 审计要求落地时 |
| 8 | 前端没接 token | 浏览器直接调会被 401 | 做前端时 |
