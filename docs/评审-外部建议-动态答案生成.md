# 评审：外部建议《RAG回答设计》（ChatGPT，2026-10-30）

> 被评对象：`docs/temp/RAG回答设计.md`（805 行，十条）。
> 结论：**方向对，但约八成内容已经在阶段 16 / ST17 计划里**；真正新增的 4 条已并入 ST17（§2），
> 不采纳的 3 条给理由与「什么时候再考虑」（§3），另有 2 处事实需要纠正（§4）——它读的是**单次运行的答案**，不是我们的能力边界。

## 0. 一句话结论

它说的「不要固定模板、要动态章节、要证据驱动、要程序校验数字」——这四件事我们**已经在做或已排期**；
它真正补上的是三件我们没想清楚的细节：**章节计划要落成可回放的中间表示（IR）**、**章节要能指到具体证据**、
**检索方向要按问题类型选而不是写死两路**。它的前端选型（Vue Markdown + DOMPurify）与我们已定的 C22 冲突，不采纳（§3.1）。

## 2. 采纳的四条（已并入 ST17）

### 2.1 章节计划要落成 IR（可回放、可分析）

它说得对的地方：**计划不只要驱动本次生成，还要能事后检查**。否则「为什么这题只有两节」「为什么成本节没出现」永远只能靠猜。

落点（ST17 Task 1 新增 1.7）：

- `AnswerSectionPlan` 改为带结构的列表（`id` / `title` / `purpose` / `layout` / `evidenceNos`），不再是纯字符串；
- 写进 `AnalysisState.ANSWER_PLAN`（全是字符串与数字，可序列化，符合 C18.2「结果不进状态」的边界）；
- `stage(compute).detail.plan` 带出章节标题；`AnswerService` 把整份计划写进 `ChatTrace`；
- 前端**不展示**（它的建议），只在 trace 里可查 —— 与 C18.3「final 是运行视图」不冲突。

### 2.2 章节要能指到具体证据（软提示，不硬切）

它建议 `AnswerSection.evidenceIds`，理由是「不要把全部检索结果无差别交给 LLM」——这一点击中我们的真问题：
阶段 16 Q1 的归因段写成了「妙想 AI」，而手续费/利息净收入的块（7531）就在上下文里。20 个块平铺，模型没有「这节该看哪几块」的提示。

但**不采纳硬切分**（按章节把上下文拆成互不相通的几份）：父块整段展开、邻居补全（`ContextBuilder` 第 3c 步）本来就要跨块引用，
硬切会让「跨节对比」失效、token 预算碎片化。

折中（ST17 Task 1 新增 1.8）：**软提示**。章节计划带「本节优先证据」的 E 编号（由章节关键词与块标题匹配得出），写进【回答要求】：

```text
三、经营数据：优先看 E5、E7（交易额、保有规模、销售额）
```

证据仍然全量给模型，只是告诉它「这节先看这几条」。成本是一次字符串匹配，收益可测（Q1 归因是否指向 7531）。

### 2.3 检索方向表（替代写死的两路）

| 方向 | 查询词（拼在原问题后） | 触发条件 |
| --- | --- | --- |
| 核心指标 | （不拼，用原问题） | 总是 |
| 结构 | 分行业 分产品 分地区 占比 | 形态含 BREAKDOWN / OVERVIEW |
| 经营数据 | 交易额 保有规模 销售额 客户数 | `profile.hasOperatingMetrics()` |
| 成本费用 | 成本 费用 毛利率 期间费用 | `profile.hasCostTable()` |
| 盈利 | 净利润 归母 扣非 净利率 | 问题含净利润/盈利/利润 |
| 同比 | 同比 增减 变动 | 形态含 COMPARISON |

规则：**按形态与证据画像选 2~4 个方向**，不是每次都跑六路（与「按需 multi-query」一致）；车道总数仍受 `MAX_LANES = 8` 约束。

### 2.4 「规则给候选 + LLM 只做取舍」列为可选扩展（不排期）

它主张 LLM 输出 JSON 计划。不直接采纳，三条理由：

1. **多一次 LLM 调用**：`qwen-plus` 一次结构化输出 1~2 s，首字延迟从 6.6 s 变 8 s 以上（阶段 13 刚把这个数压下来）；
2. **不可断言**：A1~A16 里「章节数 ≥ 3」「归因段存在」依赖计划稳定，LLM 每次给不同章节会让验收变成抽样；
3. **闸门本来就该是程序**：「没有费用表就不出费用节」是事实判断，不是创作判断。

折中方案记进 ST17 §6 风险表：**规则先算候选集，LLM 只能在候选集内挑子集并改标题**（输出受 schema 约束，失败回退规则结果），
默认关闭，等规则版跑满 20 题再评估。

## 3. 不采纳的三条

### 3.1 Vue Markdown 渲染器（v-html + DOMPurify）

C22 已经否过一次，理由仍成立：

- **chip 点不开**：引用角标是 Vue 组件、`@click` 跳 PDF 页；`v-html` 后事件绑不上，只能事件委托 + `data-` 属性，或把 HTML 再拆回 segments（等于走回自写解析）；
- **每次流式增量都要跑一遍 DOMPurify**，白名单要收到十几个标签，XSS 面变大；
- **体积**：`marked` + `DOMPurify` 约 +25 KB gzip，自写版本次只 +1.7 KB。

「前端负责渲染」我们同意 —— 本来就是前端渲染，只是解析器自己写。**换库触发条件在 C22.4**（3 层嵌套 / `answer.ts` >300 行 / 一个阶段新增 ≥3 种块 / 两次渲染 bug 查不出原因），命中即换，不是现在。

### 3.2 通用 Claims 抽取器（Evidence → Claims → Validation）

方向对，但我们已有更窄更硬的版本：

| 它要的 | 我们有的 | 差别 |
| --- | --- | --- |
| 从证据抽事实声明 | `FactCollector`（只从表格抽：指标/期间/值/单位/原文/chunkId） | 只抽**能校验的数字**，不抽自然语言主张 |
| 每条声明关联证据 | `ReportedFact.evidenceNo` + `ComputedFact.evidenceNos` | 等价 |
| 校验数字/单位/期间/口径 | `FactGuard` + `UnitConverter` + 白名单 | 更严（模型自算的比率会被抓） |
| 检查结论是否有证据支持 | 提示词「禁止推断因果」+ `gapClaims`（ST17） | 我们是「不许说」而非「说得对不对」 |

通用 claims + NLI 判定要再引一个模型或一套规则，收益是句子级归因审计，成本是每次生成后多一轮调用。**放到阶段 18 之后再评估**。

### 3.3 Langfuse / 外部可观测平台

已有 `ChatTrace`、`agent_run_step`、评测集（`AnswerEvalTest` / `RetrievalEvalTest` + 门槛）。
引入 Langfuse 属运维与成本决策，不是产品能力；单机演示多一个外部依赖不划算。§2.1 的「计划进 trace」已让排查够用。

## 4. 两处需要纠正的事实

1. **「你的 RAG 没有净利润 / 分地区 / 交易额 / 保有 / 费用」** —— 把「某一次运行的 8 条证据」当成了能力边界。库里这些块都在，阶段 16 的答案也引用过其中数字。真问题是**召回**（D4），ST17 Task 2 解决。
2. **「Answer Planning 在 Retrieval 之后」它说对了**，ST17 也这么设计（`AnswerSectionPlan.of(shapes, profile)` 依赖检索出的证据画像）。但要强调：**不能放在 `plan` 节点**，那时还没检索、`EvidenceProfile` 是空的；落点是 `compute` 节点（抽完事实、answer 之前）。
