# RAG 知识库系统：文档重索引（Reindex）与向量元数据管理架构教程

## 一、 核心概念与背景

在 RAG（检索增强生成）知识库与企业级文档处理管线（Document Pipeline）中，一个文档从原始文件到最终可被检索，通常要经历以下核心处理链条：

**原始文件 (Source)** ──> 解析 (Parse) ──> **纯文本** ──> 切片 (Chunk) ──> **文本块** ──> 向量化 (Embed) ──> 向量/索引



### 为什么不能简单地做“全量重新解析”？

如果系统每次遇到微小的变更（例如修改文档标题、调整切片大小、更新向量模型）都采用全量重新解析（`FULL_REPARSE`），会产生严重的工程副作用：

- **计算资源开销大**：复杂 PDF 版面分析、表格提取及 OCR 解析会极大地占用 CPU/GPU 算力。
- **API 成本高昂**：频繁且无差别的增量数据重新调用商用 Embedding 接口会带来高额费用。
- **吞吐量急剧下降**：对海量文档做全量处理会导致数据处理管线长时间阻塞，影响上层业务。

为了实现**按需更新、精准增量刷刷索引**，系统通常会在事件驱动架构中定义细粒度的 `document.reindex` 模式以及配套的 Chunk 级元数据控制机制。

## 二、 `document.reindex` 四种模式详解

| **模式**             | **影响范围**      | **核心处理逻辑**                                             | **典型应用场景**                                             |
| -------------------- | ----------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **`RETRIEVAL_ONLY`** | 仅检索/元数据     | **不重新解析、不重新分块、不重新向量化**。  仅更新文档属性、权限控制、分类标签，或刷新倒排索引/BM25 权重。 | 修改文档阅读权限、调整后台检索加权策略、更新文档元数据标签。 |
| **`RECHUNK`**        | 文本切片 + 向量化 | **保留已有解析文本，重新切分**。  跳过文档解析阶段，依据新分块策略（如 `chunk_size` / `chunk_overlap`）重新切片，并重新生成新 Chunk 的向量。 | 调整分块参数（如发现 Chunk 粒度过小，需调整切片大小）。      |
| **`REEMBED`**        | 向量生成          | **分块与文本保持不变，仅重新向量化**。  读取现有 Chunk，调用新 Embedding 模型重新计算特征向量并更新向量数据库。 | 底层 Embedding 模型升级或版本更替，文本分块边界未发生变化。  |
| **`FULL_REPARSE`**   | 全管线重跑        | **走完整个 Pipeline 的完整流程（兜底机制）**。  重新解析源文件（OCR/版面分析） $\rightarrow$ 重新分块 $\rightarrow$ 重新向量化 $\rightarrow$ 重建全量索引。 | 替换/更新了原始源文件，或底层文档解析器（Parser）算法升级。  |

## 三、 Chunk 级三元组元数据管理策略

为了在 `REEMBED` 或增量刷新时精准圈定重新向量化的范围，系统需在 **Chunk（文本块）级别** 维护三个核心元数据字段，而非仅仅绑定在文档层级：

1. **`embedding_model`（向量模型标识）**：标记生成该向量所使用的底层模型名称（如 `bge-large-zh-v1.5`、`text-embedding-3-small`）。
2. **`embedding_version`（模板/配置版本）**：标记组装文本块时所使用的模板或参数版本（如包含了上下文拼接前缀 `[分类]-标题-内容` 的规则版本号）。
3. **`embedding_text_hash`（文本哈希指纹）**：对最终送入 Embedding 模型的内容串计算的 MD5/SHA-256 哈希值。

### 为什么必须记录在 Chunk 级别？

- **局部差分计算（Diff）**：一篇长文档包含上百个 Chunk，若用户仅在线修改了其中一小段文本，通过比对 Chunk 级的 `embedding_text_hash`，系统可以跳过未变更的 Chunk，**仅重新向量化被修改的那 1 个 Chunk**。
- **变更范围判断**：在升级向量模型或更新拼接模板时，系统可直接筛选 `WHERE embedding_model != 'new_model'` 的 Chunk 节点进行精准批量更新。

## 四、 核心机制对比：换模型 vs 重新切片

在系统演进过程中，需要清晰区分以下两类更新场景的技术表现：

### 1. 纯粹升级 Embedding 模型（场景：`REEMBED`）

- **特点**：分块策略未变，原始文本内容与 Chunk ID 保持固定（1:1 映射）。
- **对应关系**：新旧向量完美对应。系统拿着固定的 Chunk ID 重新调用新模型获取向量后，直接在向量数据库中做 **Update（覆盖写）** 即可。

### 2. 调整分块策略（场景：`RECHUNK` 或 `FULL_REPARSE`）

- **特点**：文本切分边界改变（如 10 个旧 Chunk 重新切分为 6 个新 Chunk）。
- **对应关系**：旧 Chunk 结构失效，新旧 Chunk **无法直接对应**。
- **处理逻辑**：系统需作废该文档下所有旧 Chunk 记录，生成新 Chunk 并计算 Hash，随后在向量数据库中执行 **Delete & Insert（先删后增）** 操作。

## 五、 高级架构拓展：多模型共存模式（Multi-Model Coexistence）

在复杂企业级场景中，允许同一文档或知识库中不同的 Chunk 绑定不同的 Embedding 模型。

```
                         ┌───> [Chunk 1: 纯文本] ───> Model A (1024维) ───> Vector DB (Collection A)
[Document Source File] ──┤
                         └───> [Chunk 2: 表格数据] ─> Model B (1536维) ───> Vector DB (Collection B)
```

### 1. 应用场景

- **异构数据处理**：纯文本采用通用语义模型（如 `bge-large`），而表格/复杂图表文本使用专精多模态或表格理解的模型。
- **线上灰度升级**：大规模数据升级过程中，旧数据保留在原模型索引，新写入或修改的数据接入新模型，避免停机或瞬间倾泻过多 API 请求。

### 2. 工程实现关键点

- **存储隔离**：因不同模型生成的向量维度（Dimension）与空间分布不同，**绝对不能混存在同一个向量 Collection 中**。向量数据库层面必须按照模型划分不同的 Collection/Partition（如 `col_bge_1024`、`col_openai_1536`）。
- **检索与重排**：检索时依据多 Collection 维度并发召回候选集，最后通过外层统一的 **Reranker（重排模型）** 打分对齐后交付 LLM 拼接上下文。
