# 阶段 22：一张图 + 运行时审批闸门

> 怎么读这份报告：先看 §0 一句话结论；§1 是结果总览；想改代码看 §2；想复现看 §7。专业词（编译产物、中断、检查点）见 `docs/术语表.md`。

## 0. 一句话结论

LangGraph4j 1.9.7 支持**节点自己决定这次要不要停**（`InterruptibleAction`），所以「要不要人批」从**编译期配置**变成了**状态里的一个布尔值**：
两张图（`fastGraph` / `hitlGraph`）合并成一张，同一个实例既跑「直接出答案」也跑「停下来等审批」。

## 2. 做了什么

### 2.1 起因（两个问题叠在一起）

1. 审批触发条件只看作用域：作用域里有 2 份年报（2024、2025）+ 问题里没写 4 位年份 → 一律弹（`AmbiguityDetector`）。
   它不判断「这是不是文档问题」，所以「【数值】表格是不是程序拼的」也会弹。
2. 卡片文案写死了「确认后才会检索并生成」，但审批点在 `approve`，位于 `retrieve → verify` **之后** —— 检索早跑完了。

第 2 条是结构问题：要让「确认理解」名副其实，断点得前移到检索之前；而 `interruptsBefore` 是编译期配置，
只能编两份图按请求选。要按状态动态停，只能换机制。

### 2.2 换的机制：`InterruptibleAction`

节点动作同时实现 `AsyncNodeActionWithConfig` 与 `InterruptibleAction`，库在调用 `apply` **之前**先问
`interrupt(nodeId, state, config)`：返回非空就静停（`apply` 一次都不执行），返回空就照常执行。
库自带的 `AgentEx.ApprovalNodeAction` 就是这套写法（不是我们发明的用法）。

### 2.3 改动清单

| 文件 | 改什么 |
| --- | --- |
| `agent/ApprovalGate.java`（新增） | 实现两个接口；`interrupt()` = `approvalAllowed && decision 为空`；`apply()` 返回空 Map |
| `agent/AnalysisGraph.java` | 删 `cachedFast`/`cachedHitl` 与 `build(boolean)`，只留 `graph()`；`approve` 节点换成 `ApprovalGate`；去掉 `interruptsBefore`；`warmUp()`/`mermaid()` 复用同一张 |
| `agent/AnalysisState.java` | 新增键 `approvalAllowed`（Boolean，默认 false）与 getter |
| `agent/AgentRunService.java` | 参数 `hitl` 改名 `approvalAllowed` 并写进初始状态；删 `CompletedGraph` 与 `fast()/hitl()`；`resume` 与 `stateOf` 都用 `graph.graph()` |
| `agent/AgentStreamService.java` | 只改注释（歧义判定仍在开跑前做，但结论用来种状态而不是选图） |
| `agent/AgentGraphConfig.java` | 注释：预热一张 |

### 2.4 没改的部分（故意的）

- `settle()` 判断「停在谁前面」仍看 `getState(cfg).nextNodeId()` —— 动态中断后它同样等于 `approve`；
- 时间线仍跳过 `approve`（`AgentRunService` 里那一行 `continue`），不会多出「人工审批」行；
- `resume` 仍是 `GraphInput.resume(patch)`，把 `decision` / `decisionNote` 合并进状态。

## 4. 踩到的坑

### 4.1 恢复时会重新进入节点（不改就死循环）

**现象**：如果 `interrupt()` 只判断 `approvalAllowed`，点「通过」后会再停一次，永远出不来。
**原因**：resume 不是「跳过该节点」，而是「重新执行该节点」；`interrupt()` 会被再问一次。
**修法**：判断里加 `!state.decision().isBlank()` —— 已经批过就返回空。
**教训**：动态中断的正确性不在「第一次停」，而在「第二次别停」。

### 4.2 用条件边绕过 approve 也能做，但没必要

本来可以保留 `interruptsBefore`，在 `verify` 后加条件边「需要审批 → approve，否则 → compute」。
但那要求「判断」写在**前一个节点**里，且节点名仍然被编译期钉死一个中断点；用 `InterruptibleAction` 后判断就在节点自己身上，语义更直白、也少一条边。

### 4.3 同步接口必须永不停

`ask()`（非流式 `/api/chat`）没有通道接收审批，若它停在 `approve` 前就永远收不了尾。
所以 `approvalAllowed` 由调用方种：流式端点 = 歧义判定结果，同步接口恒 false。**这条不能靠「应该不会发生」**。

## 5. 与预期的偏差

1. **不是性能改造**：建图 0.1 ms、常驻 4.9 KB，合并两张图省下的东西可以忽略；真正的收益是「一张图 + 一个决策点」。
2. **审批点当时没前移**（B 部分已前移，见 §8）：A 阶段仍在 `verify` 之后，所以「点了通过也不改变检索」；
3. **审批卡内容当时一字未改**（B 部分已重做，见 §8）。

## 8. B 部分：审批卡从「点一下」变成「能纠正」（2026-11-03 下午）

### 8.1 用户的三条要求

1. 候选可让用户点；
2. 「按意见修改」由我判断改动程度 —— 最理想是「参数缺失时让用户补一句话」（例：问 2024 年情况、缺指标时，弹框输入「2024年的总营收」），改动太大就暂时删按钮；
3. 非文档问题直接回答能力边界。

### 8.2 结构性前提：审批点前移到 plan 之后

如果闸门仍在 verify 之后，用户在卡片上选「只看 2024 年」，检索已经跑完了 —— 选什么都不可能改变证据。所以顺序改成：

```text
understand → plan ─┬─ 可答 ──▶ approve ─▶ retrieve → verify …
                    └─ REFUSE ─▶ respond_insufficient
```

- plan 的条件边由三标签（direct/decompose/refuse）简化成两标签（review/refuse）：拆分与否是 retrieve 节点内部的事；
- verify 的 enough 直接去 compute，不再经过 approve；
- approve 是透传节点，不发 stage（e2e 的 phases 因此是 retrieve, verify, compute, answer, cite_check）。

### 8.3 停不停的三个条件（少一个就出错）

```java
if (!state.approvalAllowed()) return Optional.empty();      // 同步接口没有通道收审批
if (state.approvalReasons().isEmpty()) return Optional.empty();  // 没说不清 → 不打扰
if (!state.decision().isBlank()) return Optional.empty();   // 恢复会重入节点，必须这半句
```

approvalReasons 由 understand 写（AmbiguityDetector.reasons(scope.documents(), question)），和闸门读的是同一份状态 —— 所以「为什么弹」和「弹的时候显示什么原因」不可能对不上。

### 8.4 卡片长什么样

```text
先确认一下理解   没说看哪一年，确认后才会检索并生成
[没说看哪一年]
检索范围 2024 / 2025 年   年份 未指定（按范围里全部年份）
公司 300059              指标 营业总收入、净利润
(2024 年报（1 份）) (2025 年报（1 份）) (两份都看（2024 + 2025）)
[也可以补一句，例如：只看 2024 年的总营收]
还没开始检索；确认后才召回证据并生成答案。
[按这个继续] [驳回]
```

三个交互都对应一段后端逻辑（AgentRunService.approvalPatch）：

| 用户动作 | 请求体 | 状态变化 |
| --- | --- | --- |
| 点「2025 年报」→ 按这个继续 | {decision:"APPROVE", yearFrom:2025, yearTo:2025} | YEAR_FROM/YEAR_TO=2025，计划追加「人工指定：2025 年」 |
| 点「两份都看」→ 按这个继续 | {decision:"APPROVE"} | 只写 decision，不动检索条件 |
| 补一句 → 按补充继续 | {decision:"EDIT", note:"只看2024年的总营收"} | REWRITTEN_QUERY = 原检索式 + 空格 + note，正则抽出 2024 → YEAR_FROM/YEAR_TO |

**为什么 EDIT 不重跑 QU**：QU 是 3~4 秒的模型调用；补充文本里的年份一条正则就够，指标词本来就在检索式里。代价写清楚了：只换指标不改 metrics 状态。这是有意的取舍，不是遗漏（C17 §17.5）。

### 8.5 非文档问题：答能力边界，不弹卡

OffTopicDetector.isOffTopic 三条同时成立才判：
1. 没有指标、没有公司、没有年份（QU 结果为空）；
2. 原文里没有 4 位年份、没有文档词（年报/报告/财报/文档/披露/页…）；
3. 命中对话/界面用词（你、刚才、表格、按钮、界面、系统、程序、接口、部署…）。

命中后 understand 写 REFUSE_REASON 直接返回 → plan 走 refuse → respondInsufficient 输出能力边界文案，warning = off_topic。**只拦一眼能看出在问系统的话**；「经营情况怎么样」这种拿不准的仍走正常检索。

### 8.7 已知边界

- **公司候选只在多公司作用域出现**：本项目语料只有东方财富一家，所以真链路上看不到公司 chip；
- **审批载荷里的 evidence 为空**：因为还没检索。卡片改成显示「还没开始检索」，不再显示「已检索到 N 条」；
- **补充文本里的指标不写回 metrics**：影响的是检索文本，不是结构化理解。要真重理解，得在 EDIT 里再跑一次 QU（4 秒），目前不值得。

### 8.8 真链路验证（2026-11-03 12:24，8081，demo 账号）

**第一次请求**（`POST /api/chat/stream`，问题「营业总收入和净利润分别是多少」）：

```text
status=200   events = stage > stage > approval
approval.runId=caf1be41…  status=WAITING_APPROVAL  steps=3（understand / plan / approval SKIPPED）
approval.ambiguity.reasons   = [year_not_specified]
approval.ambiguity.candidates= 2024 年报（1 份） / 2025 年报（1 份） / 两份都看（2024 + 2025）
approval.ambiguity.understood= queryType=SEMANTIC_EXPLANATION, metrics=[营业总收入, 净利润]
approval.evidence=[]   ← 还没检索，所以卡片显示「还没开始检索」
```

**点「2025 年报」并续跑**（`POST /api/agent/runs/{id}/resume`，body `{decision:APPROVE, note:"只看2025年", yearFrom:2025, yearTo:2025}`）：

```text
events = stage ×2 > meta > stage > delta ×18 > stage ×2 > final
final.status=DONE  citations=3
answer=营业总收入为 16,067,741,039.51 元（≈160.68 亿元）[E1][E2]；归属于上市公司股东的净利润为 12,084,594,947.22 元（≈120.85 亿元）[E2][E3]。
plan 末尾多了一行：「人工指定：2025 年」
```

三点值得记：
1. `steps` 只有 3 条就停了 —— 审批点确实在 `retrieve` 之前（旧版本停在这一步时已经跑过检索，`steps` 是 5 条）；
2. 恢复后 `plan` 里能看到「人工指定：2025 年」—— 说明选择真的写进了状态，而不只是回了句「收到」；
3. 答案是 2025 年的数（16,067,741,039.51），不是 2024 年的 11,604,343,090.16 —— 点选生效的证据在这里。
