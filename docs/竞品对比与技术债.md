# 竞品对比与技术债（国内开源 RAG 产品）

> 写作日期：2026-10-28　｜　对比对象：国内主流的开源 / 免费 RAG 产品　｜　我方：本项目（阶段 1~10 已完成）
> 资料口径：产品功能取自各自 GitHub README 与公开评测文章（2026 年）；我方数字全部来自本仓库实测（行号、SQL、测试计数）。
> 说明：各产品迭代很快，这里记录的是「2026-10 时点的公开信息」，没有逐一把它们自部署跑一遍——对比目的是找出我们该补什么，不是给它们排名。

## 怎么读这份文档（先看这 6 个词）

| 词 | 一句话解释（完整版见 `docs/术语表.md`） |
| --- | --- |
| RAG | 检索增强生成：先从文档里找出证据，再让模型只依据证据回答 |
| 开源版 / SaaS | 前者自己部署、数据不出内网、功能完整；后者按量付费、通常只有免费额度 |
| Dify | LLM 应用平台，强在「编排工作流 + 接各种模型」，知识库只是其中一块 |
| FastGPT | 专用知识库问答，强在开箱即用的问答流程与可视化编排 |
| RAGFlow | 以「深度文档理解」为卖点的知识库，强在复杂 PDF / 扫描件的解析 |
| SSE | Server-Sent Events，服务端一边生成一边往浏览器推字，用户不用干等 |

## 1. 一句话结论

**我们不缺「检索 + 回答」这条主链路，缺的是「让人相信并愿意用」的三件事：流式输出（体感）、引用点开看原文（可信）、切块可视化（可运维）。** 前两项是演示时最容易被追问的地方，也是本期 P0。

## 2. 三类产品，别混着比

| 类别 | 代表 | 它们真正卖的是什么 | 和我们可比吗 |
| --- | --- | --- | --- |
| LLM 应用平台 | Dify | 模型接入 + 工作流编排 + 插件生态 | 部分可比：它的知识库是附属能力 |
| 专用知识库 | FastGPT、MaxKB、QAnything（网易有道） | 上传即用的问答机器人、可视化编排 | 直接可比 |
| 文档解析引擎 | RAGFlow（InfiniFlow）、WeKnora（腾讯，MIT） | 把复杂 PDF / 扫描件解析成高质量块 | 直接可比，且解析比我们强 |
| 追赶者 | Langchain-Chatchat | 早期开源知识库，迭代已落后 | 参考实现 |

「免费」这个词要拆开看：这些产品都是**开源版自部署免费**，企业版才加 SSO / RBAC / 审计；SaaS 版通常只给免费额度。所以「免费」不等于「功能齐全」，也不等于「能商用」。

## 4. 我们真正领先的三件事（面试要主动讲）

### 4.1 数字可核验，不是「引用看起来对」

`src/main/java/com/finagent/answer/AnswerService.java:168-216` 的 `ground()`：答案里每个千分位 / 四位以上数字都要回查到被引证据的正文，全部对不上就拒答。这是本项目最硬的一条，因为「引用是真的、数字是编的」是检索类产品最常见也最难发现的错（阶段 6 抓到过：答「5,560 人」，库里 0 个 chunk 含这个数）。

### 4.2 评测是门禁，不是报表

32 题 golden set + `EvalGateTest` 卡门槛：Recall@10 = 1.000、MRR = 0.782、引用准确率 = 1.000、拒答 5/5。改检索参数、改提示词、重切块之后先跑评测再提交，这条纪律在开源产品里通常是缺失的。

### 4.3 多租户是「数据库兜底」，不是「代码里记得加 where」

RLS 策略 + `SET ROLE finagent_app` + ACL 过滤 + `ZeroLeakGateTest`（扫对象键 / 标题 / 正文样本）。开源版多数只做到「团队空间 + 应用层过滤」。

## 5. 我们缺的六件事（按「演示时被追问的概率」排序）

| 排序 | 缺口 | 为什么演示时会被问 | 成本 |
| --- | --- | --- | --- |
| 1 | 无流式输出 | 长答案要等 6~10 秒，屏幕上什么都不动，像卡死 | 中（要拆编排 + 增量解析 JSON） |
| 2 | 引用点不开原文 | 「你这页码是真的吗」——只能口头解释 | 中（后端渲页 + 前端高亮框） |
| 3 | 切块不可视 | 「你怎么切的、切坏了怎么办」——只能翻数据库 | 中（只读接口 + 前端列表） |
| 4 | 仅 PDF | 真实研报还有 Word、网页、Excel | 高（解析引擎扩展） |
| 5 | 无多知识库/标签 | 一个库里混所有公司，只能靠作用域筛选 | 高（数据模型） |
| 6 | 无团队与角色管理 UI | 只能改数据库授权 | 中（界面 + 接口） |

## 6. 优先级：这一期只做 P0

| 级别 | 内容 | 判断依据 |
| --- | --- | --- |
| **P0** | ① SSE 流式输出　② 引用跳 PDF 原文并高亮　③ 切块可视化预览 | 都是「看得见」的能力：演示时每一分钟都在被看，且不需要改数据模型 |
| P1 | 检索参数面板与 A/B、评测看板、放开 Docling 多格式 + OCR | 需要先有 P0 的界面骨架；多格式要重跑解析，成本高 |
| P2 | 多知识库 / 标签、团队与角色管理 UI、Agent 工作流、API Key 与分享 | 属于另一层产品能力，等阶段 11 之后 |

P0 三项的取舍理由：它们全都在「现有数据的另一种呈现」，不新增表、不改检索算法，风险最低、演示收益最高。切块可视化（③）依赖 ① 的流式框架不多，可以最后做。

## 7. 从对比里学到的三个判断

1. **不做全能平台。** Dify 的宽度是靠插件生态堆出来的，我们一个人做宽度必输；把「金融数字可核验」做深才有辨识度。
2. **可信度要能被点开。** RAGFlow 的引用直接给原文截图，这是它最说服人的地方——比任何指标都直观。我们已经有 bbox，只差把它画出来。
3. **等待时间要能被看见。** 流式不是为了炫技：同样的 8 秒，有字在动就是「在思考」，没字在动就是「挂了」。

## 8. 技术债（与本次对比直接相关的三条）

| # | 技术债 | 现状 | 处理 |
| --- | --- | --- | --- |
| 1 | Sparse 精确模式排序无相关性 | 17 条命中数全是 1 → `ORDER BY score DESC, id ASC` 退化成按主键排序；命中数超过 topSparse 时会按 id 截断，正确块可能被截掉 | 修打分（按命中位置/词距加权），或按 §8 的条件跳过 Dense 一起做 |
| 2 | 精准事实仍全量跑 Dense | 每题多一次 embedding（实测 174~373 ms）+ 一路向量检索；Sparse EXACT 已能覆盖 | 条件跳过：`EXACT_FACT` + metrics 非空 + Sparse 命中数在 [3, 30) 才跳过，trace 记 `dense_skipped_exact_fact`，用评测守 Recall@10 |
| 3 | 兼容构造器梯度 / 旧 chunk 版本堆积 | 见 `docs/superpowers/plans/2026-10-05-demo-roadmap.md` 的「技术债」节 | 收尾阶段统一处理 |
