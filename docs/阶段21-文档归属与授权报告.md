# 阶段 21 报告：文档归属与授权（默认私有 / 多主体批量授权）

> 本阶段**没有单独的 ST21 计划文件**：需求与口径是在对话里直接定的（先「文档默认属于上传者，想要别人访问全部通过授权」，再「授权可同时给多个角色」），
> 落点以本报告 + `docs/关键契约.md` **C38** 为准。
> 契约：`docs/关键契约.md` **C38**　迁移：`src/main/resources/db/migration/V19__document_ownership_and_grants.sql`

## 0. 一句话结论

**做成了**：文档不再有「全公司可见」这种状态 —— 每份文档只属于上传它的人，别人要看必须被**显式授权到这份文档**
（授权给个人，或授权给他的某个角色）。判定逻辑从四份复制粘贴的 SQL 收敛到一处，重复授权幂等，一次可以「多主体 × 多份文档」批量写。

**没做成 / 故意不做**：「整家公司」授权是**快照** —— 落库时展开成当时那 N 份文档，公司以后新传的文档不会自动可读。
这是为了可审计而付的代价，写在 2.3 与 C38 里，不是漏做。

## 2. 做了什么

### 2.1 判定：只留一处 SQL

| 文件 | 职责 |
| --- | --- |
| `src/main/java/com/finagent/scope/DocumentAccessSql.java` | 唯一谓词来源：`readableBy(用户表达式)` / `visibleTo(...)` / `readableByRole(...)`，外加 `IS_ADMIN` |
| `src/main/java/com/finagent/scope/AclScopeAuthorizer.java` | 检索期收窄：`SELECT d.id FROM document d WHERE d.tenant_id = ? AND d.id IN (…) AND EXISTS (…)` |
| `src/main/java/com/finagent/security/AdminRepository.java` | 管理页三个查询（某人能读哪些 / 角色卡片文档数 / 角色文档列表）改用同一谓词，`reason` 区分 `ADMIN`/`OWNER`/`USER`/`ROLE` |

### 2.2 归属：上传即认主

- `DocumentRepository.upsertDocument(..., Long ownerUserId)` 写入 `owner_user_id`；上传链路传 `TenantContext.require().userId()`，解析服务/CLI 传 `null`，
  落库时 `COALESCE(?, (SELECT min(u.id) FROM app_user u WHERE u.tenant_id = c.tenant_id AND u.status = 'ACTIVE'))` 兜底。
- `ON CONFLICT (tenant_id, content_hash)` 分支**不改** `owner_user_id`：同一份 PDF 被别人重传，文档仍归第一个人。

### 2.3 授权：批量 + 展开 + 幂等

| 文件 | 职责 |
| --- | --- |
| `src/main/java/com/finagent/security/AdminController.java` | `POST /api/admin/grants` 接受 `subjectIds[]` / `resourceIds[]`；`resourceType=COMPANY` 只作请求写法，落库前用 `documentIdsOfCompany` 展开 |
| 同上 | 三个上限：主体 ≤ 50、请求资源 ≤ 200、展开后文档 ≤ 500；公司下无文档直接 400 |
| `AdminRepository.createDocumentGrants(...)` | 逐条 `INSERT … ON CONFLICT (tenant_id, subject_type, subject_id, resource_type, resource_id) DO NOTHING`，返回新建条数 |

响应体：`{created, skipped, subjects, documents}` → 前端提示「新建 X 条，Y 条已存在跳过」。

### 2.4 前端

- `D:/Project/myproject/financial-ai-web/src/views/AdminView.vue`：授权弹窗改多选（勾多份文档 + 可选「整家公司」+ 可同时授给多个角色），表格删「可见性」列、加「公司」列。

## 4. 踩到的坑

### 4.1 测试 profile 的假 api-key 顶掉了 `.env` 里的真 key：401

**现象**：全量回归里 `EmbeddingTextRoundTripTest`、`DenseRetrieverTest` 与几个 Agent 系用例报
`com.openai.errors.UnauthorizedException: 401: Incorrect API key provided`，而这些用例前一天还是绿的。

**原因**：`src/test/resources/application-test.yml` 里写死 `spring.ai.openai.api-key: test-key-not-used`。
阶段 20 加的 `.env` 自动加载（C37）把 `.env` 放在属性源**最低优先级**，于是 test profile 的假 key 合法地压过真 key ——
以前能跑，是因为大家用 `. .\scripts\load-env.ps1` 把真 key 注入成**真实环境变量**（优先级高于一切配置文件）。

**修法**：`application-test.yml` 改成 `api-key: ${SPRING_AI_OPENAI_API_KEY:test-key-not-used}`；
需要真模型的用例加 `Assumptions.assumeTrue(apiKey.startsWith("sk-"), "未配置真实嵌入 Key")`。
**教训**：把配置挪到「更低的优先级」是全局行为变化，必须重新检查所有「靠优先级压制」的测试。

### 4.2 `owner_user_id NOT NULL` 打挂了 8 个老测试文件

**现象**：一批 DB 测试报 `DataIntegrityViolationException: null value in column "owner_user_id"`（例如 `VectorStoreSmokeTest`）。

**原因**：这些用例手写 `INSERT INTO document (...)`，列清单是老的。收紧 NOT NULL 之后，任何漏列的插入都会失败。

**修法**：逐个补列，值统一用 `(SELECT id FROM app_user WHERE username = 'demo')`：
`DocumentListDbTest`、`DocumentProgressDbTest`、`DocumentPeriodTest`、`IngestRunDbTest`、`DocumentScopeQueryTest`、
`ChunkWriterTest`、`ChunkRetentionDbTest`、`VectorStoreSmokeTest`。
**教训**：收紧约束的那次回归，失败会集中在「手写 INSERT 的测试」上 —— 先 `grep -rn "INSERT INTO document" src/test` 一次改完，比逐个跑快得多。

### 4.3 demo 账号的 ADMIN 角色莫名消失

**现象**：`PasswordLoginTest.demoLoginReturnsTokenAndIdentity` 断言 `roles.contains("ADMIN")` 失败；查库发现 `demo` 只剩 `{ANALYST}`。

**原因**：**不是测试**（2026-11-02 22:00 复查：连续两次全量回归前后都查库，`demo` 的 `{ADMIN, ANALYST}` 一直没变）。
最可能是管理页上的一次「保存用户」：`PUT /api/admin/users/{id}` 里的 `roles` 是**整体替换**
（`AdminRepository.replaceRoles` = `DELETE FROM user_role WHERE user_id = ?` 再插入），
把某一行的 ADMIN 取消勾选再保存，就等于把自己降级。

**修法**：先手工恢复（`INSERT INTO user_role … ON CONFLICT DO NOTHING`）；随后在 `AdminController.updateUser` 加了两条防线 ——
不能移除自己的 ADMIN、不能移除本租户最后一个 ACTIVE 管理员（详见 §6 第 1 条）。
**教训**：「整体替换」型接口最容易造成静默丢数据：界面上少勾一个框，后端就是一次 `DELETE`。
写这类接口时，必须先回答「如果这次提交把唯一的管理员/唯一的属主删掉，系统还能自愈吗」。

### 4.4 旧模型里那条「单份授权无效」的拒绝是死代码

**现象**：`AdminController` 原先有一段：文档 `visibility='TENANT'` 时收到文档级授权请求就返回 400「该文档是全租户可见，单份授权不会生效」。

**原因**：这不是防御，而是旧模型的自证 —— 两种授权互斥，所以文档级授权对 TENANT 文档**永远**没有意义。

**修法**：整段删掉；现在文档级授权是唯一机制。
**教训**：当一段代码在解释「为什么这个功能不起作用」时，先怀疑设计，而不是给它加注释。

### 4.5 「撤销授权」确认框跑到屏幕左上角（用户验收时发现）

**现象**：在管理页点「撤销」，确认框不是一个居中的卡片，而是挤在遮罩层的左上角，像一段没有样式的大字。

**原因**：Element Plus 是**按需引入**的（`unplugin-vue-components` + `ElementPlusResolver`），
插件只给「模板里出现的组件」注入 CSS。`ElMessageBox` 是**函数式 API**（`ElMessageBox.confirm(...)`），
模板里根本没有它，所以它的样式表 `el-message-box.css` 从来没人引。

那为什么平时看着没问题？因为这份 CSS 恰好被别的组件带进了 **`ChatView` 的懒加载分块**：
先逛过聊天页，浏览器就把它缓存下来了，确认框正常；直接打开管理页（`AdminView` 分块里没有这份 CSS），
`.el-message-box` 的 `display:inline-block` 与父级 `.el-overlay-message-box` 的 `text-align:center` 都不存在，
盒子退化成普通块级元素，贴着遮罩层左上角排。**同一个组件在不同路由下表现不同**，就是这么来的。

**修法**：在 `src/main.ts` 里显式引一次 `element-plus/es/components/message-box/style/css`
（它会把 base / input / button / overlay / message-box 五份 CSS 一起带进来），
并在 `theme.css` 里给 `.el-message-box` 补上跟对话框同一套圆角、描边、阴影。

**验收**：用 Chrome 无头模式加载真实构建产物里的三份 CSS + 与 Vue 渲染一致的 DOM，
量 `.el-message-box` 的矩形：视口 1262×704，盒子 420×154 落在 `x=419, y=275`，横竖都居中（±2 px 是滚动条取整）；
修复前同一份 DOM 的盒子挂在 `x=16, y=16`，高度 0 的外层容器把固定定位的父级压成 32 px。

**教训**：按需引入 + 函数式 API 是天生一对坑。凡是用 `ElMessageBox` / `ElNotification` / `ElLoading.service()`
这类「不在模板里」的 API，都要在入口手动补一份 `style/css`；判断办法是构建后 `grep` 入口 CSS 里有没有对应的类名。

1. ~~**demo 的 ADMIN 角色消失的元凶**没查出来（见 4.3）~~ → **已定性**：不是测试干的。连续两次全量回归（`target/full-test-tz2.log`、`target/full-test-guard.log`）前后都查了库，`demo` 的 `{ADMIN, ANALYST}` 一直没变；而掉角色发生在「15:50 回归全绿」到「21:53 又一次 401」之间，那段时间只在管理页上操作过。
   机制上也说得通：`PUT /api/admin/users/{id}` 的 `roles` 是**整体替换**（`DELETE FROM user_role WHERE user_id = ?` 再插入），管理员在弹窗里把自己那一行的 ADMIN 取消勾选、点保存，就会把自己降级，而且下一次请求立刻 403 —— 连改回来的入口都没有了。
   **已加防线**：`AdminController.updateUser` 现在拒绝「移除自己的 ADMIN」（400），也拒绝「移除本租户最后一个 ACTIVE 管理员」；`AdminRepository.countOtherAdmins` 负责数人数。新增 3 个控制器用例 + 1 个真库用例（`AdminControllerTest` 31 例、`AdminAccessDbTest` 10 例全绿）。

3. `resource_grant.permission` 目前只有 `READ` 在用，`READ_WRITE` 已在谓词里预留但没有任何写路径 —— 等真正出现「共享编辑」需求再启用。
4. 管理页没有「按文档看谁能读」的反向视图（只有「按人/按角色看能读什么」）。做起来不难，但当前两份文档的规模用不上。
