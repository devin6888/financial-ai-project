# 微调工作流程

大模型微调（Fine-Tuning）是让通用大语言模型（LLM）适应特定垂直领域、专业任务或特定交互风格的核心技术。

简单来说，如果把大模型的基础训练比作“通识教育”（让模型具备广泛的语言理解和世界知识），那么微调就是“专业培训”（让模型学会写代码、看医学报告、或者按特定格式回复）。

### 一、 为什么需要大模型微调？

虽然现在的基座大模型（如 DeepSeek、Qwen、Llama 等）知识极其渊博，但在实际落地时往往会遇到以下痛点：

- **专业领域知识不足**：对企业内部文档、医疗、法律等垂直领域的专业术语理解不够深。
- **输出格式不稳定**：难以严格按照指定的 JSON 格式、特定模板或字数要求输出。
- **对话风格不契合**：无法完美契合特定品牌的人设、语气或客服规范。
- **幻觉率高**：在没有引导的情况下容易瞎编。

通过微调，我们可以用相对较低的成本，大幅提升模型在特定场景下的**准确率、稳定性和安全性**。

### 二、 主流的微调方法

大模型的参数量通常动辄几十亿甚至上千亿，全量更新所有参数的成本极高。因此，目前行业内主要采用以下两类方法：

1. **全量微调（Full Fine-Tuning）**
   - **做法**：更新模型的所有参数。
   - **优缺点**：效果最好，但极度依赖算力（需要大量高端 GPU），显存开销和训练成本极高，一般只有大厂或实力雄厚的机构会用。
2. **高效参数微调（PEFT - Parameter-Efficient Fine-Tuning）**
   - **做法**：锁定模型的大部分原有参数不变，只训练极少数的附加参数或通过低阶矩阵近似来调整模型。
   - **核心代表技术**：
     - **LoRA (Low-Rank Adaptation)**：通过向原模型中注入可训练的低阶矩阵，冻结原参数，大大减少了显存占用（目前最主流的做法）。
     - **QLoRA**：在 LoRA 的基础上引入了 4-bit 量化技术，进一步把消费级显卡微调大模型的门槛拉低。

### 三、 典型的微调工作流

一个标准的微调项目通常包含以下几个步骤：

1. **数据准备与清洗（最关键的一步）**

   - 收集高质量的领域数据，通常整理为问答对（Instruction-following 格式），例如：

     JSON

     ```
     {"instruction": "请根据以下合同条款解释违约责任...", "input": "...", "output": "..."}
     ```

   - 数据质量直接决定了微调上限（Garbage in, garbage out）。

2. **选择基座模型与框架**

   - 选择适合的开源基座（如 Qwen、Llama、Mistral）。
   - 使用成熟的**开源微调框架**（如 **LLaMA-Factory**、**Unsloth**、Swift 等），这些工具提供了可视化的 WebUI 或极简的命令行脚本。
     - 一般在受限资源下推荐使用 Unsloth 它的核心目的就是让开发者能够**用极低的硬件门槛、极快的速度**去微调各种主流开源大模型

3. **模型训练与调优**

   - 设置超参数（如学习率 Learning Rate、Batch Size、Epoch 轮数）。
   - 监控训练过程中的 Loss（损失函数）下降趋势，防止过拟合。

4. **模型评估与部署**

   - 使用测试集评估微调后的效果（可通过自动化评测或人工盲测）。
   - 将模型量化部署到推理框架中（如 vLLM、Ollama）。

### 四、 微调 vs 提示词工程 vs RAG

在实际开发中，很多团队会纠结是用微调、提示词（Prompt Engineering）还是 RAG（检索增强生成）：

- **提示词工程**：成本最低，适合临时规范输出、简单任务，但无法注入新知识。
- **RAG（知识库检索）**：最适合解决“海量事实性数据查询”和“实时动态数据更新”的问题，不用重新训练模型。
- **微调**：最适合改变模型的**行为模式、说话语气、专业领域深度逻辑以及固定的输出格式**。

在生产环境中，**“RAG + 微调”** 往往是企业级 AI 应用的最佳组合拳。

# 数据准备与清洗 - 工作流程

在大模型微调（Fine-Tuning）的项目中，业界流传着一句话：“**垃圾进，垃圾出（Garbage in, garbage out）**”。数据准备与清洗通常会占整个微调项目 **70% 到 80% 的时间和精力**。高质量的数据集是模型能力跃升的关键。

针对大模型微调的数据准备与清洗，标准且落地性强的工程化流程主要包含以下四个核心阶段：

---

### 一、 数据收集与来源设计

在动手清洗前，首先要明确数据的来源。常见的数据源包括：

1. **内部业务数据**：企业私域知识库、历史工单、客服聊天记录、API 文档、内部规范等。
2. **公开垂直领域数据集**：学术论文、开源专业语料、行业标准等。
3. **合成数据（Synthetic Data）**：当真实高质量数据不足时，利用强模型（如 GPT-4 或 Claude 3.5）基于少量种子数据批量生成训练样本。

无论来源如何，最终都需要转化为大模型友好的结构化格式，最主流的是 **JSONL 格式**（每行一个 JSON 对象），常见结构如 **Alpaca 风格**或 **ShareGPT 多轮对话风格**：

```json
{"instruction": "请根据系统日志排查死锁异常", "input": "java.sql.SQLException: Deadlock found...", "output": "分析：该异常由两个事务互相等待锁导致。建议：1. 调整事务中的加锁顺序；2. 缩短事务持有锁的时间。"}

```

---

### 二、 核心数据清洗（Data Cleaning）

原始数据往往充满了噪音，清洗阶段的核心目标是**去除干扰、提升信噪比**。主要包括以下几个维度：

1. **基础文本清洗与去噪**
* **去除无效字符**：清洗掉不可见字符、乱码、多余的 HTML 标签、Markdown 语法错误、表情符号（除非对话需要）等。
* **空白字符规范化**：将连续的换行符、空格、制表符进行标准化，避免占用不必要的 Token。


2. **敏感信息脱敏（Privacy & Security）**
* **企业红线**：绝对不能包含公司内部机密、服务器 IP、数据库连接串、API Secret Key 等。
* **个人隐私（PII）**：自动或半自动过滤用户的真实姓名、手机号、身份证号、邮箱等敏感字段（可编写正则表达式或使用专用的脱敏工具库）。


3. **文本长度过滤**
* **过短数据**：如“好的”、“谢谢”、“不知道”，这类数据缺乏上下文和语义信息，直接剔除。
* **过长数据**：如果单条样本超过了模型的最大上下文窗口（如 4K / 8K tokens），会导致显存溢出或截断，需要进行合理切分或丢弃。


4. **数据去重（Deduplication）**
* **精确去重**：利用哈希（MD5 / SimHash）剔除完全重复的文本。
* **语义去重**：通过嵌入模型（Embedding）计算文本相似度，剔除表达方式高度雷同的冗余样本，防止模型对某些特定句式产生过拟合。



---

### 三、 数据质量优化与增强

清洗完“脏数据”后，接下来要提升数据的“含金量”：

1. **确保指令（Instruction）的多样性与明确性**
* 避免所有样本的提问方式千篇一律。指令应该清晰、具备约束力（例如明确规定：“用表格形式回答”、“分三点说明”等）。


2. **控制幻觉与纠错**
* 确保 `output`（标准答案）的准确性。如果训练数据中本身包含错误信息或大模型幻觉，微调后的模型会学得更加彻底。


3. **数据配比与平衡**
* 如果微调包含多种任务（如：代码生成、文本摘要、多轮客服、格式化输出），要注意各任务之间的数据量平衡，防止某一类任务的数据压倒性地占据主导，导致模型其他能力退化（灾难性遗忘）。



---

### 四、 自动化清洗与评估（LLM-as-a-Judge）

在现代大模型工程中，纯靠人工肉眼检查海量数据是不现实的。通常会引入 **LLM-as-a-Judge（大模型作为裁判）** 机制：

1. **用脚本进行初筛**：通过规则、正则和长度限制过滤掉 80% 的低质数据。
2. **用强模型进行质量打分**：编写自动化评测脚本，调用大模型 API 对清洗后的问答对进行打分（从逻辑性、相关性、可读性维度评分），自动剔除低分样本。
3. **数据集划分**：
* **训练集（Train Set）**：占比约 90% - 95%，用于模型参数微调。
* **验证集/测试集（Eval Set）**：占比约 5% - 10%，不参与训练，用于在训练过程中评估 Loss 变化和模型能力防退化。



做好上述的数据准备与清洗，微调的成功率通常能提升 80% 以上。

# 数据准备与清洗 - 工具介绍

在大模型微调（Fine-Tuning）的数据准备与清洗流程中，社区和企业目前已经沉淀出了一套成熟的工具生态。这些工具涵盖了**文档解析、大规模数据清洗、合成数据生成以及微调框架内置的数据处理模块**。

以下是各个环节中最常用的主流工具：

### 一、 文档解析与多模态转结构化工具

如果你的原始数据包含大量的 PDF、扫描件、表格、公式或专业论文，直接复制往往会变成乱码。这些工具能帮你高精度提取并转化为 Markdown 或纯文本：

1. **MinerU / Magic-PDF**：
   - **特点**：目前国内非常火爆的开源开源智能文档解析工具，专门用来解析复杂 PDF、表格、图表和公式，效果极佳。
2. **Marker**：
   - **特点**：国外的开源 PDF 转 Markdown 工具，速度快且保留了良好的排版结构。
3. **PaddleOCR**：
   - **特点**：百度开源的 OCR（光学字符识别）工具，特别适合处理各类扫描件、发票或图片中的文字提取。

### 二、 专业的大模型数据清洗与审阅框架（Data Curation）

当需要处理海量文本（如几十 GB 甚至 TB 级的语料）并进行去重、过滤和去噪时，通常会用到专业的开源数据清洗平台：

1. **Data-Juicer (阿里开源)**：
   - **特点**：国内大模型数据处理领域的明星开源项目。它提供了上百种高效的数据算子（Operators），支持数据的清洗、格式化、去重、质量打分和数据增强，非常适合大规模中文语料。
2. **NeMo Curator (英伟达出品)**：
   - **特点**：NVIDIA 开发的超大规模 LLM 数据 curation 框架，支持 GPU 加速的文本清洗、敏感信息过滤和去重。

### 三、 Python 基础数据处理与脚本库

在绝大多数日常微调项目中，开发人员通常会使用一组 Python 黄金组合来编写自定义清洗脚本（如处理正则表达式、脱敏、JSONL 转换等）：

- **`pandas` / `polars`**：用于表格化数据的清洗、筛选、合并与统计。
- **`jsonlines`**：专门用来读写大模型微调标准的 `.jsonl` 文件格式。
- **`regex` (正则库)**：用于编写复杂的模式匹配规则，精准过滤手机号、身份证、IP 地址等敏感信息（PII 脱敏）。
- **`tiktoken` / `transformers` (Tokenizer)**：用于计算文本的 Token 长度，防止样本超出模型的上下文窗口。

### 四、 合成数据与大模型辅助清洗（LLM-as-a-Judge）

当高质量的标注数据不够时，利用强模型（如 GPT-4 / Claude）来生成或清洗数据，常用的工具有：

1. **Distilabel (by Argilla)**：
   - **特点**：一个强大的开源合成数据与 AI 反馈（RLHF/AI Feedback）框架，支持通过大模型流水线自动生成微调问答对并进行质量过滤。
2. **Instructor / Outlines**：
   - **特点**：用于约束大模型输出特定 JSON 结构格式的工具库，在用大模型批量生成结构化微调数据集时极为好用。

### 五、 主流微调框架自带的数据处理与转换器

很多时候，你不需要从零写代码清洗，因为主流的**微调框架**本身就内置了强大且兼容各种数据格式的加载器：

1. **LLM-Factory**：
   - **特点**：国内使用最广泛的开源微调框架。它自带了极为完善的数据集模板映射（支持 Alpaca、ShareGPT、Llama 等多种格式），你只需要把数据整理成基础 JSON，它就能自动完成 Token 化和格式对齐。
2. **Axolotl**：
   - **特点**：国外面向企业级和研究员的高性能微调配置框架，对各种 YAML 格式的数据管道支持非常完善。

# 什么场景才需要用到微调

在作为 **FDE（前置部署工程师 / Forward Deployed Engineer）** 为企业客户落地 AI 解决方案时，最核心的挑战之一就是帮客户厘清边界：**什么时候该用 RAG（检索增强生成），什么时候该用提示词工程，什么时候才真正需要做微调（Fine-Tuning）？**

在企业级 AI 落地中，大模型微调通常**不是用来存储动态事实性知识的**（那是向量数据库和 RAG 的事），而是用来**改变模型的“行为模式、输出格式、专业语感和任务执行逻辑”**。

在实际业务场景中，真正必须或强烈建议做微调的场景主要有以下四大类：

### 一、 严苛的结构化输出与特定 DSL/API 代码生成

企业内部系统往往需要大模型输出高度稳定的结构化数据，供下游系统（如 Java/Go 后端）自动解析。

- **业务场景**：
  - **特定 DSL 或内部方言转换**：例如将自然语言转换为企业内部的特定查询语法、私有 SQL 方言、或复杂的风控规则表达式。
  - **零误差 JSON/XML 契约输出**：虽然通过 Prompt 或结构化输出框架（如 Instructor）可以约束，但在高并发、复杂嵌套的业务报文生成中，基座模型经常会漏字段或格式崩溃。通过微调可以让小模型（如 7B/8B）稳稳掌握这种契约。
- **FDE 视角的价值**：省去了大量后端的容错重试逻辑，确保系统间对接的稳定性。

### 二、 行业专业话术、品牌人设与合规对齐

通用大模型（如 GPT-4、Qwen 等）往往带有浓厚的互联网“AI味儿”（如“好的，作为一个人工智能助手……”），或者在特定行业的合规性上不够严谨。

- **业务场景**：
  - **金融/医疗客服**：要求模型必须使用极度严谨、符合监管合规的术语，绝对不能出现诱导性或承诺性话术。
  - **品牌专属人设**：例如奢侈品、汽车品牌的智能顾问，要求具备特定的说话语气、幽默感或尊贵感，拒绝“机翻感”。
- **FDE 视角的价值**：用 Prompt 很难长期稳定地约束几百条复杂的语气和合规红线，微调可以把这种“行为习惯”刻进模型的权重里。

### 三、 复杂多步业务逻辑或内部工作流的“内化”

当企业有一套非常固定的标准化作业流程（SOP），而用 Prompt 引导大模型时，大模型经常会“偷懒”或跳过某些步骤。

- **业务场景**：
  - **IT 运维自动化排查**：输入一段晦涩的 Java 异常日志，要求模型严格按照企业的三步排查法（1. 检查连接池 -> 2. 检查慢 SQL -> 3. 查看下游依赖）输出诊断报告。
  - **法律合同审查与红线标注**：要求模型严格按照公司法务部的审查细则，对合同逐条进行风险评级和批注。
- **FDE 视角的价值**：将专家经验（SOP）通过高质量的问答对“教”给模型，让普通员工在提问时直接享受专家级的思考路径。

### 四、 用小模型替代大模型以实现降本增效（模型蒸馏）

这是 FDE 在企业落地时非常常用的一种工程策略。

- **业务场景**：
  - 如果企业初期用 GPT-4 或 Claude 3.5 实现了某个复杂的业务流，效果很好，但**调用成本极高、延迟大（几秒钟）**，且涉及敏感数据不能走公有云大厂 API。
  - **解决方案**：利用大模型（Teacher Model）批量生成高质量的训练数据，然后去微调一个开源的轻量级小模型（如 Qwen-7B / Llama-3-8B）（即**模型蒸馏**），将其私有化部署在企业本地的 GPU 服务器上。
- **FDE 视角的价值**：在保证业务准确率的前提下，把推理成本降到几十分之一，并将首字延迟压到毫秒级。

### 💡 FDE 落地经验小结

在跟企业客户沟通时，通常的决策逻辑是：

1. **能用 RAG 解决的绝不微调**（涉及找文档、查规章、实时数据更新）。
2. **能用 Prompt 约束的尽量不微调**（涉及简单的角色扮演、临时翻译）。
3. **当且仅当需要“固定复杂的输出格式、对齐行业专业行为、或者为了私有化小模型压降成本”时**，才果断引入微调。
