# RAG 知识库高级召回与重排（Retrieval & Reranking）技术指南

> **文档说明**：本指南专为知识库/RAG 系统开发与架构学习设计，系统化梳理了从多路召回到精细重排的完整技术链路，包含算法原理、数学推导、核心公式、工程示例与选型决策，适合作为后续系统搭建与技术复习的参考手册。

## 一、 为什么单靠向量检索不够？

在传统的简易 RAG 实现中，通常仅使用**向量相似度检索（Dense Vector Search）**。然而在生产环境中，纯向量检索面临两个致命硬伤：

1. **专有名词与精确匹配不敏感**：向量模型将文本压缩为高维语义空间，容易忽略具体的版本号（如 `Kafka 3.2.0`）、产品型号、人名、错误码（如 `ERR-502`）或缩写。
2. **Query 与 Document 表达不对称**：用户的提问通常短而抽象（口语化），而知识库的切块（Chunk）长而具体，两者的向量表示在空间距离上天然存在偏差。

为解决上述问题，工业级成熟 RAG 构建了 **多路召回（Hybrid Retrieval） $\rightarrow$ 排序重排（Rerank） $\rightarrow$ 上下文组装** 的多级流水线：

```
[用户提问 Query]
       │
       ▼
[ Query 改写 / 元数据提取 ] ──(提取过滤条件，如部门/年份)
       │
       ├───────────────────────────────┐
       ▼                               ▼
[ 1. 向量检索 (Dense) ]        [ 1. BM25 全文检索 (Sparse) ]
(语义范化，召回 Top 30)         (精准词汇，召回 Top 30)
       │                               │
       └───────────────┬───────────────┘
                       ▼
            [ 1. RRF 排名融合去重 ] ──(基于排名的评分累加)
                       │
                       ▼ (截取 Top 30 候选)
            [ 2. Cross-Encoder Reranker 重排 ] ──(深度词级交叉 Attention)
                       │
                       ▼ (精选 Top 3~5 高分 Chunk)
            [ 组装 Prompt 送入 LLM 生成 ]
```

## 二、 核心召回与重排方案详解

### 1. 多路混合检索（Hybrid Search & RRF 融合）

#### 核心原理

结合语义检索（Dense Retrieval）**与传统**关键词检索（Sparse Retrieval / BM25）的优势，取长补短：

- **向量检索**：基于双塔 Embedding 模型，擅长捕捉同义词、隐式意图和跨词表达。
- **BM25 检索**：基于词频（TF）与逆文档频率（IDF），擅长精准匹配专有名词、代码和型号。

两路检索各自返回 Top N 结果后，使用 **倒数排名融合算法（RRF, Reciprocal Rank Fusion）** 进行排序融合。

#### RRF 算法公式与计算过程

$$RRF\_Score(d) = \sum_{m \in M} \frac{1}{k + r_m(d)}$$

- **参数含义**：

  - $M$：检索路数的集合（如 $M = \{\text{向量路}, \text{BM25 路}\}$）。
  - $r_m(d)$：文档 $d$ 在第 $m$ 路检索中的**名次**（从 1 开始）。若未命中，该项为 0。
  - $k$：**平滑常数（Penalty Parameter）**，工业界通用缺省值为 **$60$**（来自于 Cormack 等人的 TREC 实验结果）。

- **平滑常数 $k=60$ 的作用**：

  防止排名第一的文档获得过大的权重独霸结果。将得分曲线平缓化，使得**在两路检索中均获得靠前排名的文档（共识文档）**，综合得分能够超越仅在单路拿第一、另一路未命中的文档。

#### 实例计算

- **用户输入**：`MySQL 8.0 怎么配置 max_connections 内存优化`

| **候选文档片段**                                      | **向量检索排名 r1** | **BM25 检索排名 r2** | **RRF 综合得分计算 (k=60)**                                  | **综合得分** | **最终排序** |
| ----------------------------------------------------- | ------------------- | -------------------- | ------------------------------------------------------------ | ------------ | ------------ |
| **Doc A**：*MySQL 8.0 参数 `max_connections` 调优...* | 第 5 名             | 第 1 名              | $\frac{1}{60+5} + \frac{1}{60+1} \approx 0.01538 + 0.01639$  | **0.03177**  | **第 1 名**  |
| **Doc B**：*连接数过多导致 RAM 爆满的优化思路...*     | 第 1 名             | 未命中 (0)           | $\frac{1}{60+1} + 0 \approx 0.01639$                         | **0.01639**  | **第 3 名**  |
| **Doc C**：*MySQL 8.0 安装配置手册...*                | 第 12 名            | 第 3 名              | $\frac{1}{60+12} + \frac{1}{60+3} \approx 0.01388 + 0.01587$ | **0.02975**  | **第 2 名**  |

### 2. 精细化重排（Cross-Encoder Rerank）

#### 核心原理

向量数据库检索使用的 Embedding 模型属于 **双塔架构（Bi-Encoder）**，Query 和 Document 是分别独立编码的，无法计算词与词之间的交叉注意力。

**Reranker 模型** 采用 **单塔架构（Cross-Encoder）**（如 BERT / RoBERTa 架构，代表模型有 `bge-reranker-v2-m3`、`Cohere Rerank`）：

1. **拼接序列**：将 Query 和 Document Chunk 直接拼接：

   $$\text{Input} = [\text{CLS}] + \text{Query} + [\text{SEP}] + \text{Document Chunk} + [\text{SEP}]$$

2. **交叉计算**：在 Transformer 多层 Self-Attention 机制下，Query 中的每个 Token（如“官网”）与 Document 中的每个 Token（如“官方网站”）直接在底层相乘计算注意力。

3. **输出标量**：利用 `[CLS]` 提取特征，经线性层和 Sigmoid 输出 $0 \sim 1$ 之间的语义相关度得分：

   $$Score = \text{Sigmoid}(\mathbf{W} \cdot \mathbf{h}_{[\text{CLS}]} + b)$$

```
[ Query + Document ]
         │
         ▼
[ Transformer Encoder (全交叉 Attention 算力耗费较高) ]
         │
         ▼
[ 线性分类层 Classifier Head ] ──> 输出 0.985 (精准标量得分)
```

#### 部署模式对比

由于 Reranker 是判别式神经网络模型，**必须作为一个模型服务运行**：

- **SaaS API 模式**：调用 Cohere Rerank API、硅基流动 API。
- **独立微服务部署（生产推荐）**：使用 HuggingFace **TEI（Text Embeddings Inference）** 或 ONNX Runtime 在 Docker 中启动服务（如 `bge-reranker-v2-m3`），单次推理仅需 10~30ms。

### 3. 查询改写与扩展（Query Reformulation）

#### 核心原理

在检索前，利用轻量级 LLM 对用户的原始 Query 进行预处理，解决口语化、过于短小或多意图混杂的问题。

#### 常用改写策略

1. **多查询生成（Multi-Query Expansion）**：
   - **逻辑**：将单一 Query 改写为 3 个视角不同的同义提问，并行检索后取并集，扩大**召回率（Recall）**。
   - **示例**：`社保断缴怎么办` $\rightarrow$ 改写为：① `社保中断后如何补缴或续缴？` ② `离职后断交社保的处理流程` ③ `个人社保断缴补救措施`。
2. **假设性文档嵌入（HyDE - Hypothetical Document Embeddings）**：
   - **逻辑**：先让 LLM 根据提问“凭空生成”一段假设性答案，再用这段答案去向量库匹配真实文档。因为“答案对答案”的向量距离比“问题对答案”近得多。
   - **示例**：提问 `Python 字典存 Redis` $\rightarrow$ 生成假设代码片段（包含 `json.dumps` 和 `r.set`） $\rightarrow$ 成功匹配带有代码的真实 Markdown 文档。

### 4. 元数据过滤（Metadata Filtering）

#### 1. 核心原理

文档切块入库时，附加结构化属性（如 `department`、`year`、`access_level`）。检索时利用 **结构化硬过滤 + 向量检索** 的联合查询方式，优先缩小检索范围，防止数据越权或噪音干扰。

#### 2. 工作流水线与 SQL 示例

- **用户提问**：`查找 2024 年研发部最新的差旅报销标准`
- **提取过滤条件**：`department = '研发部' AND year = 2024 AND category = '差旅报销'`
- **数据库执行（以 PostgreSQL / Qdrant 为例）**：

SQL

```
SELECT chunk_id, content, 1 - (embedding <=> '[0.12, 0.45, ...]') AS similarity
FROM knowledge_chunks
WHERE department = '研发部'
  AND doc_year = 2024
  AND category = '差旅报销'
  AND min_access_level <= 2  -- 结合用户权限过滤
ORDER BY embedding <=> '[0.12, 0.45, ...]'
LIMIT 5;
```

## 三、 4 种方案的横向对比与技术选型

| **方案**                  | **核心解决问题**                     | **响应延迟 (RT)**         | **额外算力/API 成本**          | **推荐引入节点**                                |
| ------------------------- | ------------------------------------ | ------------------------- | ------------------------------ | ----------------------------------------------- |
| **多路混合检索 (Hybrid)** | 精确匹配失效、专有名词漏召回         | +10~30ms                  | 极低（数据库原生）             | **阶段一（无条件必选，RAG 基石）**              |
| **精细重排 (Reranker)**   | 向量得分不准、Top N 结果混入噪音     | +10~50ms                  | 低~中（需要小 GPU / CPU 推理） | **阶段二（提升准确度必选，工业级标准）**        |
| **元数据过滤 (Metadata)** | 数据隔离、部门权限控制、指定时间范围 | -50ms（过滤后计算量变小） | 零                             | **阶段二（有权限/多维度查询需求时）**           |
| **查询改写 / HyDE**       | 口语化提问、极短提问、语义不对称     | +300~1000ms               | 高（增加一次 LLM 预处理调用）  | **阶段三（针对特定短句/高频坏 case 专项优化）** |

## 四、 落地演进路线与决策建议

在构建 RAG 系统时，切忌第一天就堆叠全套方案。推荐遵循**三阶段演进路线**：

```
【第一阶段：MVP 快速上线】
  配置：PostgreSQL (pgvector + 全文检索) 搭建 混合检索 (Vector + BM25)
  目标：解决基本专有名词与语义匹配，零额外运维成本。
  
         │
         ▼
【第二阶段：工业级标准形态 (推荐标准态)】
  配置：混合检索 + BGE-Reranker (通过 Docker 部署 TEI) + Metadata 过滤
  目标：解决 80% 以上的准确率痛点，控制系统延迟在 200ms 以内，性价比最高。

         │
         ▼
【第三阶段：高难场景攻坚】
  配置：在前级增加 LLM Query Rewrite / HyDE / 多意图路由
  目标：攻坚极短口语化提问与复杂多意图检索。
```
