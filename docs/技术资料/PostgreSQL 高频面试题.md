## 一、一分钟回答：为什么 RAG 选 PostgreSQL

**面试标准答法**：

> 我们的金融研报 RAG 同时需要文档元数据与权限管理、Dense 向量检索、Sparse 关键词检索及复杂过滤。
>
> PostgreSQL 既能处理常规关系型事务，又能通过 pgvector 实现向量距离计算和 HNSW/IVFFlat 索引，通过 `tsvector`、`tsquery`、GIN 及中文分词扩展做全文检索。把文档、Parent/Child Chunk、检索字段放在同一个数据库中，降低了初期的数据同步和运维复杂度。
>
> MySQL 在普通事务业务上同样成熟，但在我们当前使用的 Community 部署方案下，PostgreSQL 的扩展能力更方便。等向量规模、并发和延迟要求证明有必要，再评估 Milvus 等独立检索引擎。

**关键补充**：不要说 PostgreSQL CRUD 一定比 MySQL 快；也不要说 MySQL 所有版本都不支持向量。技术选型取决于**现有版本/产品、团队能力、查询场景、数据规模、延迟和成本**。

## 二、基础与 MySQL 对比（Q1–Q8）

### Q1 ⭐⭐⭐ PostgreSQL 与 MySQL 最大的区别是什么？
**回答**：两者都是成熟关系型数据库。MySQL（通常讨论 InnoDB）常见架构是单服务进程+多工作线程；PostgreSQL 常见架构是一个客户端连接对应一个 Backend 进程。

PostgreSQL 原生类型和扩展体系更丰富，例如 JSONB、数组、范围类型、GIN、GiST、BRIN、pgvector。

InnoDB 主键是聚簇索引，PostgreSQL 普通 Heap 表默认独立存储行、索引以 TID 定位行版本。

**追问**：PostgreSQL 一定更快吗？**不是**，必须比较具体 SQL、索引、并发和硬件。

### Q2 ⭐⭐⭐ PostgreSQL 一个连接对应一个进程吗？
**回答**：在常规直连 PostgreSQL 模型下，通常每个数据库会话对应一个 Backend 进程；连接池代理（例如 PgBouncer 的事务池模式）可能让大量客户端连接复用少量数据库会话。连接数多会消耗进程/内存及调度资源。

**项目落地**：Spring Boot/HikariCP 每实例 `maximumPoolSize × 实例数` 只是理论最大数据库连接需求；控制总量，避免无脑调大。

### Q3 ⭐⭐ PostgreSQL 常见数据类型如何选？
- 主键：`bigint GENERATED ... AS IDENTITY`，或按系统方案使用 UUID；不要不加分析地全部使用 UUID。
- 金额：`numeric(p,s)`（精确十进制），不要用 `real/double precision` 存财务金额。
- 时间：`timestamptz` 存绝对时间点；`timestamp` 不带时区语义。前者显示会受会话时区影响。
- 文档原文：`text`；PG 中 `text` 与无限制 `varchar` 在多数普通使用中不存在显著的固有性能差异。
- 动态元数据：`jsonb`；需要保留输入原始格式/重复键语义时才考虑 `json`。
- 标签集合：`text[]` 可用，但高复杂度标签关系仍可建关联表。

### Q4 ⭐⭐ `serial`、`identity`、`uuid` 有什么区别？
**回答**：`serial` 是序列+默认值的语法便利写法；标准化写法倾向 `GENERATED BY DEFAULT/ALWAYS AS IDENTITY`；`uuid` 是原生 128 位标识类型，不等于数据库自动一定帮你生成。序列生成值可能有空洞，不能保证连续、也不能天然按提交顺序排序。

```sql
CREATE TABLE document (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title text NOT NULL
);
```

### Q5 ⭐⭐⭐ PostgreSQL `json` 与 `jsonb` 的区别？
**回答**：`json` 保存输入文本表示，`jsonb` 保存可操作的二进制结构，便于检索和索引。`jsonb` 不保留原始空白与键顺序，重复键按其规范化规则处理。大多数需要过滤的业务元数据优先 JSONB；高频主过滤列如 `tenant_id`、`report_year` 最好单独存列。

```sql
SELECT * FROM documents
WHERE metadata @> '{"report_type":"annual"}'::jsonb;
CREATE INDEX idx_documents_metadata ON documents USING gin(metadata);
```

### Q6 ⭐⭐ 原生数组 `ARRAY` 如何使用？何时不适合？
**回答**：`text[]` 直接保存多个标签，`@>` 为包含，`&&` 为有交集；GIN 可索引部分数组操作。如果标签需要独立权限、复杂筛选与统计，采用多对多关联表更合适。

```sql
SELECT * FROM documents WHERE tags @> ARRAY['财报'];
SELECT * FROM documents WHERE tags && ARRAY['消费','金融'];
```

### Q7 ⭐⭐ `LIMIT/OFFSET` 与 MySQL 有差异吗？如何做深分页？
**回答**：都支持 `LIMIT/OFFSET`，偏移很大时通常要跳过大量结果。更适合使用 keyset/cursor 分页，并让排序字段稳定、建立相应索引。

```sql
SELECT id, created_at FROM documents
WHERE (created_at, id) < (:cursor_time, :cursor_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

### Q8 ⭐⭐ PostgreSQL `schema` 是什么？与 MySQL 的 database 概念一样吗？
**回答**：PG 集群下有多个 database；一个 database 内可有多个 schema，schema 是表、视图、函数等对象的命名空间。同名表可存在于不同 schema。`search_path` 影响未限定对象名的解析。MySQL 的 schema 在常见使用中通常与 database 近似同义。

## 三、SQL 与数据类型（Q9–Q17）

### Q9 ⭐⭐⭐ `RETURNING` 有什么价值？
**回答**：INSERT/UPDATE/DELETE 时可直接返回受影响记录的数据，减少再查一次；特别适合创建文档任务和更新处理状态。

```sql
INSERT INTO documents(title, status) VALUES ('2024年报', 'PENDING')
RETURNING id, status;
UPDATE documents SET status='DONE' WHERE id=10 RETURNING id, status;
DELETE FROM documents WHERE id=10 RETURNING id;
```

### Q10 ⭐⭐⭐ `ON CONFLICT` 如何实现 UPSERT？
**回答**：按唯一约束/唯一索引的冲突条件决定 DO NOTHING 或 DO UPDATE。`EXCLUDED` 表示本次尝试插入的行。

```sql
INSERT INTO document_versions(document_id, version_no, content)
VALUES (10, 2, '内容')
ON CONFLICT (document_id, version_no)
DO UPDATE SET content=EXCLUDED.content
RETURNING document_id, version_no;
```

**追问**：是否绝对避免所有并发冲突？不是，仍需要考虑约束、锁顺序、死锁与事务重试。

### Q11 ⭐⭐⭐ `DISTINCT ON` 解决什么问题？
**回答**：每组保留排序后的第一条，非常适合“每个文档最新版本”；`ORDER BY` 左侧需与 DISTINCT ON 表达式匹配，并追加稳定排序字段。

```sql
SELECT DISTINCT ON (document_id) document_id, version_no, created_at
FROM document_versions
ORDER BY document_id, created_at DESC, version_no DESC;
```

MySQL 通常通过 `ROW_NUMBER() OVER (PARTITION BY ...)` 实现。

### Q12 ⭐⭐ `FILTER` 条件聚合比 `CASE WHEN` 好在哪里？
**回答**：语法清晰，一次 GROUP BY 可统计多个条件聚合；不是任何情况下都天然更快。

```sql
SELECT
  count(*) FILTER (WHERE status='DONE') AS done_count,
  count(*) FILTER (WHERE status='FAILED') AS failed_count
FROM ingest_jobs;
```

### Q13 ⭐⭐ CTE (`WITH`) 有什么用？是否每次都物化？
**回答**：把复杂查询拆成可读的逻辑步骤，也支持递归查询。现代 PostgreSQL 对符合条件的非递归、无副作用的 CTE 可以内联；`MATERIALIZED` / `NOT MATERIALIZED` 可以影响规划，不要背“CTE 一定是优化屏障”。

```sql
WITH recent AS (
  SELECT * FROM documents WHERE created_at >= now() - interval '7 days'
)
SELECT count(*) FROM recent;
```

### Q14 ⭐⭐ 窗口函数与 GROUP BY 的区别？
**回答**：`GROUP BY` 聚合压缩行数；窗口函数保留行，并计算分组排名、累计值和前后行。比如每个文档版本排名：

```sql
SELECT document_id, version_no,
       row_number() OVER(PARTITION BY document_id ORDER BY version_no DESC) AS rn
FROM document_versions;
```

### Q15 ⭐⭐ `LATERAL` 有什么用？
**回答**：让 FROM 中的子查询引用它左侧表的列。适合“每个文档取最近 N 条 Chunk”这类每行关联 Top N 查询。

```sql
SELECT d.id, c.id AS chunk_id
FROM documents d
CROSS JOIN LATERAL (
  SELECT id FROM child_chunks c
  WHERE c.document_id=d.id
  ORDER BY c.created_at DESC LIMIT 2
) c;
```

### Q16 ⭐⭐ `ILIKE` 和 `pg_trgm` 有什么用途？
**回答**：`ILIKE` 支持大小写不敏感的模式匹配；通配符前缀为 `%` 的模糊匹配普通 B-Tree 往往不合适，可以评估 `pg_trgm` + GIN/GiST。对金融文档名称、公司名称模糊搜索较实用。

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_doc_title_trgm ON documents USING gin(title gin_trgm_ops);
SELECT * FROM documents WHERE title ILIKE '%年度报告%';
```

### Q17 ⭐⭐ PostgreSQL 如何实现物化视图？
**回答**：`CREATE MATERIALIZED VIEW` 将查询结果存储下来，查询快，但不会因底表变化自动实时更新；需 `REFRESH MATERIALIZED VIEW`。`CONCURRENTLY` 需要满足唯一索引等要求。适合更新频率不高的统计报表，不适合实时强一致数据。

## 四、索引与执行计划（Q18–Q27）

### Q18 ⭐⭐⭐ PostgreSQL 有哪些常用索引？如何选？
| 类型 | 常见用途 | 一句话 |
|---|---|---|
| B-Tree | 等值、范围、排序 | 最常用默认索引 |
| GIN | 全文、数组、JSONB | 倒排式多值索引，查“包含哪些元素” |
| GiST | 空间、范围等 | 按操作类支持特定搜索结构 |
| BRIN | 大表且数据与物理顺序相关 | 索引体积小但精度粗 |
| Hash | 等值 | 比 B-Tree 适用面窄 |

### Q19 ⭐⭐⭐ 什么是部分索引（Partial Index）？
**回答**：只索引符合条件的行，适合数据分布明显倾斜的业务，比如只查待处理任务。其索引是否能被使用取决于查询谓词能否被优化器识别为满足部分索引条件。

```sql
CREATE INDEX idx_jobs_pending ON ingest_jobs(created_at)
WHERE status='PENDING';
```

**坑**：参数化 SQL、表达式写法与统计信息可能影响优化器是否选中索引。

### Q20 ⭐⭐⭐ 表达式索引与覆盖索引怎么用？
**回答**：表达式索引将计算结果写入索引，如 `lower(email)` 或 `(metadata->>'stock_code')`。`INCLUDE` 包含额外列让部分查询具备 Index Only Scan 的条件，但并不保证绝不访问 Heap。

```sql
CREATE INDEX idx_doc_stock ON documents ((metadata->>'stock_code'));
CREATE INDEX idx_doc_tenant_time ON documents(tenant_id, created_at DESC) INCLUDE (title);
```

### Q21 ⭐⭐⭐ 为什么有索引却走 Seq Scan？
**回答模板**：表很小、要读比例太大、谓词与索引不匹配、统计信息失真、函数/类型转换、排序/回表成本、参数化计划差异等。**先看 EXPLAIN ANALYZE，不要先强行改参数**。

### Q22 ⭐⭐⭐ `EXPLAIN ANALYZE` 重点看什么？
1. `Seq Scan / Index Scan / Bitmap Heap Scan / Index Only Scan`：使用了什么访问方法。
2. `rows` 估算 vs 实际：优化器是否估错行数。
3. `actual time`、`loops`：节点实际执行情况；嵌套节点时间不能简单相加。
4. `Buffers: shared hit/read`：共享缓冲区缓存命中/读取，`read` 不等于一定物理磁盘 I/O。
5. `Sort Method / Disk`、`temp read/written`：排序或 Hash 是否溢出。
6. `Planning Time`、`Execution Time`：规划和执行耗时。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM documents WHERE tenant_id=10 ORDER BY created_at DESC LIMIT 20;
```

**提醒**：`ANALYZE` 真执行 SQL；对 UPDATE/DELETE 先在测试环境或事务中验证。

### Q23 ⭐⭐ `Index Scan`、`Index Only Scan`、`Bitmap Heap Scan` 区别？
**回答**：Index Scan 用索引定位，再访问 Heap；Index Only Scan 在索引覆盖所需列时可减少 Heap 访问，但仍受 VM All-Visible 状态影响；Bitmap Scan 先收集候选 Heap 块，再批量访问，常见于中等选择性、多条件组合查询。

### Q24 ⭐⭐ GIN 索引一定比 B-Tree 快吗？
**回答**：不。GIN 适合一个字段拆成多个可索引键（词条、JSONB 键值、数组元素等）；普通主键/时间范围使用 B-Tree 往往更合适。GIN 有写入维护成本和更复杂的更新行为。

### Q25 ⭐⭐ 为什么联合索引的列顺序很重要？
**回答**：列顺序影响可利用的前缀过滤、排序和扫描范围。常见场景 `(tenant_id, created_at DESC)` 对“某租户按时间倒序分页”有利；不能机械背“选择性高的一定放最前”，应依据查询谓词、排序和统计信息。

### Q26 ⭐⭐ `CREATE INDEX CONCURRENTLY` 为什么重要？
**回答**：它允许在较少阻塞写入的情况下创建索引，适合线上大表，但构建更复杂、更耗资源，不能在普通事务块中运行，失败时可能留下无效索引需要处理。

### Q27 ⭐⭐ 如何定位生产慢 SQL？
**步骤**：从监控/`pg_stat_statements` 定位高总耗时、高 P95 或调用量大的 SQL → `EXPLAIN (ANALYZE, BUFFERS)` 复现 → 比较估计行数和执行计划 → 检查索引、统计、锁等待、磁盘、排序溢出 → 做基准测试 → 灰度发布与回归。避免只看 SQL 本身忽略锁与连接池。

## 五、事务、并发、运维（Q28–Q35）

### Q28 ⭐⭐⭐ PostgreSQL 的 MVCC 与 InnoDB 的区别？
**回答**：两者都提供多版本并发读取。InnoDB 通过 Undo Log 等机制组织历史版本；PostgreSQL 通常在 Heap 中保留新旧 Tuple 版本，以事务可见性规则判断能读到哪个版本，并通过 VACUUM 清理不再需要的死元组。面试使用层面知道区别即可，不必先背所有 `xmin/xmax` 规则。

### Q29 ⭐⭐⭐ PostgreSQL 的隔离级别有什么特点？
**回答**：支持 Read Committed、Repeatable Read、Serializable；SQL 标准中的 Read Uncommitted 在 PostgreSQL 表现为 Read Committed。默认 Read Committed，每条语句通常获取新的快照；Repeatable Read 使用事务级快照，PG 的实现不会出现幻读；Serializable 使用 SSI 机制防止序列化异常，但可能报 serialization failure，需要应用重试。注意 MySQL InnoDB 的 RR 与 PG RR 具体行为并非完全一致。

### Q30 ⭐⭐⭐ `SELECT ... FOR UPDATE` 与 `SKIP LOCKED` 怎么用？
**回答**：`FOR UPDATE` 锁住选择的行；`SKIP LOCKED` 遇到已锁行就跳过，适合多 Worker 争抢待处理任务，不适合要求完整一致查询结果的通用报表。

```sql
BEGIN;
SELECT id FROM ingest_jobs WHERE status='PENDING'
ORDER BY created_at, id
FOR UPDATE SKIP LOCKED LIMIT 10;
-- 在同一事务内更新这些任务为 RUNNING
COMMIT;
```

**追问**：多 Worker 如何避免重复执行？除了领取任务事务，还需幂等键、任务租约/超时恢复与失败重试。

### Q31 ⭐⭐ `VACUUM`、`ANALYZE`、`VACUUM FULL` 有什么区别？
**回答**：VACUUM 回收可复用的死元组空间并维护可见性；ANALYZE 更新优化器统计；普通 VACUUM 通常不直接把内部可复用空间全还给 OS；VACUUM FULL 重写表以压缩文件，需更强锁、额外空间，不应当作日常任务。

### Q32 ⭐⭐ 什么是 WAL？提交是不是马上写表文件？
**回答**：WAL 是预写式日志；在通常持久化配置下，事务成功提交的恢复保证依赖必要 WAL 持久化，不要求所有相关数据页在 COMMIT 时立即写回表文件。用于崩溃恢复，也支持复制与 PITR。实际保证受 `synchronous_commit`、`fsync` 等配置影响。

### Q33 ⭐⭐ 遇到死锁如何处理？
**回答**：PG 能检测死锁并回滚其中一个事务。应用端捕获相应 SQLSTATE（常见 `40P01`）、对可重试事务执行有界重试与退避；设计上固定表/行访问顺序，缩短事务，确保合适索引，避免长期持锁。

### Q34 ⭐⭐ PostgreSQL 连接池怎么配？
**回答**：HikariCP 控制应用实例连接数，PG 连接数不是越多越好。综合数据库 CPU、SQL 时长、实例数和后台连接需求决定上限。高并发短事务可评估 PgBouncer，但事务池模式可能影响会话变量、临时表、会话级 prepared statement 等使用方式，需评估具体版本与驱动行为。

### Q35 ⭐⭐ 复制、备份和 PITR 是什么关系？
**回答**：流复制提供副本与读扩展/容灾基础，但副本不是备份；误删数据可复制到备库。PITR（Point-In-Time Recovery）依赖基础备份和连续 WAL 归档恢复到目标时间点。面试应区分 RPO（可容忍丢失的数据时间窗口）和 RTO（恢复时间）。

## 六、金融 RAG / pgvector / 全文检索（Q36–Q48）

### Q36 ⭐⭐⭐ 为什么选择 PostgreSQL 而不是 MySQL / Milvus？
**回答**：看文档首章。补一句：选择 PG 是 V1 的复杂度与能力平衡；高规模、独立扩缩容或严苛延迟下可逐步拆出专用向量引擎。须用 Recall@K、P95、CPU、索引大小、成本验证。

### Q37 ⭐⭐⭐ `tsvector` 与 `tsquery` 是什么？
- `tsvector`：文档分词及规范化后的可检索词条（可含位置/权重）。通常入库时生成。
- `tsquery`：搜索词及 AND/OR/NOT/词距规则构成的查询表达式**类型**。通常查询时动态构建。
- `@@`：判断 `tsvector` 是否匹配 `tsquery`。
- `GIN`：加快匹配的索引，不是相关性评分算法。

```sql
CREATE INDEX idx_chunk_fts ON child_chunks USING gin(search_vector);
SELECT id FROM child_chunks
WHERE search_vector @@ plainto_tsquery('english', 'revenue growth');
```

**中文场景**：需要对应的中文 text search configuration（如 zhparser）；不能直接认为内置 `english` 会正确分词中文。

### Q38 ⭐⭐⭐ `tsquery` 就是查询语法吗？
**回答**：工程上可以叫“全文检索查询表达式”；更精确是 PostgreSQL 的一种数据类型，其值承载检索逻辑。`to_tsquery()` 是把输入转换成这种类型的函数；普通用户输入通常更适合用 `plainto_tsquery` / `websearch_to_tsquery` 而不是自己拼接操作符。

### Q39 ⭐⭐⭐ GIN、zhparser、BM25 的分工？
**回答**：`zhparser` 做中文分词；`tsvector/tsquery` 表示索引文档与查询；`GIN` 加速候选匹配；**BM25 是排序算法**。PG 原生 `ts_rank` / `ts_rank_cd` **不等于 BM25**。如果面试官问“用的是标准 BM25 吗”，必须说清当前实际实现和差异。

### Q40 ⭐⭐⭐ pgvector 是什么？它会产生 Embedding 吗？
**回答**：pgvector 是 PostgreSQL 扩展，提供 `vector` 等数据类型、距离操作符和 ANN 索引。**不会生成文本 Embedding**：向量由外部 Embedding 模型生成，存入 PG 后用距离算子检索。

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE embeddings(id bigint PRIMARY KEY, embedding vector(3));
```

### Q41 ⭐⭐⭐ pgvector 的 `<->`、`<=>`、`<#>` 区别？
| 算子 | 含义 | 方向 |
|---|---|---|
| `<->` | L2 / 欧氏距离 | 越小越近 |
| `<=>` | 余弦距离 | 越小越近 |
| `<#>` | **负内积** | 越小代表内积越大 |

`<#>` 返回负内积，是为了便于升序距离排序。**向量已归一化**时，L2 / cosine / inner product 对同一批向量的**排序等价**（数值本身不同）；未归一化时不能混用。精度取决于 Embedding 模型与实际评测，不能只凭算子名判断谁更准确。

### Q42 ⭐⭐⭐ KNN、ANN、HNSW、IVFFlat 分别是什么？
**回答**：KNN 是找最近的 K 个，通常指精确最近邻；ANN 是以一定召回损失换速度的近似最近邻。HNSW 是多层近邻图索引；IVFFlat 是分簇/倒排列表方案。pgvector 默认无 ANN 索引时可执行精确近邻查询；创建 HNSW/IVFFlat 索引后可用近似方式加速。

### Q43 ⭐⭐⭐ HNSW 参数怎么调？
- `m`：建图时每层邻居连接规模，增大通常增加索引体积、构建成本，也可能改善召回。
- `ef_construction`：构建索引的候选队列大小，增大一般提高建图质量但建得更慢。
- `hnsw.ef_search`：查询时的候选搜索范围，增大常提高召回但增加延迟。

```sql
CREATE INDEX idx_chunk_embedding ON child_chunks
USING hnsw (embedding vector_cosine_ops)
WITH (m=16, ef_construction=64);
SET hnsw.ef_search=100;
```

**面试亮点**：调参不能只看速度，必须同一测试集同时画出 Recall@K 与 P95 延迟的权衡。

### Q44 ⭐⭐⭐ HNSW 检索加 `WHERE tenant_id = ?` 为什么可能不足 Top K？
**回答**：ANN 候选搜索与 SQL 过滤组合时，过滤可能发生在候选扫描之后，导致实际满足条件不足 K。优化路径：基于过滤字段的 B-Tree 精确检索、提升 `ef_search`、使用支持的 iterative scan、合适的部分索引、分区或租户隔离。需确保租户权限过滤始终正确，不能因为召回不足就去掉隔离条件。

### Q45 ⭐⭐⭐ 如何设计 Parent-Child Chunk 存储？
**建议模型**：`documents` 存文档和权限；`parent_chunks` 存大上下文；`child_chunks` 存小块、Embedding、tsvector、parent_id 和过滤字段。召回时先按 child 检索，在完成候选过滤、融合及重排后根据 `parent_id` 获取父块用于生成。防止跨租户/越权读取，关联时同时校验权限与租户归属。

### Q46 ⭐⭐⭐ Sparse + Dense 混合检索如何做？
**回答**：Dense 用 Embedding + pgvector；Sparse 用 `tsvector/tsquery` + GIN；两路各取候选并做独立排序，再通过 RRF 或其他融合方式整合，必要时使用 Reranker。RRF 公式：

\[
\mathrm{RRF}(d)=\sum_{r\in R}\frac{1}{k+\operatorname{rank}_r(d)}
\]

常见 `k=60` 是经验参数，不是固定真理。所有排序结果需要统一候选 ID、做去重；保留每路召回来源和分数用于排障。

### Q47 ⭐⭐⭐ RAG 的全文检索为什么不能只用向量？
**回答**：财务指标、股票代码、年份、公司名、产品名等精确实体，向量近邻可能不够稳定。关键词检索能够提供精确词条匹配，向量检索解决同义表达和语义相关；混合通常更稳，但效果必须通过自建评测集验证。

### Q48 ⭐⭐⭐ PostgreSQL 做 RAG 检索怎么评估与扩容？
**回答**：同时看 Recall@K / nDCG / MRR、端到端回答正确率、P50/P95/P99、索引大小、CPU/内存/IO、更新与重建成本、过滤后 Top K 足额率。先优化 SQL/索引/过滤与模型参数，再考虑读副本、分区或独立向量服务。不要只凭“几百万 Chunk”就宣布需要迁移。

## 七、项目实战：5 个可讲述的面试场景

### 场景 A：金融文档上传后异步解析与检索入库
**需求**：用户上传 PDF/研报；解析、切分、Embedding、写入数据库，过程异步可重试。

**可讲设计**：`documents` 记录状态；任务表通过唯一键控制幂等；`INSERT ... ON CONFLICT` 避免重复；`UPDATE ... RETURNING` 或 `FOR UPDATE SKIP LOCKED` 领取任务；解析与 Embedding 外部调用通常不放在长事务里；以版本号或任务阶段保证切块重建一致性。

**追问**：任务超时怎么办？**回答**：租约/重试次数/超时回收；对外部调用的副作用设计幂等键。

### 场景 B：百万级 Chunk 查询慢
**现象**：向量检索查询 P95 高，且限定用户选定文档后性能变化大。

**排查**：先拆分 Dense 与 Sparse 各自耗时；`EXPLAIN (ANALYZE, BUFFERS)` 观察 HNSW/Seq Scan；查看 `WHERE` 过滤选择性和 K；检索候选和原文读取是否耦合；调整 `ef_search` 并测 Recall@K；对少量文档范围可比较 B-Tree 过滤+精确距离扫描；不要一次取回所有 `content` 大字段。

### 场景 C：用户选定文档对话，权限与 Top K 冲突
**需求**：同一向量池有多租户、多文档，用户只允许指定文档。

**设计**：权限校验不只在 UI；SQL 强制 `tenant_id` / `document_id` 范围；分析 ANN 过滤导致的候选不足；必要时使用分区/部分索引或精确检索；结果进入 Parent Chunk 获取阶段再次做权限校验。

### 场景 D：金融全文检索效果不佳
**现象**：“营业收入”“营收”“总收入”词汇匹配不稳定。

**设计**：检查 zhparser 分词输出、停用词词典、同义词映射、查询清洗；对股票代码、年份等做结构化过滤；`ts_rank` 与 BM25 明确区分；建立标注数据集做 Keyword Recall 和 Hybrid Recall 对比，而非只“调大权重”。

### 场景 E：数据更新和删除后，检索结果过期
**需求**：用户删除文档后，原文和索引中不应再被检索到。

**设计**：`documents` 作为权限/生命周期事实来源；删除时先立刻撤销可见权限或软删除，再异步清理 chunk/embedding/索引数据；所有检索强制过滤逻辑状态；重建用版本号切换，避免新旧 Chunk 混用；监控孤儿 Chunk、版本错配、删除延迟。

> **面试经验表述原则**：只讲你实际做过和验证过的数字；如果尚未压测，不要编造 QPS、P95 或数据规模。可以说“计划以 Recall@K、P95 和索引资源做决策”。

## 八、高频 SQL 速查

> 以下片段是分场景独立示例，假定业务表/列已存在。需要 `vector` 的语句先安装 pgvector 扩展。

```sql
-- 1. 查看 PostgreSQL 版本和基础配置
SELECT version();
SHOW shared_buffers;
SHOW work_mem;
SHOW max_connections;

-- 2. 当前活动会话
SELECT pid, usename, state, wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE datname = current_database();

-- 3. 快速检查表与索引大小
SELECT pg_size_pretty(pg_relation_size('documents')) AS heap_size,
       pg_size_pretty(pg_total_relation_size('documents')) AS total_size;

-- 4. 建索引时减少写阻塞（事务外执行）
CREATE INDEX CONCURRENTLY idx_documents_tenant_time
ON documents (tenant_id, created_at DESC);

-- 5. 查询执行计划
EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM documents WHERE tenant_id=10 ORDER BY created_at DESC LIMIT 20;

-- 6. JSONB 包含查询
SELECT id FROM documents
WHERE metadata @> '{"report_type":"annual"}'::jsonb;

-- 7. 全文检索（英文配置演示）
SELECT to_tsvector('english', 'revenue growth in 2024')
       @@ plainto_tsquery('english', 'revenue growth') AS matched;

-- 8. pgvector 距离算子（最小示例）
SELECT '[1,0,0]'::vector <=> '[0.9,0.1,0]'::vector AS cosine_distance;

-- 9. 最近 N 条数据：游标分页
SELECT id, created_at FROM documents
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC LIMIT 20;

-- 10. 每个文档的最新版本
SELECT DISTINCT ON (document_id) document_id, version_no, created_at
FROM document_versions
ORDER BY document_id, created_at DESC, version_no DESC;
```
