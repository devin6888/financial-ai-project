# 一、先看两份回答的本质区别

## 1. 你的 RAG：模板驱动型回答

你的回答基本是：

不管用户问的是营收、净利润、现金流，还是企业业务发展情况，最终可能都会按照：

```

```

这个结构组织答案。

这就是典型的固定模板式生成。

它的优点是：

- 格式统一。
- 容易控制输出。
- 适合金融数据分析。
- 不容易遗漏预设板块。

但缺点也很明显：它要求模型先适应模板，再组织答案，而不是根据问题本身决定如何组织答案。

## 2. 腾讯 ima：内容驱动型回答

ima 的回答则不同。

它根据当前问题，动态组织出了：

三、核心业务经营数据

1. 证券业务
2. 金融电子商务服务
3. 金融数据服务

四、成本与费用情况

使用另一张表格展示费用情况。

五、总结

提炼业务结构变化和经营特征。

这里有几个关键特点：

1. 不同类型的信息使用不同的展示形式。
2. 相关数据会被合并到同一张表格，而不是机械地拆分。
3. 会根据内容重要程度决定篇幅。
4. 不同问题可以生成不同数量的章节。
5. 不会强制每个问题都出现相同的板块。

这实际上是一种 动态答案规划（Dynamic Answer Planning）+ 自适应内容生成（Adaptive Answer Generation） 的思路。

# 三、应该如何实现动态回答？

我建议你引入一个概念：

# Dynamic Answer Generation

## 动态答案生成

不再预先规定答案必须包含哪些板块，而是让 LLM 根据问题、证据和分析目标，决定答案的组织方式。

输入

用户问题 + RAG 检索证据

① Answer Planning

动态分析问题，决定需要回答什么、如何组织、使用什么展示形式。

② Answer Generation

根据规划和证据生成自然语言答案。

③ Answer Validation

校验数字、口径、事实和引用是否有证据支持。

④ Answer Rendering

将答案转换成前端能够展示的 Markdown 或结构化内容。

这四个环节，是我认为你最应该采用的方案。

## 1. 第一步：Answer Planning（动态答案规划）

这是最关键的一步。

传统做法：

```
用户提问
   ↓
检索文档
   ↓
套用固定 Prompt
   ↓
生成答案
```

我建议改成：

```
用户提问
   ↓
检索文档
   ↓
分析问题 + 证据
   ↓
动态制定回答计划
   ↓
按照计划生成答案
```

例如，同样是金融研报分析，用户提出不同问题时，回答计划应该完全不同。

场景 A：分析 2024 年营收情况

适合经营分析结构

- 营收总体情况
- 分行业、分业务收入
- 核心业务经营数据
- 成本费用（有相关证据时）
- 总结

场景 B：分析 2024 年净利润变化原因

适合因果分析结构

- 净利润变化概况
- 收入端变化
- 成本费用端变化
- 非经常性损益影响
- 主要驱动因素及证据不足之处

场景 C：对比 2023 年和 2024 年现金流

适合对比分析结构

- 现金流总体变化
- 经营活动现金流
- 投资活动现金流
- 筹资活动现金流
- 现金流质量分析

场景 D：东方财富的主要业务有哪些？

适合业务介绍结构

- 业务板块介绍
- 各板块收入构成
- 主要业务之间的关系
- 业务特点

注意，这些只是可能的回答方式，不是四套固定模板。

例如场景 A，如果检索不到成本费用数据，就不应该强制出现成本费用章节。

反过来，如果检索到了分地区、分产品、分客户等有价值的数据，也应该允许模型主动增加章节。

核心原则：先看问题和证据，再决定答案结构。

## 2. 第二步：让 LLM 输出动态的 Answer Plan

这里建议使用 Structured Output，让模型先生成一个 JSON 规划结果。

例如，用户问：

> 分析下2024年的营收情况

模型可能生成：

```
{
  "answer_type": "financial_analysis",
  "title": "东方财富2024年营收分析",
  "sections": [
    {
      "id": "overview",
      "title": "营业总收入总体情况",
      "purpose": "介绍营收规模及同比变化",
      "priority": "high",
      "layout": "paragraph"
    },
    {
      "id": "business",
      "title": "分行业及分产品收入结构",
      "purpose": "分析收入构成和业务变化",
      "priority": "high",
      "layout": "table"
    },
    {
      "id": "operation",
      "title": "核心业务经营数据",
      "purpose": "结合经营数据分析收入变化",
      "priority": "medium",
      "layout": "mixed"
    },
    {
      "id": "cost",
      "title": "成本与费用情况",
      "purpose": "补充成本费用变化",
      "priority": "medium",
      "layout": "table"
    },
    {
      "id": "summary",
      "title": "总结",
      "purpose": "提炼主要经营特征",
      "priority": "high",
      "layout": "paragraph"
    }
  ]
}
```

这里有几个值得注意的设计：

- `sections` 是数组，章节数量不固定。
- `title` 是模型动态生成的。
- `purpose` 决定该章节要表达什么。
- `layout` 决定该章节适合使用什么展示形式。
- `priority` 用来控制内容的重要程度。

还可以支持：

| layout        | 展示方式 | 适用情况           |
| ------------- | -------- | ------------------ |
| paragraph     | 普通段落 | 简单事实、解释     |
| table         | 表格     | 多维数据对比       |
| bullets       | 无序列表 | 多个业务特点       |
| numbered_list | 有序列表 | 分析步骤、排名     |
| mixed         | 混合形式 | 综合分析           |
| quote         | 引用块   | 特别说明、报告原文 |
| callout       | 强调内容 | 核心结论、风险提示 |

这就解决了你目前固定板块的问题。

但要注意：这些 layout 是可选的表达工具，而不是要求每个章节必须选择一种固定组件。

## 3. 第三步：Answer Generation（动态内容生成）

有了 Answer Plan，接下来才是真正生成答案。

这里我建议你不要再使用原来那种强制格式的 Prompt。

可以把生成 Prompt 改造成下面这样。

System Prompt 示例：

```
你是一名专业的金融研究分析师，负责根据用户问题和知识库证据生成高质量的金融分析回答。

1. 根据用户的问题和检索到的证据，自主决定回答结构。
2. 不允许使用固定的章节模板。
3. 不要求每次回答都包含结论、数据、归因、总结等固定板块。
4. 根据不同内容选择合适的表达方式，包括段落、表格、列表等。
5. 允许根据实际证据增加、合并或省略章节。
6. 简单问题直接回答，不要为了结构完整而过度拆分。
7. 复杂问题可以分成多个章节，逐层展开分析。

# 二、内容组织

1. 优先回答用户最关心的问题。
2. 重要数据可以使用表格展示。
3. 对于相关性较强的数据，尽可能合并展示。
4. 对于业务特点、变化原因等内容，使用自然语言分析。
5. 不要为了追求内容丰富而重复表达相同信息。
6. 只有证据支持的内容才能作为事实陈述。
7. 不同章节应有明确的分析目的。

# 三、金融数据要求

1. 严格区分营业收入、营业利润、净利润等指标。
2. 注意统计期间、单位、合并报表和母公司口径。
3. 涉及同比、环比时必须有准确的计算依据。
4. 不允许根据相关性直接推断因果关系。
5. 对于证据不足的原因，应明确说明无法确认。

# 四、证据引用

1. 每个重要事实、数据和分析结论都必须有对应证据。
2. 使用 [E1]、[E2] 等引用标识。
3. 不允许编造引用。
4. 如果多个证据共同支持一个结论，应同时引用。

# 五、表达风格

1. 使用专业、自然、流畅的金融分析语言。
2. 避免机械化、报告模板化的表达。
3. 不要为了格式统一而强制增加章节。
4. 根据内容复杂度控制回答长度。
5. 优先保证信息价值，而不是追求章节数量。

# 六、输出要求

直接按照 Answer Plan 组织最终回答。
使用 Markdown 格式。
不输出内部规划过程。
```

这只是基础版本，后续还需要根据你的实际测试数据持续优化。

我特别强调一点：

不要在 Prompt 里面写死必须输出 Markdown 表格，也不要写死必须输出五个章节。

否则，你只是把原来 Java 代码中的模板，搬到了 Prompt 里面而已。

# 四、如何让答案的布局更灵活？

这里还有一个非常重要的细节。

ima 的回答不只是章节灵活，内容内部的布局也很灵活。

例如：

- 关键数字使用加粗。
- 相关业务数据放在同一张表格。
- 经营情况使用列表。
- 对关键结论进行提炼。
- 不同内容使用不同层级的标题。

这部分实际上可以交给 LLM 生成 Markdown。

例如：

普通段落：

东方财富2024年实现营业总收入116.04亿元，同比增长4.72%。整体营收保持增长，但不同业务板块表现出现明显分化。

数据表格：

| 业务板块     | 收入      | 同比    |
| ------------ | --------- | ------- |
| 证券服务     | 84.94亿元 | +18.07% |
| 金融电子商务 | 28.41亿元 | -21.62% |
| 金融数据服务 | 1.92亿元  | -3.13%  |

业务分析：

证券服务是主要增长来源，金融电子商务服务收入则出现下滑，两者表现形成明显对比。

这三种表达形式可以自然地出现在同一个章节中。

我的建议是：

后端负责生成内容和 Markdown，前端负责 Markdown 渲染，不要在后端预先拼接固定 HTML 模板。

前端可以使用 Vue Markdown 渲染方案，支持：

- GFM 表格
- 标题层级
- 加粗和斜体
- 有序、无序列表
- 引用块
- 代码块
- 自定义引用组件

引用 `[E1]` 还可以在前端进一步解析成可点击的证据标记，点击后显示原始文档、页码和证据内容。

这样，回答的布局完全由内容决定，而不是由固定页面组件决定。

# 五、结合你现有的 Spring AI + LangGraph4j，如何落地？

这一部分我认为最重要。

你之前确定的技术路线是：

- Java 21 + Spring Boot
- Spring AI 负责 LLM、Embedding、VectorStore、RAG
- LangGraph4j 负责 State、Node、Edge、Checkpoint
- PostgreSQL + pgvector 负责知识库检索

我建议保留这套架构，不需要为了实现动态回答更换技术。

只需要在现有 Agent Graph 中增加和调整几个节点。

## 1. 推荐的 LangGraph 工作流

START

用户问题

Query Analysis

问题理解、分析任务类型、确定检索方向

Retrieval

向量检索、关键词检索、Metadata Filter、Reranking、Parent-Child 扩展

新增核心节点

Answer Planning

根据问题和证据生成动态答案计划

Answer Generation

根据 Answer Plan 和 Evidence 生成答案

Answer Validation

数字校验、口径校验、引用校验、事实校验

END

Markdown 答案 + 引用信息

其中 Answer Planning 和 Answer Generation 是这次新增的重点。

如果 Validation 发现证据不足，可以通过条件边返回 Retrieval，执行一次补充检索；如果只是表达问题，则可以要求 Generation 修正，而不是重复检索。

## 2. LangGraph State 应该如何设计？

可以在你原来的 State 基础上增加以下字段：

```
public class RAGState {

    // 用户问题
    private String question;

    // 检索结果
    private List<RetrievedChunk> retrievedChunks;

    // 证据集合
    private List<Evidence> evidences;

    // 动态答案计划
    private AnswerPlan answerPlan;

    // 生成的初稿
    private String draftAnswer;

    // 提取出的事实声明
    private List<Claim> claims;

    // 校验结果
    private ValidationResult validationResult;

    // 最终答案
    private String finalAnswer;

    // 重试次数
    private int retryCount;
}
```

其中 `AnswerPlan` 可以设计成：

```
public record AnswerPlan(
    String answerType,
    String title,
    List<AnswerSection> sections
) {}

public record AnswerSection(
    String id,
    String title,
    String purpose,
    String priority,
    String layout,
    List<String> evidenceIds
) {}
```

这里我建议保留 `evidenceIds`。

这样，每个章节都可以明确知道自己应该使用哪些证据，而不是把全部检索结果无差别地交给 LLM。

## 3. Spring AI 负责什么？

在这个设计中：

| 模块                        | 职责                            |
| --------------------------- | ------------------------------- |
| Spring AI ChatClient        | 调用 LLM                        |
| Spring AI Structured Output | 将模型规划结果转换成 AnswerPlan |
| Spring AI VectorStore       | 向量检索                        |
| 业务检索服务                | 混合检索、重排、父子块扩展      |
| LangGraph4j                 | 控制整个工作流                  |
| Answer Validator            | 校验数据和引用                  |
| Vue Markdown Renderer       | 动态渲染最终答案                |

注意：Answer Planning 和 Answer Generation 可以调用同一个模型，也可以根据成本和效果选择不同模型，不需要为了规划专门部署一个模型。

对于简单问题，还可以通过问题复杂度判断跳过 Answer Planning，直接生成答案，减少一次 LLM 调用。

## 4. 你还需要特别注意检索阶段的改造

回到前面的东方财富案例。

你的 RAG 只展示了营收、分行业、分服务等信息，而 ima 还展示了净利润、分地区、经营数据、费用等信息。

因此，我建议你在 Retrieval 阶段也做一点调整。

比如用户问：

> 分析下2024年的营收情况

不要只检索：

```
2024年 东方财富 营业收入
```

可以让 Query Analysis 进一步生成相关检索方向：

| 检索方向 | 检索内容                     |
| -------- | ---------------------------- |
| 核心指标 | 2024年营业收入、同比增长     |
| 业务结构 | 分行业、分产品收入及占比     |
| 地区结构 | 分地区收入及占比             |
| 经营数据 | 交易额、基金销售额、保有规模 |
| 费用情况 | 销售费用、管理费用、研发费用 |
| 盈利情况 | 净利润、利润增长情况         |

然后分别检索，合并、去重、重排。

这里不是说每次都必须执行六次检索，而是根据问题类型动态选择检索方向。

例如用户只问：

> 2024年营业收入是多少？

就没有必要进行这么全面的检索。

这也与你之前决定的 Multi-Query 按需启用的思路一致。

# 六、一个我认为非常重要的设计：不要让 Answer Plan 变成新的固定模板

你可能会想：

```
COMPARISON_ANALYSIS
```

然后每种类型都有自己的固定章节？

我不太建议这样做。

因为这很容易从原来的固定模板，变成多个固定模板。

更合理的设计是：

Answer Type 只负责确定分析方向，具体章节由 LLM 根据问题和证据动态决定。

例如：

```
answerType = FINANCIAL_ANALYSIS
```

它只表示这是金融分析任务。

至于需要几个章节、每个章节叫什么、是否使用表格，都由模型决定。

你可以保留一些通用的回答类型用于控制分析策略，但不要让它们直接决定最终输出结构。

# 七、金融 RAG 还需要增加一个约束：内容灵活，事实必须严格

这一点比普通知识库 RAG 更重要。

我建议把两个事情彻底分开：

| 维度       | 控制方式     |
| ---------- | ------------ |
| 章节数量   | LLM 动态决定 |
| 章节名称   | LLM 动态决定 |
| 内容顺序   | LLM 动态决定 |
| 段落和表格 | LLM 动态决定 |
| 内容详略   | LLM 动态决定 |
| 财务数字   | 证据约束     |
| 统计口径   | 证据约束     |
| 同比计算   | 程序校验     |
| 事实引用   | 程序校验     |
| 因果结论   | 证据支持     |

例如，ima 的回答中提到：

> 基金销售收入下滑，受费率下降等因素影响。

如果检索证据没有明确披露费率下降的影响，就不能让模型将其当成公司年报明确披露的事实。

我更推荐你之前讨论过的那套机制：

```
Evidence → Claims → Validation → Answer
```

也就是：

1. 从检索证据中提取事实声明。
2. 每个事实声明关联原始证据。
3. 校验数字、单位、期间、口径。
4. 检查结论是否有证据支持。
5. 通过校验后再生成最终答案。

这样既能获得 ima 那种灵活的表达方式，又不会牺牲金融分析最重要的准确性。

# 八、结合你现有的 SSE 流式输出

你之前提到 Spring Boot 使用 `SseEmitter`，需要在模型正式输出前，先把各个处理阶段的状态发送给前端。

引入 Answer Planning 后，可以扩展为：

| SSE Event | 前端展示         |
| --------- | ---------------- |
| `status`  | 正在理解问题     |
| `status`  | 正在检索相关资料 |
| `status`  | 正在整理分析思路 |
| `status`  | 正在组织回答     |
| `delta`   | 逐字输出答案     |
| `sources` | 证据来源         |
| `done`    | 生成完成         |

这里有一个建议：

Answer Plan 不一定要展示给用户，但你可以在后台记录它，方便后续通过 Langfuse 分析不同问题的答案质量。

另外，Answer Planning 如果采用一次完整的 Structured Output 调用，就不能像最终答案一样逐字流式输出；但它可以在完成后立即发送状态，再开始流式生成最终答案。

# 九、我建议你按照什么顺序实施？

不要一次性改造整个 RAG。

我建议分三个阶段。

第一阶段：改造答案生成

优先实施

- 移除固定答案模板。
- 增加 Answer Planning。
- 使用动态章节结构。
- 允许 Markdown 自由组合段落、表格和列表。
- 保留原来的引用机制。

目标：先解决答案死板、章节固定、布局单一的问题。

第二阶段：完善检索覆盖

- 根据问题动态生成检索方向。
- 按需执行 Multi-Query。
- 对不同业务维度进行补充检索。
- 合并去重并重新排序。
- 建立证据覆盖率评估。

目标：解决答案信息不完整的问题。

第三阶段：完善金融答案质量

- Claims 事实提取。
- FinancialFact 数值校验。
- Citation Validation。
- 证据不足时补充检索或拒绝推断。
- 使用 Langfuse 建立答案质量评估集。

目标：让回答既灵活又可靠。

## 十、最后说说我的核心建议

我认为你现在的 RAG 已经不应该仅仅定位成一个传统的：

```
问题 → 检索 → LLM → 答案
```

而应该逐步演进成一个真正的金融研究分析 Agent。

两者的差异在于：

| 传统 RAG        | 金融研究 Agent     |
| --------------- | ------------------ |
| 检索相关文档    | 分析用户意图       |
| 拼接上下文      | 规划信息获取方向   |
| 使用固定 Prompt | 动态制定回答计划   |
| 生成答案        | 分析、归纳、对比   |
| 输出固定格式    | 动态组织内容       |
| 简单引用        | 事实与证据关联校验 |

我最推荐你优先落地的三个东西是：

1. Answer Planning：解决回答结构死板的问题。
2. Dynamic Markdown Generation：解决内容布局单一的问题。
3. Evidence-based Validation：保证金融数据和结论的可靠性。

这三个模块不需要推翻你现有的技术架构，完全可以融入 Spring AI + LangGraph4j。

还有一个值得深入研究的方向：把 Answer Plan 设计成一种可扩展的中间表示（Intermediate Representation，IR），以后不管是生成 Markdown、前端交互式分析报告，还是导出 PDF，都可以复用同一份分析结果，而不必重新调用 LLM。

我认为这会是你的金融 RAG 从简单问答系统走向专业研报分析产品的一个很重要的架构设计。
