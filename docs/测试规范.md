# 测试规范（怎么分层、怎么跑、什么时候删）

> 建立于 2026-10-28。适用于后端 `financial-ai-project` 与前端 `financial-ai-web`。
> 这份文档回答四个问题：一次改动该跑哪些测试、新测试该放哪一层、断言要写成什么样、旧测试什么时候可以删。
> 背景数字来自 2026-10-28 对本仓库 89 个测试类的实测（§10）。

## 怎么读这份文档（先看这 6 个词）

| 词 | 一句话解释（完整版见 docs/术语表.md） |
| --- | --- |
| 单元测试 | 只测一个类，数据库、模型、网络全是假的（Mock），毫秒级 |
| 集成测试 | 起真的 Spring 容器、连真的 PostgreSQL，但模型、Kafka、COS 仍是假的 |
| 端到端（e2e） | 真模型 + 真 Kafka + 真 COS + 真库，跑一遍完整链路，慢且花钱 |
| 测试标签 | JUnit 5 的 `@Tag("db")` / `@Tag("e2e")`，用来按层筛选测试 |
| Spring 上下文 | 一次 `@SpringBootTest` 启动的应用本质，一次 3~6 秒，是集成测试的固定开销之一（详见 §6） |
| 门槛 | 断言里的硬阈值（如 MRR ≥ 0.7）。没有门槛的测试只能证明「没崩」，不能证明「没坏」 |

## 1. 一句话

测试分三层，**默认的 `mvn test` 只跑前两层**：单测 39 秒、全量 2 分 18 秒；e2e 不进默认执行，按需点名跑。

## 2. 三层模型

| 层 | 标记 | 启动 Spring | 外部依赖 | 规模 | 实测耗时 | 什么时候跑 | 命令 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| L1 单元测试 | 无 | 否 | 无 | 63 类 / 441 用例 | **31 s**（Maven 37 s） | 改一行代码就想知道有没有写错 | `mvn -B -Pfast test` |
| L2 集成测试 | `@Tag("db")` | 是 | PostgreSQL（必需）、COS 环境变量（部分类） | 26 类 / 127 用例 | **101 s** | 改了 SQL、迁移、仓储、上下文装配 | `mvn -B -Pdb test` |
| 全量（L1+L2） | — | — | 同上 | 89 类 / 568 用例 | **2 分 18 秒**（测试执行合计 128 s） | 每个任务收尾、提交前 | `mvn -B test` |
| L3 端到端 | `@Tag("e2e")` | 是 | 真模型 / 真 Kafka / 真 COS / 真 Docling | 14 类 | 约 13 分钟（合计口径，按需单跑） | 改了链路（检索、答案、Kafka、权限）或要出报告 | 见 §9 |

「耗时」口径：Maven 报告里的 `Total time`（含编译），机器为开发机，数据库容器已启动。

## 3. 一个测试该放哪一层

按顺序问，命中即停：

1. **要调真的外部服务吗？**（大模型 API、Kafka、COS、Docling 解析服务、真 HTTP 请求真 Tomcat）→ 是 → L3，打 `@Tag("e2e")`。
2. **要真的 PostgreSQL 吗？**（真 SQL、真约束、真 RLS、真迁移）→ 是 → L2，打 `@Tag("db")`。
3. **要真的 Spring 容器吗？**（Bean 装配、配置绑定、自动配置条件）→ 是 → L2，打 `@Tag("db")`（它本质是集成测试，只是不碰外部服务）。
4. 其余 → L1，不打标签。

三条补充规则：

- **一个类只属于一层**。同时需要「真库 + 真模型」时只打 `e2e`（L3 优先），否则它会混进默认全量里偷偷调模型。
- **能 Mock 就别起容器**。仓储查询的边界用 Mock 掉 `JdbcTemplate` 的方式测逻辑，只有 SQL 本身值得验证时才升到 L2。
- **不确定就写 L1**。L1 跑 39 秒，写错了立刻就疼；L2 一次 130 秒，写多了没人跑。

## 4. 命名与注解约定

| 约定 | 要求 | 理由 |
| --- | --- | --- |
| 类名 | `XxxTest`（被测类 + Test） | Maven Surefire 默认只认这个后缀，改名才能被扫到 |
| 集成测试类名 | 建议带 `Db` 后缀（`ConversationSummarizerDbTest`） | 一眼看出它要数据库，不用点开看注解 |
| `@DisplayName` | 写「验的是什么行为」，中文一句话；不写方法名 | 失败时报告里只有这句话，读它就知道坏在哪 |
| 标签位置 | `@Tag("db")` / `@Tag("e2e")` 紧挨 `@SpringBootTest` 上方 | 扫一眼就知道这个类属于哪层 |
| profile | 集成测试统一 `@ActiveProfiles("test")`，需要时可加 `properties = ...` | 复用同一份 Spring 上下文缓存，见 §6 |

## 5. 断言规范（防「假绿」）

1. **必须有门槛**。断言写「≥ / ≤ / 等于多少」，不能只 `println` 结果。反例：已删除的 `RetrievalSmokeTest` 打印了 10 个问题的 top-1，却不断言相关性 —— 检索全坏它也绿。
2. **断言行为，不断言措辞**。大模型的答案是自然语言，断言具体句子会把测试变成脆皮；断言结构性不变量（引用能反解析回真实行、数字逐字出现在被引证据里、引用不越出作用域）。
3. **失败信息带上下文**。用 `assertThat(x).as("Q07 引用越界：doc=%s", docId).isTrue()`，报告里直接能定位。
4. **数值比较先归一化**：去掉千分位逗号与空格再比（`12,084,594,947.22` 与 `12084594947.22` 是同一个数）。
5. **异步不许 sleep 等结果**：用轮询 + 上限（`awaitStatus` 每 300 ms 查一次、最多 60 秒），sleep 既慢又不稳定。
6. **断言别人的产物要留退路**。例如「流式增量拼起来 == 最终答案」在引用编号重排（C15）后不成立，正确写法是比对「去掉 `[E\\d+]` 后的正文」。

## 6. Spring 上下文成本（集成测试为什么慢）

`@SpringBootTest` 每遇到一个**新的注解组合**就要重新启动一次应用上下文（约 3~6 秒）。26 个集成测试类实测只产生 **6 种组合**：

| 组合 | 类数 | 例子 |
| --- | --- | --- |
| `@ActiveProfiles("test")`（默认组合） | 17 | `ChunkWriterTest`、`TaskMessageRepositoryTest` |
| 默认 + `properties = "finagent.memory.enabled=true"` + `@MockitoBean` | 3 | `ConversationSummarizerDbTest` |
| 默认 + `memory.enabled=true`（无 Mock） | 1 | `MemoryIntegrationTest` |
| 默认 + `acl-enabled=true` | 2 | `AclScopeAuthorizerTest` |
| 默认 + `RANDOM_PORT` + 认证/ACL 开关 | 2 | `RestAuthContractTest` |
| `@ActiveProfiles("rls")` | 1 | `RlsEnforcementTest` |

6 次启动合计约 **20~30 秒**，占集成层 101 秒的四分之一。**剩下的时间是真在干活**（不是框架开销）：

| 类 | 耗时 | 时间花在哪 |
| --- | --- | --- |
| `ChunkWriterTest` | 28.4 s | 真写 654 个块 + 拼 1024 维向量字面量 + 版本切换，5 个用例各写一遍 |
| `PasswordLoginTest` | 9.4 s | bcrypt（故意慢，防爆破）+ 真 HTTP + 登录限流 |
| `CosObjectStorageTest` | 9.1 s | 到 COS 的真实网络往返 |
| `ConversationSummarizerDbTest` | 6.4 s | 30 条消息 + 多轮摘要 |
| `RestAuthContractTest` | 6.2 s | 真 Tomcat + 6 个 HTTP 用例 |

规则：

- 新增集成测试**优先复用现有组合**：每多一种组合就多付一次 3~6 秒启动，而且它在全量里每次都付。
- `@MockitoBean` 的**集合不同**也算新组合（缓存键包含它），换 Mock 就等于换上下文。
- 只想验「配置绑定 / 条件装配」时用 `ApplicationContextRunner`（如 `RerankConfigTest`、`KafkaTopicConfigTest`），它不启动整个应用，0.1 秒级。

## 7. 什么时候可以删一个测试

**可删，当且仅当它的每一条断言都被另一个更严格的测试覆盖**（更严格 = 有门槛、覆盖更多边界）。三个信号：

1. 它只打印不断言（冒烟脚本）；
2. 它的断言是「结果非空」这种永真式；
3. 它跑一次要几分钟且只在「出报告」时有用。

五种「看起来该删其实不能删」：

- 只剩 1 条断言，但那条断言别处没有（例：`ScopeFilteringTest` 的「QU 抽 2024 但作用域是 2025 → 年份条件必须丢弃」，这是 SQL 拼接的独有行为）；
- 用真库真向量、单测替代不了的（`HybridRetrievalTest`）；
- 复现过历史 bug 的（`TableRendererTest` 里两条员工表回归用例）；
- 验证「不该发生」的（越权、拒答、DLQ 重投）；
- 慢但唯一的（唯一真跑 Docling 的路径 —— 见下面「一次性脚本」）。

### 7.1 一次性报告脚本不要放进 `src/test`

「跑一次、把数字贴进报告」的脚本没有回归价值，放进测试目录后会：占着 e2e 名额、随 API 变更腐烂、被人误当成防线。做法是跑完就删，**报告里保留数字 + 手工步骤**。

### 7.2 2026-10-28 删除的 5 个类

| 类 | 原耗时 | 为什么删 | 断言被谁接管 |
| --- | --- | --- | --- |
| `FullDocumentPipelineTest` | 7,596 s | 阶段 2 出报告的一次性脚本（COS→Docling→COS→document 行） | `DocumentTaskE2ETest`（真 HTTP + Kafka + 全链路）；解析质量见阶段 2 报告 |
| `IngestReportTest` | 3,513 s | 阶段 3 的上传版脚本，同上 | `DocumentTaskE2ETest` + `ChunkWriterTest` |
| `ChatE2ETest` | 112 s | 14 题（12 指标 + 2 陷阱）与评测集完全重合 | `AnswerEvalTest`（32 题，含同样的 Q01~Q12、Q31「2023 年」、Q19「两年对比」）+ `EvalGateTest` 门槛 |
| `ChunkPipelineTest` | 95 s | 切块→向量化→原子切换 | `DocumentTaskE2ETest`（版本 +1、复用率 >80%）+ `ReindexServiceTest` |
| `RetrievalSmokeTest` | 46 s | 只打印 top-3，无门槛 | `RetrievalEvalTest`（27 题 + Recall@10 / MRR 门槛）+ `GoldenSetTest` |

合计省掉 **11,362 秒（约 3 小时 9 分）**的按需运行时间和约 600 行会腐化的代码。

历史计划（ST2~ST5）与历史报告里还写着这些类名，那是对当时事实的记录，**不追改**；活跃文档（README / 术语表 / 本文）已更新。

### 7.3 数据库清理必须按主键，不许按标题模式（2026-10-28 补）

**规则**：测试造的数据，`@AfterEach` 里必须用**测试自己记下的 id 列表**删除，禁止 `WHERE title LIKE 'test-%'` 这种模式匹配。

原因：标题会被被测代码改掉，模式就匹配不上了，于是每跑一次测试库里多几行 —— 这正是 2026-10-28 那次「35 个会话」的来源。两个真实漏删案例：

| 位置 | 怎么漏的 | 现象 |
| --- | --- | --- |
| `ConversationServiceTest.recordTurnWritesTwoMessagesAndSnapshot` | 用 `DEFAULT_TITLE`（`新会话`）建行，`recordTurn` 按首轮问题把标题改成「2025 年 营业总收入是多少」，而清的是 `title LIKE 'test-conv-%' OR title = '新会话'` —— 改名后两个条件都不中 | 库里留下「2025 年 营业总收入是多少」 |
| `ConversationServiceTest.renameTruncatesToSixty` | 断言里故意把标题改成 64 个「长」字，同样逃出 `test-conv-%` | 库里留下「长长长长…」 |

修法（配套代码）：

- 新增 `src/test/java/com/finagent/support/ConversationCleanup.java`：`delete(JdbcTemplate, Collection<Long> ids)` 先删 `memory_event`（`target_type` 为 `CONVERSATION_CONTEXT` / `CONVERSATION_SUMMARY` 的行），再按 id 删 `conversation`（消息、摘要、上下文由外键 `ON DELETE CASCADE` 带走）；空列表安全返回。
- 各集成测试在 `@AfterEach` 里 `created.forEach(...)` 或 `ConversationCleanup.delete(jdbc, created)`，`created` 在 `@BeforeEach`/用例里 add。
- 清完之后加一条断言兜底（可选）：`SELECT count(*) FROM conversation WHERE id IN (…)` 必须为 0，防止「清理代码本身写错」也静默通过。

**e2e 与探针同样适用**：`ConversationE2ETest` 已经是 id 列表删除；headless 探针（`target/ui-*.js`）每次真发问都会新建会话，跑完要用 `DELETE /api/conversations/{id}` 收尾。
## 8. 环境前提

| 层 | 需要什么 | 说明 |
| --- | --- | --- |
| L1 单测 | 只要 JDK 21 | **不需要数据库、不需要 `load-env`**（实测裸跑通过） |
| L2 集成 | PostgreSQL 容器 `finagent-postgres` + `. .\\scripts\\load-env.ps1` | 不加载环境变量会有 36 个类报 `NoSuchBeanDefinition: ObjectStorage` |

## 9. 命令速查

```powershell
# 改了一个类，只想跑它的测试（最快，十几秒）
mvn -B test -Dtest=ChatServiceTest

# 内循环：只跑不启容器的单测（39 秒，不需要数据库）
mvn -B -Pfast test

# 只跑集成测试（@Tag("db")，约 130 秒，需要数据库 + load-env）
. .\\scripts\\load-env.ps1
mvn -B -Pdb test

# 收尾全量（单测 + 集成，2 分 18 秒）
mvn -B test

# e2e：点名跑，必须同时清空默认排除（PowerShell 里空值要加引号）
mvn -B test "-Dsurefire.excludedGroups=" "-Dgroups=e2e" "-Dtest=AnswerEvalTest"

# 前端
cd ..\\financial-ai-web
npx vitest run
```

两个坑：

- `-Dtest=A,B` 的逗号必须在同一对引号里（PowerShell 会把它当数组拆开）；
- `-Dsurefire.excludedGroups=` 不能省：`-Dgroups=e2e` 是包含语义，配置里的排除仍在生效，两者叠加会一条都不跑。
- 不要同时用 `-Pdb` 和 `-Dgroups=e2e`：profile 里的 `<groups>` 是 pom 配置，优先级高于命令行 `-Dgroups`，结果会变成「跑 db 层」。e2e 一律不激活 profile 跑。

## 11. 已知成本与后续

1. **个别类的「第一个用例」慢**：`ChatControllerTest.listsOnlyReadableDocuments` 4.5 s（同类其余用例 0.05~0.3 s）、`AnswerServiceTest.unparsableAnswer` 1.8 s、`PdfPageRendererTest` 3~4 s（PDFBox 字体加载）。原以为是 `ChatControllerTest` 每个用例新建一对线程池且不关闭造成泄漏 —— **实测证伪**：那两个线程池是懒创建的，创建本身不启动线程。真正原因是「类内第一个用例承担框架初始化（Jackson / Mockito / MockMvc 首次加载）」，没有便宜的消除办法；顺带把线程池改成类内共享 + `@AfterAll` 关闭（该类 9.8 s → 5.1 s，含系统缓存差异，不全是改动带来的）。
2. **未开 JUnit 并行**：开了能把全量压到 1 分钟出头，但集成测试共享同一个数据库，要先逐类确认隔离性（都在 `@AfterEach` 里清自己造的行），属于单独一件事。
3. **e2e 不能进 CI**：真模型按次计费、真 Kafka 与 COS 需要凭据，保持「按需点名跑」。
4. **评测集的证据块按 `embedding_text_hash` 解析**（`EvidenceResolver`）：重切文档后 golden set 里的 id 会失效，hash 兜住了这件事，新增评测集时不要直接写死 chunk id。
