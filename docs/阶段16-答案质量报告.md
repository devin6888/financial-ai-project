问题（腾讯 ima 用过的那条）：

> 分析下2024年和2025年的营业总收入，然后看下是什么原因导致的

### 1.1 改之前（2026-10-30 00:1x 实测）

一句话把结论、数据、归因全挤在一起，没有段落，也没有「口径/缺口」：

> 2025年营业总收入为16,067,741,039.51元，较2024年11,604,343,090.16元增长38.46%；增长主要由证券业收入（+47.59%）和信息技术服务业收入（+13.60%）共同驱动，其中证券服务贡献最大增量，金融电子商务服务与金融数据服务亦分别增长11.99%和25.18%[E1][E2]。

问题：读者拿不到「哪些是证据直给、哪些没披露」；归因只到业务线，不落到科目（手续费/利息）；一句话 120 字，手机上一整屏。

### 1.2 改之后（2026-10-30 01:5x 实测，Task 1 落地后）

```text
结论：2025年营业总收入为16,067,741,039.51元，2024年为11,604,343,090.16元，同比增长38.46%；
增长主要由证券业收入大幅增加（+47.59%）驱动，信息技术服务业收入亦增长13.60%，
归因于证券服务、金融电子商务服务及金融数据服务等分产品线收入提升，
且均在证据中明确列示了同比增减率 [E1][E2]。

数据：2025年 / 2024年 营业总收入：16,067,741,039.51元 / 11,604,343,090.16元；
证券业收入：12,535,471,036.46元 / 8,493,612,633.32元；
信息技术服务业收入：3,527,509,133.65元 / 3,105,168,705.16元；
金融电子商务服务：3,182,040,383.70元 / 2,841,371,321.01元；
金融数据服务：240,327,781.69元 / 191,981,245.64元 [E1][E2]。

归因：证券业收入增长47.59%对应「证券服务」分产品项下同幅度增长，
系手续费及佣金净收入（9,100,013,336.56元 vs 6,112,631,919.02元）和
利息净收入（3,435,457,699.90元 vs 2,380,980,714.30元）双增长所致；
信息技术服务业增长13.60%对应「金融电子商务服务」（+11.99%）与「金融数据服务」（+25.18%）共同贡献，
证据中未进一步拆解至交易额、保有规模或销售额等底层指标，仅列示分产品收入变动 [E1][E2]。

口径：单位为元，期间为2025年度与2024年度，口径为合并报表；
证据中未披露营业总收入的母公司口径数据，
亦未提供交易额、保有规模、销售额等归因所需的底层业务量指标 [E1][E2]。
```

三处肉眼可见的变化：

1. **四段结构**：结论先给答案，数据段逐项并列两期，归因段落到了科目级（手续费及佣金净收入、利息净收入），口径段写明单位/期间/合并口径。
2. **主动写缺口**：「证据中未进一步拆解至交易额、保有规模或销售额」「未披露母公司口径」——这正是 ima 那条答案里最像「专业分析师」的部分（知道什么不知道）。
3. **facts 从 0 条变成 8 条**：同一套代码，之前模型只写正文不填结构体。

### 2.1 形态判定词表（`AnswerShape`）

| 形态 | 触发词 |
| --- | --- |
| 归因 ATTRIBUTION | 原因、为什么、为何、驱动、因素、归因、得益于、受益于、拉动、带动、主因 |
| 结构 BREAKDOWN | 结构、构成、占比、分行业、分产品、分地区、明细、拆开、板块 |
| 对比 COMPARISON | 对比、相比、同比、环比、较、变化、差异；另外 `yearRange = [2024, 2025]` 时也补一个（「2024 和 2025 年的营业总收入」不含「对比」二字，但答案必须两期并列） |

两个**故意不收录**的词：

- 「增长 / 下降」：一句「2025 年营业总收入是多少，增长多少」是取数题，不是归因题；收了会把纯取数题逼出归因段。
- 「贡献」：会误判「各板块贡献度」这类结构题（记在 §6 偏差 2）。

### 2.2 覆盖检查（verify 节点的第 4 条防线）

```text
attributionMissing = !tooFew && !metricMissing && retryCount == 0
                     && 形态含 ATTRIBUTION && !attributionCovered(state)
```

`attributionCovered` 的判据（任一成立即算覆盖）：

- 命中块的 `sectionPath` 含驱动章节：管理层讨论 / 主营业务分析 / 行业情况 / 经营情况；
- 命中块的 `snippet` 含驱动词：交易额、保有、销售额、手续费及佣金、利息净收入、同比增减、主要原因。

缺则 `insufficient=true` + `warnings += "coverage_missing:attribution"`，图里走一次 rewrite（检索式追加「原因 驱动 交易额 保有规模 手续费」）。

**`retryCount == 0` 这个条件很关键**：不判第二次，否则「改写后还是缺归因」会变成整题拒答——缺归因应该是「答案里写明缺口」，而不是「不回答」。

## 5. 踩坑（四段式）

### 5.1 骨架写进提示词了，答案还是一句话

- **现象**：SYSTEM 里已经有「① 结论 ② 数据 ③ 归因 ④ 口径」四段，实测答案仍是一句话把三件事挤在一起。
- **原因**：提示词里写的是「内容要包含这四块」，模型理解成「这几块内容都要有」，于是把它们合并进一句；而前端渲染器此时**还不支持 markdown 标题**（Task 4 才加），所以也不能靠 `##` 强制分段。
- **修法**：把「排版」单独写成一条硬规则——段落之间空一行，每段以「结论：」「数据：」「归因：」「口径：」开头，没有内容的段整段省略，并明确「用中文标签加冒号，不要用 `#`」。
- **教训**：**「要求包含哪些内容」和「要求怎么排版」是两条不同的指令**，写在一起时模型只执行前者。凡是要肉眼可见的结构差异，提示词里必须单独给排版约束。

### 5.2 `verify` 的覆盖检查会让整题拒答

- **现象**：首版没有 `retryCount == 0` 条件，改写一次后仍然缺归因 → 第二次 verify 继续判 insufficient → 图走到 respondInsufficient，用户看到「证据不足」，明明有可用的数字。
- **原因**：把「答案该不该写归因段」当成了「这题能不能答」。
- **修法**：只在首次 verify 判；改写后的第二次不再判，缺口交给提示词第 ④ 段写明。
- **教训**：**校验的严厉程度要和「失败后的出路」匹配**——能靠改写补救的，就不能升级成拒答。

### 5.3 断言 `List<?>` 用 `containsExactlyInAnyOrder("A","B")` 编译不过

- **现象**：`RealAnalysisNodesTest` 编译报 `需要: capture#1, 共 ?[]，找到: java.lang.String`。
- **原因**：AssertJ 的 `AbstractIterableAssert` 在 `List<?>` 上做 varargs 匹配时，通配符捕获类型与 `String` 不兼容。
- **修法**：先强转 `List<String> shapes = (List<String>) patch.get(...)` 再断言。
- **教训**：这一条在 ST15 也踩过，已写进术语表；**状态里的集合一律按已知具体类型取出来再断言**。

## 9. Task 2：事实层与派生指标（2026-10-30 02:0x~02:5x）

### 9.1 要解决的是哪件事

Task 1 把「答案有没有骨架」解决了，但骨架里填的东西还是模型自己从证据里挑的：它挑哪几个数、算不算同比、换不换算单位，全凭当场发挥。
于是出现两个具体毛病：

1. **该算的它不算**。问「同比增长多少」，答案写「16,067,741,039.51 元」，把算式留给用户；
2. **算了的它算错**。同一轮答案里它自己减出「手续费及佣金净收入 +47.23%」，而披露值是 **+48.87%** —— 没人发现，因为旧校验只认四位以上整数，百分比从来没被查过。

Task 2 的做法是：**把「抽事实」和「算数」从模型手里拿走**，改成两个确定性步骤，算完再把结果交回去。
模型只负责「挑哪些事实来讲、怎么说」，不再负责「数字从哪来」。

### 9.3 五条公式（计划写的是四条，实现加了第五条，见 9.7 偏差 3）

| 公式 | 表达式 | 单位 | 口径说明 |
| --- | --- | --- | --- |
| 同比增长率 | (本期 − 上期) / &#124;上期&#124; × 100 | % | 上期为负时用绝对值做分母 |
| 结构占比 | 分项 / 合计 × 100 | % | 合计必须与分项同期、同口径 |
| 占比变动 | 本期占比 − 上期占比 | 百分点 | 输出用「百分点」，不是「%」 |
| 收入贡献度 | (分项本期 − 分项上期) / (合计本期 − 合计上期) × 100 | % | 合计增量为 0 时跳过 |
| 增长额 | 本期 − 上期 | 元 | 与同比增长率同期、同口径 |

**故意不做的**：毛利率 / 净利率 / ROE。券商不按制造业口径披露营业成本（7248 里证券业那两列是空的），
分母口径有争议，见 `docs/阶段15-多路检索证据覆盖报告.md` §6。

### 9.4 三条设计决策

**① 合并表头必须重排，不能照字面取列。**
chunk 7246 的表头是：

```
|  | 2025年 | 2025年 | 2025年 | 2024年 | 同比增减 |
| --- | --- | --- | --- | --- | --- |
|  | 金额 | 占营业总收入比重 | 金额 | 占营业总收入比重 |  |
```

「2025年」出现三次。照字面按列名映射，三次都会落到 2025 列 —— **2024 的金额会被写进 2025 列**，
这正是我们花了一整个阶段在防的那类错误。
修法：遇到子表头（金额 / 占比 / 增减）之后，按「每遇到一个金额列就换一组」重新分配年份；
再加一道保险 —— 同一行里出现两个同义列（两个「金额」映射到同一年份）就整行丢弃，不猜。

**② 计算事实的预算要分配，不能拼接。**
一张分行业表能算出十几条同比。按「同比 → 贡献度 → 占比 → 占比变动」的顺序拼接，
前几条预算全被同比吃掉，「证券业贡献度 90.56%」这种最该讲的反而进不去。
实现里按 3 / 2 / 2 / 2 / 1 的格子分配：问题点名的指标与合计行的同比（3）→ 增长额（2）→ 贡献度（2）→ 占比变动（2）→ 结构占比（1）→ 其余同比补满。
结构占比只出**最新一年**（上一年已经有「占比变动」了）。

**③ 与披露值冲突时，放弃计算值。**
算出来的同比若与证据里披露的同比相差 > 0.011，记 `compute_conflict:*` 并**不输出这条计算值** ——
同一段提示词里同时出现 41.00% 和 38.46%，模型必然挑一个，而它挑错了没人能发现。披露值永远优先。

## 10. Task 3：跨年份与章节车道（2026-10-30 02:57~03:2x）

### 10.1 要解决的是哪件事

任务 2 之后，「抽事实、算比率」都交给了系统，但**证据本身可能只覆盖了一半问题**。

实测（2026-10-30 00:1x）问「分析下2024年和2025年的营业总收入，然后看下是什么原因导致的」：
18 条证据**全部来自 doc 7（2025 年报）**。2024 年的数字是从 2025 年报的对比列里读出来的 ——
那一列是不是同口径、有没有被重述，系统没有任何校验，只是「碰巧对了」。

原因不是检索坏了，而是**检索只发了一次查询**：一条查询返回 topK 个块，谁分高谁进；
两份年报在同一句话上打平，2025 年报因为标题/章节更贴近问题而系统性占优。

### 10.2 车道（lane）是什么

把「一次查询」换成「一组车道」：每条车道是一次**带过滤条件的独立检索**，结果按 chunkId 取最高分合并。

| 车道 id | 什么时候开 | 过滤条件 | topK |
| --- | --- | --- | --- |
| `full` | 永远第一路 | 无 | 默认（Dense/Sparse 各自默认） |
| `sub:N` | 问题被拆成子问题 | 无 | 默认 |
| `attr` | 答案形态含 `ATTRIBUTION` 或 `BREAKDOWN` | `sectionPathPrefix = "第三节"` | 4 |
| `year:YYYY` | 问题跨 2~3 个年份 | `docYear = YYYY` | 4（补跑 8） |

代码：`agent/RetrievalLane`（一条车道，含 `toRequest()`）、`agent/RetrievalLanes`（怎么排车道 + 缺年份检测）、
`agent/RealAnalysisNodes.retrieve`（执行与合并）。过滤条件复用既有的 `retrieval.RetrievalFilters`
（`DenseRetriever:99-101` 早就有 `AND d.doc_year = ?`，`sectionPathPrefix` 在 `:107-109` 拼 `LIKE ?%`），
本次**没有改检索器**，只是开始用它。

### 10.3 三条硬规则

1. **整句永远占一路**（ST15 §3.2 的结论不能退回）：车道顺序是 `full` → 子问题 → `attr` → 年份，
   合并时同 chunkId 保留最高分（不是先到先得，否则 `attr` 的低分会把 `full` 的高分覆盖掉）。
2. **年份超过 3 个不开车道**：`year_range_too_wide`，退化成只有 `full`。
   理由是成本线性：每多一年就多一次 embedding + rerank 调用；4 年以上的问题应该走「全量检索 + 文档配额」，
   那是另一个任务（见 10.7）。
3. **缺年份先补跑、再告警、不拒答**：某年一条都没命中时，用同一句话 + `docYear=Y` + topK 8 再跑一轮；
   补到就只留 `year_lane_retried` 痕迹，仍缺才记 `year_coverage_missing:YYYY`。
   不拒答的理由：少一年不等于答不了，答案的「口径与缺口」段正好用来写「2024 年报未检索到，以下 2024 数字来自 2025 年报对比列」。

### 10.5 顺带修掉的「同一段两个矛盾比率」

Task 3 第一次跑通时，答案里出现：

> 二者合计增量占总增量的 84.22%（计算依据：(9,100,013,336.56−6,112,631,919.02)+(3,435,457,699.90−2,380,980,714.30)=4,041,858,403.14元，占总增量4,463,397,949.35元的90.56%，与一致）

两个问题叠在一起：模型自己做了一步加法（84.22% 是它算的，且与同段后面的 90.56% 矛盾），
以及算式里 4,041,858,403.14 / 4,463,397,949.35 **不在任何证据里**，于是被 `answer_value_not_in_evidence:2` 记了一笔。

> 禁止自己把两个证据数字相加、相减或相除得出新数字（合计、占比、增速、贡献度都算）：
> 这几个数只能来自【已计算事实】里已有的条目，没有对应条目就只写原始数字，不要给比率。

复测（03:1x）：`warnings=[]`，正文只剩系统算的 38.46% 与 90.56%，没有再出现自造比率。

第一次跑通时答案是 `数据：| 指标 | 2025年 | ` —— 标签与表格写在同一行。
前端解析器只认「行首是竖线」，于是整张表退化成段落里的竖线文本。
提示词已经写了「表格前后各留一个空行」，但模型不总是照做（和 §10.5 的「归因：」接句末是同一类问题）。
修法：`normalizeSkeleton` 里加一条 —— 标签后面紧跟 `|` 或 `###` 就断行。**骨架与排版是承诺，不能只靠提示词。**

**问题二：一开表格就冒出 `answer_value_not_in_evidence:10`。**
模型把表格两列相减算增量（4,041,858,403.14 / 422,340,428.49 / 800,882.28…），这些数既不在证据里也不在事实白名单里。
两条路：把它们算进【已计算事实】（8 个槽位装不下十几条），或者承认「两个证据金额之差」是可复核的。
选了后者：`ground` 新增 `derivedValues(allowed)`，把白名单金额（≥1000）两两相减的结果也视为落地。
**只做减法不做加总** —— 加总几乎总能对应到证据里的合计行，放开它等于给凑数开口子。
复测：`warnings` 回到只剩 `facts_table_skipped`。

| # | 计划写的 | 实际做法 | 为什么 |

### 11.7 未决

1. **分项增量仍由模型算**：表格里没有「增量」列，模型自己相减。现在不告警（等于两个证据数之差），
   但也没有进【已计算事实】。要不要把每条子项的增长额都算出来（再把 MAX_COMPUTED 提到 12），等 Task 5 看答案质量再定。
2. **表格列宽**：现在是 `white-space: nowrap` + 横向滚动，6 列以上在手机上要滑很久。是否需要按列数切分或缩字号，未做。
3. **复制没有端到端测试**：纯函数有 6 例、按钮有 3 例，但「粘到飞书里表格是否真对齐」只能人工验证。

## 12. Task 5：验收（5 个固定问题人审 + 全量回归）

### 12.1 验收怎么做

计划 §4 定的是「5 个固定问题 + 六列人审表」。实际做法：把 5 个问题一次写进 `target/e2e-t5.ps1`，
登录后逐题打 `POST /api/chat/stream`，结果落在 `target/a5_1.txt` ~ `target/a5_5.txt`；
再把每题的 `final` 事件取出来，按下面六列逐条核对（数字回数据库里对应的 chunk 逐字比）。

六列含义：

| 列 | 看什么 |
| --- | --- |
| 问题 | 原话，不改一个标点 |
| 期望 | 这个问题「合格答案」的最低要求（计划 §4 的 A1~A16） |
| 实际 | 真实回答的结构与关键内容 |
| 数字核验 | 答案里每个数字回哪个 chunk、是否逐字一致 |
| 形态 | `AnswerShape` 判定出来的形态（决定【回答要求】段） |
| 差在哪 | 仍不满足的地方，进 12.6 未决 |

### 12.3 逐题点评（差在哪，一句话说清）

- **Q1**：素材问题。手续费及佣金净收入（9,100,013,336.56 vs 6,112,631,919.02）与利息净收入（3,435,457,699.90 vs 2,380,980,714.30）都在 E4 里，
  模型把它们写进了「口径」段而不是「归因」段。这是**提示词对「归因段该写什么」的指向不够硬**，不是检索没给。
- **Q2**：合格。一句话答案不套骨架，是期望行为（形态没触发）。
- **Q3**：合格。「其他 0.03%」被过度解释成业务板块，属表述瑕疵。
- **Q4**：合格，且这正是我们比竞品严谨的地方——不硬算一个券商口径下没有意义的净利率。
- **Q5**：数字对、结论对，但降级为 `low`。原因是「两个百分比的差」这种计算 System 给不出白名单（见 12.6 第 1 条）。

### 12.6 未决

1. **比率之差（百分点）不在白名单**：Q5 的「下降 3.21 个百分点」被判成「模型自算」。要修就得加第六条公式（两个比率之差），
   但比率白名单不带语义，`78.02% − 21.95%` 这种胡算也会被放行。取舍：先保留告警（只降 confidence，不拒答），等这种问法复现 ≥3 次再加公式。
2. **归因段没指向驱动指标**：Q1 证明了「证据在、模型不用」。下一步是让覆盖检查把「驱动词只出现在口径段」也算不达标，
   或在【回答要求】里写死「归因段必须引用至少一条驱动指标（交易额 / 保有规模 / 手续费及佣金 / 利息净收入）」。
3. **事实卡冗余**：Q2 只有一句话，事实卡却列 7 条。可以让 facts 只留答案真正引用到的（但那样 facts 就成了渲染结果，不再是证据快照）。
4. **「其他」行被当业务板块**：分行业表的兜底行需要标记，否则结构类答案永远多解释一行。
## 8. 复现

```powershell
# 1. 重启（8080 被占用时先杀）
Get-NetTCPConnection -LocalPort 8080 -State Listen | ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }
. .\scripts\load-env.ps1 | Out-Null
mvn -o -q spring-boot:run 2>&1 | Tee-Object -FilePath target\boot-st16.log

# 2. 登录（body 必须写文件，PowerShell 会吃掉 -d 里的双引号）
[IO.File]::WriteAllText("$PWD\target\login.json", '{"username":"demo","password":"demo123456"}', (New-Object System.Text.UTF8Encoding($false)))
$tok = (curl.exe -s -X POST http://localhost:8080/api/auth/login -H "Content-Type: application/json" --data-binary '@target/login.json' | ConvertFrom-Json).token

# 3. 流式提问
[IO.File]::WriteAllText("$PWD\target\q.json", '{"question":"分析下2024年和2025年的营业总收入，然后看下是什么原因导致的"}', (New-Object System.Text.UTF8Encoding($false)))
curl.exe -s -N -X POST http://localhost:8080/api/chat/stream -H "Content-Type: application/json" -H ('Authorization: Bearer ' + $tok) --data-binary '@target/q.json' -o target\s.txt
```
