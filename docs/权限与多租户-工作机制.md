# 权限与多租户 工作机制

> 面向「第一次做多租户 RAG / 想搞清楚 RLS 到底怎么生效」的读者。
> 每一节都是「是什么 → 为什么这么设计 → 本项目落在哪个文件／哪一行 → 踩过的坑」。
> 所有数字都带口径与时间：实测于 2026-10-27 本机（PostgreSQL 16.15，容器 finagent-postgres）。

## 0. 先看一张图：一次问答要过四道门

~~~
① 认证            ② 租户            ③ 租户内可见性        ④ 本次查询范围
你是谁？          你属于哪个租户？    你能不能看这份文档？   这一轮到底问哪几份？

Authorization:    TenantContext      resource_grant         ScopeResolver
Bearer dev-...    .tenantId()        + document.visibility  → 检索 filter
      │                 │                    │                    │
      ▼                 ▼                    ▼                    ▼
AuthenticationFilter → TenantAwareDataSource → AclScopeAuthorizer → DenseRetriever
   查 app_user         SET ROLE finagent_app   查授权表             WHERE document_id IN (…)
   api_token_hash      set_config(app.tenant_id)                     + document_chunk.status='ACTIVE'
      │                 │
      └── 401 ──────────┴── RLS 在数据库里静默过滤（跨租户 0 行）
~~~

四道门各管一件事，混在一起就会出现「测试全绿但线上泄漏」：

| 层 | 管什么 | 落在哪里 | 失效时的表现 |
|---|---|---|---|
| ① 认证 | 你是谁（userId / tenantId / roles） | `AuthenticationFilter` + `ApiTokenRepository` | 401 AUTH_REQUIRED / AUTH_INVALID |
| ② 租户隔离 | 你只能碰本租户的行 | `TenantAwareDataSource` + 5 条 RLS 策略 | 查询**静默返回 0 行**（不报错，最难查） |
| ③ 租户内可见性 | 同事之间也要分权限 | `AclScopeAuthorizer` + `resource_grant` / `document.visibility` | 作用域为空 → 409 SCOPE_EMPTY |
| ④ 查询范围 | 这一轮问哪几份 | `ScopeResolver` → 检索 SQL 的 `document_id IN (…)` | 空集被当成「不过滤」= 全库检索（阶段 4 的老坑） |

一个记忆点：**②是硬边界，③是软边界**。跨租户是「绝不允许」，靠数据库兜底；租户内是「业务上不该看」，靠应用层判断。

## 1. 认证：token → 用户

### 1.1 为什么是「查库」而不是 JWT

~~~http
Authorization: Bearer dev-analyst-token
~~~

「解析 token」这件事有三种常见做法，本项目的取舍：

| 做法 | 好处 | 代价 | 本项目 |
|---|---|---|---|
| JWT（自包含签名） | 不用查库，无状态 | 纯无状态形态下**撤不了**（改权限要等过期；密钥泄漏=可伪造任意用户）；要撤销就得加一次状态查询 → 见 §1.1.1 | ✗ |
| Session（服务端存） | 可随时踢下线 | 要存会话，横向扩展要共享存储 | ✗ |
| **随机 token + 库里存 SHA-256** | 可随时撤销（改一行 status）；库被拖走也拿不到明文 token | 每请求一次索引查询（`api_token_hash` 上有 UNIQUE 索引，实测 0.08~0.125 ms） | ✓ |

「库被拖走也拿不到明文」这句要能自己解释：库里存的是 `SHA-256(token)`，单向；攻击者拿到哈希不能反推出 token，也就不能拿去调接口。

#### 1.1.1 如果对方说「JWT 配 Redis 黑名单就能撤销」——他说得对，但要接着算账

「JWT 无法撤销」这句话只在**纯无状态验证**下成立。只要在验证链路上加一次状态查询，JWT 就能撤销：

| 加什么 | 怎么撤销 | 代价 |
|---|---|---|
| Redis 白名单（登录写 key，TTL = token 有效期） | 删 key → 下次请求 401 → 客户端重新登录换新 token | 每请求一次 Redis；Redis 变成会话存储 |
| Redis / DB 黑名单（`jti`） | 把 `jti` 写进黑名单直到 `exp` | 同上；黑名单只增不减，要等过期才能清 |
| `token_version` 计数器（用户表一列，写进 claim） | 改版本号 → 所有旧 token 全失效 | 每请求要读一次版本号（缓存或 DB） |

**关键结论：一旦加了这一步，JWT 就退化成「有状态的会话 token，只是体积更大、还要管签名密钥」。**

| 形态 | 撤销 | 每请求外部查询 | 每请求额外计算 |
|---|---|---|---|
| 纯 JWT | ❌ | 0 | 验签 + Base64 解码 |
| JWT + Redis | ✅ | 1 次 Redis | 验签 + 解码 + 查缓存 |
| **本项目：随机 token + SHA-256** | ✅ | 1 次索引查询（同一条数据库连接上） | 一次 SHA-256 |

本项目还有一条结构性理由：**每个请求本来就必开一个数据库连接**（`TenantAwareDataSource` 要 `SET ROLE finagent_app` + `set_config('app.tenant_id')`，RLS 才有边界）。所以 token 查询挂在同一条连接上几乎免费——实测 `EXPLAIN ANALYZE` 0.08~0.125 ms，`Index Scan using app_user_api_token_hash_key`，`shared hit = 6`；而 Redis 是**新增的第二个网络跳**。JWT 的卖点恰恰是省掉「验证方访问状态存储」这一跳，加了黑名单之后这个卖点就没了。

两个真实世界的坑：

1. **「删缓存 → 401 → 重新登录」的传播边界**取决于「先删缓存还是先改库」的顺序与原子性；多副本时还要保证删到正确的那份缓存。
2. **多服务一致性**：只要有一个验证方只做本地验签、不查 Redis，它就会继续接受旧 token——无状态 JWT 想避免的问题，在「加校验」之后以另一种形式回来了。

**什么时候 JWT 才对**：对外发短期凭证（第三方 / OIDC）、拆成多个资源服务器各自验签、边缘节点连不到内网 DB、离线客户端、权限变更频率极低（月级，可以等过期）。共同点是：**验证方确实无法访问状态存储，或者根本不需要撤销**。

### 1.2 为什么只用一条 SQL 拿用户+角色

~~~sql
SELECT u.id AS user_id, u.tenant_id, u.username, u.display_name, u.status, r.code
  FROM app_user u
  LEFT JOIN user_role ur ON ur.user_id = u.id
  LEFT JOIN role r ON r.id = ur.role_id
 WHERE u.api_token_hash = ?
~~~

文件：`src/main/java/com/finagent/security/ApiTokenRepository.java:21-27`。

- 一个用户有 N 个角色就是 N 行，Java 侧按 `user_id` 折叠成 `Set<String> roles`（角色 **code**，不是 id）。
- 用 `LEFT JOIN` 而不是 `JOIN`：没角色的用户也要能登录（只是什么都看不到），否则会变成「登录失败」这种误导性表现。
- 查不到 / `status != 'ACTIVE'` 都返回 `Optional.empty()`，对外统一 `AUTH_INVALID` —— 否则这个接口就成了**用户枚举器**。

### 1.3 401 而不是 403，也不是 200

| 场景 | 状态码 | 响应体 | 为什么 |
|---|---|---|---|
| 没带 `Authorization` 头 | 401 | `AUTH_REQUIRED` | 缺身份 |
| token 不存在 / 已停用 | 401 | `AUTH_INVALID` | 身份无效（**不区分**这两种，防枚举） |
| 有身份但这份文档没权限 | 409 | `SCOPE_EMPTY` | 身份没问题，是「你问的东西不在你能看的范围里」 |

把「没权限」写成 403 看着更「语义正确」，但本项目的产品语义是「**拒答**」：作用域解析为空时，聊天接口返回 409 并说明「所选文档均不可检索」，而不是给一个空的、看起来像正常回答的 200。

### 1.4 为什么不用 Spring Security

需求只有三件事：解析 token、建上下文、401。「引入框架」会顺带接管过滤器链、默认登录页、CSRF，对一个无状态 JSON API 是负资产。代价是自己写，所以两条纪律必须自己守住：

1. `@Order(Ordered.HIGHEST_PRECEDENCE + 10)`：必须排在业务过滤器/拦截器之前，否则 Controller 先跑、身份还没建。
2. `finally { TenantContext.clear(); }`：Tomcat **复用线程**，残留上下文会让下一个请求带上别人的身份 —— 这是最典型的「偶发越权」。

还有一条容易忘的：`shouldNotFilter` 要跳过 `/error`。否则容器内部转发到 `/error` 时又被拦一次，401 变成「401 的 401」。

### 1.5 认证可以关：`finagent.tenant.auth-enabled`

~~~yaml
finagent:
  tenant:
    auth-enabled: true      # 生产默认；测试 profile 置 false
    fallback-tenant-id: 1   # 无身份连接（Kafka worker / CLI）用的租户；rls profile 置 0 = 不使用兜底
~~~

`src/test/resources/application-test.yml:24-28` 把 `auth-enabled` 置为 `false`：300 多个既有测试不关心身份，逐个造 token 会把被测逻辑淹掉。**代价必须说清楚**：test profile 下不验认证，所以认证要有自己的测试（`AuthenticationFilterTest`），越权要有独立的 e2e（`TenantIsolationE2ETest`）。

## 2. 租户：为什么把租户「绑在连接上」

### 2.1 两种传租户的方式

| 方式 | 写法 | 漏一处的后果 |
|---|---|---|
| 拼进每条 SQL | `WHERE tenant_id = ?` 每处都要带 | 漏一处 = 泄漏，且没有任何机制提醒你 |
| **绑在连接上**（本项目） | 借连接时 `SET ROLE` + `set_config('app.tenant_id', …)`，SQL 里不写租户 | 数据库自己过滤；写错也漏不出去 |

第二种的关键认识：**PostgreSQL 的 RLS 只看会话变量，不看你的 Java 参数**。所以「租户」这个事实必须落到连接（session）上，而不是消灭在某个方法参数里。

### 2.2 实现：`TenantAwareDataSource`

文件：`src/main/java/com/finagent/security/TenantAwareDataSource.java:42-81`。

~~~java
@Override
public Connection getConnection() throws SQLException {
    return withTenant(super.getConnection());
}

private void apply(Connection connection) throws SQLException {
    CurrentUser user = TenantContext.current();
    long tenantId = user != null ? user.tenantId() : fallbackTenantId;
    try (Statement st = connection.createStatement()) {
        if (user != null) {
            st.execute("SET ROLE finagent_app");   // 换成非 owner → RLS 生效
        } else {
            st.execute("RESET ROLE");             // 回到 owner → 用于「先读父行再定租户」的路径
        }
    }
    ...  set_config('app.tenant_id', '<tenantId>', false) ...
}
~~~

四个设计点，每个都是踩过坑才有的：

**(1) 为什么用 `set_config(..., false)` 而不是 `SET LOCAL`**
`SET LOCAL` 只在事务里有效。本项目大量 `JdbcTemplate` 是 **autocommit 的单语句**，语句一结束变量就没了，RLS 永远看到 NULL → 全部查不到（表现为「登录了但什么都搜不到」）。所以用 **session 级**变量，并且每次借出都重设，不依赖 close 时清理。

**(2) 为什么每次借出都重设，而不是关闭时清理**
连接池会把连接借给任何线程。如果只在 close 时清，任何一个「中途抛异常没走到 close」的路径都会把租户变量留在连接上；反过来「每次借出先设」是幂等的，最坏情况是多设一次。

**(3) 为什么设不上就不要把连接借出去**
`withTenant` 里 catch 到 `SQLException` 会先 `close` 再抛 —— 否则后续查询会在「无租户」状态下**静默返回 0 行**，排查成本极高。fail closed 的第一条：不确定就断开，不要带着可疑状态继续跑。

**(4) 为什么还有「无身份」分支（`RESET ROLE` → owner）**
这一条最反直觉：Kafka worker 与 CLI 明明没有用户，为什么让它们用 owner（绕过 RLS）？

因为它们的租户**是从父行推导出来的**：

~~~
document_chunk.tenant_id  ← 从 document.tenant_id 复制
task_message.tenant_id    ← 从 document.tenant_id 推导
~~~

如果 worker 也被 RLS 挡住，就变成死循环：**要读 document 才能知道租户，要设租户才能读 document**。实测表现（不是在文档里推的，是真跑出来的）：

| 操作（以错误租户身份） | 结果 |
|---|---|
| `INSERT … SELECT … FROM document WHERE id=7` | **INSERT 0 0**，不报错 |
| `UPDATE document SET … WHERE id=7`（行不可见） | **UPDATE 0**，不报错 |
| `INSERT INTO document(tenant_id=2, company_id=7)`（公司属租户 1） | 成功 —— RLS 只校验本行 tenant_id，不校验父子一致 |

所以最终方案是「双角色」：

| 角色 | 谁用 | RLS | 为什么 |
|---|---|---|---|
| `finagent`（表 owner） | Flyway 迁移、Kafka worker、CLI、启动恢复 | **绕过**（owner 默认不受策略约束） | 迁移没有租户上下文；worker 要先读父行 |
| `finagent_app`（普通角色） | HTTP 请求线程 | 生效 | 这是唯一会接触「用户可控输入」的路径 |

这里有一个必须知道的 PostgreSQL 事实：**表 owner 默认绕过 RLS**，除非 `ALTER TABLE … FORCE ROW LEVEL SECURITY`。本项目**故意不加 FORCE**（`V8__tenant_and_acl.sql:124-125`）：加了之后连 Flyway 的回填数据语句都会被拦（迁移时没有租户上下文）。

> 推论（也是最好用的一条排错经验）：如果你用 owner 连接手工验证 RLS，**永远看起来是对的** —— 那是假绿。验证 RLS 必须换成非 owner 角色，这就是 `application-rls.yml` 存在的唯一理由。

## 3. RLS：策略那一行到底在说什么

### 3.1 策略原文

`V8__tenant_and_acl.sql:132-145` 用一个 DO 块给五张表建**同名同构**的策略：

~~~sql
CREATE POLICY p_document_tenant ON document FOR ALL
  USING      (tenant_id = nullif(current_setting('app.tenant_id', true), '')::bigint)
  WITH CHECK (tenant_id = nullif(current_setting('app.tenant_id', true), '')::bigint);
~~~

五张表：`company`、`document`、`document_chunk`、`financial_fact`、`task_message` → `p_company_tenant` … `p_task_message_tenant`。

### 3.2 逐字拆解

| 片段 | 作用 | 去掉它会怎样 |
|---|---|---|
| `current_setting('app.tenant_id', true)` | 读会话变量；第二个参数 `true` = 变量不存在时返回 NULL 而不是报错 | 不写 `true` 时，未设置变量直接抛 `unrecognized configuration parameter` —— 每个请求都 500 |
| `nullif(…, '')` | 把空串变 NULL | 变量被清成空串时，`''::bigint` 抛类型错误 500，而不是「查不到」 |
| `::bigint` | 文本转数字 | 与 `tenant_id` 类型不匹配，PG 可能不做隐式转换 |
| `USING` | 管**读**（SELECT/UPDATE/DELETE 的可见性） | 能读到全部租户的数据 |
| `WITH CHECK` | 管**写**（INSERT/UPDATE 的新行必须满足） | 能往别人租户插数据 |

「未设置 → NULL → 比较结果 NULL → 不满足 → 0 行」这条链是 fail closed 的核心：**忘了设，就是什么都看不见，而不是什么都能看见**。

### 3.3 三条实测（2026-10-27，psql 手工）

~~~sql
SET ROLE finagent_app;
SELECT count(*) FROM document;                              -- 0（变量未设）
SELECT set_config('app.tenant_id', '1', false);
SELECT count(*) FROM document;                              -- 4（租户 1 的全部文档）
SELECT set_config('app.tenant_id', '', false);
SELECT count(*) FROM document;                              -- 0（清空后立刻失效）
~~~

注意第二个数字是 **4** 而不是计划里写的 2：库里 document 的实际行是 id 2/4/7/38（早期测试残留也在租户 1）。写死期望值之前一定要先查真值 —— 这条坑在阶段 8 的计划里就踩过一次。

### 3.4 为什么把 `tenant_id` 冗余到 `document_chunk`

`COMMENT ON COLUMN document_chunk.tenant_id`（`V8:212`）写着：**冗余自 document**，理由是 RLS 要能直接过滤 chunk，不 join document。

- 一个 654 块的文档，检索 SQL 每轮都要扫 chunk；如果租户条件要靠 join 才能判断，RLS 就无法用上「策略表达式里只有本表列」这一优化。
- 冗余的代价是「两处不一致」的风险，所以写入时由 `ChunkPersister` 统一从 document 读一次租户再落两个表。

### 3.5 RLS 挡不住什么（必须知道的三条）

1. **挡不住「写错父子」**：策略只看本行的 `tenant_id`，所以「租户 2 的行指向租户 1 的 company」照样能插进去。父子一致性靠应用（`upsertDocument` 用 `INSERT … SELECT c.id, c.tenant_id FROM company c WHERE c.id=?`）。
2. **挡不住 `UPDATE … 0 行`**：行不可见时 UPDATE 命中 0 行且**不报错**。所以每个 `jdbc.update` 都应当检查返回值，否则日志会打印「已切到版本 3」而实际上什么都没改。
3. **挡不住 owner / `BYPASSRLS` 角色**：任何用 `finagent` 连接的代码路径都没有租户隔离 —— 包括 CLI、worker、以及所有非 rls profile 的测试。

### 3.6 一个绕不开的连锁：唯一约束必须也是「租户内唯一」

V1 建表时是全局唯一：`company.code UNIQUE`、`document.content_hash UNIQUE`。接第二个租户时会立刻炸：同一个公司代码、同一份 PDF 都必然冲突；更糟的是 `ON CONFLICT` 撞上别的租户的行时，RLS 报的是 `42501 new row violates row-level security policy`（看起来像权限问题，实际是唯一约束跨租户）。

V9 的改法（`V9__tenant_unique_and_not_null.sql:10-19`）：

| 原约束 | 改成 |
|---|---|
| `company_code_key` | `uq_company_tenant_code (tenant_id, code)` |
| `document_content_hash_key` | `uq_document_tenant_hash (tenant_id, content_hash)` |
| `uq_document_identity (company_id, doc_year, doc_type, version)` | 改成 `(tenant_id, company_id, doc_year, doc_type, version)` 的部分唯一索引 |

同一批还把 `company / document / document_chunk / financial_fact` 的 `tenant_id` 收紧成 `NOT NULL`，但 **`task_message` 故意不收紧**：坏消息（`documentId` 指向不存在的文档）根本推不出租户，而「坏消息也要留痕」是阶段 7 的硬要求（`V7__task_messaging.sql:24`）。这类「为了排障而放宽的约束」必须写进注释，否则后人会当成疏漏「修」掉。

## 4. ACL：租户内的「谁能看哪份」

RLS 只解决跨租户。同一个租户里，分析师 A 不该看到分析师 B 负责的公司，别人的私有笔记也不该被同事看到 —— 这层是应用侧的 ACL。

### 4.1 数据模型（V8 第 4 节 + document 两个新列）

~~~
resource_grant(subject_type: USER|ROLE, subject_id, resource_type: COMPANY|DOCUMENT|SECTION,
               resource_id, permission: READ|READ_WRITE, expires_at)

document.visibility = 'TENANT' | 'PRIVATE'
document.owner_user_id  ← 仅 PRIVATE 有值
~~~

### 4.2 判定表：可见性 × 授权类型

| 文档可见性 | 看什么授权 | 谁能看 |
|---|---|---|
| `TENANT` | `COMPANY`（按 `document.company_id`） | 对该**公司**有 USER/ROLE 授权的人 |
| `PRIVATE` | `DOCUMENT`（按 `document.id`） | owner 本人，或对该**文档**显式授权的人 |
| 任意 | — | 管理员（本租户内） |

这里有两条容易写出漏洞的细节：

1. **公司级授权不能穿透到私有文档**。所以要用 `CASE d.visibility WHEN 'TENANT' THEN 'COMPANY' ELSE 'DOCUMENT' END` 同时决定「查哪种 resource_type」和「拿哪个 id 去比」，两个 CASE 必须同步 —— 只改一个就会出现「公司授权能看到别人的私有笔记」。
2. **过期授权等于没有**：`(g.expires_at IS NULL OR g.expires_at > now())`。

### 4.3 角色授权为什么要绕一次 `user_role`

`CurrentUser.roles()` 里是角色 **code**（`ADMIN / ANALYST / VIEWER`），而 `resource_grant.subject_id` 存的是 `role.id`。所以「按角色授权」不能直接 `subject_id IN (codes)`，必须换一次：

~~~sql
OR (g.subject_type = 'ROLE' AND EXISTS (
      SELECT 1 FROM user_role ur JOIN role r ON r.id = ur.role_id
       WHERE ur.user_id = ? AND r.tenant_id = d.tenant_id
         AND r.id = g.subject_id AND r.code IN (…)))
~~~

顺手也验证了「这个用户现在真的有这个角色」（改权限不用等 session 过期）。

### 4.4 空集 = 全库：ACL 求交后必须抛错

这是本项目最危险的一处历史坑，值得单独记：

- `ScopeResolver` 的「全库」用 `CORPUS` 表示，且 **空集合就表示全库**（`ResolvedScope.java:17-19`）；
- 检索层看到空过滤条件就 `return base`（`HybridRetriever.java:361-364`、`DenseRetriever.java:85`）；
- 于是「ACL 求交后剩 0 份」如果原样传给检索层，结果不是「什么都查不到」，而是「**查全库**」。

规则：**ACL 求交之后如果为空，抛 `ScopeEmptyException`，绝不允许返回空作用域对象**。同样，判空的位置必须在求交**之后** —— 顺序反了会把「有权限但筛选条件不匹配」误报成权限错误。

### 4.5 「可选文档列表」是最容易被忘的泄漏点

`GET /api/scope/documents` 返回「下拉框里能选的文档」。这个接口不过 ACL 的话，攻击者不需要猜 id，直接把全库列表拉走（设计文档 §15.4 的第 2 类越权）。所以它也要过同一个 `filterReadable`。

## 5. 串起来：一次带身份的问答（时序）

~~~
客户端  Authorization: Bearer dev-analyst-token
   │
   ▼
AuthenticationFilter  ── sha256(token) → app_user(JOIN user_role/role) → CurrentUser(1, tenant=1, {ANALYST})
   │                       TenantContext.set(user)   [finally 必 clear]
   ▼
ChatController ─ ScopeResolver.resolve(scope)
   │                ├─ 候选文档（SQL，tenant 由 RLS 兜底）
   │                ├─ AclScopeAuthorizer.filterReadable(候选 id)  ← 租户内可见性
   │                └─ 交集为空 → 409 SCOPE_EMPTY（绝不返回空作用域）
   ▼
Retrieval（Dense + Sparse + RRF）   WHERE document_chunk.status='ACTIVE' AND document_id IN (…)
   │                                 ↑ 每个借出的连接都已被 SET ROLE + set_config
   ▼
ContextBuilder → AnswerService → CitationValidator → 响应（引用只到子块）
~~~

注意 `SET ROLE` + `set_config` 发生在**每次借连接**时（`getConnection`），所以同一次请求里的几十条 SQL 用的是不同连接，但看到的是同一个租户 —— 这正是「绑在连接上」而不是「绑在请求上的一个变量」的意义：不管 ORM/JdbcTemplate 怎么拿连接，租户都跟着走。实测代价：每次借出多两次极小的往返（本机 < 0.5 ms）。

## 8. 面试要点（自测清单）

1. **RLS 是什么、和「每条 SQL 都写 WHERE tenant_id」有什么区别？**
   RLS 是数据库在**行级**追加的隐式条件，策略只认会话变量；写完一次就覆盖所有读路径，漏写不会泄漏。代价是「看不见的行会静默消失」，排错要靠「先确认变量设了没」。
2. **为什么表 owner 绕过 RLS？怎么办？**
   PG 的设计：owner 视为可信。所以要有非 owner 的运行时角色，或用 `FORCE ROW LEVEL SECURITY`（本项目不用，因为会拦住迁移的数据回填）。
3. **`USING` 和 `WITH CHECK` 的区别？**
   `USING` 决定「哪些行对读/改可见」，`WITH CHECK` 决定「写入的新行是否合法」。只写 `USING` 能被插入别人的数据。
4. **`set_config(..., false)` 与 `SET LOCAL` 的差别，为什么会选前者？**
   `SET LOCAL` 随事务结束消失；autocommit 单语句场景下等于永远没设。session 级变量 + 每次借连接重设，才与连接池兼容。
5. **为什么把租户绑在连接上而不是方法参数？**
   因为 RLS 只看会话；绑在连接上后，无论哪层代码忘记传参，数据库侧仍然过滤。代价是「一次请求多次借连接会有多次往返」。
6. **认证为什么不用 JWT？**
   要可撤销、要能立刻改权限、要库里不存明文也没法离线伪造。如果对方追问「JWT 加 Redis 黑名单不就能撤销了？」，接着答两句：① 能，但那时 JWT 就退化成有状态的会话 token，每请求成本 ≥ 现在的一次索引查询（实测 0.08~0.125 ms，且这条查询本来就和租户设置共用同一条连接），还多一个 Redis 容器；② JWT 的真正卖点是「验证方不必访问状态存储」，加了黑名单这个卖点就没了，只剩「token 更大、密钥要管」。JWT 该用的是「对外短期凭证 / 多资源服务器 / 边缘校验」这些验证方碰不到状态存储的场景。详见 §1.1.1。
7. **401 / 403 / 409 怎么分？**
   401 = 没身份或身份无效；409 SCOPE_EMPTY = 有身份但这次请求的范围为空（产品语义是「拒答」）；403 本项目不用，因为「有身份但没权限」在 RAG 里表现为「检索不到证据」。
8. **ACL 求交后为空会发生什么？**
   如果直接把空集合传给检索层，等于「不过滤」→ 全库检索。这是本项目真实踩过的坑，规则是「求交为空必须抛异常」。
9. **为什么 `document_chunk` 要冗余 `tenant_id`？**
   让 RLS 策略只依赖本表列，避免 join；写入时从 document 复制一次，并由统一入口（`ChunkPersister`）保证一致。
10. **怎么证明 RLS 真的生效，而不是「看起来对」？**
    两个必要条件：非 owner 角色 + 三种状态各测一次（未设变量 0 行 / 设正确租户看到本租户 / 设成空串回到 0 行）。「用 owner 连接手工查一遍」是最常见的假绿。
