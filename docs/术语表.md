# 术语表（给第一次做 RAG / Agent 的人）

> 这份文档只有一个用途：**让你在任何一个报告里遇到不认识的词，都能在这里找到「它是什么、为什么需要它、在我们项目里具体长什么样」**。
> 用法：报告里第一次出现某个词时，会写成「中文名（English, 缩写）」并指向这里。看到裸缩写也回这里查。

## 0. 先看一张链路图（所有术语都在图上有位置）

用户在页面上问一句「2024 年营业总收入是多少？」，系统内部是这样走的：

```
PDF 文件
  │ ① 解析（Docling）：PDF → 带页码、带表格的结构化文本
  ▼
NormalizedDocument（一页一页、一块一块的文本）
  │ ② 切块（Chunking）：切成 Parent / Child 两级
  ▼
Chunk（一段话或一张表，带页码、章节路径）
  │ ③ 向量化（Embedding）：每块 → 1024 个数字
  ▼
pgvector（PostgreSQL 里的向量列 + HNSW 索引）
  │ ④ 检索（Retrieval）：Dense 路 + Sparse 路 → RRF 融合 → Rerank 精排
  ▼
候选证据块（Top-8）
  │ ⑤ 上下文装配（Context Building）：挑块、补邻居、控预算
  ▼
提示词里的 [E1]..[En]
  │ ⑥ 答案生成（LLM）+ 引用校验 + 数字落地校验
  ▼
JSON 答案（answer + facts + citations + trace）
```

后面的每一个词，都对应这张图上的某一步。看不懂某个词时，先问自己：**它在图上的哪一步？**

## 1. 最容易被缩写搞晕的几个词（先解决这几个）

### e2e（端到端测试，end-to-end test）

**是什么**：从最外层入口开始，一路跑到最外层出口的测试。我们项目里的 e2e 是：真 PDF 已在库里 → 真的调百炼（阿里云）的向量与对话模型 → 真的查 PostgreSQL → 真的生成答案 → 断言答案里的数值有没有出现在引用的原文里。

**打个比方**：单元测试是「单独测发动机能不能转」，e2e 是「把车开上路，从 A 地开到 B 地」。

**为什么单独有一类**：单元测试里模型、数据库全是假的（Mock），跑得快但证明不了「串起来能用」。e2e 慢（几十秒到几分钟）、要花钱（调模型 API）、结果还会抖（模型有随机性），所以**默认不跑**，用 Maven 的 @Tag("e2e") 标记，需要时用 -Dgroups=e2e 显式挑出来跑。

**在我们项目里**：ChatE2ETest（14 题）、CrossDocumentEvalTest（14 题）、RetrievalSmokeTest、AnswerEvalTest、ScopeFilteringTest……文件里的 @Tag("e2e") 就是标记。

**常见误解**：以为「测试全绿 = 功能对」。e2e 绿只说明「这条路径今天能走通」，不说明「换个问法也对」。这就是阶段 6 要做评测集的原因。

### smoke test（冒烟测试）

**是什么**：只验「通不通」，不验「好不好」的最小测试。名字来自硬件行业：通电看冒不冒烟。

**我们项目里**：RetrievalSmokeTest 只跑 10 个问题，打印每题的 top-1 是什么、耗时多少，不断言相关性 —— 它的作用是「改完代码，先确认检索没整个坏掉」。

### 集成测试（integration test）

**是什么**：测两个以上真实组件之间的配合（比如「Java 代码 + 真 PostgreSQL」），但通常不包含最外层的用户入口。

**我们项目里**：ChunkWriterTest、DocumentScopeQueryTest 都连真库，但不起 Web 服务、不调模型 → 属于集成测试。

### 单元测试（unit test）

**是什么**：一次只测一个类/一个函数，依赖全部替换成假对象（Mockito 的 mock）。

**我们项目里**：RrfFusionTest（只测融合公式）、DocumentQuotaBalancerTest（只测配额分配）。跑一次几毫秒。

### 一句话对照

| 类型 | 依赖 | 速度 | 证明了什么 |
| --- | --- | --- | --- |
| 单元测试 | 全假 | 毫秒 | 这段逻辑本身对不对 |
| 集成测试 | 真库/真组件 | 秒 | 组件之间拼得对不对 |
| 冒烟测试 | 真链路但只看通不通 | 几十秒 | 有没有整个坏掉 |
| e2e / 评测 | 真链路 + 真模型 | 分钟 | 「问一句答一句」对不对 |

## 2. 文档解析（PDF → 文本）

### PDF 解析（PDF parsing）

**是什么**：把 PDF 里「画出来的字」还原成「有结构的文本」。PDF 本质是排版指令（这个字放在 x=104,y=755），不是文档结构，所以「哪些字属于同一段、哪个是表头」全靠解析器猜。

**为什么难**：年报里表格多、跨页多、脚注多。解析器把表格读成流水账，后面无论检索多准，答案都会错 —— 这就是我们 2025 年报「员工表只剩表头」那个缺陷的性质。

### Docling

**是什么**：IBM 开源的文档解析库（Python），能把 PDF/Word/PPT 转成结构化 JSON（Markdown、表格、阅读顺序、坐标）。我们只用它做 PDF。

**为什么是它**：本地可跑、中文支持不错、能给出每个元素的 bbox（坐标），不用把年报传到第三方。代价是慢 —— 181 页要 57 分钟。

### NormalizedDocument / normalized.json

**是什么**：Docling 输出的中间产物，我们自己的叫法。里面是一串 block（段落/表格/标题），每块带 type、页码、bbox、markdown 文本。

**为什么需要中间态**：解析（Python）和切块（Java）是两个进程、两种语言，中间必须有个可落盘的约定格式。它也是「解析出了问题」时唯一能回看的证据。

### bbox（bounding box，包围盒）

**是什么**：一个矩形框的坐标，用来标出「这段文字在页面上的哪一块」。我们是归一化坐标：top/left/right/bottom 都是 0~1 的比例（0.104 = 页面宽度的 10.4%）。

**为什么要**：前端要把答案里的引用「高亮到那一块」，光有页码不够 —— 一页上可能有三个表。

### 表格转 Markdown（table → markdown）

**是什么**：把识别出的表格写成竖线分隔的文本：

```
| 项目 | 2024年 | 2023年 |
| --- | --- | --- |
| 营业总收入 | 11,604,343,090.16 | 11,081,439,282.37 |
```

**为什么这么做**：大模型读 Markdown 表格比读「空格对齐的文本」准得多，而且竖线天然表达「哪一格属于哪一列」。

## 3. 切块（Chunking）

### chunk（块）

**是什么**：检索的最小单位。一段话、一张表、一节标题+正文，都可以是一块。

**为什么必须切**：① 模型的上下文长度有限，整份 181 页塞不进去；② 向量是「一整块一个向量」，块太大语义就糊了（一整章的平均语义谁也不是）；③ 引用要精确到页，块太大就没法指。

### token（词元）

**是什么**：模型处理文本的最小单位。中文大约 1 个字 ≈ 1 个 token，英文一个单词 ≈ 1~2 个 token。

**为什么到处都在说 token**：① 上下文窗口按 token 算（我们的预算是 6000）；② 向量化接口按 token 收费；③ 切块目标大小也用 token 表示（我们 Child 目标 300~700 token）。

**注意**：不同模型的 token 切法不同，所以「6000 token」是估算值。我们用 TokenEstimator 估（中文按字、英文按词）。

### Parent / Child（父块 / 子块）

**是什么**：两级切块。Parent 是「一节」（偏大，用来给上下文），Child 是「一小段」（偏小，用来做向量检索）。

**为什么两级**：检索要「小」才准（一块只讲一件事），生成要「大」才完整（不能只给半句话）。所以用 Child 去匹配，命中后把它所在的 Parent 或邻居一起交给模型。这是「Parent-Child 检索」这个模式的全部内容。

**我们项目里**：doc 7 有 104 个 Parent、654 个 Child。平均一个 Parent 带 6 个 Child。

### chunk_index / readingOrder（阅读顺序）

**是什么**：块在文档里的顺序号。我们用全局唯一的 chunk_index（在「同一个切块版本」内从 0 递增）。

**为什么需要**：① 补「前后邻居」时要靠它找相邻块；② 引用显示「第 N 页 第 M 块」；③ 排序稳定性。

### section_path（章节路径）

**是什么**：这一块在文档里的位置，比如「第四节 § 主营业务分析 § 营业收入构成」，用 § 分隔。

**为什么要**：① 让模型知道「这段话在讲哪个话题」（上下文里会显示）；② 支持「只在某一节里搜」的过滤；③ 向量化时拼进文本，帮助区分「同一句话在不同章节含义不同」。

### overlap（重叠）

**是什么**：相邻两块刻意重复的一小段文字（我们文本块重叠 60 token）。

**为什么要**：句子被硬切在两块之间时，重叠能让至少一块保留完整语义。

### 原子块（atomic chunk）

**是什么**：不能再切的最小单位，比如表格的一行、一个完整的句子。

**为什么要**：切表格时不能把「2024年」和「11,604,343,090.16」切到两块去 —— 那样两块都没意义。

## 4. 向量与检索

### embedding（向量化 / 嵌入）

**是什么**：把一段文字变成一串数字（我们是 1024 个浮点数），语义相近的文字，数字也相近。

**打个比方**：给每段文字在 1024 维空间里定一个坐标，意思越像，坐标越近。

**关键性质**：**它不是「理解」，是「压缩后的相似度」**。所以「归母净利润」和「归属于母公司股东的净利润」向量很近，但「净利润」和「扣非净利润」也很近 —— 后者是灾难（口径不同），这正是需要 Rerank 和引用校验的原因。

**我们项目里**：阿里云百炼 text-embedding-v4，1024 维，存在 document_chunk.embedding 列（vector 类型）。

**容易踩的坑**：embedding 是普通列，**不会自动更新**。改了正文不会重算向量 —— 必须显式重跑（ReindexService）。

### 维度（dimension）

**是什么**：向量里有几个数字。我们是 1024。

**为什么锁死**：不同维度的向量不能比较；pgvector 的 HNSW 索引只支持到 2000 维。换模型=换维度=整表重算，所以项目一开始就锁定 1024。

### 余弦距离 / 余弦相似度（cosine distance / similarity）

**是什么**：两个向量夹角的余弦。方向越一致越接近 1。距离 = 1 - 相似度。pgvector 里 <=> 是余弦距离（0 最好）。

**为什么用它**：文本向量的「长度」没意义（长文本不因为长就更相关），只看方向。

**实测事实（我们写过）**：模型输出的向量长度都约等于 1（范数 0.99999993），所以余弦距离、内积、欧氏距离三种排序结果几乎一样 —— 面试常问这个。

### pgvector

**是什么**：PostgreSQL 的一个扩展插件，给数据库加了 vector 类型和向量索引。

**关键认知**：**它不是另一个数据库**。向量就存在普通表的普通列里，和标题、页码、文档 id 在同一行、同一个事务里。所以「切换切块版本」可以是一个事务内的原子操作 —— 这是我们选它而不是「另起一个向量库」的核心理由。

### 精确 kNN 与 ANN（approximate nearest neighbor）

**精确 kNN**：把每一行都算一遍距离再排序。结果 100% 正确，但行数一多就慢。

**ANN（近似最近邻）**：牺牲一点正确率换速度，用索引（HNSW/IVFFlat）只算「可能最近」的一小部分。

**我们实测的反直觉结论**：行数少的时候（我们 1516 行），优化器**故意不用 HNSW** —— 因为全表顺序扫比走索引还快（表 503 页 vs 索引 656 页）。到 1500 行左右 HNSW 才开始接管，4 万行时快 419 倍。详见 docs/pgvector-工作机制.md。

### HNSW

**是什么**：一种 ANN 索引算法（Hierarchical Navigable Small World），分层图：上层稀疏用于快速跳远，下层密集用于精确定位。

**关键参数**：m（每个节点的邻居数，我们 16）、ef_construction（建图时的候选数，64）、ef_search（查询时探索多少候选，默认 40）。

**坑**：带 WHERE 过滤时 HNSW 可能不生效或漏结果 —— 因为「先找 40 个最近」再「过滤掉不符合条件的」，很容易凑不满。pgvector 用 iterative_scan 缓解。我们项目的候选集只有 654 行，所以根本不走 HNSW，这是刻意的。

### Dense / Sparse（稠密 / 稀疏检索）

**Dense**：向量检索。擅长「意思相近但用词不同」（问「赚钱能力」，命中「盈利能力」）。

**Sparse**：关键词检索（我们的实现是 PostgreSQL 全文检索 tsvector + zhparser 中文分词）。擅长「精确词命中」（问「300059」，必须命中这个代码）。

**为什么要两条路**：单一方式都有盲区。财务报表问答尤其如此 —— 用户经常直接报指标名或数字，向量反而不擅长。

### tsvector / 全文检索（Full Text Search, FTS）

**是什么**：PostgreSQL 内置的文本索引类型。它把文本切成词项（lexeme），记录每个词出现的位置，然后用 tsquery 匹配。

**我们的问题**：中文没有空格，必须先分词（zhparser）。实测还发现：plainto_tsquery 默认 AND（每个词都要出现），对自然语言长问题直接返回 0 条 —— 所以我们做了 AND→OR 回退。

### zhparser

**是什么**：PostgreSQL 的中文分词扩展（基于 SCWS）。我们建了 text search configuration 叫 chinese_zh。

**实测缺陷**：会把「营业收入」切成「营业」+「收入」；「每股收益」只留「收益」（「每股」被标成代词 r 然后被丢弃）；对 38% 的块会切出无意义的「其他」。这些不是配置错，是分词模型的局限，所以我们把 Sparse 当辅助而非主力。

### pg_trgm（三元组相似度）

**是什么**：PostgreSQL 扩展，把文本切成 3 个字符的片段（中文按单字算，比如「每股收益」→ 5 个片段），用片段的交集算相似度。支持 LIKE '%关键词%' 走索引（否则 LIKE 只能全表扫）。

**我们为什么加它**：用户常常只记得半句话（「每股收益」），这时 tsvector 会切碎、向量会糊，模糊匹配反而最稳。

### RRF（Reciprocal Rank Fusion，倒数排名融合）

**是什么**：把多条检索结果合并成一个排名的公式：每路对某个文档贡献 1/(k + 名次)，k 通常取 60，把各路贡献相加再排序。

**为什么不用分数直接相加**：向量距离（0~1）和全文检索分数（0~10 不等）**不可比**，相加等于让量纲大的那一路说了算。RRF 只用名次，天然可比。

**关键性质**：RRF 奖励「共识」—— 两路都排第 5 的文档，分会高于只有一路排第 1 的文档。

### Rerank（重排 / 精排）

**是什么**：用第二个模型（qwen3-rerank）对「问题 + 候选块」逐对打分，重新排序。

**为什么需要第二层**：第一层（向量）是 bi-encoder —— 问题和文档各自编码，快但粗；Rerank 是 cross-encoder —— 把问题和文档拼在一起读，准但慢（只能对候选一条条算）。

**所以我们只精排 50 条取 8 条**，不可能对全库做。

### bi-encoder / cross-encoder

**bi-encoder**：分别编码，可以预计算、可以建索引 → 用于召回（海量）。
**cross-encoder**：拼在一起编码，必须现场算 → 用于精排（少量）。

这张对照表是面试高频题，也是「为什么 RAG 是漏斗结构」的答案。

### top-K（取前 K 条）

**是什么**：每路检索取多少条。我们 Dense 30、Sparse 30 → 融合后截 50 → 精排取 8。

**为什么要分这么多层数字**：召回要宽（宁滥勿缺），精排要窄（模型成本 + 上下文预算）。

### Recall（召回率）/ Precision（精确率）

**召回率**：该找到的，找到多少（分母是「全部该找到的」）。
**精确率**：找到的里，有多少是对的（分母是「找出来的」）。

检索层关心召回（先别漏），精排层关心精确（别把噪声给模型）。

### QU（Query Understanding，查询理解）

**是什么**：在检索之前，先解析用户问题，抽出结构化条件：公司代码、年份、指标名、文档类型（年报/半年报/一季报），并判断问题类型（精确取值 / 语义解释 / 对比分析……）。

**为什么要**：把「自然语言问题」变成「SQL 过滤条件」，能大幅缩小候选集，也避免把 2024 年的问题拿去 2025 年报里瞎猜。

**我们的实现**：规则（正则抓 6 位股票代码、年份、25 个指标词）+ 大模型兜底（LlmRouter 返回 JSON）+ 4 层校验（格式、取值、越界、降级）。降级时 queryType 记为 DEGRADED:原因，绝不猜。

## 5. 上下文装配与答案

### Context Builder（上下文装配）

**是什么**：把检索到的块「整理成提示词里的证据段」的那一步。

**做四件事**：① 同 Parent 内二次筛选（只留分数 ≥ 最高分 60% 的兄弟块）；② 补前后各 1 个邻居（让句子完整）；③ 按 token 预算 6000 整块取舍；④ 给每块编号 [E1]..[En]。

**为什么要编号**：让模型只能「引用编号」，不能自己编 id。后端再把编号映射回真实 chunk —— 这是引用可靠性的结构性保证。

### Token Budget（token 预算）

**是什么**：上下文最多允许多少 token。我们 6000。

**关键规则**：超预算时**整块出局**，绝不截断字符串。截断会把「2024年营业总收入 11,604,343,090.16」切成半句，比不给更危险。

### Citation（引用）

**是什么**：答案里「这句话来自哪一块」的结构化记录：documentId、chunkId、页码、bbox、表格行范围、证据类型。

**我们的三道保证**：① 模型只能引用本轮上下文里的编号；② 后端校验编号合法性、越界即剔除；③ 剔除后仍要检查「答案里的数字是否真在被引块里」（数字落地校验）。

### ground / grounding（落地校验 / 有据可依）

**是什么**：检查「模型说的话」能不能在证据里找到依据。

**我们做了什么**：AnswerService.ground() 把答案里的报告式数字（带千分位或四位以上）逐个回查被引块正文，全部找不到 → 拒答。

**为什么必须有**：模型编数字时，它给的引用编号往往完全合法（编号是真的，数字是假的）。

### 幻觉（hallucination）

**是什么**：模型生成看起来合理、实际不存在的内容。

**在我们项目里的两种形态**：① 编数字（员工总数 5,560）；② 主体错位（问五粮液，答东方财富的数）—— 第二种更隐蔽，因为数字本身是真的。

### 拒答（refusal）

**是什么**：证据不足时明确回答「查不到」，而不是硬编。

**我们的触发条件**：证据包为空、公司不在作用域、答案数字全部无法落地、解析失败。

### confidence（置信度）

**是什么**：对答案可靠性的分级（high / medium / low / insufficient / error）。

**我们的降级规则**：引用被剔除过半 → medium；跨文档数值冲突 → low；无引用 → low。

### facts（结构化事实）

**是什么**：答案旁边的「指标-期间-数值-单位-口径」结构化清单，供前端画表格、供校验比对。

**我们的做法**：不接 XBRL/FinancialFact 数据源（阶段 4 决策），facts 由模型从引用原文抽取，标 source=PDF。

## 6. 评测（怎么证明它变好了）

### golden set（黄金集 / 标准答案集）

**是什么**：一批「问题 + 期望文档 + 期望数值 + 期望证据块」的人工标注数据，用来回归测试。

**关键纪律**：证据块不能手写，要用 SQL 反查（在库里搜哪个块真的含这个数值）。手写必然与数据脱节。

### Recall@K（前 K 条召回率）

**是什么**：前 K 条结果里至少含一条「标注证据」的题目占比。

**为什么用「至少一条」**：一道题可能有多个正确证据块，命中任何一个都算检索成功。

### MRR（Mean Reciprocal Rank，平均倒数排名）

**是什么**：对每题取「第一个正确结果的名次」的倒数（第 1 名 = 1，第 2 名 = 0.5，第 3 名 = 0.33），再求平均。

**它比 Recall 严格**：Recall@10 只要进前 10 就满分，MRR 会惩罚「排在第 5」。

**我们实测 0.779**：17 题第 1 名、6 题第 2 名、1 题第 3 名、3 题第 4~5 名。

### 引用准确率 / 数值准确率

**引用准确率**：每条引用「文档对不对 + 块里是否真的有这个数」的比例。
**数值准确率**：答案里的期望数值是否全部出现（去掉千分位后比对）。

**为什么必须两个都看**：数值对但引用错（问 2024 答成 2025 年报的对比列）在数值上完全正确 —— 这是本项目最危险的一类错误。

### 拒答正确率

**是什么**：该拒答的题（语料里根本没有答案），系统真的拒答的比例。我们 5/5。

### 消融（ablation）

**是什么**：关掉某个模块，看指标掉多少，以此证明它有用。

**我们做的消融**：QU 开 vs 关。结论是两条道指标完全相同 —— 说明在当前「作用域已锁定」的场景下 QU 没贡献。这个结论不好看，但它是有价值的：它避免我们为一个无效模块继续付费。

### 门槛（gate）

**是什么**：写死在代码里的指标下限，低于就不许合并（EvalGateTest）。避免「这次 0.92，下次 0.88，没人发现」。

### 采样噪声（sampling noise）

**是什么**：模型输出有随机性，同一题跑两次结果可能不同。

**为什么要提**：我们只跑了一次 32 题，1.000 不等于「永远 1.000」。要看趋势就得多跑几次。

## 7. 工程与基础设施

### Flyway / 数据库迁移（migration）

**是什么**：把「数据库结构变更」写成有序的 SQL 文件（V1、V2……），启动时自动按序执行、记录已执行到第几版（flyway_schema_history 表）。

**为什么必须**：手动改表结构，换台机器就复现不出来，也没人知道线上是第几版。我们的硬规则：**schema 只由 Flyway 管**，改表就新增 V*.sql，绝不手工 ALTER。

### COS（对象存储，Cloud Object Storage）

**是什么**：存文件的服务（这里用腾讯云）。原始 PDF、解析产物都放这里，数据库只存路径与哈希。

**为什么不用本地磁盘**：文件与计算节点解耦，多实例部署时才不会「文件在 A 机器上」。

### Docker / 容器

**是什么**：把「数据库 + 扩展 + 配置」打包成一个可复制的运行环境。我们用它跑 PostgreSQL 16 + pgvector + zhparser。

**为什么必须容器化**：zhparser 需要编译安装，手工装一次能跑，换台机器就要重来。镜像里装好，一条 docker run 就到位。

### Spring Boot / Spring AI

**Spring Boot**：Java 的服务端框架，负责依赖注入、配置、Web 端点、事务等「地基」。

**Spring AI**：Boot 生态里调大模型的抽象层（ChatClient、EmbeddingModel、VectorStore）。我们用它的 ChatClient 调 qwen，用 EmbeddingModel 调 text-embedding-v4。

**注意版本坑（我们踩过）**：Spring Boot 4 把自动配置拆成了多个模块（flyway、jdbc、jackson 各自独立），Jackson 升级到 3（包名从 com.fasterxml 变 tools.jackson），但注解还在旧包 —— 这类「版本迁移细节」比业务代码更耗时间。

### ChatClient

**是什么**：Spring AI 的对话客户端。写法是链式的：chatClient.prompt().system(...).user(...).call().content()。

**两种用法**：.content() 拿字符串；.entity(SomeDto.class) 让模型直接返回结构化对象（内部帮我们拼「请输出 JSON」的指令并解析）。

### profile（配置档）

**是什么**：Spring 的多套配置（application.yml / application-test.yml）。测试用 test 档，把日志、trace 文件都指到 target/ 下，不污染工作目录。

### trace（链路追踪记录）

**是什么**：一次请求的完整执行记录：每阶段耗时、命中多少条、走了哪条回退路径、最终引用了哪些块。

**为什么要**：「答案不对」时必须能回答「是哪一步不对」。没有 trace 就只能靠猜。我们把它写成一行一条 JSON 追加到 logs/chat-trace.jsonl。

### JSONL

**是什么**：一行一个 JSON 对象的文本文件。好处是可追加、可 tail、可逐行解析，坏处是不能直接当 JSON 整体读。

### 幂等（idempotent）

**是什么**：同一个操作执行一次和执行十次，结果一样。

**我们为什么在意**：解析作业重试、报告入库重跑时，不能产生重复数据或重复扣费。做法是「先查再写」+ 唯一约束。

### 事务（transaction）

**是什么**：一组数据库操作要么全成功、要么全回滚。

**我们用它做的事**：切块版本切换 —— 旧版本标 SUPERSEDED、新版本标 ACTIVE、更新 document.active_chunk_version，三件事必须在同一个事务里，否则用户可能看到「两版都是 ACTIVE」的瞬间。

## 8. 异步与消息（阶段 7 用的那一套）

### 事件驱动（event-driven）

**是什么**：不直接调用「去做某事」的方法，而是往队列里投一条「应该做某事」的消息，由另一方取走执行。投的一方不等结果。

**为什么要**：解析一份 181 页年报要 50 分钟。同步接口会挂死 HTTP 连接、失败没有第二次机会、也查不到「到底处理过几次」。

**我们项目里**：`POST /api/documents` 只做「登记 + 投递」，立刻返回 documentId；真正解析在 `DocumentParseListener` 里异步跑。

**常见误解**：「用了消息队列就等于异步了」。其实关键在于**投递方不等结果**；哪怕用数据库表当队列也能做到异步。

### Kafka / topic（主题）/ 分区（partition）

**是什么**：Kafka 是一个「消息的持久化日志」。topic 是分类频道，一个 topic 切成若干分区（partition）并行读写。同一条消息进哪个分区由 key 决定 —— key 相同必进同一分区，也就保证了同 key 的顺序。

**为什么要**：解析与重切都是「一次做一件事、做完记一笔」的流水活，用日志型队列比 RPC 调用更抗抖动，也天然支持重放。

**我们项目里**：三个业务 topic（`document.parse`、`document.reindex`、两个 `.dlt` 死信）。**key 一律用 documentId**，这样「先解析后重切」不会被重排成「先重切后解析」。

### producer / consumer（生产者 / 消费者）

**是什么**：往 topic 投消息的一方叫生产者，从 topic 取消息的一方叫消费者。

**我们项目里**：两者在**同一个 Spring Boot 应用**里 —— `DocumentTaskProducer` 投递，`DocumentParseListener` / `DocumentReindexListener` 消费。职责分开写，将来拆成两个进程只是换个 profile，不返工。

### at-least-once（至少一次投递）

**是什么**：Kafka 只保证「消息不会丢」，不保证「只送一次」。消费者崩溃后重放、网络抖动后的重投、手动重放 DLQ，都会让同一条消息再来一遍。

**为什么要**：这是「至少一次」的实现代价 —— 想要「恰好一次」需要生产端和消费端做事务协调，成本高得多。工程上的标准做法是：**接受重复投递，把消费端做成幂等的**。

**我们项目里**：两道幂等防线 —— `task_message.event_id` 唯一（消息级）+ `content_hash` 已 DONE 就跳过（业务级）。详见 `docs/关键契约.md` 的 C9。

### ack（确认）与 offset（位点）

**是什么**：offset 是「这个消费者读到第几条了」的游标；ack 是「这条我已经处理完了」的确认。确认之后位点才前移，没确认的消息会被重投。

**我们项目里**：用手动 ack（`spring.kafka.listener.ack-mode: manual`）—— **处理成功才确认**，所以失败的消息不会丢。配错的后果很典型：启动不报错，收到第一条消息才抛 `IllegalStateException: No Acknowledgment available as an argument`。

### DLQ（dead letter queue，死信队列）

**是什么**：「怎么重试都处理不好」的消息的去处。它本身也是一个 topic，只是没人自动消费，等人来看。

**为什么要**：如果没有 DLQ，一条坏消息会让消费者无限重试、卡住整个分区（后面的消息全排队）。有了 DLQ，坏消息挪走、正常消息继续走，坏消息等人修。

**我们项目里**：规则是「原 topic 名 + `.dlt`」。进 DLQ 的消息仍保留原 `eventId`，所以修好 `documentId` 重投后能命中幂等，不会产生第二条记录。

**常见误解**：「进了 DLQ 就是数据丢了」。其实消息还在，可以反复重放。真正的风险是**没人看**。

### 增量重嵌（incremental re-embedding）

**是什么**：重切文档时，只对「内容真的变了」的块重新计算向量，其余块直接复用旧向量。判断依据是 `embedding_text_hash`（内容哈希）。

**为什么要**：654 个块全量重嵌约 62 秒 + 一次 API 费用。绝大多数重切只改了几十个表格块，其余文本一个字没变 —— 重算纯属浪费。

**我们项目里**：`EmbeddingReuseService` 按 hash + `embedding_model` + `embedding_version` 三条件分类，未变块零 API 调用。契约见 `docs/关键契约.md` 的 C10。

## 9. 权限与多租户（阶段 8 用的那一套）

### 认证（authentication）与授权（authorization）

**是什么**：认证回答「你是谁」，授权回答「你能干什么」。两个词经常被混着说，但失败时给的状态码不一样。

**为什么要分开**：混在一起会导致「因为没权限所以让你重新登录」—— 用户永远登不进去。所以：认证失败 = 401（再登一次有用），授权失败 = 403 / 409（再登也没用）。

**我们项目里**：`AuthenticationFilter` 管认证（401 `AUTH_REQUIRED` / `AUTH_INVALID`）；`ScopeResolver` + `AclScopeAuthorizer` 管授权（409 `SCOPE_EMPTY`）。

**常见误解**：「返回 403 更准确」。跨租户查文档时我们**故意返回 404**：403 等于告诉对方「这个 id 是存在的」，本身就是信息泄漏。

### 租户（tenant）

**是什么**：一个客户的数据边界。同一个系统里，A 公司的数据对 B 公司完全不可见。

**比喻**：一栋写字楼里的不同公司 —— 楼层共用、电梯共用，但办公室门锁只认自己公司的工牌。

**我们项目里**：`tenant` 表 + 五张业务表上的 `tenant_id` 列；租户 1 = 演示租户（东方财富的年报），测试里另造一个 `other-test` 租户专门验「什么都看不到」。

**常见误解**：「加了 `tenant_id` 列就多租户了」。不加过滤条件的列只是装饰 —— 真正让它生效的是 RLS 或每条 SQL 都带条件。

### RLS（Row Level Security，行级安全）

**是什么**：PostgreSQL 自带的功能：给表配一条策略，之后**任何**查询都会被数据库自己补上 `AND tenant_id = 当前租户`，不用应用层记得写。

**为什么需要**：应用层有几十条 SQL、还有将来别人新写的 SQL，靠「每个人都别忘」是不现实的。放到数据库里，漏写的那条也被兜住。

**我们项目里**：V8 建的 5 条策略 `p_<table>_tenant`，条件是 `tenant_id = nullif(current_setting('app.tenant_id', true), '')::bigint`；连接借出时 `TenantAwareDataSource` 先 `SET ROLE finagent_app` 再 `set_config('app.tenant_id', …)`。决定性证据是 `EXPLAIN` 里能看到数据库自己加的过滤条件。

**常见误解**：① 「表 owner 也受 RLS 限制」—— 不受，owner 默认绕过（我们故意不加 `FORCE`，否则 Flyway 迁移会被自己的策略拦住）；② 「RLS 能管租户内的细粒度权限」—— 不能，它只认一个条件。

### ACL（Access Control List，访问控制列表）

**是什么**：「谁对哪个资源有什么权限」的清单。本项目是 `resource_grant` 表：主体（用户 / 角色）× 资源（公司 / 文档）× 权限（READ / READ_WRITE）。

**为什么要**：RLS 只隔离租户。同一个租户里，分析师只该看自己负责的公司，私有文档只该 owner 看。

**我们项目里**：`AclScopeAuthorizer.filterReadable` 一次 SQL 求出「这批 id 里哪些可读」；作用域三条路（全库 / 筛选 / 点选）+ 枚举端点都必须过它。

**常见误解**：「授权了就等于数据安全了」。授权只决定「能看哪些文档」，但列表为空时如果被当成「不过滤」，检索会退化成全库 —— 所以空集必须抛错（`ScopeEmptyException`）。

### token（令牌）与 SHA-256 存储

**是什么**：客户端在 `Authorization: Bearer <token>` 里带的一串随机字符，代替用户名密码。

**为什么不用 JWT**：JWT 是自包含的，服务端不查库就能验；但也因此「改了权限要等过期」。我们本来每个请求就要开数据库连接（RLS 需要会话变量），所以查一次令牌表只值 0.08~0.125 ms，换来「改权限立刻生效」。

**我们项目里**：库里只存 `SHA-256(token)`，拖库拿不到可用 token；比对是一次索引查找。

**常见误解**：「JWT 没法撤销，但加个 Redis 黑名单就行」。能撤销，但那时它已经退化成有状态会话 token，成本比直接查库更高（多一个 Redis 容器 + 一次网络跳）。

### 越权（broken access control）

**是什么**：OWASP 排名第一的 Web 安全问题：用户做了他没权限做的事。典型形态有四种，本项目全部落成可执行用例。

| 形态 | 长什么样 | 我们的防线 |
|---|---|---|
| 语义相关但无权限 | 无授权用户问一个库里确实有答案的问题 | ACL 过滤后为空 → 409 |
| 传别人的 id | 点选模式里塞别人的 `documentId` | `filterReadable` 先剔掉 → 409 |
| 枚举 | 拉「可选文档列表」把全库 id 收走 | 枚举端点也过 `filterReadable` |
| 对象直链 | 拿 COS 的 `object_key` 绕过应用直接下载 | 响应里永不出现对象键（零泄漏门限） |

### 零泄漏门限（zero-leak gate）

**是什么**：一条机器可判的门槛：把各类响应正文拼起来，扫描「对象键 / 他人标题 / 他人正文片段」，命中数必须为 0。

**为什么要**：状态码正确不代表正文干净。一个 404 里回显了对象键，就等于把直链送出去了。

**我们项目里**：`ZeroLeakGateTest` 三个扫描面，输出 `ZERO-LEAK|objectKeys=0|titles=0|content=0`。

### 枚举泄漏（enumeration leak）

**是什么**：不需要猜 id，直接问「你有哪些文档」就能拿到清单。

**为什么要防**：它把「猜 id」的难度从「暴力枚举 2^63」降到「读一个列表」。所以列表接口和详情接口的安全等级必须一样。

**常见误解**：「列表接口只是给前端下拉框用的，不重要」。它恰恰是最容易被忘的那个。

### fail closed（失败即关闭）

**是什么**：拿不准的时候选择「拒绝」，而不是「放行」。

**我们项目里**：借连接时设不上租户变量 → 关闭连接并抛错（绝不借出「无租户」的连接）；ACL 过滤后为空 → 抛 `ScopeEmptyException`（绝不返回空列表）。

**常见误解**：「失败就返回空结果，体验更平滑」。在权限场景里，空结果会被下游解释成「不过滤 = 全库」，比报错危险得多。

## 10. 会话与记忆（阶段 9 用的那一套）

先说一句最容易搞混的：**「记忆」不是一张表，是四层东西，每层回答一个不同的问题**。把它们合成一张表，就会出现「三个月前的寒暄」和「用户明确要求的格式」抢同一份 token 预算。

| 层 | 回答什么 | 存在哪 | 进 Prompt 吗 | 能当引用吗 |
| --- | --- | --- | --- | --- |
| 短期记忆 | 刚才几轮说了什么 | `conversation_message` | 是（默认 6 轮） | 不能 |
| 会话摘要 | 更早的对话压缩后是什么 | `conversation_summary` | 是（≤200 字） | 不能 |
| 结构化上下文 | 在聊哪家公司 / 哪几年 / 哪份文档 | `conversation_context` | 是（一行） | 不能 |
| 长期记忆 | 用户明确说过的偏好与关注点 | `long_term_memory` | 按需 | 不能 |
| 本轮证据 | 这次检索到的文档块 | `document_chunk` | 是 | **能** |

### 会话（conversation）

**是什么**：一次连续的对话，有归属人（`owner_user_id`）、有默认研究范围（`scope_json`）、有状态（ACTIVE / DELETED）。

**为什么要**：没有会话，每轮都是「第一次问」，用户得每句都重复「东方财富 2025 年」；也没地方放「他上一句问的是净利润」。

**我们项目里**：`POST /api/conversations` 建会话说；`POST /api/chat` 带 `conversationId` 就落库（两个 return 点都会 `recordTurn`）。不带 `conversationId` = 单轮，行为与阶段 8 逐字节一致 —— 这条是回归门限。

**常见误解**：「会话就是聊天记录的容器」。它同时是**作用域与记忆的作用域**：别人拿到你的 conversationId 也读不到（404），因为归属校验在读上下文之前。

### 短期记忆（short-term memory）

**是什么**：把最近 N 轮的消息对（USER + ASSISTANT）按时间顺序塞进 Prompt。

**为什么要**：指代消解要靠它 ——「那净利润呢」里的「那」指的就是上一轮问的公司与年份。

**我们项目里**：`ShortTermMemory` 默认 6 轮、占窗口 15%；超预算时**成对丢弃最旧的一轮**（只丢 USER 会留下「没有问题的回答」）。

**常见误解**：「把全部历史都放进去更保险」。窗口是有限的，全放进去等于把证据挤出去；而且旧的问答会把模型带偏（它会把上一轮的结论当事实继续推）。

### 会话摘要（conversation summary）

**是什么**：把「已经滑出短期窗口」的消息压成一段 ≤200 字的摘要，保留已确认结论（带数字与年份）、未解决的问题、用户声明的偏好。

**为什么要**：会话变长后不能既放摘要又放原文 —— 那会把同一件事说两遍。摘要让「更早的事」还能被记住，但只占 10% 预算。

**我们项目里**：未汇总消息数 > `summary-trigger-messages`（默认 12）时触发，只压**最旧的一半**（不是全量，否则每轮重写、`old → new` 的 diff 失去意义）；`summary_until_message_id` 是「原文从哪开始」的指针，只前进不后退。

**常见误解**：「摘要失败就该报错」。摘要是锦上添花：失败只加 `summary_failed` 警告，指针不动，下一轮自然重试，消息一条都不删。

### 结构化上下文（structured context）

**是什么**：四个标量 —— `companyId / yearFrom / yearTo / currentMetric`（外加 `documentIds`），回答「这一轮在聊什么主体」。

**为什么要**：它是**确定的事实**，可以直接补进检索查询；而「最近几轮」是给模型看指代的原料。两者缺一个，追问都补不全。

**我们项目里**：每轮回答成功后 `applyTurn` 合并落库（新公司覆盖旧公司，模型推断不覆盖用户显式给的值）；用户可以用 `PATCH /api/conversations/{id}/context` 显式纠错，每次变更写一条 `memory_event`。

**常见误解**：「用户随口提到的公司也该记下来」。只有**出现在本轮作用域文档里**的公司才会映射成 companyId —— 否则下一轮「那净利润呢」会被一句闲聊带偏。

### 长期记忆（LTM, long-term memory）

**是什么**：跨会话生效的偏好与关注点，例如「回答先给结论」「用中文」「长期关注 300059」。

**为什么要**：用户的偏好不该每开一个新会话都要重说一遍；而这恰恰是「会话级」记忆做不到的。

**我们项目里**：只写两类高置信来源 —— 句首显式命令（`以后…` / `记住…` / `别再…`）与 `POST /api/memories`。同 key 只允许一条 ACTIVE，冲突时旧行降级为 `SUPERSEDED`、新行 `version + 1`（部分唯一索引 `uq_memory_active` 保底）。

**常见误解**：「让模型自己从对话里提炼偏好更智能」。写错一条偏好会污染之后**每一轮**回答，而「模型判断用户在不在下指令」的准确率无法离线评估 —— 宁可漏，不可误写。

### 召回闸门（Memory Gate）

**是什么**：决定「这一轮要不要去查长期记忆」的一道前置判断（QU 字段 + 词典）。

**为什么要**：查记忆要调一次 embedding（真金白银 + 200ms 起）。简单事实问答（「2025 年营收多少」）根本不需要偏好，不该为此付费。

**我们项目里**：`MemoryGate.shouldRecall` —— 开关关 / 问题空 → 不召回；QU 的 `needLongTermMemory` 为真 → 召回；命中 14 个词（以后 / 上次 / 照旧 / 格式 / 偏好 / 按我的 …）→ 召回；否则跳过。**跳过时库都不查**；查了但一条候选都没有时**不调 embedding**（规则命中先行）。

**常见误解**：「闸门是个分类模型」。本项目刻意不用模型：可解释、可回归、零成本，且错了能立刻看出是哪条规则。

### 指代消解（coreference resolution，本项目只做单轮追问补全）

**是什么**：把「那净利润呢」「它现在的现金流怎么样」补成「东方财富（300059）2025年 净利润」这种**脱离上下文也能检索**的查询。

**为什么要**：检索器只看当前这句话。不补全的话，「它」没有公司、「那」没有指标，Dense 与 Sparse 都是瞎猜。

**我们项目里**：规则命中（问题里已有公司代码）不消解；否则把结构化槽位 + 最近几轮交给 `LlmRouter.route(query, contextBlock)`，输出 `normalizedQuery` 与 `resolved`；`resolved=false` 时**原样返回**，不许编造年份（编造的年份会变成一个真实的过滤条件，把正确答案过滤掉）。LLM 挂了就做确定性补全（只补公司与年份，不补指标）并标 `degraded`。

**常见误解**：「补全了就一定更好」。补全只影响**检索查询**，答案 Prompt 仍用用户原话；补全过的事实会在 `warnings` 里留 `query_inferred_from_context`，评测能区分「用户说的」与「模型推的」。

### 记忆版本化（SUPERSEDED）

**是什么**：同一条偏好被改写时，旧行不删，只把 `status` 从 ACTIVE 改成 SUPERSEDED，新行 `version + 1`。

**为什么要**：用户会问「我什么时候说过这个」「上次改成了什么」；而「删了重写」这两件事都答不了。审计表 `memory_event` 记 `CREATE / SUPERSEDE / DELETE` 与新旧值。

**我们项目里**：唯一约束是**部分**唯一索引 `WHERE status = 'ACTIVE'`；`ON CONFLICT` 也必须带同样的 `WHERE`，否则「一条 ACTIVE + 多条历史」这个前提根本不成立。

**常见误解**：「版本号是给数据库看的」。它是给**人**看的：召回到的内容是第几版，决定这轮回答依据的是哪次约定。

### 不可引用背景（non-citable context）

**是什么**：这四层记忆在 Prompt 里统一放在【背景信息 · 不可引用】段，明确告诉模型「这里的东西不能当证据」。

**为什么要**：引用编号 `[E1..En]` 是**数组下标**，记忆没有 documentId / 页码 / 坐标。塞进去会让编号整体错位，并产出「看起来有出处却点不开」的引用 —— 比没有引用更有害。

**我们项目里**：记忆只在 `ChatTrace.memory` 留统计（短期条数 / 丢弃数 / 摘要字符 / 长期条数 / 闸门是否命中）；引用只来自 `ContextBlock`。

**常见误解**：「反正模型不会乱引」。模型会不会乱引是概率问题；编号错位是结构问题 —— 后者必须由代码保证。

### 行基数（row cardinality）

**是什么**：每张记忆表「一个会话应该有几行」。

**为什么要**：它决定了能不能用 `ON CONFLICT` 覆盖，也决定了「历史版本」是天然存在还是需要另建表。

**我们项目里**：`conversation` / `conversation_summary` / `conversation_context` 每会话各 1 行；`conversation_message` 每轮 +2（追加）；`long_term_memory` 每 key 1 条 ACTIVE + N 条历史；`memory_event` 只追加。

**常见误解**：「摘要既然会变，就该每版存一行」。摘要是**当前状态**而不是事件，且能由消息重算；真正不可重算的是「谁在什么时候改了它」—— 那个进 `memory_event`。

### 实体链接（entity linking）

**是什么**：把「东方财富」这个字符串，对到数据库里 `company.code = '300059'` 的那一行。它与「抽取」是两件事：抽取是「问题里出现了哪些词」，链接是「这个词指的是库里哪条记录」。

**为什么要**：中文财经问题里用户几乎只写公司名，从来不写代码；让大语言模型自己把名字翻成代码，等于让它凭训练记忆背答案 —— 实测它会给「东方财富」配一个 600519（贵州茅台），整轮被作用域拒答。

**我们项目里**：模型只输出 `companyMentions`（必须是原文子串），代码由 `CompanyResolver` 在**当前作用域**的文档里查；代码为空且作用域只有一家公司时用它的代码兜底（警告 `company_from_scope`）。契约见 docs/关键契约.md 的 C13。

**常见误解**：「模型知道所有股票代码，让它输出更省事」。它知道的是**语料频率最高的那几个**，而不是你库里有的那几个；省下的那一次查库，代价是随机的主体错配。
